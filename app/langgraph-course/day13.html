Day 13：需求闭环：进 TAPD、断点续跑与评测

洞察不能停在聊天框里。需求要进 TAPD 才算落地，落地之后要能追踪，跑一半断了要能续跑。今天把这条闭环走通。

一、核心解释

1. 需求闭环是什么：从反馈到 TAPD，再到可追踪

从反馈中洞察出的需求，直接对接 TAPD 跟踪落地。闭环的意思是：需求不是写完就丢，而是能在 TAPD 里被跟踪，状态还能回写回来。

需求归纳强制绑定原文引用。没有引用的需求不进 TAPD，这是 Day 11 定下的规矩。

2. 写 TAPD 之前，先过人工审核

写 TAPD 是写操作，不能让 Agent 自己悄悄写。在工具节点前用 interrupt 停住，等人审核。

审核有三条路：批准，继续写 TAPD；修改，改了再继续；拒绝，图结束，不写 TAPD。这三条路和 Day 6 的中断三条路是同一套。

3. Checkpoint 断点续跑：审核可以慢慢等

审核可能等几小时，甚至隔天。图停在中断点，Checkpoint 用 thread_id 存住快照。

人回来点批准，同一 thread_id 再 invoke，图从快照续跑，不用从头再分析一遍。多 Agent 链路长、状态多，线上问题难复现，靠可复现工程闭环兜底：checkpoint 存快照、链路追踪留完整调用链、评估集回归、smoke test 先跑通主链路——出了问题能按 trace 和评估集复现，而不是凭印象猜。

4. 评测抓手：三条线兜底

评测不靠感觉，靠三条线：需求闭环可追踪、人工抽查 10%–20%、权限验收回归。

人工抽查看归纳得对不对、引用绑得牢不牢；权限验收回归是 Day 12 的防再犯手段：拿没权限的账号去问，看还漏不漏别家产品反馈。

容易踩的坑：中断之后以为图自己会继续跑。不会。interrupt 停住后，必须有人给决定、再 invoke 一次，图才从 Checkpoint 续跑；没人给决定，图就一直停在那里。

🎮 审批模拟：一条需求进 TAPD

需求：投放后台的操作路径太深，用户找了很久才找到。引用已绑定原文。图已停在人工审核，等你决定。

状态：⏸ 已中断，等人工审核（Checkpoint 已存，thread_id 固定）

路径：需求归纳 → 人工审核 interrupt（停在这里）

二、代码示例

示例 1：工具节点调 TAPD，前面先 interrupt（先看形状）

from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import ToolNode
from langgraph.checkpoint.memory import MemorySaver
from langgraph.types import interrupt
from langgraph.graph.message import add_messages
from typing import Annotated, TypedDict

class LoopState(TypedDict):
    messages: Annotated[list, add_messages]
    requirement: str        # 归纳出的需求，已绑定原文引用
    tapd_status: str        # TAPD 回写的状态：待写 / 已创建 / 已拒绝

# TAPD 工具：按生产配置填接口与字段，这里只看形状
def create_tapd_issue(requirement: str) -> str:
    """把需求写进 TAPD，返回 TAPD 里的状态。"""
    return "已创建（按生产配置调 TAPD 接口）"

def review_node(state: LoopState) -> LoopState:
    # 人工审核：三条路，批准 / 修改 / 拒绝
    decision = interrupt({
        "requirement": state["requirement"],
        "options": ["批准", "修改", "拒绝"],
    })
    if decision == "拒绝":
        return {"tapd_status": "已拒绝"}
    if decision == "修改":
        return {"requirement": decision["改后需求"], "tapd_status": "待写"}
    return {"tapd_status": "待写"}  # 批准：继续往下走

def route_after_review(state: LoopState) -> str:
    # 拒绝就结束，不写 TAPD；否则进工具节点写 TAPD
    return END if state["tapd_status"] == "已拒绝" else "tapd_tools"

graph = StateGraph(LoopState)
graph.add_node("review", review_node)
graph.add_node("tapd_tools", ToolNode([create_tapd_issue]))
graph.add_edge(START, "review")
graph.add_conditional_edges("review", route_after_review,
                            {END: END, "tapd_tools": "tapd_tools"})
graph.add_edge("tapd_tools", END)
app = graph.compile(checkpointer=MemorySaver())

示例 2：断点续跑 + TAPD 状态回写

# 第一次跑：图在 interrupt 处停住，等审核
config = {"configurable": {"thread_id": "loop-001"}}
app.invoke({"requirement": "投放后台操作路径太深，引用已绑定"},
           config=config)
# 图停住了，Checkpoint 已存快照，thread_id 是 loop-001

# 人回来点“批准”，同一 thread 再 invoke，接着跑
app.invoke(None, config=config)  # 从快照续跑：写 TAPD

# TAPD 状态回写：工具返回的状态写进 State，后面能查
# tapd_status 从“待写”变成“已创建”，需求闭环可追踪
state = app.get_state(config)
print(state.values["tapd_status"])  # 已创建

动手任务（10 分钟）

1. 把示例 1 跑起来：在 review 节点前故意不加 interrupt，看 Agent 会不会直接写 TAPD——再把 interrupt 加回去，对比两次的差别。
2. 模拟一次“修改”：审核时把需求改短一半，确认图改了再继续、而不是按原需求写 TAPD。
3. 模拟一次断点续跑：第一次 invoke 停在中断点，换一个 thread_id 再 invoke，看它为什么不能续跑；换回原 thread_id，看它从哪里继续。

四、可能的面试题与答案

Q1：需求怎么从 Agent 进 TAPD？

洞察出的需求先绑定原文引用，再过人工审核 interrupt，批准后由工具节点调 TAPD 写进去，TAPD 的状态再回写进 State，全程可追踪。

Q2：人工审核的三条路分别怎么走？

批准：继续，工具节点写 TAPD；修改：改了再继续，按改后的需求写；拒绝：图结束，不写 TAPD。三条路用 interrupt + 条件边实现。

Q3：审核要等很久，图会丢吗？

不会。图停在 interrupt 处，Checkpoint 用 thread_id 存住快照；人回来给决定后，同一 thread 再 invoke，图从快照续跑，不用从头再分析。

Q4：TAPD 状态回写是干嘛的？

让需求闭环可追踪：tapd_status 从“待写”变成“已创建”，后面随时能查到这条需求走到哪一步了，而不是写完就丢。

Q5：这个项目的评测怎么做？

三条线：需求闭环可追踪、人工抽查 10%–20%（看归纳得对不对、引用绑得牢不牢）、权限验收回归（拿没权限的账号去问，看还漏不漏别家产品反馈）。

五、加分项

生产视角：写操作上生产前，先问三句：写 TAPD 前有没有 interrupt？拒绝的路走不走得到（会不会误写）？中断后换了 thread_id 还能不能续跑（应该不能）？三问有一个答不上来，闭环就别上。

简历讲法：别写“做过需求自动同步”，写“从 0 到 1 主导搭建：反馈洞察出的需求绑定原文引用，人工审核 interrupt 后由工具节点写 TAPD，状态回写可追踪；Checkpoint 用 thread_id 做断点续跑；评测是闭环可追踪 + 人工抽查 10%–20% + 权限验收回归”。
