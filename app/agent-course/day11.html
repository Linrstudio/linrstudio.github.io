Day 11：RAG 进阶架构：Self-RAG、Agentic RAG 与 GraphRAG

Day 7 到 Day 10 的 RAG 是一条直线：检索 → 生成，一次过。但直线有三个硬伤：所有问题都无差别检索 k 个片段（写首诗也要检索，浪费还添噪声）；召回的片段不管对错都塞给模型（无关甚至矛盾的上下文反而带偏答案）；向量只能找“局部相似的块”，答不了“这几家公司之间是什么关系”这种多跳问题。今天的进阶架构，就是在直线里加进三样东西：判断（要不要检索、证据够不够）、循环（不够就再查）、关系（用图补向量缺的那一环）。

一、核心解释

1. Self-RAG：按需检索 + 反思 token

Self-RAG（2023 年论文《Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection》）的核心思想是：让模型自己决定要不要检索，并自己给自己的输出打分。它在模型词表里加了一组特殊的反思 token（reflection tokens），分两类：

反思 token问什么取值
Retrieve这个问题需不需要检索外部信息？Yes / No / Continue（继续用已有证据）
IsREL这个片段和问题相关吗？相关 / 不相关
IsSUP生成的这句话有片段支持吗？完全支持 / 部分支持 / 不支持
IsUSE这句回答对问题有用吗？1–5 分，5 最有用

推理流程是：模型先预测 Retrieve——写“最佳夏日假期”这种创意任务就直接生成，不检索；事实性问题则检索 K 个片段，对每个片段并行生成一个候选段落，再用 IsREL / IsSUP / IsUSE 三组分数给候选打分，选最好的。打分细节叫树解码（tree-decoding）：每个片段的得分是各反思 token 归一化概率的加权和，权重是可调的超参数——想要事实准确就调高 IsSUP 的权重，想要开放创意就调低；再用段落级束搜索（beam search）保留得分最高的 B 个续写。也可以设阈值：只有 Retrieve=Yes 的概率超过阈值才真正触发检索。

训练分两步：先用 GPT-4 生成反思 token 的标注，蒸馏到一个内部评判模型（critic model）；再用评判模型给训练语料里的每个片段打上反思 token，用标准的 next-token 目标训练生成模型——检索到的文本块在算损失时被遮住，模型只学“输出 + 反思 token”。这样推理时就不再需要评判模型，生成模型自己会反思。论文配套的 selfrag_llama2_7b / 13b 是 2023 年的模型，这里只讲机制、不推荐用这个旧模型——今天的工程落地更多是借它的思路：用结构化输出或小模型做同样的门控和打分，见示例 1。

一句话记住 Self-RAG：检索不是必经之路，而是模型每一步都要重新判断的决定；答案不是一次生成的，而是多个候选按“相关、支持、有用”打分选出来的。它的代价是：要训练（或至少要精心设计提示）才能让模型可靠地输出反思信号。

2. Agentic RAG：把 RAG 变成多步决策循环

Agentic RAG 的定义很简单：由 Agent 决定何时检索、检索什么、是否再检索，并且可以调用多个工具（搜索、数据库、代码执行），而不只是查一次向量库。普通 RAG 是“一次检索、一次生成”；Agentic RAG 是“检索 → 看结果 → 觉得不够 → 换个问法再检索 → 够了才生成”的循环，适合多跳、需要多源拼证据的复杂任务。

它和 Self-RAG 的共同点是都引入了多步决策与反思，区别在实现位置：Agentic 常外显为工具调用与规划（Agent 的循环在系统层面看得见），Self-RAG 把“要不要检索、证据是否支持”内嵌在生成格式里（反思 token），更偏训练与解码策略。面试常问这道对比题，记住“外显工具循环 vs 内嵌反思 token”就够了。

3. Corrective RAG：检索不好就纠正，而不是硬着头皮生成

Corrective RAG（CRAG）给检索加了一个质检岗：检索结果先过一道评估，不达标就触发纠正动作——改写查询、换索引源、或联网搜索——而不是把烂证据塞给模型。典型触发信号有四个，面试常考：

  • 检索置信度低：Top1 与 Top2 的分数差距很小，分不清谁更相关；
  • 实体不一致：检索结果里的实体和问题里的实体对不上；
  • 重排后仍低分：重排模型也觉得这些片段不行；
  • 生成与引用冲突：答案和引用的证据互相矛盾（可用一致性检测发现）。

4. Adaptive RAG：按问题类型路由，不过度检索

不是所有问题都值得走完整链路。Adaptive RAG 在入口放一个轻量分类器或小模型，判断“需不需要检索 / 需要 SQL 还是文档 / 是否需要多跳”，再把问题分发到不同的子管道：简单事实走单跳向量检索，复杂问题走多跳或工具链路，纯知识性问题甚至不检索。它和 Agentic RAG 的边界是：Adaptive 强调路由策略（入口一次分流），Agentic 强调循环决策与工具调用（过程中反复决定）。

路由误判怎么防？三个办法：混合路由（短路链路和完整链路并行跑，取好的）；置信度阈值 + 默认安全策略（不确定就走更强的检索，宁可多花点钱也别答错）；持续用线上反馈迭代分类器。

5. GraphRAG / KG 增强：向量找不到关系，就建一张图

典型向量 RAG 有两个短板：抓不到长程关联知识（A 和 C 的关系要经过 B，向量相似度看不出来），以及信息密度低（上下文窗口小时尤其吃亏）。KG 增强的办法是加一路与向量库平行的知识图谱：从文本抽取实体与关系建图，检索时先从问题抽实体作种子节点，在图上采样子图，再把子图转成文本片段作上下文；也可以把查询转成图查询语言（如 Cypher）直接查图。GraphRAG 在此基础上更进一步，适合多跳关系问题和全局问题（如“这批文档的整体主题是什么”），常用社区摘要做全局聚合。

但图不是免费的：构图与抽取成本高、抽取错误会污染整张图、运维复杂。判断标准很实际：如果数据以说明文、FAQ 为主，向量 RAG + 混合检索 + 重排通常足够；只有关系问题占比高、团队又有图谱与评测能力时，才值得上 GraphRAG。小公司先别急着建图。

6. 模块化 RAG：六个可插拔的模块

模块化 RAG 把“索引 → 检索 → 生成”的固定三段拆成可替换、可重排的模块，论文里列了六个：

模块干什么
搜索模块不只查向量库：可用 LLM 生成 SQL、Cypher 等查询语言查结构化数据、搜索引擎、知识图
记忆模块用 LLM 自身的记忆引导检索，找与当前输入最匹配的记忆
额外生成模块检索内容冗余或噪声大时，让 LLM 直接生成需要的上下文，而非只从数据源取
任务适应模块把 RAG 调整适配各种下游任务
对齐模块在检索器里加可训练的 Adapter，解决查询与文档之间的对齐问题
验证模块检索后加一道验证：评估文档与查询的相关性，挡住不可靠的检索结果

两种组织模式：增加或替换模块（保留“检索—阅读”骨架，加新模块，如重写—检索—阅读 RRR）；调整模块间工作流程（加强语言模型与检索模型之间的互动）。Self-RAG、Corrective RAG 都可以看作在这个框架里加了“验证 / 反思”模块。

7. RA-DIT：RAG 与微调一起做

RAG 和微调不是二选一。RA-DIT 的做法是双向更新：更新 LLM，让它在给定检索增强指令时更可能给出正确答案（更会用背景知识，即使检索到的块是错的也能靠自身知识兜底）；更新检索器，让文档与查询在语义上更相关。结果是模型既会用检索到的证据，又不被错误检索带偏。记住这个配合原则：微调改善格式与领域表达，RAG 提供可更新事实——事实类优先 RAG。

8. 多模态 RAG：文本 + 表格 + 图片

核心 idea 是多向量检索器（Multi-Vector Retriever）：把“用于检索的东西”和“用于生成的东西”分开——检索用摘要的向量，生成用原始内容。半结构化 RAG（文本 + 表格）的流程是：版面分析拆出文本与表格 → 各自生成摘要 → 摘要向量化入库（同时存摘要和原文）→ 查询召回原文喂给 LLM。多模态（再加图片）有三条路线：

  • 路线 1：文本/表格摘要 + 原始图片都用多模态 embedding 向量化入库；召回原文与原图，喂给多模态 LLM 生成；
  • 路线 2：先用多模态大模型给图片生成摘要，三类摘要一起向量化；生成时若没有多模态大模型，就召回原文 + 图片摘要，用纯文本 LLM 生成；
  • 路线 3：同路线 2 的索引方式，但生成时召回原文与原图，喂给多模态大模型。

私有化部署时整条流水线可本地化（图片摘要、开源 embedding、本地向量库、本地生成模型），源材料里的具体模型名是 2023 年的，以官方最新文档为准。

二、代码示例

示例 1：Self-RAG 思路的反思门控（可跑，无需 API Key）

不用训练模型也能落地 Self-RAG 的思路：把 Retrieve / IsREL / IsSUP 做成三个可替换的判断函数——演示里用规则实现，生产里换成 LLM 结构化输出或小分类器。控制流才是重点。

# 反思门控 RAG：演示版（规则版 critic，生产可换成 LLM 结构化输出）
from dataclasses import dataclass

@dataclass
class Doc:
    text: str
    keywords: list
    score: float = 0.0  # 检索分数，演示用关键词命中数模拟

# 演示用小知识库：每条配关键词，避免单字误命中
KB = [
    Doc("公司年假 15 天，需提前两周申请。", ["年假", "休假"]),
    Doc("报销流程：提交发票后 5 个工作日到账。", ["报销", "发票"]),
    Doc("公司总部位于上海浦东新区。", ["总部", "上海"]),
]

def retrieve(query, k=2):
    """演示检索：按关键词命中数打分排序"""
    for d in KB:
        d.score = sum(kw in query for kw in d.keywords)
    scored = sorted(KB, key=lambda d: d.score, reverse=True)
    return [d for d in scored if d.score > 0][:k]

def should_retrieve(query):
    """Retrieve 门控：创意类问题不检索（生产：LLM 判断）"""
    creative = ["写首诗", "编个故事", "起个名字"]
    return not any(c in query for c in creative)

def is_relevant(doc, query):
    """IsREL：片段与问题是否相关"""
    return doc.score >= 1

def is_supported(answer, docs):
    """IsSUP：答案里的关键主张是否有片段支持（演示：答案须复述证据原文）"""
    return any(d.text in answer for d in docs)

def self_rag_answer(query):
    if not should_retrieve(query):  # Retrieve=No：直接生成
        return f"（直接生成，不检索）关于「{query}」，这是我的创作……", []
    docs = retrieve(query)
    docs = [d for d in docs if is_relevant(d, query)]  # IsREL 过滤
    if not docs:  # 无相关证据：宁可拒答也不编
        return "知识库中没有相关内容，我无法回答。", []
    answer = f"根据资料：{docs[0].text}"  # 演示：直接引用最佳片段
    if not is_supported(answer, docs):  # IsSUP 校验
        return "检索到的证据不足以支持答案，请换个问法。", docs
    return answer, docs  # IsUSE：生产里可再让 LLM 给 1-5 分

for q in ["年假多少天？", "写首诗赞美秋天", "公司食堂在哪？"]:
    ans, used = self_rag_answer(q)
    print(q, "→", ans)
# 年假多少天？ → 根据资料：公司年假 15 天，需提前两周申请。
# 写首诗赞美秋天 → （直接生成，不检索）关于「写首诗赞美秋天」，这是我的创作……
# 公司食堂在哪？ → 知识库中没有相关内容，我无法回答。

示例 2：Corrective + Adaptive：带纠正的路由循环（可跑）

入口按问题类型路由（Adaptive），检索后检查 Top1/Top2 差距与实体一致性，不达标就改写查询再检索一次（Corrective）。

# Adaptive 路由 + Corrective 再检索：演示版
from dataclasses import dataclass

@dataclass
class Hit:
    text: str
    score: float

KB = [
    ("公司年假 15 天，需提前两周申请。", ["年假", "休假"]),
    ("报销流程：提交发票后 5 个工作日到账。", ["报销", "发票"]),
    ("上海总部地址：浦东新区陆家嘴。", ["总部", "地址", "上海"]),
]

def search(query):
    hits = []
    for text, keys in KB:
        s = sum(k in query for k in keys)
        if s:
            hits.append(Hit(text, float(s)))
    return sorted(hits, key=lambda h: h.score, reverse=True)

def route(query):
    """Adaptive 路由：简单事实走单跳，比较类问题走多路"""
    if "和" in query and ("区别" in query or "对比" in query):
        return "multi_hop"
    return "single_hop"

def needs_correction(hits, query):
    """Corrective 触发信号：无结果 / Top1 与 Top2 差距小"""
    if not hits:
        return True, "无检索结果"
    if len(hits) >= 2 and hits[0].score - hits[1].score < 1:
        return True, "Top1/Top2 差距小，置信度低"
    return False, ""

def rewrite(query):
    """查询改写：演示版只做同义词扩展，生产用 LLM 改写"""
    return query.replace("多少天", "天数").replace("在哪", "地址")

def agentic_rag(query, max_rounds=2):
    path = route(query)
    print(f"[{path}] {query}")
    q = query
    for rnd in range(max_rounds):
        hits = search(q)
        bad, reason = needs_correction(hits, q)
        if not bad:
            return f"答案：{hits[0].text}"
        print(f"  第 {rnd + 1} 轮触发纠正：{reason}，改写查询再检索")
        q = rewrite(q)
    return "多次检索仍无可靠证据，建议人工确认。"

print(agentic_rag("年假多少天？"))
print(agentic_rag("总部在哪？"))
# [single_hop] 年假多少天？
# 答案：公司年假 15 天，需提前两周申请。
# [single_hop] 总部在哪？
# 答案：上海总部地址：浦东新区陆家嘴。

四、可能的面试题与答案

Q1：Self-RAG 的核心思想是什么？四个反思 token 各自评估什么？

按需检索 + 自我反思：模型自己决定要不要检索，并给自己的输出打分。Retrieve 决定是否需要检索；IsREL 评估片段与问题是否相关；IsSUP 评估生成内容是否有片段支持；IsUSE 评估回答对问题有没有用（1–5 分）。推理时用树解码：各反思 token 概率的加权和作段落得分，束搜索选最优候选。

Q2：Agentic RAG 和 Self-RAG 有什么共同点和区别？

共同点是都引入了多步决策与反思。区别：Agentic 常外显为工具调用与规划（Agent 决定何时检索、检索什么、是否再检索，可调多工具）；Self-RAG 把“要不要检索、证据是否支持”内嵌在生成格式里（反思 token），更偏训练与解码策略。

Q3：Corrective RAG 的触发信号有哪些？触发后做什么？

检索置信度低（Top1 与 Top2 差距小）、检索结果与问题实体不一致、重排后仍低分、生成与引用冲突。触发后执行查询改写、换索引源、或联网搜索，而不是把烂证据硬塞给模型生成。

Q4：GraphRAG 解决普通 RAG 的什么痛点？成本和挑战是什么？

解决多跳关系问题和全局聚合类问题（如“整体主题是什么”）：普通向量 RAG 只擅长局部相似块，抓不到长程关联知识。成本：构图与抽取成本高、抽取错误会污染图、运维复杂。适合关系密集、愿意投入工程化的场景；FAQ 为主的小公司先用向量 RAG + 混合检索 + 重排。

Q5：Adaptive RAG 如何避免路由误判？

三招：混合路由（短路链路与完整链路并行，取好的）；置信度阈值 + 默认安全策略（不确定就走更强的检索）；持续用线上反馈迭代分类器。核心原则是宁可多花点检索成本，也别把复杂问题错分到简单链路答错。

五、加分项

生产视角：进阶架构的上线顺序应该是：先加 Corrective 质检（成本最低，挡住烂证据）→ 再加 Adaptive 路由（省成本，简单问题别走重链路）→ 有多跳需求再考虑 Agentic 循环 → 关系问题占比高才上 GraphRAG。别一上来就建图，图是最后的手段，不是第一个。

简历讲法：别写“熟悉 Self-RAG、GraphRAG 等高级架构”，写“给客服 RAG 加了反思门控：创意类问题跳过检索，检索置信度低（Top1/Top2 差距小）时自动改写再检索一次，拒答率与幻觉投诉分别下降 X%”。前者是名词堆砌，后者是可追问的落地动作——记得准备一条可量化的指标。
