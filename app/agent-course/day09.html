Day 9：Embedding 与向量库：模型选型、微调与 ANN

Day 8 我们把文档切成了可检索的块。今天回答下一个问题：这些块怎么变成机器能比大小的东西？答案是 Embedding——把文本映射成固定维度的稠密向量，语义相近的文本在向量空间里距离更近。选哪个模型、多少维度、要不要微调、向量存哪、怎么搜得快，这五个决定基本就是 RAG 检索层的一半工作量。

一、核心解释

1. Embedding 机制：文本变成向量，语义变成距离

Embedding 把离散文本映射为固定维度的稠密向量：每个维度都是一个浮点数，整条向量就是这段文本在语义空间里的坐标。语义相近的文本，坐标就离得近。比较两个向量常用余弦相似度或内积；向量先做归一化的话，余弦相似度就等于点积，计算更便宜。训练目标多为对比学习：同义句拉近、无关句推远——模型不是在“理解”文本，而是在学习一种让相似文本聚到一起的坐标系。

2. 模型选型：OpenAI、BGE、M3E，看语言、隐私、成本

先给结论：效果优先 + 不差钱 → OpenAI text-embedding-3（small 1536 维或 large 3072 维）；中文场景 + 想自己调 → BGE（如 bge-large-zh-v1.5）或 M3E；追求速度 + 内存敏感 → M3E（384 维，体积小）。Jina 的 jina-embeddings 在长文本、多语言场景有优势。具体挑的时候看三件事：语言与领域（中文优先中文强化模型，医疗/法律可看领域微调版）、数据隐私与部署（文本能不能出海、云端 API 还是私有化）、推理成本（API 费用 vs 本地 GPU）。另外注意序列长度：长文档要么用更长上下文的 embedding 模型，要么先分段再聚合。一个简单原则：先拿 BGE 跑个 baseline，速度慢就换 M3E，效果不满足再换 OpenAI。模型名与维度以官方最新文档为准。

3. 维度取舍与维度诅咒：384 维 vs 1024 维

维度越高越好吗？不一定。高维度表达力更强，但招来两个麻烦：计算慢——向量点积复杂度 O(n)，1024 维比 384 维慢了近 3 倍；过拟合风险——小数据集上高维向量容易记住噪音而非语义。384 维像瑞士军刀，日常够用；1024 维像修理厂全套工具，修飞机时很香，修自行车反而翻半天找不到合适的。什么时候上高维？数据量大（百万级以上）、细粒度区分要求高，比如法律条款检索要区分“故意伤害”和“过失伤害”。普通客服问答，384 维完全够。维度诅咒在 RAG 里有三副面孔：中心偏移——不同文档的向量都聚在球面上，余弦相似度分布变得非常窄（比如 0.82 到 0.87 之间），阈值很难调；存储膨胀——1024 维 float32 向量是 4KB/条，1000 万条就是 40GB，再加索引还要翻倍；ANN 索引退化——高维下 HNSW 等图索引的召回率会掉，经验阈值是超过 500 维就要换 IVF 或压缩。缓解办法：PCA 或 AutoEncoder 降维（实验表明 512 维降到 256 维，检索精度只降不到 1%）、量化压缩（int8 或二值化）、对业务场景做“有效维度”测试——随机抽样 query，看相似度分布是否合理分离。

4. 对比学习微调：三元组 + InfoNCE

垂直领域需要微调吗？需要。通用 Embedding 在医学术语、法律条文、代码等专业场景下会“偏科”。三种主流微调方式：对比学习（正负例对，效果最好、需要标注）、SimCSE（无监督 Dropout，省事、效果一般）、指令微调（加任务前缀，灵活、多任务）。实际操作最推荐对比学习：构造 (query, positive_doc, negative_doc) 三元组，用 InfoNCE loss 拉近正例、推远负例。负例可以来自 BM25 召回的错误文档，或同 batch 内其他 query 的正例（in-batch negative）。一个小窍门：不要把所有领域数据混着微调，按业务场景拆分（比如“发热问诊”和“药品说明书检索”分开），效果更好。

5. 负难样本挖掘：难例决定微调的上限

负例太简单，模型学不到东西；负例太难到是假正例，模型反而学歪。五种常见策略：随机采样——均匀随机抽文档当负例，问题是太简单，梯度均值接近零，模型不易收敛；Top-K 负例采样——用稠密检索模型打分，取 Top-K 当负例，保证是模型分不清的难例，但很可能把潜在正例误判为负例（假负例），导致梯度方差很大、训练不稳定；SimANS 困惑负样本采样——采与正例语义相似度接近的负例：与 query 无关的给低分（信息量不足），与 query 很可能相关的也给低分（可能是假负例），与正例相似度接近的给高分——同时具有较大梯度均值和较小梯度方差；批内负采样——同一个 batch 里其他问题的文档正例当作当前问题的负例，想要效果好需要比较大的 batch size，且同一 batch 里最好只放同一种任务的样本（否则模型会偷懒按任务前缀区分正负例）；同文章采样——正例所在文章的其他片段当难负例，至少同主题、比随机难区分。另外还有 LLM 辅助生成软标签再蒸馏的思路（bge2 提出）：让 LLM 判断每个候选片段对生成标准答案的贡献，贡献越大优化权重越大，但打标成本高、很多场景拿不到标准答案。

6. 对称 vs 非对称嵌入与双编码器

对称嵌入：query 和 doc 的语义结构相似，比如“找跟我这句话意思相近的句子”——两个短文本。非对称嵌入：query 短、doc 长，比如用户搜“怎么退款”，对应的是商品售后条款长文。Query 和 Document 能用同一个模型吗？可以，但不是最优。非对称场景下训练时通常会做双编码器（dual encoder）：两个模型参数不同但结构相同，一个编 query、一个编 doc，再跨编码器比较。硬要共享参数也能跑，但检索精度会掉 3–5 个百分点。

7. ColBERT 晚交互与 SPLADE 稀疏向量

普通双塔是早融合：query 和 doc 各自压缩成一个全局向量，最后点积，信息在压缩里丢了。ColBERT 的晚交互（late interaction）：query 的每个 token 向量和 doc 的每个 token 向量分别算相似度，再取 MaxSim 求和——保留词级别的匹配信息，又不至于像交叉编码器那样 O(n²) 复杂度。优势：比交叉编码器快 10–100 倍（doc 向量可预计算），比双塔准确率高 3–5 个百分点，尤其在细粒度匹配上。代价是存储开销大（每个 doc 保存 token 级向量而非一个向量），用 ColBERT-v2 能压缩到原大小的 1/10。SPLADE 走另一条路：生成稀疏向量（大部分维度为 0），每个维度对应一个词项或词组。优势是可解释性强（哪些词贡献了匹配一目了然）、可结合倒排索引加速、对低频词友好（不会像稠密向量那样被平滑掉）。代价是域外泛化较差、Out-of-vocab 词可能漏掉。做法律文书检索时，稀疏向量能准确匹配“故意杀人”这个完整短语，稠密向量可能拆成“故意”+“杀人”然后加权搞混。

8. 向量库选型：FAISS、Milvus、Pinecone、Chroma、Qdrant

产品特点适用场景
FAISS（Meta）单机库，非完整数据库；极致性能，研究向原型、离线实验、嵌入现有服务
Milvus云原生、分布式、可扩展至百亿级大规模生产、需要分区与多副本
Pinecone全托管 SaaS，零运维快速上线、无运维团队
Chroma轻量、易上手原型、小项目
QdrantRust 实现、过滤丰富、性能强自托管生产、复杂过滤
WeaviateGraphQL API、内置模块需要图式查询与生态集成

面试常问：FAISS 和 Milvus 本质区别？FAISS 是 ANN 算法库，需自建存储、服务、容灾；Milvus 是向量数据库系统，提供分布式存储、运维能力与数据管理接口。

9. ANN 算法：HNSW、IVF、PQ 与参数取舍

暴力精确检索在高维下不可行，向量库用 ANN（近似最近邻）换略微精度换数量级加速。HNSW（分层导航小世界图）：图索引，查询延迟低、召回高，内存占用偏高；IVF（倒排文件）：聚类划分桶，查询只搜部分桶，需要离线训练，适合大规模；PQ（乘积量化）：向量压缩，省内存、加速距离计算，有损、精度略降。取舍：数据量中等、追求低延迟高召回、内存可接受时优先 HNSW；数据量极大、内存紧张、可接受离线训练与调参时考虑 IVF（常与 PQ 组合成 IVF_PQ）。实际要在召回率、QPS、内存、建索引时间上做压测。HNSW 的 efSearch 调大：查询时访问更多邻居，召回上升、延迟上升，需在精度与 SLA 间折中。强过滤场景选对元数据索引友好的实现（Qdrant、Milvus 过滤能力强）；要磁盘级大规模可看 DiskANN 类方案（视产品支持）。

工程细节（容易踩的坑）：Embedding 算太慢怎么办？有效排序是缓存 > 批处理 > GPU 加速。缓存命中率高了速度提升 100 倍以上，适合重复查询多的场景（LRU 或 Redis，注意失效策略）；批处理时 GPU 一次处理 32 条比逐条快 10 倍，关键是把变长文本 padding 到等长，别让 GPU 空转；单条推理 GPU 其实没比 CPU 快多少（受限于内存拷贝开销），只有 batch size ≥ 16 时优势才明显。模型加载后先跑一次假数据预热，把 CUDA 内核启动开销抹掉。文档更新后：全量重算慢但一致性好，适合每天一次夜间更新；增量更新只处理新增和修改的文档，删除要记录 ID 防止残留。增量有个坑：旧 Embedding 和新算的可能分布不一致，解决办法是定期（比如每周）全量重算一次，增量只在中间顶。

二、代码示例

示例 1：本地 BGE 编码 + 余弦相似度 Top-K（sentence-transformers）

# pip install sentence-transformers numpy
# 首次运行会下载模型（约 1GB），请保证网络通畅；模型名以官方最新文档为准
import numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-large-zh-v1.5")
docs = ["公司年假为 15 天，入职满一年可休", "报销应提交发票原件", "年假申请需提前一周提交"]
emb = model.encode(docs, normalize_embeddings=True)  # 归一化后余弦=点积

q = model.encode(["年假多少天？"], normalize_embeddings=True)[0]
scores = emb @ q  # 点积即余弦相似度
top = np.argsort(scores)[::-1][:2]
for i in top:
    print(f"{scores[i]:.3f}  {docs[i]}")

示例 2：FAISS 索引——精确检索 vs HNSW（ANN）

# pip install faiss-cpu numpy sentence-transformers
import faiss
import numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-small-zh-v1.5")
texts = ["条款A：年假 15 天", "条款B：报销需发票", "无关内容C：食堂菜单"]
emb = model.encode(texts, normalize_embeddings=True).astype("float32")
dim = emb.shape[1]

# 精确检索：IndexFlatIP，归一化后内积=余弦相似度，适合小数据
flat = faiss.IndexFlatIP(dim)
flat.add(emb)

# ANN 检索：HNSW 图索引，M=32 控制每节点邻居数，efSearch 越大召回越高、延迟越高
hnsw = faiss.IndexHNSWFlat(dim, 32)
hnsw.hnsw.efSearch = 64
hnsw.add(emb)

q = model.encode(["和A相关的查询"], normalize_embeddings=True).astype("float32")
D, I = hnsw.search(q, k=2)
print("scores:", D, "indices:", I)

四、可能的面试题与答案

Q1：Embedding 模型怎么选？OpenAI、BGE、M3E 各适合什么？

看三件事：语言与领域、数据隐私与部署、推理成本。效果优先 + 不差钱选 OpenAI text-embedding-3；中文场景 + 想自己调选 BGE 或 M3E；追求速度 + 内存敏感选 M3E（384 维）。实用原则：先拿 BGE 跑 baseline，慢就换 M3E，效果不够再换 OpenAI。模型名与维度以官方最新文档为准。

Q2：维度越高越好吗？1024 维 vs 384 维怎么选？

不一定。1024 维表达力更强，但点积复杂度 O(n) 让它慢近 3 倍，小数据集上还容易过拟合；维度诅咒还会带来中心偏移（相似度分布变窄、阈值难调）、存储膨胀（1024 维 float32 是 4KB/条）和 ANN 退化。数据量大（百万级以上）、细粒度区分要求高时上高维；普通客服问答 384 维完全够。缓解办法：PCA/AutoEncoder 降维、量化压缩。

Q3：对称嵌入 vs 非对称嵌入，Query 和 Document 能用同一个模型吗？

对称是短 query 对短文本，非对称是短 query 对长文档。可以用同一个模型，但不是最优：非对称场景通常做双编码器，两个模型参数不同但结构相同，一个编 query、一个编 doc。硬共享参数能跑，但检索精度会掉 3–5 个百分点。

Q4：ColBERT 的“晚交互”是什么？比普通双塔好在哪里？

普通双塔是早融合：query 和 doc 各压成一个全局向量再点积，信息在压缩里丢了。ColBERT 是晚交互：query 每个 token 向量和 doc 每个 token 向量分别算相似度，再 MaxSim 求和。比交叉编码器快 10–100 倍（doc 向量可预计算），比双塔准 3–5 个百分点，尤其细粒度匹配。代价是存储开销大，ColBERT-v2 能压缩到原大小的 1/10。

Q5：HNSW 与 IVF 如何取舍？efSearch 调大有什么效果？

数据量中等、追求低延迟高召回、内存可接受时优先 HNSW；数据量极大、内存紧张、可接受离线训练与调参时考虑 IVF（常与 PQ 组合）。实际要在召回率、QPS、内存、建索引时间上做压测。efSearch 调大：查询时访问更多邻居，召回上升、延迟上升，需在精度与 SLA 间折中。

生产视角：换模型之前先测召回@K 与端到端问答，别凭感觉换；Embedding 算得慢先上缓存（命中率高了速度提升 100 倍以上），再谈批处理与 GPU；文档增量更新后记得定期（比如每周）全量重算一次，避免新旧向量分布不一致。
