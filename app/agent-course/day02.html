Day 2：推理与执行范式：CoT、ReAct、Plan-and-Execute

Day 1 说 Agent 是“感知—思考—行动”的闭环，今天问一个更具体的问题：思考和行动到底按什么节奏配合？三种经典范式给出三种答案：CoT 只想不动手，ReAct 边想边做，Plan-and-Execute 先想好全局再动手。这三种范式不是三选一的竞争关系，而是 Agent 工具箱里的三把尺子——选哪把，看任务是纯推理、强交互，还是强流程。

一、核心解释

1. CoT（Chain-of-Thought）：纯推理，不动手

CoT 让模型在给出最终答案前，显式写出中间推理步骤。通过增加“推理 token”，模型在潜在空间中更易进行多步分解——相当于把单跳预测拆成多跳，对多步推理、数学、逻辑题提升明显。代价是更长输出、更高延迟与成本，且有时会出现“看似合理但错误”的推理链。三种常见形态：Zero-shot CoT，不手写示例，只在问题末尾加一句触发语，如英文“Let's think step by step”或中文“请逐步推理”；Manual CoT，在 Few-shot 里直接写出“推理过程 + 答案”，模型模仿该模式；Auto-CoT，用程序采样问题、由模型生成多条推理链，再筛选高质量链作为示例，减少人工写 CoT 的成本。CoT 在 Agent 里常用于规划、工具选择、异常处理：先让模型写出“当前状态、目标、下一步动作理由”，再执行工具，降低盲目调用。生产环境可对用户隐藏推理链，仅内部记录，对外只给结论，避免泄露敏感中间信息。

2. ReAct：推理与行动交替，工具结果纠错

ReAct 全称 Reasoning + Acting：一个会做题的学生，不是一口气写完答案，而是边想边做——先在心里说一句“我接下来要干什么”（推理），然后真的去查资料、用计算器、调 API（行动），看到结果后再继续想下一步。模型在文本里显式交替写出 Thought（为什么要这么做、下一步选什么工具、预期看到什么）、Action（调用某个工具并给出参数）、Observation（环境/工具返回的结果），循环多次直到 Final Answer。一句话：ReAct = 把“思考过程”和“工具使用”写进同一条轨迹里，让推理可监督、可纠错、可复现。CoT 让模型“更会想”，ReAct 让模型“在想的同时能动手，并用真实结果纠正自己”——单轮问答时模型容易幻觉事实，ReAct 通过行动把模型锚定在外部证据上。显式 Thought 有三类价值：可解释性（便于人类审计）、可调试性（定位哪一步选错工具）、学习信号（可做监督微调或评估中间步骤质量）。

模板一：经典英文 Thought / Action / Action Input 模板。业界常用英文工具名，中文任务可把指令改为中文：

Question: the input question you must answer
Thought: think step by step about what you should do next
Action: the action to take, must be one of [{tool_names}]
Action Input: the input to the action
Observation: the result of the action
... (this Thought/Action/Action Input/Observation can repeat)
Thought: I now know the final answer
Final Answer: the final answer to the original question

也有不少论文与开源实现用单段 Action 行风格：Action: Search[query]。设计要点：工具清单与参数格式要写清，减少模型胡写工具名；强调“Observation 由系统填充”，避免模型在提示里自己续写假 Observation；给 1～3 个完整轨迹 Few-shot 示例，能显著提高格式遵从率。

模板二：JSON 工具调用模板（中文任务常用）。每轮先输出 Thought（一两句话说明为什么采取下一步），然后输出 Action：严格为 JSON 对象 {"tool": "工具名", "input": {...}}；若不需要工具，输出 {"tool": "finish", "input": {"answer": "给用户的最终自然语言答案"}}。收到 Observation 后继续循环，直到用 finish 结束。JSON 模板的优势是程序解析更稳健，代价是需要模型严格遵守 JSON 格式。解析要点：Thought / Action / Observation 通常用固定前缀或结构化格式便于程序解析；Observation 只能来自工具，不能由模型自己编造（工程上要校验）；停止条件是出现 Final Answer、步数上限，或检测到重复无效循环。

ReAct 的优点是可解释（轨迹可读，便于调试与评测中间步骤）、接地（通过工具把答案锚定在可验证数据上）、通用（与具体工具解耦，易于替换搜索/代码/SQL 等）。缺点是多轮调用成本高、延迟大；格式脆弱，模型若偏离模板需要解析器与重试策略；规划能力有限——逐步贪心，复杂任务上可能缺“全局最优计划”。

3. Plan-and-Execute：先全局规划，再分步执行

Plan-and-Execute 是两阶段：先制定计划（Planner），再逐步执行（Executor）。像旅行前先列行程单，再按天去玩；执行中若发现“景点关门”，再改行程（Re-planning）。与 ReAct 的差别可以记成：ReAct 是“走一步看一步”，Plan-and-Execute 先有一张“总蓝图”再落地，适合步骤多、依赖关系清晰的任务。Planner 的输入是用户目标、约束（时间/预算/格式）、当前已知上下文，输出是结构化计划（步骤列表、每步子目标、依赖、所需工具类型），技巧是计划粒度适中——过细易脆，过粗难执行。Executor 逐步骤执行（可调用工具或子 Agent），更新状态，每一步可选用不同工具；Executor 内部可再接 ReAct 或子 Agent。先制定完整计划再按计划执行，比 ReAct 更适合需要全局最优的任务。

重规划（Re-planning）机制是这个范式的关键。触发条件常见有：工具失败、返回空、超时；Observation 与假设冲突；新信息使原计划步骤多余或顺序错误。做法分两种：局部修复，只替换失败步骤之后的子计划；全局重规划，回到目标重新生成计划（成本高但更稳）。重规划会“计划抖动”——频繁重规划让执行轨迹不稳定，缓解方式包括限制重规划次数、局部重规划优先、在 state 中保留已验证事实、对计划变更加一致性检查（新旧计划差异说明）。最大风险是错误计划污染全局，缓解靠可验证子步骤、重规划、强 Planner 约束输出与执行期监控。

4. 三者选型对比

维度CoTReActPlan-and-Execute
是否有外部环境通常无有（工具 / Observation）有（执行阶段调工具）
规划隐式、一次性推理链隐式、逐步贪心显式、先全局后局部
纠错方式主要靠模型自省主要靠外部反馈重规划（局部 / 全局）
成本低（通常单次调用）步数多时可很高规划一次可能省执行盲目性
典型目标提升推理深度推理 + 行动闭环多步骤可审计交付

选型口诀：纯推理题用 CoT；需要调用工具、检索信息、环境反馈关键、路径不确定的用 ReAct；任务可分解、流程强、需要可审计的计划书的用 Plan-and-Execute。复杂系统常混合：Planner 先出路线图，Executor 内部每步用 ReAct 执行。

容易踩的坑：ReAct 轨迹里的 Observation 必须由执行器生成，模型只负责 Thought / Action——一旦模型自己编造 Observation，就会得到“看似合理但错误”的答案，轨迹再漂亮也没用。工程上要校验 Observation 来源，并给解析失败准备重试策略。

二、代码示例

示例 1：简化版 ReAct 循环（离线可跑，假模型 + 真计算器工具）

from dataclasses import dataclass
from typing import Callable, Dict, List, Tuple

@dataclass
class Tool:
    name: str
    run: Callable[[str], str]


def parse_action(text: str) -> Tuple[str | None, str | None]:
    """极简解析：生产环境请用更稳健的正则 / JSON。"""
    action = action_input = None
    for line in text.splitlines():
        if line.startswith("Action:"):
            action = line.split("Action:", 1)[1].strip()
        if line.startswith("Action Input:"):
            action_input = line.split("Action Input:", 1)[1].strip()
    return action, action_input


def react_loop(question, tools, llm, max_steps=6):
    history: List[Tuple[str, str, str]] = []
    for _ in range(max_steps):
        out = llm(question, history)
        if "Final Answer:" in out:
            return out.split("Final Answer:", 1)[1].strip()
        action, action_input = parse_action(out)
        if not action or action not in tools:
            obs = f"ERROR: invalid Action. Must be one of {list(tools.keys())}."
        else:
            obs = tools[action].run(action_input or "")  # Observation 只来自工具
        history.append(("", f"{action}[{action_input}]", obs))
    return "Failed: max steps exceeded."


def fake_llm(question, history):
    """假模型：第一轮调计算器，第二轮给最终答案。"""
    if not history:
        return "Thought: I need to add numbers.\nAction: calculator\nAction Input: 21+21\n"
    return f"Final Answer: 21+21 = {history[0][2]}"


tools = {"calculator": Tool("calculator", lambda s: str(eval(s)))}
print(react_loop("What is 21+21?", tools, fake_llm))
# 21+21 = 42

示例 2：极简 Planner + Executor（含重规划，离线可跑）

from typing import Any, Dict, List


def plan(task: str, llm) -> List[str]:
    prompt = f"Break the task into concrete steps. Return ONE step per line.\nTask: {task}"
    text = llm(prompt)
    return [s.strip("- ").strip() for s in text.splitlines() if s.strip()]


def execute_step(step: str, state: Dict[str, Any]) -> str:
    """单步执行器：这里用确定性逻辑演示，真实场景可接工具或 ReAct。"""
    if step == "拉取销售数据":
        raise RuntimeError("数据源超时")  # 故意制造一次失败，触发重规划
    return f"完成：{step}"


def plan_and_execute(task: str, llm, max_replans: int = 2) -> str:
    steps = plan(task, llm)
    state: Dict[str, Any] = {}
    for _ in range(max_replans + 1):
        for i, st in enumerate(steps):
            try:
                state[f"step_{i}"] = execute_step(st, state)
            except Exception as e:
                # 触发重规划：把失败信息喂回规划器，生成新计划
                steps = plan(f"{task}\nFailed step: {st}\nError: {e}\n请给出替代方案。", llm)
                break
        else:
            return f"最终结果：{state}"
    return "Failed after replanning."


def fake_llm(prompt: str) -> str:
    if "替代方案" in prompt:
        return "- 从本地缓存拉取销售数据\n- 计算同比\n- 写成摘要"
    return "- 拉取销售数据\n- 计算同比\n- 写成摘要"


print(plan_and_execute("生成上季度销售报告", fake_llm))
# 最终结果：{'step_0': '完成：从本地缓存拉取销售数据', 'step_1': '完成：计算同比', 'step_2': '完成：写成摘要'}

四、可能的面试题与答案

Q1：ReAct 和普通 CoT 提示有什么本质区别？

普通 CoT 只在模型内部展开推理链，不强制与外部环境交互；ReAct 把推理与可执行行动绑定，每一步行动后都有真实 Observation 反馈，从而用工具结果约束生成，降低闭卷幻觉。

Q2：Plan-and-Solve / Plan-and-Execute 模式是什么？比 ReAct 好在哪里？

先制定完整计划，再按计划执行；ReAct 是边做边想。Plan-and-Execute 更适合需要全局最优的任务：步骤多、结构清晰、需要可审计的计划书时，Planner 先给出路线图能减少短视。代价是计划错误会波及全局，需要重规划机制兜底。

Q3：Re-planning 会不会导致“计划抖动”？怎么缓解？

会。频繁重规划可能让执行轨迹不稳定。缓解方式包括：限制重规划次数、局部重规划优先、在 state 中保留已验证事实、对计划变更加一致性检查（新旧计划差异说明）。

Q4：ReAct Prompt 为什么要给 Few-shot 示例？

提升模型对固定格式的遵从度，降低解析失败率，稳定工具调用。给 1～3 个完整轨迹示例效果就很明显，示例要覆盖“工具清单与参数格式”，并强调 Observation 由系统填充。

Q5：你如何为一个企业场景选择 ReAct vs Plan-and-Execute？

看任务是否强流程、是否需要可审计计划书、是否允许前期规划成本。需要强工具交互与动态环境用 ReAct；强分解与多步骤交付用 Plan-and-Execute；复杂系统常混合——Planner 出路线图，Executor 内部每步用 ReAct。

五、加分项

生产视角：ReAct 落地最容易翻车的不是推理质量，而是格式解析与 Observation 校验：解析失败要重试、Observation 必须来自执行器、步数上限必须有硬编码。Plan-and-Execute 落地最容易翻车的是计划抖动：重规划次数上限与局部修复优先，写进代码里别只写在文档里。

简历讲法：别写“熟悉 ReAct”，写“用 ReAct 循环做调研 Agent：Thought/Action/Observation 轨迹可审计，Observation 由执行器生成防伪造，解析失败自动重试 + 最大步数兜底；多步骤交付场景改用 Planner-Executor，先出可审计计划再执行，失败局部重规划”。前者是名词，后者是可追问的工程取舍。
