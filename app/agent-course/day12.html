Day 12：RAG 失败、评测与生产：十二痛点、RAGAS 与上线

前面五课把 RAG 从直线做到了带反思、带循环、带图的进阶架构。但 Demo 跑通离上线还差很远：真实系统会在十二个地方翻车——知识库里没有答案它却一本正经地编，答案在库里却检索不到，检索到了又没被用来生成。更关键的是，你得先有办法量出它有多差，才能证明你的优化真的有用。今天讲三件事：十二个痛点各怎么解，怎么评测（合成测试集 + RAGAS），以及上线时多租户、增量更新、缓存这些生产必备。

一、核心解释

先记住这张漏斗：出了坏答案，别急着换模型，从上往下逐层问——答案在库里吗？检索到了吗？排前面了吗？生成用上了吗？格式对吗？每一层对应不同的痛点和解法。下面十二个痛点，前七个来自论文《Seven Failure Points When Engineering a Retrieval Augmented Generation System》，后五个是开发中常见的额外痛点。

1. 十二痛点与解法（上）：检索与生成

痛点症状解法
1. 内容缺失答案不在库里，系统却给出貌似合理但错误的答案，而不是承认不知道优化数据源（垃圾进、垃圾出）；提示词加“如果你无法确定答案，请表明你不知道”，鼓励模型表达不确定性
2. 错过排名靠前的文档答案在某个文档里，但它排名不够高，没能进给模型的那几条先召回 Top 10 再重排取 Top 2；调 chunk_size 与 top_k（如 256/512/1024 × 1/2/5 做参数搜索，在测试集上以语义相似度打分选最优）
3. 脱离上下文文档检索到了，但整合时没被用来生成答案优化检索策略（基础检索、高级检索、自动检索、知识图谱检索器、分层检索器）；微调开源 embedding 模型提升检索准确性
4. 未能提取答案上下文里有答案，但信息太多、干扰或矛盾太多，模型没提取出来清理数据；提示压缩（压缩无关上下文、突出重要段落、减少总长度）；LongContextReorder——关键信息放上下文开头或结尾，解决“丢失在中间”
5. 格式错误要求表格或清单，模型没按格式输出更精准的提示（明确指令、简化问题、给示例）；输出解析（格式化指南 + 对回答做解析校验）；结构化输出（Pydantic 模型 / JSON 模式）
6. 特异性错误回答过于含糊泛泛，缺少必要的细节更高级的检索：从细节到全局的检索、围绕特定句子的检索、逐步深入的检索（小块定位、大块展开）
7. 回答不全面答案只对了一部分，缺细节——比如问“文档 A、B、C 都讨论了什么”，只答了其中一份查询优化层：路由（明确问题涉及的工具子集）、查询改写（多种问法）、细分问题（大问题拆小问题分别查）、HyDE（先生成假设性文档再用它检索）

2. 十二痛点与解法（下）：数据、结构化与安全

痛点症状解法
8. 数据处理能力数据量大时处理慢、甚至系统崩溃并行处理（文档处理流水线多 worker 并行，源材料称可提速多倍）；批量离线任务处理大批量
9. 结构化数据查询自然语言转 SQL 等结构化查询不准，表格多信息点问题答不好Chain-of-Table（链式思考 + 表格逐步变换，每步给模型看新表格）；Mix Self-Consistency（文本推理与符号推理各采样多条路径，多数投票聚合）
10. 复杂 PDF 提取复杂表格在 PDF 里，简单检索拿不到嵌入式表格检索：用版面分析工具解析出表格并组织成结构，再按问题取相关表格；PDF 可先转 HTML 再解析
11. 备用模型主模型限流或故障，服务直接挂掉模型路由器/统一网关：按问题自动选最合适的模型，主模型故障时自动切备选；同一接口可接多个模型供应商，切换不用改代码
12. LLM 安全恶意输入操控、不安全输出、敏感信息泄露输入输出双向审核：输入分类不过就拒绝，输出分类不过就改写或拒绝；内容分类模型（如 Llama Guard 类思路）判断是否安全并指出违反的规则类别
年代提醒：源材料里的痛点解法大量用 LlamaIndex 旧 API 举例（如 ServiceContext、LlamaPack、download_llama_pack），这些 API 在后续版本里已经大变或废弃，不要直接抄那些旧代码。本课只讲思路，示例用现代写法或伪代码；要用某个框架时以官方最新文档为准。

3. 合成测试集：没有标注数据也能评测

评测需要一个数据集，四列：question（问题）、ground_truths（真实答案）、answer（RAG 预测的答案）、contexts（RAG 生成答案时用的上下文列表）。前两列是真实数据，后两列是跑 RAG 得到的预测数据。没有人工标注时可以合成：

  1. 把知识库分块、嵌入、入库；
  2. 随机选一个块作根上下文，再检索 K 个相似上下文拼成一个大上下文；
  3. 用提示模板让 LLM 从这个大上下文生成若干个“问题 + 答案”对（要求：脱离上下文也看得懂、答案完全来自上下文、难度适中、不超过 10 个词、不用“提供的上下文”这种表述）；
  4. 重复多次，换上下文生成不同问题；
  5. 把这些问题跑一遍 RAG，收集预测答案与上下文，合成数据集就齐了。

合成数据的偏差要心里有数：LLM 生成的问题可能偏简单、偏它“会问”的类型。生产里要补两类样本：从真实日志脱敏抽样的问题，以及拒答类（无答案、知识库外的问题）——只测“能答对”不测“该拒答”，评测就是自欺欺人。

4. 独立评估 vs 端到端评估

两种评估方法，回答不同的问题：

  • 独立评估：分别评检索模块和生成模块。检索好不好（上下文精确度），生成好不好（答案相关性、忠实度），定位瓶颈在检索还是生成。
  • 端到端评估：只评最终响应。无标签时评答案的准确性、相关性、无害性；有标签时评准确率（Accuracy）和精确匹配（EM）。

为什么“只看最终答案对错”不够？模型可能猜对，也可能上下文不相关却仍生成了正确答案——只看对错会把运气当能力。必须同时评检索质量与忠实度，才能定位问题到底出在检索还是生成。

5. 关键指标：一张表记住

指标评什么怎么理解
忠实度 Faithfulness生成模块答案是否可由检索上下文推出、不编造；0–1 分，高分代表与上下文一致
答案相关性 Answer Relevancy生成模块答案与问题的相关性；不完整或冗余都会拉低分数；0–1 分
答案正确性 Answer Correctness生成模块生成答案与基准答案的匹配程度；0–1 分
上下文精确度 Context Precision检索模块相关条目是否都排在前面；0–1 分
Hit Rate（命中率）检索模块Top-K 里有没有正确答案所在的文档
MRR（平均排名倒数）检索模块第一个正确答案的排名的倒数的平均——排越前分越高
NDCG（归一化折扣累积增益）检索模块考虑排名位置的加权得分，越靠前的相关结果权重越高，再归一化到 0–1

三类关键指标可以概括为：答案的准确性、答案的相关性、上下文的相关性。另外 RGB 研究提出的四项基本能力也值得记：抗噪声能力、拒绝无效回答能力、信息综合能力、反事实稳健性——评测时可以按这四个维度设计用例。

6. 评估框架：RAGAS 与 ARES

RAGAS 是基于 LLM 裁判的自动化评估框架，三个核心指标的算法原理：

  • 忠实度：LLM 把答案拆成多个陈述，逐个检验是否与上下文一致，支持的陈述占比就是得分；
  • 答案相关性：LLM 根据答案反推可能的问题，算这些问题与原始问题的相似度平均值；
  • 上下文相关性：LLM 筛出与问题直接相关的句子，用它占上下文总句数的比例打分。

ARES 的目标也是自动化评估上下文相关性、答案忠实度、答案相关性，但它想降低评估成本：用少量人工标注数据 + 合成数据，微调轻量语言模型做“裁判”，再用预测驱动推理给出统计置信区间，对多个 RAG 系统做可靠排名。两个框架的共同提醒：裁判模型本身有偏差，要抽样人工复核，别把机器打分当真理。

7. 生产优化：上线前必须做的五件事

  • 多租户隔离：逻辑隔离用 tenant_id 元数据强制过滤；大客户用物理隔离（独立集群或命名空间）；按租户做配额与限流。多租户下最常见的安全事故是检索没带租户过滤导致跨租户数据泄露——必须在数据库层与查询层双重校验。
  • 增量更新：文档变更要版本化，删除旧向量按 doc_id；大批量用离线任务重建分区索引，小批量实时 upsert；索引频繁更新时用版本号、双写切换、后台重建与灰度保持一致性。
  • 缓存：Query 级缓存（相同问题直接返回答案，注意权限与 TTL）；Embedding 缓存（热门 query 的向量）；LLM 响应缓存（低敏场景缩短延迟）。缓存键必须带租户信息，否则缓存也会串租户。
  • Token 成本控制：控制检索条数与块长度；用更小的模型做摘要与路由；压缩检索结果（抽取句子级证据再喂给主模型）。
  • 索引优化：HNSW 参数（M、efConstruction、efSearch）要在召回率、QPS、内存、建索引时间上做压测取舍——efSearch 调大，召回上升、延迟也上升；按租户、时间、产品线分段分区，减少搜索空间；定期重建与增量插入之间做权衡。

索引数据质量同样是生产项：摄取前清理数据（去特殊字符、奇怪编码、多余 HTML 标签，去重、去无关文档），用元数据加一层结构化过滤（如按日期排序、按文档章节过滤），还可以把块与“它能回答的问题”一起索引，缓解查询与文档的表述不一致。记住：垃圾输入，垃圾输出。

二、代码示例

示例 1：检索指标自己算（Hit Rate / MRR / NDCG，可跑）

不用等框架，先理解指标本身：给定每条问题的“相关文档 ID 集合”和检索返回的排名列表，三个指标都是几行代码。

# 检索指标最小实现：Hit Rate / MRR / NDCG（纯 Python，可直接跑）
import math

def hit_rate(ranked_ids, relevant_ids, k=5):
    """Top-K 里有没有命中相关文档"""
    return 1.0 if set(ranked_ids[:k]) & set(relevant_ids) else 0.0

def reciprocal_rank(ranked_ids, relevant_ids):
    """第一个相关文档的排名倒数；没命中为 0"""
    for i, doc_id in enumerate(ranked_ids, start=1):
        if doc_id in relevant_ids:
            return 1.0 / i
    return 0.0

def ndcg(ranked_ids, relevant_ids, k=5):
    """NDCG：越靠前的相关结果权重越高，再除以理想排序的 DCG 归一化"""
    def dcg(ids):
        return sum(1.0 / math.log2(i + 2) for i, d in enumerate(ids[:k]) if d in relevant_ids)
    ideal = dcg(sorted(ranked_ids, key=lambda d: d not in relevant_ids))
    return dcg(ranked_ids) / ideal if ideal else 0.0

# 演示：3 条问题，每条的检索排名与相关文档
cases = [
    (["d3", "d1", "d2"], {"d1"}),   # 相关文档排第 2
    (["d5", "d6", "d7"], {"d5"}),   # 相关文档排第 1
    (["d8", "d9", "d10"], {"d2"}),  # 没命中
]
hr = sum(hit_rate(r, rel) for r, rel in cases) / len(cases)
mrr = sum(reciprocal_rank(r, rel) for r, rel in cases) / len(cases)
nd = sum(ndcg(r, rel) for r, rel in cases) / len(cases)
print(f"Hit Rate@5: {hr:.2f}  MRR: {mrr:.2f}  NDCG@5: {nd:.2f}")
# Hit Rate@5: 0.67  MRR: 0.50  NDCG@5: 0.54
# 解读：Hit Rate 只看有没有，MRR/NDCG 还看排得靠不靠前——
# 所以“召回到了但排第 5”和“排第 1”在 Hit Rate 里一样，在 MRR 里差很多。

示例 2：多租户隔离 + 增量更新 + 缓存（可跑，现代写法）

用内存版向量库演示生产三件套的控制流：检索强制带 tenant_id 过滤、按 doc_id 增量更新、Query 缓存的键带租户。生产里把内存列表换成真实向量库即可，过滤逻辑不变。

# 生产三件套演示：tenant_id 强制过滤 + 按 doc_id 增量更新 + 带租户的查询缓存
from dataclasses import dataclass, field

@dataclass
class Chunk:
    doc_id: str
    tenant_id: str
    text: str
    version: int = 1

class TenantStore:
    """演示版向量库：重点是过滤与更新逻辑，不是向量计算"""
    def __init__(self):
        self.chunks: list[Chunk] = []
        self.cache: dict[tuple, list[str]] = {}  # 缓存键含 tenant_id

    def upsert(self, chunk: Chunk):
        """增量更新：同 doc_id + 同租户的旧版本先删再插"""
        self.chunks = [c for c in self.chunks
                       if not (c.doc_id == chunk.doc_id and c.tenant_id == chunk.tenant_id)]
        self.chunks.append(chunk)
        self.cache.clear()  # 数据变了，缓存失效

    def search(self, query: str, tenant_id: str, k: int = 2):
        """检索：强制租户过滤，查不到别人的数据；缓存键带租户"""
        key = (tenant_id, query)
        if key in self.cache:
            return self.cache[key]  # 命中缓存
        # 演示检索：关键词命中；生产换成向量相似度
        pool = [c for c in self.chunks if c.tenant_id == tenant_id]
        hits = sorted(pool, key=lambda c: sum(w in c.text for w in query),
                      reverse=True)
        result = [c.text for c in hits if sum(w in c.text for w in query) > 0][:k]
        self.cache[key] = result
        return result

store = TenantStore()
store.upsert(Chunk("d1", "tenant_a", "A 公司年假 15 天。"))
store.upsert(Chunk("d1", "tenant_b", "B 公司年假 10 天。"))
print(store.search("年假多少天", "tenant_a"))  # ['A 公司年假 15 天。']
print(store.search("年假多少天", "tenant_b"))  # ['B 公司年假 10 天。']
store.upsert(Chunk("d1", "tenant_a", "A 公司年假 20 天。", version=2))
print(store.search("年假多少天", "tenant_a"))  # ['A 公司年假 20 天。']，旧版本已被替换
print(store.search("年假多少天", "tenant_b"))  # ['B 公司年假 10 天。']，不受影响

四、可能的面试题与答案

Q1：RAG 的十二个痛点里，前七个（论文里的）是哪七个？各用一句话说解法。

内容缺失（补数据 + 提示词说不知道）；错过排名靠前的文档（宽召回 + 重排，调 chunk_size/top_k）；脱离上下文（优化检索策略、微调 embedding）；未能提取答案（清数据、提示压缩、关键信息放上下文两端）；格式错误（精准提示、输出解析、结构化输出）；特异性错误（细节到全局、围绕句子的高级检索）；回答不全面（查询优化：路由、改写、拆分、HyDE）。

Q2：没有标注数据，怎么构建 RAG 评测集？

合成测试集：知识库分块入库 → 随机选块作根上下文 + K 个相似上下文拼大上下文 → 让 LLM 按模板生成“问题 + 答案”对 → 重复多次换上下文 → 跑 RAG 收集预测答案与上下文，得到 question / ground_truths / answer / contexts 四列。注意补真实日志脱敏问题和拒答类样本，合成数据可能偏简单。

Q3：独立评估和端到端评估有什么区别？

独立评估分别评检索模块（上下文精确度等）和生成模块（答案相关性、忠实度），定位瓶颈在检索还是生成；端到端评估只评最终响应（无标签评准确性/相关性/无害性，有标签评准确率与精确匹配）。只看最终对错不够，因为模型可能猜对。

Q4：RAGAS 的三个核心指标是怎么算的？有什么局限？

忠实度：LLM 把答案拆成陈述，逐个检验与上下文是否一致，支持占比即得分；答案相关性：LLM 按答案反推问题，算与原始问题的相似度均值；上下文相关性：LLM 筛出相关句子占上下文总句数的比例。局限：依赖裁判模型，有偏好与盲区，要抽样人工复核。

Q5：多租户 RAG 上线要注意什么？增量更新怎么做？

多租户：tenant_id 元数据强制过滤（数据库层与查询层双重校验）、大客户物理隔离、按租户配额限流、缓存键带租户。增量更新：文档变更版本化，删除旧向量按 doc_id；大批量离线重建分区索引，小批量实时 upsert；用版本号、双写切换、后台重建与灰度保持一致性。

五、加分项

生产视角：上线前按这个顺序检查：评测集有没有拒答类样本（没有就先补）→ 检索有没有 tenant_id 过滤（没有就别上线）→ 有没有备用模型（主模型限流时服务不能挂）→ 增量更新会不会留下旧版本向量 → 缓存键带没带租户。这五项任何一项缺了，上线后都是事故。

简历讲法：别写“负责 RAG 系统评测与优化”，写“针对客服 RAG 的内容缺失问题，建了合成测试集（含 X 条拒答样本），用 RAGAS 评出忠实度基线 0.72；加拒答提示与宽召回重排后，忠实度到 0.88，Top-5 命中率提升 X 个点”。前者是职责描述，后者是“问题—方法—指标”的完整故事，面试官能一路追问下去。
