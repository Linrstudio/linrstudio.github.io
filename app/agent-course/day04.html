Day 4：编排框架：LangChain Agent 与 LangGraph 状态机

Day 2、Day 3 讲的是推理范式——ReAct、Plan-and-Execute、Reflexion、LATS，那是 Agent「怎么想」。今天讲的是工程落地——LangChain Agent 与 LangGraph，那是 Agent「怎么跑起来」。一句话分清两者：LangChain Agent 是一套现成的工具调用循环，拿来就能用；LangGraph 是把工作流画成一张图，流程越复杂越能看出它的好。

一、核心解释

1. 先分清：推理范式与编排框架不是一回事

ReAct、Plan-and-Execute 是策略：Agent 每一步先想还是先做、要不要反思、要不要搜多条路。LangChain Agent、LangGraph 是工程落地方式：策略定好了，用什么代码把它跑起来、跑稳、跑出可观测的轨迹。面试时把这两层说清，比背 API 名重要得多。

2. LangChain Agent 的现代写法：create_agent

LangChain 把 LLM、提示模板、工具、记忆、解析器拼成可运行程序。Agent 在这里指：由 LLM 决定下一步调用哪个工具的循环执行体。LangChain 1.x 的现代入口是 create_agent：

from langchain.agents import create_agent

agent = create_agent(model, tools, system_prompt="...")
result = agent.invoke({"messages": [{"role": "user", "content": "帮我算 21+21"}]})

它跑的循环和你 Day 2 手写过的 ReAct 循环本质上是同一个：模型决策 → 工具执行 → 结果回填 → 再决策，直到模型给出最终答案，或者触到最大迭代次数。框架替你标准化了三件事：迭代限制、解析错误处理、中间消息结构，你只需要操心工具和提示词。

3. 旧写法已废弃：AgentExecutor 与 create_react_agent

很多旧教程、旧面试题里会出现 AgentExecutor：它就是上面那个循环的旧版执行器。但在 LangChain 1.x 里 AgentExecutor 已被删除，不要再写；create_react_agent 也已 deprecated，同样不要用。新代码统一用 create_agent。面试时如果对方问起 AgentExecutor，答它的循环本质即可，再补一句“1.x 已废弃，现用 create_agent”——这比背旧 API 更能证明你跟得上版本。具体 API 以官方最新文档为准。

4. 工具描述是 Agent 的接口设计

Agent 靠工具的描述（name、description、参数 schema）做两件事：选哪个工具、怎么填参数。描述不清，模型就会错选工具或幻觉参数。好的描述要包含：用途、输入输出、边界条件、示例。记住一句话：工具描述就是 LLM 与你的代码之间的接口文档，写工具时先写描述，再写实现。

5. LangGraph 状态机：把工作流画成图

如果把 LangChain Agent 看成“一套默认的循环”，LangGraph 就是把 Agent 工作流画成一张图：节点是处理步骤（调用模型、调工具、审核），边是流转关系。复杂业务往往需要分支、循环、人工确认——用图更直观。三个零件和 LangGraph 课里讲的一致：

  • 节点（Node）：一个函数，读共享状态，返回对状态的部分更新。
  • 边（Edge）：A → B，表示执行完 A 后执行 B。
  • 条件边（Conditional Edge）：根据当前状态决定下一步去哪个节点，例如失败去修复、需要审核去 human 节点、否则继续执行。

6. 共享状态与 reducer 合并

状态通常用 TypedDict 定义 schema，全图共享。节点函数只返回它改了的那一部分更新，图按 reducer 把更新合并进旧状态。设计状态时要谨慎：多个节点写同一字段可能冲突，需要 schema 约束、明确每个节点的写入职责，并选好归约策略——是追加（append）还是替换（replace）。消息列表一般追加，路由标记一般替换。

7. 两者选型对比

维度LangChain Agent（create_agent）LangGraph
控制流偏固定循环：决策 → 工具 → 回填显式图：分支、循环、回环更自然
可观测性日志为主结构化的节点轨迹，每步状态可导出
人机协同需要额外封装容易加 human 审核节点
适用标准工具 Agent，快速落地复杂业务流程：审查、重试拓扑、并行任务

选型口诀：流程是“单一工具循环”就用 create_agent，别过度设计；流程出现多阶段流水线、条件路由、回环修复、人工审核、并行任务中的任何一个，就该上 LangGraph。多 Agent 框架（AutoGen、CrewAI 等）是另一个话题，留给 Day 16。

容易踩的坑：一是工具描述写得像内部变量名（比如“tool1：处理数据”），模型根本选不对；二是 LangGraph 节点返回整个新状态，把别的字段覆盖掉——节点只返回它改的那一部分。其余的坑（步数上限、解析失败）框架都替你兜了底，但这两个坑框架兜不住。

二、代码示例

示例 1：create_agent 跑一个带工具的 Agent（LangChain 1.x 现代写法）

from langchain.agents import create_agent
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

# 工具描述就是接口文档：用途、输入、边界都要写清
@tool
def add(a: float, b: float) -> float:
    """计算两个数的和。输入两个数字，返回它们的和。"""
    return a + b

@tool
def get_weather(city: str) -> str:
    """查询指定城市的当前天气。输入城市名，返回天气简述。"""
    return f"{city}：多云，22°C，降水概率 30%"

model = ChatOpenAI(model="gpt-4o-mini")  # 需配置 API Key 环境变量
agent = create_agent(
    model,
    tools=[add, get_weather],
    system_prompt="你是一个助手。需要计算或查天气时调用工具，不要自己编数字。",
)
result = agent.invoke({"messages": [{"role": "user", "content": "上海天气怎么样？顺便算 21+21"}]})
print(result["messages"][-1].content)

示例 2：LangGraph 状态机——条件边路由 + 失败回环（不用真实模型也能跑）

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END

class AgentState(TypedDict):
    task: str
    notes: str
    route: str  # exec / human / end

def planner(state: AgentState):
    # 节点只返回它改的那一部分更新
    needs_review = "合同" in state["task"]
    return {"notes": "已出计划", "route": "human" if needs_review else "exec"}

def exec_node(state: AgentState):
    return {"notes": state["notes"] + " | 已执行", "route": "end"}

def human_node(state: AgentState):
    return {"notes": state["notes"] + " | 人工已审核", "route": "end"}

def route_fn(state: AgentState) -> Literal["exec", "human"]:
    return "human" if state["route"] == "human" else "exec"

graph = StateGraph(AgentState)
graph.add_node("planner", planner)
graph.add_node("exec", exec_node)
graph.add_node("human", human_node)
graph.add_edge(START, "planner")
# 条件边：按状态决定下一步去哪个节点
graph.add_conditional_edges("planner", route_fn, {"exec": "exec", "human": "human"})
graph.add_edge("exec", END)
graph.add_edge("human", END)
app = graph.compile()

print(app.invoke({"task": "审阅合同", "notes": "", "route": ""}))
# route 走 human：{'task': '审阅合同', 'notes': '已出计划 | 人工已审核', 'route': 'end'}
print(app.invoke({"task": "查天气", "notes": "", "route": ""}))
# route 走 exec：{'task': '查天气', 'notes': '已出计划 | 已执行', 'route': 'end'}

四、可能的面试题与答案

Q1：create_agent 的循环是怎么跑的？

模型决策 → 工具执行 → 结果回填 → 再决策：模型先决定要不要调工具、调哪个；有工具调用就执行，把结果以 tool 消息回填进上下文；再由模型决定下一步。直到模型给出最终答案，或者触到最大迭代次数。框架标准化了迭代限制、解析错误处理和中间消息结构，开发者专注工具与提示词。

Q2：AgentExecutor 是什么？现在还能用吗？

AgentExecutor 是 LangChain 旧版里驱动“决策 → 工具 → 回填”循环的执行器。但在 LangChain 1.x 里它已被删除，create_react_agent 也已 deprecated，现在统一用 create_agent。面试时答出循环本质，再点明版本变迁即可；具体 API 以官方最新文档为准。

Q3：什么时候选 LangGraph 而不是 LangChain Agent？

当流程不是单一工具循环，而是需要多阶段流水线、条件路由、回环修复、人工审核节点、并行任务时，用图编排更清晰可维护。标准工具 Agent 用 create_agent 快速落地即可，图会增加不必要的复杂度。

Q4：LangGraph 的状态更新为什么要谨慎设计？

多节点写入同一字段可能冲突。需要 schema 约束（TypedDict）、明确每个节点的写入职责、选好归约策略：消息列表一般追加（append），路由标记一般替换（replace）。节点只返回它改的那一部分更新，返回整个新状态会覆盖别的字段。

Q5：LangGraph 的条件边解决什么业务问题？

根据中间状态动态路由：工具失败时回环重试、敏感操作走人工审核节点、不同客户等级走不同流程、执行结果不达标时回到规划节点重做。没有条件边，这些分支只能写在节点函数里的 if/else 中，流程就看不见了。

五、加分项

生产视角：工具描述要当接口文档来评审，写完让同事只看描述猜“这个工具是干嘛的、参数怎么填”，猜不对就重写。LangGraph 上线前先画图：节点、边、状态字段列一张表，画不出来就别写代码——流程想不清楚，代码只会更乱。

简历讲法：别写“会用 LangChain/LangGraph”，写“用 create_agent 落地标准工具 Agent（模型决策—工具执行—结果回填循环）；复杂审核流程改用 LangGraph 状态机，条件边做失败重试与人工审核路由，节点轨迹可观测”。前者是名词，后者是可追问的选型过程。
