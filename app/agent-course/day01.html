Day 1：Agent 是什么：定义、组成与分类

大模型本身只会一件事：接一句话，回一段话。你问它“帮我查上季度销量并写成摘要”，它能写出漂亮的回答框架，却查不到真实数据，也记不住上次的结论。Agent 就是把模型放进一个能办事的身体里：它能拆任务、查资料、调工具、记结果，再根据环境反馈决定下一步。今天先把 Agent 的定义、组成与分类这张全景图立起来，后面 21 天就是往这张图里逐块填血肉。

一、核心解释

1. 一句话定义与 Agent 公式

AI Agent（智能体）是以大模型为认知核心，结合规划、记忆与工具调用，能在多步交互中根据环境反馈持续决策并完成任务的系统。业界常用一句公式概括：

Agent ≈ LLM + Planning（规划）+ Memory（记忆）+ Tools（工具）

缺一块会怎样？缺规划，Agent 变成“只会接话”的聊天，长任务容易跑偏；缺记忆，长对话丢线索，多会话无法延续用户偏好；缺工具，只能“空谈”，查不了实时信息、改不了系统状态。LLM 是中枢，但单靠 LLM、没有外环，就不是完整的 Agent。

2. 四能力闭环：感知、规划、记忆、行动

LLM 是 Agent 的“大脑”，提供推理和生成能力；Agent 是 LLM 的“完整身体”，具备四个能力组成的闭环。感知把多模态输入（文本、文件、接口返回、页面结构）转成模型可用的表示，并抽取任务相关状态；规划把模糊目标拆成可执行步骤，并在执行中动态调整；行动真正调用工具、触发环境变化；记忆把中间结果记下来，供下一轮使用。闭环的典型形态是 Thought（推理）→ Action（行动）→ Observation（观察）→ … → Final Answer：模型输出的往往不是最终答案，而是“下一步动作”，环境返回观察结果，再进入下一轮推理。

3. 与 Chain、ChatBot 的本质区别

三者常被混用，面试最爱问的区分点就一个：控制流在哪。

维度ChatBotLLM ChainAgent
控制流多为线性对话开发者定义的 DAG / 序列模型驱动的分支与循环
工具可有可无可嵌入固定节点动态选择与多轮调用
状态主要会话上下文链各节点显式传递记忆 + 环境观察
适用问答、闲聊、简单引导ETL 式固定流程开放问题、研究、自动化任务

本质区别一句话：Chain 的控制流在代码里；Agent 的控制流在模型决策 + 环境反馈里（仍可由代码设边界）。ChatBot 加上插件也不一定就变成 Agent——若插件调用由固定规则触发（如关键词路由），更像“带工具的 Bot”；只有模型在多步推理中自主选择工具与参数、并形成闭环迭代，才贴近 Agent。关键在是否具备多步自主决策与反馈闭环。二者也可结合：链负责稳定流程，Agent 负责链内某段的灵活分支。

4. 六大组成

感知（Perception）：输入处理与状态抽取，常与结构化抽取、OCR、HTML 解析、日志解析结合，关键是减少噪声进上下文。规划（Planning）：拆子目标与步骤，可以是一次性计划或每步重规划，常见实现有 CoT、ReAct、Planner-Executor 双模块、树搜索、任务图。记忆（Memory）：短期（当前会话上下文、工具轨迹）与长期（用户画像、文档知识、向量库、图数据库），工程要点是摘要压缩、引用溯源、记忆冲突解决、权限与隐私。工具（Tools）：对外部世界可执行的操作抽象，要有清晰 schema（名称、描述、参数 JSON Schema），要点是最小权限、参数校验、错误信息回灌模型。执行（Action）：真正调用工具并处理超时、重试、幂等等工程问题。反思（Reflection）：对失败或质量不佳的结果自省——纠错、换策略、生成检查清单，常与自我批评、验证器配合；不是必须，但对高风险或易错工具场景收益大，代价是额外延迟与 Token。

5. 五步工作流程

可以记成一句口诀：听懂 → 拆活 → 动手 → 对账 → 交卷。① 输入处理：意图识别、指代消解、安全过滤、加载相关记忆与文档；② 任务分解：生成子任务列表或决策树，复杂任务可配合人在回路确认里程碑；③ 工具选择与调用：由模型或路由模块选工具，执行器做鉴权、限流与结果规范化；④ 结果整合：合并多源信息，解决冲突（例如时间更新的数据优先）；⑤ 输出生成：面向用户的自然语言答案 + 可选引用与操作轨迹（便于审计）。为避免 Agent 在工具调用间“迷失”，要明确停止条件与最大步数、维护任务清单与当前子目标、对每步输出要求结构化、关键步骤强制验证。

6. 五种经典分类

分类来自经典 AI 教材的智能体理论，可与 LLM Agent 对照理解。反应式（Reactive）：类似反射，输入→动作，几乎不维护复杂内部模型，优点是快、可解释、易测试，缺点是对长程依赖与复杂推理弱。基于模型（Model-based）：脑中有“世界模型”，能预测行动后果，如显式维护状态机、仿真环境或知识图谱。基于目标（Goal-based）：明确要达成什么状态，能选路径。基于效用（Utility-based）：在多个冲突目标间权衡，选期望效用最大的行动——目标型关注“是否达成”，效用型在成本、时延、风险、用户偏好之间做综合最优。学习型（Learning）：从反馈中更新策略或模型，如 RLHF、在线反馈、Bandit 选工具。LLM Agent 一般是混合型：底层是模型推理，上层可接目标/效用（打分选路径）+ 记忆（世界状态）+ 学习（反馈更新）。

7. 应用场景速览

优先落地的场景是“高频、可工具化、可评估”的。智能客服：工单查询、订单状态、退换货政策，需知识库对齐、身份鉴权、升级人工策略。代码助手：读仓库、跑测试、提 PR，需沙箱、diff 审查、最小权限。数据分析：NL2SQL、制图、解读，需数据治理、行级权限、结果校验。自动化运维：查日志、重启服务、开单，需审批流、灰度、回滚。知识管理：摘要、标签、关联检索，需溯源、版本、权限。企业内部落地最先关心的三个非功能需求是：安全与合规（权限、审计）、可控性（人在回路、工具白名单）、可观测性（轨迹、指标、回放）。

容易踩的坑：Agent 的“自主”不是不受控。自主是在约束空间内的决策：工具白名单、参数校验、人在回路（HITL）、预算与步数上限、输出审核，缺了护栏的自主就是事故。面试被追问“自主是不是不受控”，就按这五条护栏答。

二、代码示例

示例 1：最小“思考—行动—观察”循环（离线可跑，用假模型演示循环骨架）

def run_agent(user_goal, tools, llm, max_steps=8):
    """最小 Agent 循环：模型决定下一步动作，工具返回观察结果，再进入下一轮。"""
    messages = [
        {"role": "system", "content": "你是可调用工具的 Agent。"},
        {"role": "user", "content": user_goal},
    ]
    for _ in range(max_steps):
        plan = llm(messages)  # 模型决定：结束 or 调用某工具
        action = parse_tool_call(plan)  # 从模型输出解析结构化动作
        if action["name"] == "finish":
            return action["args"]["answer"]
        obs = tools[action["name"]](**action["args"])  # 真实环境反馈
        messages.append({"role": "assistant", "content": plan})
        messages.append({"role": "user", "content": f"工具结果：{obs}"})
    return "超过最大步数，未完成。"


def parse_tool_call(text):
    """极简解析：生产环境请用 JSON / tool_calls 结构化输出。"""
    import json
    return json.loads(text)


def fake_llm(messages):
    """假模型：第一轮调搜索，第二轮结束。真实场景换成 API 调用。"""
    if len(messages) <= 2:
        return '{"name": "search_kb", "args": {"query": "退货政策"}}'
    return '{"name": "finish", "args": {"answer": "已查到：7 天无理由退货。"}}'


tools = {"search_kb": lambda query: f"知识库命中：[{query}] 相关条款 3 条"}
print(run_agent("我们公司的退货政策是什么？", tools, fake_llm))
# 已查到：7 天无理由退货。

示例 2：现代 LangChain 1.x 写法——create_agent（需配模型 API Key）

# LangChain 1.x：Agent 用 create_agent 构建。
# 注意：AgentExecutor 在 1.x 已删除，不要再用；create_react_agent 已 deprecated，也不要再用。
from langchain.agents import create_agent
from langchain_core.tools import tool


@tool
def search_kb(query: str) -> str:
    """在公司知识库中按关键词搜索。"""
    return f"知识库命中：[{query}] 相关条款 3 条"


# model 换成你项目里实际的 ChatModel；以官方最新文档为准
agent = create_agent(
    model="gpt-4o-mini",
    tools=[search_kb],
    system_prompt="你是客服助手。涉及事实类问题必须先调用工具查证，不要凭记忆回答。",
)

result = agent.invoke({"messages": [{"role": "user", "content": "退货政策是什么？"}]})
print(result["messages"][-1].content)

四、可能的面试题与答案

Q1：一句话说明什么是 AI Agent？

AI Agent 是以大模型为认知核心，结合规划、记忆与工具调用，能在多步交互中根据环境反馈持续决策并完成任务的系统；其本质是闭环的感知—思考—行动循环，而不仅是单次文本生成。

Q2：为什么说 Agent = LLM + Planning + Memory + Tools？缺一块会怎样？

缺规划：容易变成“只会接话”的聊天，长任务易跑偏或一步登天完不成。缺记忆：长对话会丢线索，多会话无法延续用户偏好与任务状态。缺工具：只能“空谈”，无法查实时信息、执行代码、改系统状态。LLM 仍是中枢，但单靠 LLM 没有外环则不是完整 Agent。

Q3：Agent 和 Prompt Chain 有什么本质区别？

Prompt Chain 的拓扑与顺序主要由工程侧固定；Agent 在运行时在动作空间中做选择，并依赖 Observation 更新信念，适合输入与路径不确定的任务。二者可结合：链负责稳定流程，Agent 负责链内某段的灵活分支。

Q4：Agent 的记忆一般怎么设计？

分层设计最常见：工作记忆（当前轨迹与关键结论）+ 会话记忆（摘要滚动）+ 长期记忆（向量检索/结构化库）。写入要区分“事实”与“推断”，并带时间戳与来源，便于更新与撤销。Day 15 会展开讲记忆系统。

Q5：规划和执行要不要拆开两个模型？

视任务而定。Planner-Executor 拆分可提升可控性（强模型规划、快模型执行）；单模型端到端更简单但易在长链路漂移。可混合：规划用强模型，执行层做确定性校验。Day 2 会讲 Planner-Executor 的具体形态。

五、加分项

生产视角：企业内部落地 Agent，先关心的不是模型选型，而是三个非功能需求：安全与合规（权限、审计）、可控性（人在回路、工具白名单）、可观测性（轨迹、指标、回放）。先把护栏搭好，再谈能力。

简历讲法：别写“了解 AI Agent”，写“用 LLM + 规划 + 记忆 + 工具搭了客服 Agent：模型多步自主选工具查知识库，工具白名单 + 最大步数 + 人在回路做护栏，轨迹可审计”。前者是名词，后者是可追问的架构。
