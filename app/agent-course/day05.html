Day 5：Prompt 工程基础：结构、原则与 Few-shot

同一模型、同一个问题，换个 Prompt，答案可以从“完全不能用”变成“直接能上生产”。Prompt 工程不是写几句咒语，而是把业务目标翻译成模型能稳定利用的上下文与指令。今天先把地基打牢：Prompt 为什么有这么大威力、一个完整的 Prompt 由哪五段组成、四条设计原则，以及 Zero/One/Few-shot 该怎么用。

一、核心解释

1. Prompt 是什么：为什么同一模型表现差异巨大

LLM 本质是“在给定前文条件下预测下一个 token”：你提供的 Prompt 会强烈偏置后续生成的概率分布。模糊指令 → 模型随机发挥；清晰指令 + 示例 + 格式 → 可控输出。所以 Prompt 工程的定义不是“写提示词”，而是设计、组织、迭代输入给模型的文本（以及配套的参数与格式约束），使模型在任务理解、推理质量、输出格式、安全性上达到预期效果。

在 Agent 场景里，Prompt 还承担角色定义、工具使用规范、错误恢复策略等职责，比纯问答复杂得多。规划、工具选择、结果汇总都依赖提示词，一环薄弱会导致错误级联。这也是为什么有人说 Prompt 是 Agent 的“软代码”：行为策略大量编码在 System/User Prompt 与模板里，变更 Prompt 就像改业务规则，需要版本管理与评审。

2. 五段结构：角色、任务、上下文、格式、约束

一个完整的 Prompt 通常可拆成五块。不必每次全写，但脑中要有谱：

组成部分含义典型写法
角色模型以什么身份作答“你是一名资深数据分析师……”
任务具体要完成什么，动词要清晰可验证“请根据下列工单判断优先级并说明理由”
上下文事实材料、用户状态、检索片段“以下为知识库片段：……”
格式JSON / XML / 字段列表 / 步骤“仅输出 JSON，键为 …”
约束禁止项、长度、风格、安全“不得编造链接；不超过 200 字”

其中最容易被忽略的是格式与负向约束（不要做什么）：没有格式，程序难接；没有约束，模型容易啰嗦、幻觉或越权。另外注意，上下文与指令要分段或打标签，避免模型混淆“要遵守的规则”和“要处理的材料”——这个区分在 Day 6 讲注入防御时会再次出现。

3. 四原则：清晰、具体、结构化、迭代

清晰（Clear）：用词准确、无歧义，避免“它、这个、上面”指代不明；关键术语与业务定义写清楚。歧义会放大模型的随机性，清晰指令缩小“合法输出”的空间，提高一致性。反面例子是“把日期改一下格式”，正面例子是“请将下面文本中的日期统一转换为 ISO 8601 格式（YYYY-MM-DD），若无法解析某日期，保留原文并在该行末尾标注 [UNPARSED]”。

具体（Specific）：说明粒度（多长、几个要点）、判定标准（何为“高优先级”）、反例（什么情况算错误）。“简要总结”不如“用三条要点总结下文，每条不超过 25 个汉字；不得引入文中未出现的人名或数字”。

结构化（Structured）：用标题、编号、XML 标签、Markdown 小节、分隔线，让模型与人类都易于解析“哪部分是规则、哪部分是数据”。标签化（如 <document>…</document>）还能降低“把用户数据当指令”的风险。

迭代（Iterative）：第一版 Prompt 很少完美，要建立“失败样本集 → 改 Prompt → 回归测试”的闭环。标准做法是：固定评测集与评分标准；分类错误（理解错、知识错、格式错、安全错）；小步修改，一次改一个变量；记录版本与效果，避免“感觉变好”但无数据。

4. Zero-shot、One-shot、Few-shot

Zero-shot：不给示例，只给指令与任务说明。One-shot：给 1 个输入输出样例。Few-shot：给少量（通常 2～8 个）样例，示范期望行为。背后的机制叫上下文学习（in-context learning）：模型在不更新权重的情况下，从前文示例中推断映射关系；示例越多，对格式与边界的约束越强，但占用更多 token，且可能过拟合到示例风格。

Few-shot 不一定比 Zero-shot 好：任务简单且指令已足够清晰时，Zero-shot 更省 token；输出格式复杂或边界情况多时，Few-shot 往往更稳；若示例质量差或与测试分布不一致，反而有害。示例也不是越多越好，收益递减，且上下文变长会挤占其他信息。

5. 示例选择与顺序的影响

选示例优先覆盖三类：典型模式、边界情况、易错反例，避免高度重复的同质示例。具体建议：包含“最难的合法输入”与“应拒绝/应降级”的样例；若有多类意图，每类至少一例；示例输出风格与生产环境一致（尤其是 JSON 键名与大小写）。

顺序也有影响：有研究表明（因模型与任务而异），首尾位置往往印象更深，中间示例可能被“平均化”。实践中常见做法是由简到繁或先典型后边界，避免第一个示例过难导致整体跑偏。但工程上不要依赖“神秘顺序”，应配合明确规则与格式约束，必要时对比几种顺序做 A/B。

6. 动态 Few-shot：按输入检索最相关的示例

动态 Few-shot 不是固定写死 5 个例子，而是每次请求前用检索（向量相似度、BM25、规则路由）从示例库中选出与当前用户输入最相近的 k 条，拼进 Prompt。相当于“小样本集合上的 RAG”，提升示例与用户问题的分布匹配度，减少不相关示例带来的干扰。

它和 RAG 的区别要分清：RAG 检索的是知识文档，动态 Few-shot 检索的是输入输出对（示范），二者可以并存。RAG 的完整机制是 Day 7～12 的内容。

容易踩的坑：一是写 Prompt 只写任务，把格式和约束全漏了——下游解析靠猜，等于白做；二是 Few-shot 示例直接用真实用户对话当样例，泄露隐私——示例要脱敏或用合成数据；三是示例与生产输出风格不一致，比如示例里 JSON 键是驼峰、生产要求下划线，模型会跟着示例走。

二、代码示例

示例 1：五段式 Prompt 模板函数（纯 Python，可直接跑）

def build_prompt(role, task, context, output_format, constraints):
    """按角色/任务/上下文/格式/约束五段拼装 Prompt。"""
    return (
        f"角色：{role}\n\n"
        f"任务：{task}\n\n"
        f"上下文：\n{context}\n\n"
        f"格式：\n{output_format}\n\n"
        f"约束：\n{constraints}"
    )

prompt = build_prompt(
    role="你是电商售后客服质检助手，只根据给定规则做分类，不编造订单信息。",
    task="阅读用户留言，输出唯一标签：退货 / 换货 / 物流查询 / 其他。",
    context="用户留言：收到的鞋子尺码小了，想换大一码。",
    output_format='仅输出一行 JSON：{"label":"...", "confidence":0.0-1.0, "reason":"一句话理由"}',
    constraints="- 若信息不足以判断，label 填 \"其他\"，confidence 降低并在 reason 说明缺失信息。\n- 不要输出 JSON 以外的任何文字。",
)
print(prompt)
# 把这段 prompt 发给模型，得到的输出可直接 json.loads 解析——
# 格式段就是为下游解析器服务的。

示例 2：动态 Few-shot——按输入检索最相关的示例（纯 Python，可直接跑）

import re

# 示例库：输入输出对（示范），生产中应脱敏或用合成数据
EXAMPLES = [
    ("App 登录一直转圈，重装也没用。", '{"category":"登录故障","severity":4}'),
    ("想了解一下会员有哪些权益。", '{"category":"售前咨询","severity":1}'),
    ("上周扣款两次，要求退款并赔偿。", '{"category":"计费争议","severity":5}'),
    ("密码忘了，收不到重置短信。", '{"category":"登录故障","severity":3}'),
    ("发票怎么开？需要提供什么？", '{"category":"售前咨询","severity":1}'),
]

def score(query, example_text):
    # 演示用简易相似度：单字重叠数（中文无空格，按词切分会整句成一个词）；
    # 生产可用向量相似度或 BM25
    q = set(re.findall(r"[\u4e00-\u9fff]|[a-zA-Z]+", query))
    e = set(re.findall(r"[\u4e00-\u9fff]|[a-zA-Z]+", example_text))
    return len(q & e)

def dynamic_few_shot_prompt(user_input, k=2):
    ranked = sorted(EXAMPLES, key=lambda ex: score(user_input, ex[0]), reverse=True)
    shots = "\n\n".join(
        f"示例{i+1}：\n输入：{text}\n输出：{out}"
        for i, (text, out) in enumerate(ranked[:k])
    )
    return (
        '你是工单分类器。根据用户描述输出 JSON：{"category":"...", "severity":1-5}\n\n'
        f"{shots}\n\n现在分类：\n输入：{user_input}\n输出："
    )

print(dynamic_few_shot_prompt("登录验证码一直收不到，急！"))
# 选中的应是两条登录故障示例，而非固定写死的示例——
# 这就是动态 Few-shot：检索输入输出对，而不是知识文档。

动手任务（10 分钟）

1. 把示例 1 的模板改成你自己的任务（比如从邮件提取会议时间与参会人邮箱），先故意删掉“格式”与“约束”两段，再补回去，对比两次 Prompt 的完整度。
2. 把示例 2 的 k 从 2 改成 4，再换一个与示例库完全无关的输入（比如“今天天气怎么样”），看看选出的示例是否还相关——体会“不相关示例带来干扰”是什么意思。
3. 准备 10 条你自己任务的测试用例，跑一遍你的 Prompt，把失败按“理解错 / 知识错 / 格式错 / 安全错”分个类，这是迭代优化的第一步。

四、可能的面试题与答案

Q1：你如何理解 Prompt Engineering？它和“调参”有什么区别？

Prompt Engineering 主要优化输入侧：措辞、结构、示例、系统提示，有时配合温度、top-p 等解码参数；而传统“调参”多指训练阶段的权重更新（或 LoRA 等）。推理时我们最常动的是 Prompt 与少量解码参数，而不是改模型权重。数据少、迭代快优先 Prompt + 评测；要固化领域行为、长期一致再考虑微调，二者常组合。

Q2：为什么说 Prompt 是 Agent 的“软代码”？

因为 Agent 的行为策略——何时推理、何时调工具、输出什么格式——大量编码在 System/User Prompt 与模板里，变更 Prompt 就像改业务规则，需要版本管理与评审，类似代码。规划、工具选择、结果汇总都依赖提示词，一环薄弱会导致错误级联。

Q3：写 Prompt 时最容易忽略哪一块？

格式与负向约束。没有格式，程序难接；没有约束，模型容易啰嗦、幻觉或越权。自检清单：是否有明确任务与输出格式？材料与指令是否分开？是否有禁止项与缺信息时的行为？是否可用 10 条用例跑通并记录失败模式？

Q4：Few-shot 示例顺序会影响结果吗？

会，属于位置偏差的一种表现：首尾位置往往印象更深，中间示例可能被平均化（因模型与任务而异）。工程上不要依赖“神秘顺序”，应配合明确规则与格式约束，可对比几种顺序做 A/B；常见做法是由简到繁或先典型后边界。

Q5：你如何迭代优化 Prompt？

（1）固定评测集与评分标准；（2）分类错误：理解错、知识错、格式错、安全错；（3）小步修改，一次改一个变量；（4）记录版本与效果，避免“感觉变好”但无数据。复杂任务拆步或拆调用，一次只让模型做一件事。

五、加分项

生产视角：Prompt 模板要进 Git 做版本管理，与模型名、温度一起记录元数据，线上灰度与回滚。评测集是 Prompt 的单元测试：没有 10 条能跑通的用例，就不要说“这个 Prompt 可以了”。示例库要脱敏，禁止把真实用户对话直接当示例。

简历讲法：别写“熟悉 Prompt 工程”，写“按角色/任务/上下文/格式/约束五段结构设计工单分类 Prompt，Few-shot 覆盖典型、边界与反例，格式合法率从 X% 提升到 Y%（评测集 N 条）”。前者是名词，后者是可追问的工程过程——数字用你自己的实测填。
