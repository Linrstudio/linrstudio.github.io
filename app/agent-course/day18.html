Day 18：循环控制与可靠性：终止、收敛、防死循环与错误恢复

Day 17 把 Loop 搭起来了，今天解决它最要命的问题：怎么停下来。一个没有终止条件的 Loop 可能无限循环，直到烧光 Token；一个没有错误恢复的 Loop，一错就崩。今天讲循环在“循环”什么、四类终止条件、三法收敛判断、Goal 模式、多层防死循环，以及出错时怎么分层恢复、兜底收尾。

一、核心解释

1. 循环到底在“循环”什么：五个要素

Loop 循环的是五个关键要素：上下文（每轮携带的历史信息）、状态与记忆（当前进度和过往记录）、预算（Token 消耗和步数限制）、可用工具集（Agent 能调用的工具范围）、终止与收敛判断（何时停止）。本质上，Loop 循环的是一段不断增长和演化的“工作流状态”——每跑一轮，系统根据上一轮的观察结果决定下一步，直到任务完成或达到终止条件。控制循环，就是控制这五个要素。

2. 终止条件四类：正常与异常要分开

终止条件属于说明
任务完成正常终止目标达成，这是最理想的终止
达到预算上限异常终止Token 消耗或步数超限
遇到不可恢复的错误异常终止工具调用持续失败或陷入死循环
需要人工介入异常终止遇到需要人类判断的决策点

设计良好的 Loop 应该能区分“正常终止”和“异常终止”，并分别给出不同的输出。预算控制要考虑五个维度：Token 消耗、步数/轮数、时间（单轮超时和总超时）、工具调用次数（外部 API 可能产生费用）、子 Agent 数量。

3. 收敛判断三法：怎么知道“做完了”

收敛判断是评估“任务是否已经完成”或“是否在朝着正确方向前进”的机制，实现方式有三类：① 规则检查——如测试全部通过、文件已修改、PR 已创建，这是最可靠的；② 独立评估 Agent——用一个独立的 Agent（甚至不同模型）在每轮结束时检查目标是否达成；③ 阈值判断——如代码覆盖率提升到 X%、性能指标达到 Y。Claude Code 和 Codex 的 /goal 功能就是这种模式——每跑完一轮，由独立 Agent 判断是否完成。

4. Goal 模式 vs 普通 Loop：目标驱动 vs 轮数驱动

Goal 模式是 Loop 的一种运行模式——不按时间触发，而是一直运行到最开始制定的标准真正完成为止，每跑完一轮由独立 Agent 判断是否完成。普通 Loop 可能基于定时或事件触发，跑完预设轮数就停；Goal 模式则是“目标驱动”——目标是终止条件，没达成就不停。Goal 模式更彻底，但也更依赖收敛判断的可靠性：判断错了，要么提前停、要么一直跑。

5. 四种触发器：Loop 是被什么启动的

① 定时触发——cron 调度，适合周期性任务（如每日报告）；② 事件触发——GitHub hook、Webhook，适合响应外部事件；③ 持续目标模式（/goal）——一直运行到目标完成为止；④ 手动触发——用户主动启动，适合需要人工判断的场景。触发器是 Day 17 六大组件里的“心跳”，这里补齐它的四种形态。

6. 防死循环：多层防御 + 三层工程解法

防止死循环需要多层防御：① 硬性约束——设置最大迭代次数和超时机制；② 循环检测——Agent 连续做出相同的 Action，强制触发反思或中断；③ 熔断机制——同一工具连续失败 3 次，立即终止当前推理链；④ 兜底方案——达到上限后返回当前阶段最接近的结果，标记为“未完成”。

工程上再分三层落实：第一层——工具层硬隔离：Agent 调用外部 API 时必须包裹 try-catch，返回结构化错误信息；第二层——推理层熔断：实现 Max Iteration Check 和 Loop Detection 模块；第三层——规划层自我修正：工具调用失败时让 Agent 反思“哪里做错了？是不是参数不对？要不要换工具？”

其中反思节点（Reflection Node）值得单独记住：Agent 连续两次做出相同 Action 时，强制触发一个反思 Prompt，提示模型“你已经尝试过此路径且失败了，请更换策略”。实现方式是在循环中维护一个“最近 Action 历史”，每次执行前检查是否与上一次相同，相同则插入反思指令。

7. 结构化错误回传：别只说“Error”

工具调用失败时，不能只返回简单的“Error”，而应该返回结构化的错误信息，包含错误类型、原因和可操作的建议，例如：{"status": "failed", "error_type": "Timeout", "retry_after": 5}。如果是 SQL 报错，要把报错堆栈中最关键的信息塞回上下文，让 Agent 像程序员修 Bug 一样根据报错信息修正下一步。错误信息是 Agent 自我修正的燃料，给得越结构化，修正越准。

8. 兜底方案与分层错误恢复：错了怎么办

兜底方案是当 Loop 达到最大迭代次数或遇到不可恢复错误时，返回“当前阶段最接近的结果”并标记为“未完成”。设计思路：① 保存中间状态——每轮结束时持久化当前进度；② 定义“最小可用结果”——即使未完成，也能输出有价值的信息；③ 清晰标记状态——让用户知道“完成了什么、没完成什么、为什么没完成”。

分层错误恢复则按错误类型给不同策略：① 可重试错误（如网络超时）——自动重试，带指数退避；② 可修正错误（如参数错误）——让 Agent 反思并修正；③ 不可恢复错误（如权限不足）——终止并通知人工；④ 部分失败——跳过失败子任务，继续执行其他任务。每层都需要明确的“错误类型识别”和“恢复策略映射”。

9. 循环依赖检测四法：Agent 之间互相等怎么办

多 Agent 协作时还可能出现循环依赖——A 等 B、B 等 A。检测方法：① 调用图检测——构建 Agent/任务调用图，检测是否有环；② 状态指纹——比较不同轮次的状态哈希，相同则说明在循环；③ 行为模式检测——检测重复的 Action 序列；④ 超时检测——Loop 运行时间远超预期，可能陷入了循环。一旦检测到循环依赖，应触发熔断并通知人工。

自动化与人工控制的平衡：关键操作（如删除数据、发版、修改生产配置）前应预留人工确认接口。原则是：低风险操作全自动；中风险操作自动执行但记录日志，事后可追溯；高风险操作必须人工确认才能继续。Loop 不是要完全取代人，而是让人的精力从“频繁下指令”转移到“设定目标和验收结果”。

二、代码示例

示例 1：带熔断与反思节点的循环骨架

"""防死循环骨架：最大轮数 + 相同 Action 反思 + 同工具连败 3 次熔断。
用模拟的 agent_action() 代替真实模型，先把控制逻辑跑通。"""

MAX_ROUNDS = 10
MAX_SAME_ACTION = 2   # 连续两次相同 Action → 强制反思
MAX_TOOL_FAILS = 3    # 同一工具连败 3 次 → 熔断

def agent_action(state):
    """模拟 Agent 的一轮决策：这里故意让它重复同一个 Action。"""
    return "read_file"  # 模拟卡住的 Agent：每轮都做同一件事

def run_loop():
    state = {"round": 0, "history": [], "tool_fails": {}}
    while state["round"] < MAX_ROUNDS:  # 硬性约束：最大轮数
        state["round"] += 1
        action = agent_action(state)

        # 循环检测：连续两次相同 Action → 强制反思
        if len(state["history"]) >= 1 and state["history"][-1] == action:
            print(f"第 {state['round']} 轮：连续两次相同 Action，强制反思——"
                  f"你已经尝试过此路径且失败了，请更换策略")
            state["history"].append("reflect")
            continue
        state["history"].append(action)

        # 模拟工具调用失败并计数
        state["tool_fails"][action] = state["tool_fails"].get(action, 0) + 1
        fails = state["tool_fails"][action]
        print(f"第 {state['round']} 轮：执行 {action}，失败 {fails} 次")

        # 熔断：同一工具连败 3 次，立即终止当前推理链
        if fails >= MAX_TOOL_FAILS:
            print(f"熔断：工具 {action} 连续失败 {fails} 次，终止")
            return {"status": "aborted", "reason": "circuit_breaker"}
    print("达到最大轮数，终止")
    return {"status": "aborted", "reason": "max_rounds"}

run_loop()

示例 2：结构化错误回传 + 分层恢复 + 兜底方案

"""错误处理骨架：结构化错误 → 按类型分层恢复 → 兜底返回部分结果。"""
import time

def call_tool(name, attempt):
    """模拟工具调用：前两次超时，第三次成功。"""
    if attempt < 2:
        return {"status": "failed", "error_type": "Timeout",
                "message": f"{name} 超时", "retry_after": 1}
    return {"status": "ok", "result": f"{name} 的结果"}

def recover(error, attempt):
    """分层错误恢复：按错误类型映射恢复策略。"""
    if error["error_type"] == "Timeout":
        print(f"可重试错误：{attempt} 秒后重试（指数退避）")
        time.sleep(attempt)  # 指数退避的简化版
        return "retry"
    if error["error_type"] == "PermissionDenied":
        print("不可恢复错误：权限不足，终止并通知人工")
        return "abort"
    print("可修正错误：把报错塞回上下文，让 Agent 反思修正")
    return "fix"

def run_loop():
    best_result = None  # 兜底：保存当前阶段最接近的结果
    attempt = 0
    while attempt < 5:
        attempt += 1
        res = call_tool("search_api", attempt)
        if res["status"] == "ok":
            best_result = res["result"]
            print(f"成功：{best_result}")
            return {"status": "done", "result": best_result}
        # 结构化错误回传：错误类型 + 原因 + 可操作建议
        decision = recover(res, attempt)
        if decision == "abort":
            break
    # 兜底方案：返回最接近的结果，标记为未完成
    return {"status": "incomplete", "partial": best_result,
            "note": "完成了什么、没完成什么、为什么没完成，见日志"}

print(run_loop())

四、可能的面试题与答案

Q1：Loop 的终止条件有哪些？怎么区分正常与异常终止？

四类：任务完成、达到预算上限、遇到不可恢复的错误、需要人工介入。其中任务完成是正常终止，其余三类是异常终止。设计良好的 Loop 应该区分两者并分别给出不同的输出，异常终止时还要走兜底方案，返回最接近的结果并标记“未完成”。

Q2：如何防止 Agent 陷入死循环？

多层防御：硬性约束（最大迭代次数和超时）、循环检测（连续相同 Action 强制反思或中断）、熔断机制（同一工具连败 3 次终止推理链）、兜底方案（达上限后返回最接近的结果并标记未完成）。

Q3：Agent 陷入死循环时，工程上怎么解决？

三层防御：工具层硬隔离——调用外部 API 包裹 try-catch，返回结构化错误；推理层熔断——实现 Max Iteration Check 和 Loop Detection 模块；规划层自我修正——工具调用失败时让 Agent 反思哪里做错了、是不是参数不对、要不要换工具。

Q4：工具调用失败时，应该返回什么信息给 LLM？

不能只返回简单的“Error”，要返回结构化的错误信息，包含错误类型、原因和可操作的建议，例如 {"status": "failed", "error_type": "Timeout", "retry_after": 5}。SQL 报错要把堆栈中最关键的信息塞回上下文，让 Agent 像程序员修 Bug 一样修正下一步。

Q5：如何设计 Loop 的错误恢复机制？

分层设计：可重试错误（如网络超时）自动重试，带指数退避；可修正错误（如参数错误）让 Agent 反思并修正；不可恢复错误（如权限不足）终止并通知人工；部分失败跳过失败子任务，继续执行其他任务。每层都需要明确的“错误类型识别”和“恢复策略映射”。

五、加分项

生产视角：上线前先给 Loop 定好三条线：最大轮数、单轮超时、总预算。没有这三条线的 Loop，凌晨 3 点跑了 47 轮输出一堆问题代码，你连它在哪一轮走偏的都找不到。熔断和兜底不是“可选优化”，是无人值守运行的前提。

简历讲法：别写“做过 Agent 循环”，写“设计循环控制：四类终止条件区分正常/异常终止，收敛判断用规则检查 + 独立评估 Agent，同一工具连败 3 次熔断，连续相同 Action 强制反思，异常时兜底返回部分结果”。前者是名词，后者是可追问的可靠性设计。
