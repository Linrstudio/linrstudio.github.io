Day 11：多应用、命令行与部署优化

前面十课讲的都是“写代码时”的框架能力，今天讲“项目长大之后”的三件事：一个项目要拆成前台、后台、API 多个应用怎么办？定时任务、数据迁移这些不在 HTTP 请求里跑的活儿怎么写？代码写完了，上线前要做哪些优化？这三块都是面试里区分“会用框架”和“能扛项目”的题目，答案大多是固定套路，记下来就能答。

一、核心解释

1. 多应用：一个项目，多个入口应用

单应用模式下，项目只有一个应用：控制器在 app/controller/，路由在 route/app.php。当项目长大，需要同时做 API 接口、后台管理、移动端接口时，可以拆成多应用：多应用是扩展 topthink/think-multi-app，安装后 app/ 下每个子目录就是一个应用，比如 app/api、app/admin。

每个应用可以有自己独立的 config/（配置）、route/（路由）、middleware.php（中间件）、event.php（事件）。多应用的路由文件就放在各应用自己的 route/ 目录里，不再共用根目录的 route/app.php。JS 对照：像一个 monorepo 里多个 app，各自有自己的路由和配置，但共享同一套框架与依赖。

两个高频考点要记牢：

  • 单应用的判断依据：系统以 app/controller 目录是否存在作为判断单应用的依据。部署多应用后，记得删除 app/controller，否则框架会以为你还是单应用，多应用不生效。
  • 应用映射与域名绑定：在 config/app.php 里，app_map 做应用映射（把 URL 前缀映射到某个应用），domain_bind 做域名绑定（把某个域名绑定到某个应用，比如 api.example.com 绑到 api 应用）。

面试答法：“多应用通过 think-multi-app 扩展实现，app/ 下每个子目录是一个应用，各有独立的 config、route、middleware.php、event.php。系统以 app/controller 目录是否存在判断单应用，部署多应用后要删除它；config/app.php 的 app_map 做应用映射，domain_bind 做域名绑定。”

容易踩的坑：装了多应用扩展却发现不生效，第一件事就是检查 app/controller 还在不在——它在，框架就按单应用走。这个坑面试官很爱问，线上也真实常见。

2. 命令行：php think 是项目的瑞士军刀

项目根目录的 think 文件是 CLI 入口，所有命令行操作都从 php think 开始。php think list 可以看全部命令——记不住命令名时先 list 一下，比翻文档快。

自定义命令分三步：① 用生成器 php think make:command 生成命令类骨架；② 命令类继承 think\console\Command；③ 在 configure() 里设置命令名称、参数、选项，在 execute(Input $input, Output $output) 里写逻辑。Input 读用户输入的参数与选项，Output 负责往终端输出。JS 对照：像用 commander 写 Node CLI——configure() 相当于定义 program.command().option()，execute() 相当于 .action() 回调。

内置生成器（脚手架命令，面试可能顺带问）：make:controller 生成控制器、make:model 生成模型、make:middleware 生成中间件、make:validate 生成验证器。生成器省的是样板代码，生成的类仍需自己填逻辑。

优化命令（上线前必跑，见第 4 节）：optimize:autoload（类映射）、optimize:config（配置缓存）、optimize:route（路由缓存）、optimize:schema（数据表结构缓存）。另外两个常用命令：php think clear 清理缓存（改了配置、路由后缓存没更新时先 clear 再试）；php think run 启动开发服务器，默认地址是 http://localhost:8000，可用 -p 指定端口。JS 对照：php think run 相当于 npm run dev 起本地开发服务器。

3. 扩展生态：官方与常用扩展一张表

ThinkPHP 8.x 线把很多能力拆成了独立扩展包，按需安装。下面这些都是真实存在的官方或常用扩展，面试提到“我用过哪些 TP 扩展”时按需引用，不要编不存在的包名：

扩展用途
think-view模板引擎
think-queue队列（异步任务）
think-annotation注解路由
think-multi-app多应用
think-trace调试跟踪
think-orm独立 ORM 包（模型与查询构建器）
think-captcha验证码

面试答法：“TP 8.x 线是核心精简加扩展按需安装的思路，比如队列用 think-queue、多应用用 think-multi-app、注解路由用 think-annotation、模板用 think-view。扩展通过 composer 安装，服务提供者自动发现。”

4. 部署与性能优化：上线检查清单

部署部分面试常以“上线前要做哪些事”或“线上慢怎么排查”出现，按下面这张清单答，基本不会丢分：

  • Nginx 配置：root 必须指向 public/ 目录（只暴露入口目录，应用代码不直接对外）；try_files $uri $uri/ /index.php?$query_string; 把不存在的路径交给入口文件做路由分发。
  • 环境配置：.env 里 APP_DEBUG=false，生产环境绝不开调试模式（会暴露敏感信息）。
  • 目录权限：runtime/ 等需要写权限的目录要可写（缓存、日志都写在这里），不可写会导致运行时报错。
  • 依赖安装：生产用 composer install --no-dev --optimize-autoloader，不装开发依赖、生成优化的类加载映射。
  • OPcache：开启 OPcache（php.ini 里 opcache.enable=1），生产可设 opcache.validate_timestamps=0（不检查文件时间戳，性能更好，但改代码后要重启或手动刷新缓存才生效）。
  • 缓存预热：上线后跑 optimize:config、optimize:route、optimize:schema，把配置、路由、表结构都缓存起来，避免每次请求重复解析。
  • 会话与缓存：生产用 Redis 做会话与缓存存储，不要用默认文件存储（多台服务器部署时文件缓存不共享）。
  • 性能要点：路由与配置缓存（上面已做）、避免 N+1（模型用 with 预载关联）、给查询字段加索引、耗时任务进队列异步处理。

面试答法：“部署上 Nginx root 指向 public 目录、.env 关调试、runtime/ 可写、生产依赖用 --no-dev --optimize-autoloader 安装、开启 OPcache、上线后跑 optimize:config、optimize:route、optimize:schema，会话与缓存用 Redis。性能方面重点是缓存预热、with 预载避免 N+1、加索引、耗时任务进队列。”

二、代码示例

示例 1：自定义命令——每天凌晨清理过期订单

<?php
// 先用生成器搭骨架：php think make:command CleanOrder
// 生成的类继承 think\console\Command
namespace app\command;

use think\console\Command;
use think\console\Input;
use think\console\Output;

class CleanOrder extends Command
{
    // configure：设置命令名称、参数、选项（只做声明，不写业务逻辑）
    // JS 对照：commander 的 program.command('order:clean').option(...)
    protected function configure()
    {
        $this->setName('order:clean')          // 命令名，终端里跑 php think order:clean
            ->setDescription('清理过期未支付订单'); // php think list 里显示的描述
    }

    // execute：真正的逻辑。Input 读参数选项，Output 往终端输出
    // JS 对照：commander 的 .action((options) => {...})
    protected function execute(Input $input, Output $output)
    {
        // 业务逻辑写这里，比如：把 30 分钟未支付的订单置为已取消
        $output->writeln('清理完成'); // writeln 往终端输出一行，相当于 console.log
    }
}

示例 2：Nginx 配置 + .env 生产设置 + 上线命令

# Nginx：root 必须指向 public/ 目录，应用代码不直接对外
server {
    listen 80;
    server_name example.com;
    root /var/www/myapp/public;  # 注意是 public 子目录，不是项目根目录

    location / {
        # 文件不存在时交给 index.php，由框架做路由分发
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass 127.0.0.1:9000;      # 转给 PHP-FPM 处理
        fastcgi_index index.php;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }
}
# .env 生产设置
APP_DEBUG=false   # 生产环境必须关闭调试模式，否则会暴露敏感信息

# 上线命令清单（按顺序跑）
composer install --no-dev --optimize-autoloader  # 生产依赖，不装 dev 包，优化类加载
php think optimize:config   # 配置缓存
php think optimize:route    # 路由缓存
php think optimize:schema   # 数据表结构缓存
php think clear             # 改配置或路由后缓存没更新时，先 clear 再试

# 开发时启动本地服务器（默认 http://localhost:8000，-p 指定端口）
php think run -p 8080

三、ThinkJS 对比

多应用、CLI、部署这三块，ThinkJS 都有对位物，但形态差异恰好反映了 PHP 与 Node 的根本不同——PHP 每次请求重建应用，Node 常驻进程。这条差异线要记牢，Day 12 还会总复习。

维度ThinkPHPThinkJS
多模块组织多应用扩展，每个应用独立 config / route / middleware.php / event.php多模块项目用 src/common 放公共配置，各模块 src/xxx/
CLIphp think，自定义命令继承 think\console\Commandthinkjs 命令（think-cli），如 thinkjs controller user -r 同时创建 controller 与 logic 文件
部署Nginx + PHP-FPM，每次请求重建应用PM2 常驻进程 + Nginx 反代
进程内状态每次请求干净启动，天然无跨请求污染常驻内存，要注意跨请求状态污染

CLI 对比：ThinkJS 的脚手架是 thinkjs 命令（think-cli 提供）。比如 thinkjs controller user -r 会同时创建 controller 与 logic 两个文件——因为 ThinkJS 把校验逻辑放 Logic 层（Day 12 对比表还会提到），脚手架顺手把配套文件一起生成。TP 的 make:controller 只生成控制器，验证器要另外用 make:validate 生成。两者思路相同（生成器省样板代码），只是配套文件的拆分不同。

部署对比（面试可展开的点）：TP 部署是 Nginx + PHP-FPM：Nginx 把 PHP 请求转给 PHP-FPM，PHP-FPM 每次请求拉起应用、跑完即销毁，下次请求重新来过。ThinkJS 部署是 PM2 + Nginx 反代：PM2 让 Node 应用常驻内存，Nginx 只做反向代理转发。常驻进程的好处是启动开销只付一次、内存缓存跨请求可用；代价是要注意跨请求状态污染——模块级变量、单例里的可变状态，一个请求改了，下一个请求还能看到，写代码时必须有意识地隔离。而 PHP 每次请求干净启动，天然没有这个问题，这是 PHP 在 Web 场景下一个被低估的优点。

四、小测验

得分：0 / 3

1. 部署多应用后，以下哪件事必须做？

解析：选 B。系统以 app/controller 目录是否存在作为判断单应用的依据，部署多应用后记得删除它。多应用路由文件放在各应用自己的 route/ 目录，不用复制根路由文件。

2. 自定义命令的两个关键方法分别做什么？

解析：选 A。configure() 只做声明（名称、参数、选项），execute(Input $input, Output $output) 写业务逻辑，Input 读输入、Output 输出。

3. 上线后应该跑哪几个 optimize 命令做缓存预热？

解析：选 C。上线后跑配置缓存、路由缓存、表结构缓存三个命令；optimize:autoload 是类映射（composer 安装时 --optimize-autoloader 已覆盖类似效果）；php think clear 是清理缓存，不是预热。

五、面试高频问答

Q1：多应用怎么实现？部署时有什么坑？

通过 think-multi-app 扩展实现，app/ 下每个子目录是一个应用，各有独立的 config、route、middleware.php、event.php。最大的坑：系统以 app/controller 目录是否存在判断单应用，部署多应用后必须删除它，否则多应用不生效。config/app.php 的 app_map 做应用映射，domain_bind 做域名绑定。

Q2：自定义命令怎么写？

用 php think make:command 生成骨架，命令类继承 think\console\Command，在 configure() 里设置名称、参数、选项，在 execute(Input $input, Output $output) 里写逻辑。php think list 可以查看全部命令。

Q3：上线前要做哪些优化和检查？

Nginx root 指向 public/ 目录；.env 里 APP_DEBUG=false；runtime/ 等目录可写；生产用 composer install --no-dev --optimize-autoloader；开启 OPcache（生产可设 opcache.validate_timestamps=0）；上线后跑 optimize:config、optimize:route、optimize:schema；会话与缓存生产用 Redis。

Q4：线上接口慢，一般从哪几方面排查？

先看缓存有没有预热（路由、配置、表结构缓存是否已生成）、再看有没有 N+1（模型关联用 with 预载）、查询字段是否加了索引、耗时任务是否进了队列异步处理。配合 think-trace 调试跟踪看各环节耗时，定位到具体瓶颈再动手。
