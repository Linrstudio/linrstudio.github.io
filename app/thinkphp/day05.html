Day 5：中间件与事件

请求在进控制器之前，要先经过一串关卡：登录检查、跨域处理、请求缓存……这些横切在请求链路上的逻辑，就是中间件。而“用户登录后要发欢迎邮件、记一条日志”这种“一个动作触发多个后续动作”的需求，硬写在控制器里会把控制器越写越臃肿，解耦的办法是事件系统。今天把这两块一次讲透。

一、核心解释

1. 中间件是什么：handle() + 必须返回 Response

中间件是一个类，唯一硬性要求是有一个 handle($request, \Closure $next) 方法，并且必须返回一个 Response 实例。生成命令是 php think make:middleware Check，生成的类放在 app\middleware 命名空间下。

典型骨架长这样：$next($request) 之前是前置逻辑（请求进来先执行），$next($request) 之后是后置逻辑（响应出来后执行）。想放行就调 $next($request)；想拦截就直接 return 一个 Response，后续中间件和控制器都不会再执行——登录检查就是这么实现的。

容易踩的坑：handle() 里忘了 return $next($request) 的结果，请求就会“断”在中间件里，控制器永远收不到请求；或者写了 $next($request); 却没 return，响应直接丢了。记住：handle() 必须返回 Response 实例，要么 return 自己造的响应，要么 return $next($request) 的返回值。

2. 洋葱模型与四级执行顺序

中间件的执行是洋葱模型：请求从外向内一层层穿过中间件到达控制器，响应再从内向外一层层原路返回。所以前置逻辑按注册顺序执行，后置逻辑按逆序执行。底层实现是一个队列，先进先出（array_shift 逐个取出执行）。

四级中间件按执行顺序排列：

级别配置位置作用范围
全局中间件app/middleware.php 或 config/middleware.php所有请求
应用中间件多应用下 app/xxx/middleware.php某个应用内的请求
路由中间件Route::middleware() 或分组挂载某条路由或某个路由分组
控制器中间件类内 protected $middleware = [...]某个控制器内的 Action

面试答法：被问“中间件执行顺序”，答：全局 → 应用 → 路由 → 控制器，请求按顺序进、响应按逆序出；同一级内按注册顺序，先进先出。能把“洋葱模型”四个字和这张表说出来，这道题就稳了。

3. 别名与 priority：给中间件起名字、排优先级

在 config/middleware.php 里可以用 alias 给中间件起别名：'alias' => ['auth' => \app\middleware\AuthCheck::class]，之后路由上挂中间件时写别名 'auth' 就行，不用每次写完整类名。

同一个文件里还有 priority 数组，控制中间件的优先执行顺序：写在 priority 里的中间件会优先于其他中间件执行，适合把 Session 初始化、跨域这类“必须最先跑”的中间件排到前面。

4. 内置中间件：框架自带的四个

内置中间件作用
think\middleware\SessionInitSession 初始化，用 Session 之前要先跑它
think\middleware\AllowCrossDomain跨域处理，给响应加上跨域头
think\middleware\FormTokenCheck表单令牌检查，防表单重复提交与跨站请求
think\middleware\CheckRequestCache请求缓存，命中缓存时直接返回，不再进控制器

面试常考的是 AllowCrossDomain：前后端分离项目里跨域问题怎么处理，答“挂 AllowCrossDomain 中间件”就是标准答案之一。

5. 事件系统：一个动作，多个监听

事件系统把“触发动作”和“后续处理”解耦：触发方只管抛一个事件名和数据，谁来响应、响应几个，都由配置决定。配置在 app/event.php，分三段：

配置段含义
bind事件名直接绑一个处理类
listen一个事件绑多个监听类（数组）
subscribe订阅者类，一个类可监听多个事件

触发用 Event::trigger('UserLogin', $user) 或 event() 助手，第二个参数是传给监听类的数据。监听类里写一个 handle($params) 方法，$params 就是触发时传来的数据。

框架还内置了几个事件：AppInit（应用初始化）、HttpRun（HTTP 请求开始）、HttpEnd（请求结束）、LogWrite（写日志时）。想在请求开始时做点事（比如记一条访问日志），监听 HttpRun 即可，不用改框架代码。

面试答法：被问“中间件和事件有什么区别”，答：中间件是请求链路上的横切逻辑（鉴权、限流、跨域），请求必须经过它；事件是业务解耦（登录后发邮件、记日志），触发方不知道也不关心谁在听。一个是“必经之路”，一个是“广播通知”。

二、代码示例

示例 1：登录检查中间件（放到 app\middleware\Check.php 可跑）

<?php
namespace app\middleware;              // 中间件类的命名空间

class Check
{
    // handle() 是中间件的唯一入口：$request 是请求，$next 是“下一个环节”
    // \Closure 是 PHP 的闭包类型，相当于 JS 里的 () => {} 函数类型
    public function handle($request, \Closure $next)
    {
        // 前置逻辑：请求进来先执行
        if (! $request->header('token')) {
            // 没带 token：直接返回响应，拦截请求，后续中间件与控制器不再执行
            return json(['code' => 401, 'msg' => '未登录']);
        }

        $response = $next($request);   // 放行：交给下一个中间件，最终到达控制器

        // 后置逻辑：响应出来后执行，可以在这里改响应头、记日志
        return $response;              // 必须返回 Response 实例，别忘了 return
    }
}

挂载方式（三种，任选其一）：全局挂载写进 app/middleware.php 的返回数组；路由挂载用 Route::get('user', 'User/index')->middleware(\app\middleware\Check::class)；控制器挂载在类内写 protected $middleware = [\app\middleware\Check::class];。

示例 2：用户登录事件——配置、监听类与触发

<?php
// app/event.php：事件配置分 bind / listen / subscribe 三段
return [
    'bind' => [
        // 事件名直接绑一个处理类
        'UserLogin' => \app\listener\UserLogin::class,
    ],
    'listen' => [
        // 一个事件绑多个监听类：订单支付后既发短信又记日志
        'OrderPaid' => [\app\listener\SendSms::class, \app\listener\LogOrder::class],
    ],
    'subscribe' => [
        // 订阅者类：一个类可监听多个事件
        \app\subscribe\User::class,
    ],
];
<?php
namespace app\listener;                // 监听类放 app\listener 命名空间

class SendSms
{
    // handle($params)：$params 是触发时传来的数据
    public function handle($params)
    {
        // $params 就是触发时传的订单数据，这里发短信
        // 触发方不用知道这个类的存在，这就是解耦
    }
}
<?php
// 在控制器里触发事件（两种写法等价）
use think\facade\Event;

Event::trigger('OrderPaid', $order);   // 门面静态调用，第二个参数是传给监听类的数据
event('OrderPaid', $order);            // event() 助手函数，等价写法

动手任务（10 分钟）

1. 跑 php think make:middleware Check 生成中间件，把示例 1 的逻辑贴进去，挂到一条路由上，不带 token 访问一次、带 token 访问一次，对比结果。
2. 写两个中间件 A 和 B，都在 $next() 前后各记一行日志，挂到同一条路由上，看日志顺序是不是“进 A → 进 B → 出 B → 出 A”，亲手验证洋葱模型。
3. 在 app/event.php 的 listen 里给一个事件绑两个监听类，触发一次，确认两个 handle() 都执行了。

三、ThinkJS 对比

中间件这一块，ThinkJS 与 TP 是“同一个人写的”既视感；事件系统则是两者分道扬镳的地方：

维度ThinkPHPThinkJS
中间件形态类 + handle($request, \Closure $next)Koa 中间件 (ctx, next) => { await next(); }
执行模型洋葱模型洋葱模型，完全一致
配置位置app/middleware.php、路由、控制器四级统一在 src/config/middleware.js 管理
事件机制app/event.php 的 bind / listen / subscribe没有 TP 式的事件订阅配置，应用级事件一般用 Koa 的 app.on（EventEmitter）或中间件实现
// ThinkJS 中间件：就是 Koa 中间件，洋葱模型与 TP 完全一致
module.exports = (options) => {
  return async (ctx, next) => {
    // 前置逻辑：相当于 TP 里 $next($request) 之前的代码
    if (!ctx.header.token) {
      ctx.body = {code: 401, msg: '未登录'};
      return;  // 直接返回，不调 next()，就是 TP 里的拦截
    }
    await next();  // 放行，相当于 TP 的 $next($request)
    // 后置逻辑：相当于 TP 里 $next($request) 之后的代码
  };
};

版本注意：ThinkJS 3.0 废弃了 2.x 的 hook 机制，改用 Koa 中间件。面试时如果对方问“ThinkJS 的 hook 怎么用”，答“3.x 已经废弃 hook，统一用 Koa 中间件”，这是个能加分的版本细节。

记忆锚点：TP 的 $next($request) 就是 Koa 的 await next()；TP 的四级中间件就是 ThinkJS 在 middleware.js 里统一配置的那一串。事件系统是 TP 独有的，ThinkJS 没有对应物，不要硬对。

四、小测验（点选项判分，答完点解析）

得分：0 / 3

1. 中间件的 handle() 方法必须返回什么？

解析：选 A。handle() 必须返回 Response 实例：要么 return 自己造的响应（拦截），要么 return $next($request) 的返回值（放行）。

2. 四级中间件的执行顺序是？

解析：选 C。请求按全局、应用、路由、控制器的顺序进，响应按逆序出，这就是洋葱模型。

3. 一个事件要绑多个监听类，应该写在 app/event.php 的哪一段？

解析：选 B。bind 是一个事件绑一个处理类；listen 是一个事件绑多个监听类数组；subscribe 是订阅者类，一个类监听多个事件。

五、面试高频问答

Q1：洋葱模型怎么理解？

请求从外向内一层层穿过中间件到达控制器，响应再从内向外一层层原路返回。前置逻辑按注册顺序执行，后置逻辑按逆序执行。底层是一个队列，先进先出。画图时画同心圆，请求进、响应出，一句话就说清了。

Q2：中间件里怎么提前返回、不让请求继续往下走？

直接 return 一个 Response，不调 $next($request)。后续中间件和控制器都不会再执行。典型场景是登录检查：没带 token 就直接 return 401 的 JSON。

Q3：bind、listen、subscribe 三者有什么区别？

bind 是事件名直接绑一个处理类；listen 是一个事件绑多个监听类数组，触发时依次执行；subscribe 是订阅者类，一个类里可以监听多个事件，适合把同一业务的多个监听收在一起。三者都是 app/event.php 里的配置段。

Q4：中间件和事件分别适合什么场景？

中间件适合请求链路上的横切逻辑：鉴权、限流、跨域、日志，请求必须经过它。事件适合业务解耦：登录后发欢迎邮件、订单支付后发短信记日志，触发方不知道也不关心谁在听。一个是必经之路，一个是广播通知。

Q5：前后端分离项目跨域怎么处理？

挂框架内置的 think\middleware\AllowCrossDomain 中间件，它会给响应加上跨域头。也可以在全局中间件里统一挂上，所有接口一次性解决。

加分项

生产视角：中间件里不要写业务逻辑，只写横切逻辑（鉴权、限流、日志、跨域）；业务解耦用事件，不要把“登录后发邮件、记日志、送积分”全塞进登录控制器——每加一个后续动作都要改控制器，迟早改出 bug。

简历讲法：别写“会用中间件”，写“用中间件做登录鉴权与限流：全局挂跨域与 Session 初始化，路由分组挂鉴权中间件；订单支付后用事件触发短信与日志监听，控制器只负责主流程”。前者是名词，后者是可追问的架构。
