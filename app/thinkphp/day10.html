Day 10：容器、门面与服务

前面九课你一直在用框架给的现成东西：控制器里随手拿到的 Request、Db::name()、Cache::get()。今天把盖子掀开：这些对象是谁创建的？为什么控制器方法声明一个参数就能拿到实例？答案是同一套机制——容器（Container）负责创建和管理对象，门面（Facade）负责把调用写得简洁，服务提供者（Service）负责把扩展的服务注册进容器。理解这三者，ThinkPHP 的骨架就通了，面试里“说说依赖注入”“门面是怎么实现的”也都有话可说。

一、核心解释

1. 容器：think\App 本身就是容器

ThinkPHP 的容器是 topthink/think-container 3.x 包，实现 PSR-11 容器接口。PSR-11 是 PHP 社区的一个通用标准：规定容器必须有“按名字取实例”的能力（get / has），至于内部怎么创建对象，各框架自己定。

关键认知：应用类 think\App 本身就是容器。入口文件创建的那个 $app，既是应用对象，也是装着所有服务实例的大盒子。app() 助手函数返回的就是这个应用（容器）实例——你在任何地方调 app()，拿到的都是同一个容器。

容器最常用的三个方法：

  • $app->make(Class::class)：解析一个类的实例。容器会看它的构造函数需要什么参数，递归把依赖都造出来，再返回实例。JS 对照：像 NestJS 里 app.get(ServiceClass) 从容器里取一个已装配好的服务。
  • $app->bind()：绑定。告诉容器“当有人要 A 时，给他 B”。典型用法是把接口绑定到实现类，或者把一个类名绑定到一个闭包（闭包返回实例）。
  • $app->instance()：把一个已经造好的实例直接放进容器。之后任何人来取这个类，拿到的都是这个现成的实例，相当于单例注册。

面试答法：“容器是 ThinkPHP 管理对象创建与依赖关系的核心，think\App 本身就是容器，实现 PSR-11。通过 make 解析实例、bind 绑定抽象与实现、instance 注册已有实例。框架里的 Request、Cache、Db 这些服务都由容器统一管理。”

2. 依赖注入原理：反射读类型提示，递归实例化

依赖注入（DI）说白了就一句话：一个类需要的东西，不由它自己 new，而是由容器在外面造好再塞进来。容器怎么知道要塞什么？靠 PHP 的反射（Reflection）：容器读取构造函数或方法参数的类型提示（比如 __construct(Request $request) 里的 Request），发现这个参数是个类，就递归地先把这个类实例化出来，再传进去。如果依赖的类自己还有依赖，继续递归，直到整棵依赖树都造完。

这套机制贯穿框架各处：控制器方法参数、中间件、控制台命令、事件监听，都是靠它自动装配的。这就是为什么控制器方法里写 public function index(Request $request) 就能直接用 $request——不是魔法，是容器在调用这个方法前用反射看了参数表，自动把 Request 实例注进来了。

两个补充机制要记住：

  • __make 优先：依赖解析时，如果类定义了静态方法 __make(App $app, ...)，容器会优先调用它来创建实例，而不是直接 new。典型例子是 think\Middleware，它的 __make 会从配置里加载中间件列表。面试答法：“类可以通过静态 __make 方法自定义自己的创建逻辑，容器解析时会优先调用它。”
  • $app->invoke($callable, $vars)：用反射调用一个可调用对象（函数、方法、闭包），并自动注入它声明的参数。$vars 是你额外传入的参数，会优先于自动解析的结果。框架内部调度控制器、执行中间件时用的就是这类机制。
容易踩的坑：依赖注入只对“有类型提示”的参数生效。如果参数没有类型提示（比如 function index($id)），容器不知道要注什么，只能靠路由参数或你手动传。$id 这种标量参数走的是路由传参，不是容器注入——面试追问“为什么 $id 不用注入”时就按这条答。

3. 门面：静态调用的壳，容器实例的核

你每天写的 Db::name('user')、Cache::get('key')、Config::get('app.debug')，看起来都是静态调用，其实背后是门面（Facade）：think\Facade 基类利用 PHP 的魔术方法 __callStatic，把静态调用转发给容器里的真实实例。

机制分三步：① 你调 Cache::get('key')；② Cache 门面类本身没有 get 静态方法，PHP 触发 __callStatic；③ __callStatic 从容器里取出真正的缓存服务实例，再调它的 get 方法。门面子类只需要定义一个方法：getFacadeClass()，返回它代理的服务类名，告诉基类“去容器里拿哪个实例”。

门面是静态代理，不是真正的静态类。真正干活的实例仍由容器管理、仍可被替换。这带来两个后果，面试常考：

  • 优点：调用简洁，不用每次 app()->make(...) 再调方法；写起来像全局函数，读起来直观。
  • 缺点：隐藏依赖——从方法签名上看不出它依赖了哪些服务，类的依赖关系被藏在了方法体内部；测试时要通过容器替换实例（用 instance() 把真服务换成 mock），不能像构造函数注入那样直接传假对象。

面试答法：“门面通过 __callStatic 把静态调用转发给容器中的实例，子类用 getFacadeClass() 指定代理的服务类。它本质是静态代理，实例仍由容器管理，所以优点是调用简洁，缺点是隐藏依赖、测试时需要替换容器实例。”

4. 服务提供者：扩展把自己注册进容器的方式

框架自带的服务（Request、Cache、Db……）是框架注册的，那第三方扩展的服务怎么进容器？靠服务提供者（Service）：think\Service。

  • register()：在这里把服务绑定到容器（调 $this->app->bind(...) 之类）。只做绑定，不做重活。
  • boot()：在应用启动时执行，适合做初始化工作（比如注册路由、注册事件监听、加载配置）。

注册位置有两个层次：应用自己的服务提供者写在 app/provider.php 里；扩展包则通过 composer.json 的 extra.think.services 字段自动发现——装上扩展包，服务提供者就自动注册了，不用手动改配置。如果想关掉自动发现，在 config/app.php 里把 auto_discover 设为 false，关闭后就需要手动在 services 里注册。

面试答法：“服务提供者是扩展向容器注册服务的方式：register() 做绑定，boot() 在应用启动时做初始化。应用的提供者注册在 app/provider.php，扩展包通过 composer.json 的 extra.think.services 自动发现，config/app.php 的 auto_discover 可以关闭自动发现。”

5. app/service/：业务服务层的约定目录

最后区分一个容易混的概念：app/service/ 目录。它是业务服务层的约定目录——放你自己写的业务逻辑服务类（比如 UserService、OrderService），让控制器变薄、逻辑可复用。它不是框架强制的，框架不会自动加载这个目录里的类，你的服务类该 bind 还是 make，按容器规则来。别把它和 think\Service（服务提供者）混为一谈：一个是放业务代码的目录约定，一个是向容器注册服务的机制。

二、代码示例

示例 1：容器三件套——make / bind / instance

<?php
// $app 就是容器：think\App 本身就是容器实例
// app() 助手返回应用（容器）实例，和入口文件里的 $app 是同一个
$app = app();

// make：解析实例。容器看 MailService 构造函数需要什么，递归造好再返回
// JS 对照：NestJS 的 app.get(MailService)，或手动 new MailService(new SmtpClient())
$mail = $app->make(MailService::class);
// -> 相当于 JS 的 . ：$app->make(...) 就是 app.make(...)
// ::class 是 PHP 取类名字符串的语法，MailService::class 得到 'app\service\MailService'

// bind：绑定接口到实现。之后凡是需要 MailerInterface 的地方，容器都给 SmtpMailer
// JS 对照：NestJS 的 { provide: MailerInterface, useClass: SmtpMailer }
$app->bind(MailerInterface::class, SmtpMailer::class);

// bind 也可以绑闭包：需要时才执行闭包创建实例（延迟创建）
$app->bind(MailerInterface::class, function () {
    return new SmtpMailer('smtp.example.com', 465);
});

// instance：把已经造好的实例直接放进容器，之后取到的都是这一个（单例效果）
// 测试时常用这招：把真服务换成假对象（mock）
$fakeMailer = new FakeMailer();
$app->instance(MailerInterface::class, $fakeMailer);

示例 2：__make 自定义创建逻辑 + invoke 自动注入参数

<?php
// 类定义了静态 __make 方法时，容器解析它会优先调 __make，而不是直接 new
// 框架里的 think\Middleware 就是这样从配置加载中间件列表的
class MiddlewareLoader
{
    // __make 的第一个参数固定是 App（容器），后面可跟额外参数
    public static function __make(App $app)
    {
        $list = $app->config->get('middleware'); // 从配置读中间件列表
        return new static($list);                // 自己决定怎么造实例
    }
}

// invoke：用反射调用可调用对象，自动注入它声明的参数
// $vars 里传的参数优先于自动解析
$app->invoke(function (Request $request) {
    // $request 由容器自动注入，不用手动传
    return $request->param('id');
}, ['id' => 42]); // => 是 PHP 的键值对语法，相当于 JS 对象字面量里的冒号 { id: 42 }

示例 3：写一个自己的门面（静态代理的完整形态）

<?php
// 第一步：真正的服务类，干活的逻辑都在这里
namespace app\service;

class SmsService
{
    public function send(string $phone, string $text): bool
    {
        // 真正发短信的逻辑……
        return true;
    }
}

// 第二步：门面类，只做一件事——告诉基类去容器里拿哪个服务
namespace app\facade;

use think\Facade;

// use 相当于 JS 的 import：把 think\Facade 引入当前命名空间
class Sms extends Facade
{
    // getFacadeClass 返回服务类名，基类 __callStatic 会据此从容器取实例
    protected static function getFacadeClass()
    {
        return \app\service\SmsService::class;
    }
}

// 第三步：调用方写起来像静态调用，实际跑的是容器里的 SmsService 实例
// Sms::send(...) → __callStatic 触发 → 容器取 SmsService 实例 → 调实例的 send 方法
Sms::send('13800000000', '您的验证码是 123456');

示例 4：服务提供者——register 绑定，boot 初始化

<?php
// 文件：app/service/SmsServiceProvider.php（名字自定，习惯以 ServiceProvider 结尾）
namespace app\service;

use think\Service;

class SmsServiceProvider extends Service
{
    // register：只做绑定，把服务注册进容器
    public function register()
    {
        // $this->app 就是容器；绑接口到实现，控制器里类型提示接口即可注入
        $this->app->bind(SmsInterface::class, SmsService::class);
    }

    // boot：应用启动时执行，做初始化工作
    public function boot()
    {
        // 比如：注册事件监听、加载扩展配置等
    }
}
<?php
// 文件：app/provider.php —— 应用自己的服务提供者在这里注册
// 返回一个数组，列出所有要注册的提供者类
return [
    app\service\SmsServiceProvider::class,
];

// 扩展包不用写这里：它们在自己的 composer.json 里声明
// "extra": { "think": { "services": ["vendor\\xxx\\XxxService"] } }
// 框架安装扩展后自动发现并注册。
// 想关掉自动发现：config/app.php 里 auto_discover 设为 false，
// 关闭后扩展的服务提供者要手动写进 services 数组。

三、ThinkJS 对比

这一课是 ThinkJS 对比最“不对位”的一课——因为 ThinkJS 没有 DI 容器这个概念。这本身就是面试可以聊的点：不是每个框架都需要容器，容器的价值取决于语言和生态。

维度ThinkPHPThinkJS
依赖管理DI 容器（think-container 3.x，PSR-11），反射自动注入没有 DI 容器对位概念，依赖通过 require 与全局 think 对象组织
取服务app()->make()、控制器方法参数自动注入require 模块、think.xxx 全局挂载
扩展机制服务提供者 + composer 自动发现src/extend/ 目录扩展内置对象
请求上下文Request 对象注入控制器方法Koa 的 ctx 是请求级上下文传递

ThinkJS 的扩展机制：src/extend/ 目录。ThinkJS 没有服务提供者，扩展靠往内置对象上挂方法：在 src/extend/ 下放文件，就能扩展七类对象——think、application（Koa app，即 think.app）、context、request、response、controller、logic、service。比如在 src/extend/think.js 里写 think.xxx = ...，项目里任何地方都能用 think.xxx。JS 对照：这更像给全局对象打补丁（monkey-patch），而不是往容器里注册服务——简单直接，但没有容器的“绑定接口到实现”“测试时替换实例”那套能力。

请求上下文的相似点：Koa 的 ctx 是请求级上下文传递——每个请求一个 ctx，中间件和控制器都通过它拿请求数据、写响应。这和 TP 把 Request 对象注入控制器方法在目的上是相似的（都是“当前请求的数据载体”），只是传递方式不同：Koa 是把 ctx 沿中间件链一路传下去，TP 是容器在调用时把 Request 实例注进来。

为什么 PHP 需要容器、Node 不太需要？可以这样理解：PHP 是每次请求重建应用，对象图每请求都要重新装配一遍，容器就是干这件事的装配线；Node 是常驻进程，模块 require 一次就缓存在内存里，天然就是单例，require 本身就承担了“取共享实例”的角色。当然 Node 生态也有真正的 DI 容器（NestJS 内置、Awilix、Inversify），只是 ThinkJS 这个框架没有引入这个概念。

四、小测验

得分：0 / 3

1. 关于 ThinkPHP 容器，哪个说法正确？

解析：选 B。think\App 本身就是容器实例，app() 返回应用（容器）实例；业务类同样可以用 bind / make 管理。

2. 门面 Cache::get() 的调用，实际是怎么执行的？

解析：选 A。门面是静态代理：__callStatic 按 getFacadeClass() 返回的类名从容器取实例再转发，实例仍由容器管理。

3. 扩展包的服务提供者默认是怎么注册的？

解析：选 C。扩展包通过 composer.json 的 extra.think.services 自动发现；只有把 config/app.php 的 auto_discover 关闭后，才需要手动在 services 里注册。应用自己的提供者才写 app/provider.php。

五、面试高频问答

Q1：说说 ThinkPHP 的依赖注入是怎么实现的？

容器通过 PHP 反射读取构造函数或方法参数的类型提示，递归实例化依赖，再注入目标对象。控制器方法参数、中间件、命令、事件监听都靠这套机制自动装配。如果类定义了静态 __make(App $app, ...) 方法，容器解析时会优先调用它（如 think\Middleware::__make 从配置加载中间件）。$app->invoke() 则用反射调用任意可调用对象并自动注入参数。

Q2：门面和真正的静态类有什么区别？

门面是静态代理，不是真正的静态类：think\Facade 通过 __callStatic 把静态调用转发给容器里的实例，子类用 getFacadeClass() 指定服务类名。真正干活的实例仍由容器管理、可替换。优点是调用简洁，缺点是隐藏依赖、测试时要通过容器替换实例。

Q3：服务提供者的 register() 和 boot() 有什么区别？

register() 里只做绑定——把服务注册进容器；boot() 在应用启动时执行，做初始化工作。应用自己的提供者注册在 app/provider.php，扩展包通过 composer.json 的 extra.think.services 自动发现，config/app.php 的 auto_discover 可关闭自动发现，关闭后需手动在 services 里注册。

Q4：app/service/ 目录是框架强制的吗？

不是。它是业务服务层的约定目录，放自己写的业务逻辑服务类，让控制器变薄、逻辑可复用。框架不会自动加载它，服务类该绑定还是解析仍按容器规则来。不要把它和 think\Service（服务提供者，向容器注册服务的机制）混为一谈。

六、加分项

简历讲法：别写“熟悉 ThinkPHP 容器”，写“用容器管理业务服务：接口与实现通过服务提供者 register() 绑定，控制器用构造函数注入；测试时用 instance() 把短信、支付服务替换为 mock，核心下单流程可脱离第三方接口单测”。前者是名词，后者是可追问的工程实践。
