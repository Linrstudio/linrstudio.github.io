Day 8：验证器与安全

数据进库之前先过验证器，安全问题多半出在“信了用户输入”上。今天讲两块：验证器（ThinkPHP 8.x 线的参数校验机制）和安全四件套（SQL 注入、XSS、CSRF、密码存储）。面试里这部分考得很实在——不是问你背过多少规则，而是问“这段代码有没有注入风险”“密码为什么不能 MD5”。JS 对照也很好找：验证器相当于 zod / Joi 的服务端版，参数绑定相当于 pg 的占位符查询，思路都是相通的。

一、核心解释

1. 验证器：规则集中写，控制器只调用

验证器继承 think\Validate，用命令 php think make:validate User 生成，放在 app/validate/ 目录下。类里三个关键属性：protected $rule 写规则，如 ['name' => 'require|max:25', 'email' => 'require|email', 'age' => 'number|between:1,120']，多个规则用 | 连接；protected $message 自定义错误信息，格式是 '字段名.规则名' => '错误信息'；protected $scene 定义场景，如 ['add' => ['name', 'email']]，不同场景只校验指定字段。

调用方式是 validate(UserValidate::class)->scene('add')->check($data)，其中 validate() 是框架助手函数，返回验证器实例；check() 通过返回 true，失败时用 $validate->getError() 取错误信息。验证器还支持批量验证，一次返回所有字段的错误。

简单场景不用单独建类，控制器内可以直接内联校验：$this->validate($data, ['user_id' => 'require|integer', 'amount' => 'require|float|gt:0'])，返回 true 或错误信息字符串。面试答法：“规则复用、字段多的用验证器类；一次性的简单校验用控制器内联。场景解决的是新增和编辑校验字段不同的问题。”

3. SQL 注入：参数绑定是底线

注入的根本原因是把用户输入拼进了 SQL 字符串，输入里的引号和关键字改变了 SQL 的结构。防护就一条：永远不要拼接原生 SQL。查询构造器默认用 PDO 参数绑定（预处理），值和 SQL 结构是分开传给数据库的，输入再刁钻也只会被当成普通值。必须写原生查询时，用 Db::query($sql, [$bindings]) 的占位符形式，绑定值以数组传入。

面试答法：“注入是因为拼接；查询构造器用 PDO 预处理，值与结构分离，从根上防注入；原生 SQL 必须用占位符绑定。”

4. XSS：输出时转义

XSS 是恶意脚本被当成页面内容输出并执行。ThinkPHP 的模板引擎默认对变量输出做转义，<script> 这类输入会被转成无害文本显示出来。手动输出（比如直接 echo）时用 htmlspecialchars 转义。富文本场景（用户要发带格式的内容）不能一转了之，要用白名单过滤，只允许安全的标签和属性。

5. CSRF：表单令牌

CSRF 是攻击者诱导已登录用户的浏览器向你的站点发请求。表单场景的防护是令牌：在 config/app.php 里配 'form_token' => ['token_on' => true, 'token_name' => '__token__', 'token_type' => 'md5', 'token_reset' => true]，模板表单里加 {:token()} 输出隐藏域（或 {__TOKEN__} 只输出令牌值），提交时由 FormTokenCheck 中间件校验，失败提示“令牌数据无效”。

注意边界：这套令牌机制防的是浏览器表单 + Cookie 会话的场景；API 用 Token 鉴权而非 Cookie 会话时，CSRF 的风险模型不同，不能照搬同一套说法。面试被追问“API 还要不要 CSRF 令牌”时，答出“风险模型不同”就比简单说要/不要强。

6. 密码：只用 password_hash

密码存储只用 PHP 原生函数：password_hash($pwd, PASSWORD_DEFAULT) 生成哈希，password_verify($pwd, $hash) 验证。不要用 MD5 存密码——MD5 是摘要算法不是密码哈希，计算太快、彩虹表可查；password_hash 自动加盐、计算成本可调，是专门为密码设计的。面试一句话：“存密码只用 password_hash + password_verify，MD5 是摘要不是密码哈希。”

容易踩的坑：① 任何情况下都不要把变量拼进 SQL 字符串，占位符是唯一正确的原生查询写法；② $this->validate() 返回 true 或错误信息字符串，记得判断返回值，别当成“失败会抛异常”；③ CSRF 令牌只防浏览器表单场景，API Token 鉴权是另一套风险模型；④ 密码绝不用 MD5，哪怕“先 MD5 再加盐”也不行。

二、代码示例

示例 1：验证器类 + 两种调用方式

<?php
namespace app\validate;

use think\Validate;

class UserValidate extends Validate
{
    // $rule：字段 => 规则，多个规则用 | 连接
    protected $rule = [
        'name'  => 'require|max:25',
        'email' => 'require|email',
        'age'   => 'number|between:1,120',
    ];

    // $message：自定义错误信息，格式是 '字段名.规则名' => '错误信息'
    protected $message = [
        'name.require' => '用户名不能为空',
        'email.email'  => '邮箱格式不正确',
    ];

    // $scene：场景，只校验指定字段；新增和编辑共用一个类时很有用
    protected $scene = [
        'add' => ['name', 'email'],
    ];
}
<?php
use app\validate\UserValidate;

// validate() 是框架助手函数，返回验证器实例
$validate = validate(UserValidate::class);
// scene('add') 选场景，check($data) 执行校验
if (!$validate->scene('add')->check($data)) {
    // getError() 取错误信息
    return json(['msg' => $validate->getError()]);
}

// 控制器内也可以内联校验，不用单独建类
// 返回 true 或错误信息字符串
$result = $this->validate($data, [
    'user_id' => 'require|integer',
    'amount'  => 'require|float|gt:0',
]);
if ($result !== true) {
    return json(['msg' => $result]);
}

三、ThinkJS 对比

ThinkJS 里没有和 TP 验证器同名的类，但 Logic 层就是它的对位概念：src/logic/ 下的文件与 src/controller/ 下的文件一一对应，参数校验与权限校验前置到 Action 执行前——和 TP “验证器先行、控制器只做业务”的分层思路完全一致，只是 TP 把校验规则收进独立的验证器类，ThinkJS 把它收进与控制器配对的 Logic 文件。

另外两个可对照的点：ThinkJS 的 __before() 可以集中做登录校验与 CSRF 校验（例如检查 referrer 域名），对应 TP 里中间件 + 表单令牌的组合；Node 侧的密码哈希用 bcryptjs / argon2 等 npm 包，对应 PHP 原生的 password_hash——两边都是“慢哈希 + 自动加盐”，不要用 MD5 的道理在两个生态里一样成立。

面试怎么说：“校验前置是通用原则：TP 用验证器类 + 场景，ThinkJS 用 Logic 层；CSRF 防护 TP 靠表单令牌 + 中间件，ThinkJS 靠 __before() 集中校验；密码哈希两边都是慢哈希，PHP 是 password_hash，Node 是 bcryptjs / argon2。”

五、面试高频问答

Q1：验证器类和控制器内联校验怎么选？

规则要复用、字段多、需要场景区分时用验证器类（继承 think\Validate，放在 app/validate/）；一次性的简单校验用控制器内联 $this->validate($data, [...])，返回 true 或错误信息字符串。选型的标准是复用程度，不是功能强弱。

Q2：场景（scene）解决什么问题？

同一个模型在不同操作下校验字段不同：新增时 name、email 都必填，编辑时可能只校验其中几个。场景就是给同一套规则分组，调用时 scene('add') 选组，只校验该组字段，避免为每个操作各写一个验证器类。

Q3：SQL 注入的根本原因和防护手段是什么？

根本原因是把用户输入拼进了 SQL 字符串，输入里的引号和关键字改变了 SQL 结构。防护：查询构造器默认用 PDO 参数绑定（预处理），值与结构分离；原生查询用 Db::query($sql, [$bindings]) 的占位符形式。永远不要拼接。

Q4：CSRF 表单令牌是怎么工作的？

服务端生成令牌，模板里用 {:token()} 输出到表单隐藏域；提交时 FormTokenCheck 中间件校验令牌是否一致，失败提示“令牌数据无效”。配置在 config/app.php 的 form_token 里，可控制开关、字段名、生成方式和是否重置。

Q5：为什么不能用 MD5 存密码？

MD5 是摘要算法不是密码哈希：计算太快，暴力破解和彩虹表成本很低。正确做法是 PHP 原生的 password_hash($pwd, PASSWORD_DEFAULT) 存储、password_verify($pwd, $hash) 验证，它自动加盐、计算成本可调，是专门为密码设计的。
