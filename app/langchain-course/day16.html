Day 16：切分与 Embedding：按标题切为什么比固定长度好

RAG 的第一步，切块，决定了后面所有步骤的上限：块切碎了语义，检索再准也拼不回原意；块切太大了，检索回来的全是噪音。今天讲切块的三个选择：按什么切、切多大、重叠多少。

一、核心解释

1. 切块的原则：一块讲一件事

好的块有一个标准：一块只讲一件事，单独拿出来也能看懂。按标题切、按段落切、按语义切，都是为了这个标准；固定长度切（每 500 字一刀）不是，因为一刀下去可能正好切在句子中间、论点中间，块本身就不完整了。

2. 按标题切为什么比固定长度好

按标题 / 段落切固定长度切
边界标题、段落就是天然边界，语义不断字数到了就切，句子、论点都可能被切断
块大小不均匀，但每块都完整均匀，但完整性靠运气
适合有结构的文档：手册、FAQ、教程实在没有结构时的兜底

做法是分层：先按标题切，标题下的块如果还太大，再按段落切，段落还太大，再按句子切。每一层都先保语义完整，再保大小合适，顺序不能反。

3. 块多大合适：看问题，不看感觉

块太小，检索回来一堆碎片，模型要自己拼；块太大，检索回来一堆噪音，模型要自己筛。起步值可以给一个：300 到 500 Token 一块，跑评测集看命中率，再调。块大小不是拍脑袋定的，是评测调出来的，Day 19 会讲怎么调。

4. 重叠是干嘛的：防边界丢失

切块时让相邻块重叠一小段（比如 50 Token），上一块的结尾、下一块的开头是同一段话。这样，刚好跨在边界上的答案，不会因为被切成两半而两边都搜不到。重叠太小没用，太大又浪费 Token 和索引空间，起步 10% 到 20% 的块大小，再按评测调。

5. Embedding 选型看什么

Embedding 是把文本变成向量的模型，选型看三点：语言（中文文档要用中文效果好的模型，别拿英文模型硬上）、维度（维度越高信息越细，但索引越大、检索越慢）、成本和速度（离线建索引可以慢，在线查问题不能慢）。最重要的一条：问题和文档必须用同一个 Embedding 模型，不同模型的向量不在同一个空间里，相似度根本算不了。

容易踩的坑：切块时把标题、编号、表格头切掉了。块单独拿出来时，没有标题就不知道在讲哪一章，没有表格头就不知道列是什么意思。切块要保留上下文：标题带进块里，表格头每块都带一份。

二、代码示例

示例 1：按段落累积切块，超预算才切（本地实测逻辑）

def split_paragraphs(text, max_chars=1000, overlap=100):
    chunks, current = [], ""
    for para in text.split("\n\n"):
        if len(current) + len(para) > max_chars and current:
            chunks.append(current)
            # 重叠：下一块带上上一块的结尾，避免边界上的答案被切成两半
            current = current[-overlap:] + para
        else:
            current += para + "\n\n"
    if current.strip():
        chunks.append(current)
    return chunks

# 逻辑要点：先按段落分（语义边界），再按预算切（大小控制）
# 段落本身就是天然边界，比固定字数一刀切更保语义

示例 3：Section 感知切分（按标题切成节，块首拼标题路径）

import re

def split_by_section(text, max_chars=1000, overlap=100):
    # 1. 按标题切成节，同时拼出标题路径
    sections, stack, buf = [], [], []
    def flush():
        if buf:
            sections.append((" > ".join(stack) if stack else "全文", "\n".join(buf)))
            buf.clear()
    for line in text.splitlines():
        m = re.match(r"^(#{1,3})\s+(.*)", line)
        if m:
            flush()
            level = len(m.group(1))
            stack = stack[:level - 1] + [m.group(2).strip()]
        else:
            buf.append(line)
    flush()
    # 2. 每节再按段落累积，超预算才切；块首拼标题路径
    chunks = []
    for title, body in sections:
        current = ""
        for para in body.split("\n\n"):
            para = para.strip()
            if not para:
                continue
            if current and len(current) + len(para) > max_chars:
                chunks.append(f"【{title}】\n{current}")
                current = current[-overlap:] + para
            else:
                current = (current + "\n\n" + para) if current else para
        if current.strip():
            chunks.append(f"【{title}】\n{current}")
    return chunks

# 块 1 = 【退货政策 > 退货期限】\n自签收之日起 7 天内可申请退货……
#        超过 7 天后，仅质量问题可申请换货……
# 块 2 = 【退货政策 > 退货流程】\n第一步，在 App 内提交退货申请……
#        第二步，等待审核，审核通过后寄回商品。
# 要点：标题路径拼在块首，块单独拿出来也知道出自哪里；一节太长时，
# 在段落边界继续切，不在句子中间断；表格要整块进，实在太长也要每块带表头

四、可能的面试题与答案

Q1：切块怎么切？为什么不固定长度？

按标题、段落、语义分层切：一块只讲一件事，单独拿出来也能看懂。固定长度切可能切在句子、论点中间，块本身就不完整了，检索再准也拼不回原意。

Q2：块大小和重叠怎么定？

起步块 300 到 500 Token、重叠 10% 到 20%，跑评测集看命中率再调。块太小，检索回来一堆碎片；块太大，检索回来一堆噪音；重叠太小防不住边界丢失，太大浪费 Token 和索引。

Q3：Embedding 选型看什么？

语言（中文文档用中文效果好的模型）、维度（越高越细，但索引越大、检索越慢）、成本和速度。最重要的一条：问题和文档必须用同一个模型，否则向量不在同一个空间。

Q4：切块时，标题和表格头怎么处理？

带进块里：标题是块的上下文，没有标题就不知道在讲哪一章；表格头每块都带一份，没有表格头就不知道列是什么意思。切块丢上下文，检索回来也是残缺的。

Q5：切块不好，检索和生成会怎样？

切碎了语义，检索回来的块本身就不完整，生成只能拼碎片；切太大了，检索回来的全是噪音，生成要自己筛。切块是 RAG 的上限，检索和生成都补不回来。

五、加分项

生产视角：切块上线前，先跑三个用例：跨边界的答案能不能搜到？表格块单独拿出来能不能看懂？标题丢了没有？三个有一个没过，切块就别上。

六、补充：Section 感知切分（结合岗位要求）

固定长度切块最大的问题是把一个意思切成两半，Section 感知切分就是先按结构切、再按长度切：先按标题层级（Markdown 的 #、##、###，或文档的章节）把文档切成节，每块保留它的标题路径作为元数据，比如“第 3 章 > 3.2 退货政策”，切块时把这条路径拼在块的开头，检索时模型就知道这块出自哪里，不用靠猜。

规则四条：一、标题优先，一节太长才在段落边界继续切，不在句子中间断；二、表格不拆，一张表尽量整块进一个块，实在太长也要每块都带表头，否则后半张表没列名，检索回来也看不懂；三、块内只讲一件事，一节里混了两个主题，就按主题再切，块的主题越单一，Embedding 越准；四、重叠只补边界，上一块尾巴带一两句到下一块开头就够了，重叠太大等于把同一内容存了好几份，检索结果全是重复块。

七、三种切法对照：按标题、按段落、按语义，各一个示例

用同一份文档对比，三种切法看得最清楚。源文档（产品手册《退货政策》节选）：

# 退货政策
## 退货期限
自签收之日起 7 天内可申请退货，商品需保持完好。
超过 7 天后，仅质量问题可申请换货，不再退货。
## 退货流程
第一步，在 App 内提交退货申请并选择原因。
第二步，等待审核，审核通过后寄回商品，运费由商家承担（质量问题）或用户承担（非质量问题）。

示例 1：按标题切。按 ## 标题切成节，每块前面拼上标题路径。块 1 = “退货政策 > 退货期限：自签收之日起 7 天内可申请退货……超过 7 天后，仅质量问题可申请换货”；块 2 = “退货政策 > 退货流程：第一步……第二步……”。优点是块的主题最干净、单独拿出来也知道出处；缺点是一节太长时还得再切，标题层级乱的文档没法用。

示例 2：按段落切。按空行切成段，再把小段拼到 300–500 Token 为止。块 1 = “自签收之日起 7 天内可申请退货，商品需保持完好。超过 7 天后，仅质量问题可申请换货，不再退货。”（一段就是一块）；块 2 = “第一步……第二步……”（一段就是一块）。优点是简单、稳定、处处可用；缺点是段落本身可能混了两个主题，而且段落切完不知道这段出自哪一节——所以实操里要把标题拼到段首，变成“标题 + 段落”。

示例 3：按语义切。先按句子切，再算相邻句子的向量相似度，相似度突然掉下去的地方就是切点。假设有一段混写了两个主题：“退货期限是 7 天，退款在仓库签收后 3 个工作日内原路返回。”语义切会把它拆成两块：块 1 = “退货期限是 7 天”（期限主题），块 2 = “退款在仓库签收后 3 个工作日内原路返回”（退款主题），尽管它们原来在同一个段落里。优点是块的主题最纯，检索最准；缺点是要对每个句子算向量、慢且贵，相似度阈值也不好调，调不好会切得忽大忽小。

主流是按段落切吗？是，但准确说是“段落优先、再按大小兜底”的混合切法，也就是 LangChain 里最常用的 RecursiveCharacterTextSplitter 的思路：先按段落（\n\n）切，再按换行、句子、字符逐级兜底，块满了就切、块小了就拼。生产里这就是默认答案，因为它简单、稳定、好排错。纯语义切（SemanticChunker）不是主流，是升级选项：只有当你实测发现“段落里混主题、检索回来的块一半是噪音”时，才值得上它。

怎么选，一张表：有结构的文档（手册、FAQ、教程、Markdown）→ 按标题切开头，再按段落切；没结构的长文本（合同、论文、聊天记录、转写稿）→ 按段落切，加大小上限；一问一答的 FAQ → 一问一答就是一块；表格、代码 → 整块不拆。最后一条不变：先上最简单的段落切法，跑评测集看命中率，只有实测证明它不够了，再升级到语义切。
