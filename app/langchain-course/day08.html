Day 8：代码 Agent 的架构：索引、对话、改代码、跑测试

第 2 周的第一课，不写完整 Mini Cursor，先把它的骨架讲清：一个代码 Agent 其实就是第 1 周那个工具循环，换了一套工具、加了两道关卡——改之前先给人看 diff，改之后必须跑测试验算。

一、核心解释

1. 一张图：代码 Agent 的主循环

用户需求
  → 检索：先在仓库索引里找相关文件（不是全量塞给模型）
  → 出 plan：改哪几个文件、每个文件改什么，先说清楚
  → 出 diff：改之前先生成 diff 预览，给人确认
  → 确认后落盘：只改 diff 里写明的部分
  → 跑测试：白名单里的命令，测试过了才算完成
  → 测试不过：把报错贴回给模型，再走一轮（步数有上限）

对照第 1 周：检索、读文件、改代码、跑命令，全是工具；模型还是做决策，工具还是干活。变的是工具集和关卡，不是循环本身。

2. 为什么不能全量塞文件：上下文是有预算的

第 1 周 Day 6 讲过记忆预算，这里是同一个道理，换到代码上：一个仓库几百个文件，全塞进去 Token 爆了不说，模型还会在无关文件里“找”答案，越找越偏。所以正确顺序永远是：先检索、再读文件——检索给“可能相关”的短名单，模型只读名单里的文件。Day 9 会专门讲索引和检索怎么做，今天先记住顺序。

3. 五个工具，分工要干净

工具干什么不干什么
list_files列出仓库结构，让模型知道有什么不读内容
search_code按关键词/函数名找相关位置不直接改代码
read_file读指定文件的指定范围不一次读整个大文件
write_patch生成 diff 预览，确认后才落盘不直接整文件重写
run_command跑白名单里的命令，如测试不跑白名单外的任意命令

分工干净的好处：出了问题能定位到某一步——是检索没找对、还是 diff 写错了、还是测试本身就不过。工具一锅烩，排障就只能靠猜。

4. 两道关卡，是 Mini Cursor 和“让模型直接改代码”的区别

第一道：改之前先出 plan + diff，给人确认。模型先说“改哪、怎么改”，生成 diff 预览，人点头了才落盘。没这道关，模型改错一个地方，你都不知道它改了什么，更没法回滚。

第二道：改之后必须跑测试，测试是验收标准。模型说“改好了”不算数，测试过了才算。测试不过就把报错原样贴回给模型再改一轮——这就是第 2 周验收里“测试能跑”的意思。Day 11 会讲命令白名单和测试闭环的细节。

容易翻车的点：别让模型直接输出整文件覆盖。整文件重写会悄悄丢掉没注意到的逻辑（比如一个边界条件、一个注释里的约定），diff 只改写明的地方，丢东西的面小得多，出了问题也好回滚。这就是计划里那句“为什么不直接让模型输出整文件”的答案。

5. 步数上限：代码 Agent 也会死循环

测试不过 → 再改 → 再测，这个循环和第 1 周的工具循环一样需要上限。第 2 周的验收标准里写着“步骤 ≤5 步”，意思就是：一个任务最多走 5 步，超了就停下来给人看——是需求本身说不清，还是检索一直找错地方，停下来比一直烧 Token 瞎改强。模糊需求时 Agent 该问澄清问题而不是瞎猜，Day 14 复盘会专门讲这个取舍。

示例 2：白名单 + diff 预览，两个护栏的最小实现（本地实测）

ALLOWED = ("npm test", "tsc", "git diff", "pytest")

def run_command(cmd):
    # 白名单是前缀匹配：命令必须以白名单里的某一项开头，否则拒绝执行
    if not any(cmd.startswith(a) for a in ALLOWED):
        return f"拒绝执行：{cmd} 不在白名单里"
    return f"放行：{cmd}（这里接真实执行）"

import difflib
def preview_diff(old, new):
    # diff 预览：只展示改动行，人确认后才落盘
    return "".join(difflib.unified_diff(old.splitlines(True), new.splitlines(True)))

# 本地实测结果：
# run_command("npm test") → 放行；run_command("rm -rf /") → 拒绝执行
# preview_diff 只输出改动的那几行，没改的行不会出现在 diff 里

注意：示例 2 的 run_command 在课程页面里是“放行判断”演示，真实执行要接 subprocess 并设超时，第 2 周动手时再补——护栏的形状先对，执行细节后补，不跳步。

四、可能的面试题与答案

Q1：代码 Agent 的上下文怎么组织？全量塞文件为什么不行？

先检索、再读文件：索引给“可能相关”的短名单，模型只读名单里的文件。全量塞文件 Token 爆了不说，模型还会在无关文件里找答案，越找越偏。上下文预算和第 1 周的记忆预算是同一个道理。

Q2：改错代码时，你的 Agent 怎么发现并回滚？

两道关卡：改之前 diff 预览给人确认，改错的面本身就小；改之后跑测试，测试不过就是发现，报错贴回再改。回滚靠 diff：只改写明的地方，没改的行原样不动，出了问题按 diff 往回撤就行。

Q3：为什么 Mini Cursor 不直接让模型输出整文件？

整文件重写会悄悄丢掉边界条件、注释里的约定这些没注意到的逻辑。diff 只改写明的地方，丢东西的面小、出了问题好定位、好回滚。面试时把“面小、好回滚”讲清，比只说“更安全”可信。

Q4：第 1 周的循环、记忆、图，在 Mini Cursor 里分别复用在哪？

循环是主循环本身：检索 → plan → diff → 测试 → 再改；记忆是上下文预算：只读检索到的文件，不全量塞；图是流程有分支时的形态：比如“测试不过”走回改代码那一步，“人没确认”停在确认节点，都是条件边。不是新学一套，是旧骨架换工具。

Q5：第 2 周结束时，你能拿出什么可演示的东西？

一个 mini-cursor：对着一个真实小项目，能改 3 个真实需求（加功能、修 Bug、重构），每个任务 diff 可审、测试能跑、步骤 ≤5 步。面试讲的时候按任务讲：需求是什么、检索找对没有、diff 长什么样、测试第几次过的——比罗列工具名可信得多。

五、加分项

生产视角：代码 Agent 上线前，先问三个问题：改之前人看没看 diff？改之后测试跑没跑？命令白名单外的路堵没堵？三问有一个答不上来，就别让它碰真实仓库。

简历讲法：别写“做过代码 Agent”，写“给代码 Agent 定了五工具分工：检索先行、diff 预览经人确认才落盘、跑测试做验收、白名单外的命令拒绝、步骤上限 5 步防死循环”。前者是名词，后者是可追问的架构。
