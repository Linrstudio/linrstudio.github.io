Day 17：向量库与检索：TopK 怎么选

切块和向量都准备好了，今天讲存和查：向量库存什么、相似度怎么算、TopK 怎么选、关键词和向量怎么混合——这一步决定模型面前摆的是哪几块资料。

一、核心解释

1. 向量库存什么：向量 + 原文 + 元数据，三件套

向量库里每条记录有三样东西：向量（用来算相似度）、原文块（检索回来要拼进提示词的）、元数据（出处、章节、时间、编号，回答引用和过滤都靠它）。只存向量不存原文，检索回来没东西可拼；只存原文不存元数据，回答没法引用、没法按时间过滤。

2. 相似度怎么算：余弦相似度，方向比长度重要

最常用的是余弦相似度：算两个向量方向的夹角，方向越接近，相似度越高。为什么用方向不用长度？因为向量长度受文本长短影响大，方向才代表语义。实际使用时，向量通常先归一化，归一化后余弦相似度就等于点积，算起来更快。

3. TopK 怎么选：看命中率和 Token 预算，不看感觉

TopK 太小TopK 太大
漏关键块：答案在第 6 块，你只取了 5 块噪音太多：模型要在无关块里筛答案，还烧 Token

起步值可以给一个：TopK = 5，跑评测集看命中率，再调。调的时候看两个数一起变：命中率上去了、Token 消耗没爆，才算调对了；只看一个，另一个迟早反噬。Day 19 会讲评测集怎么做。

4. 关键词和向量怎么混合：精确在前、语义补位

和 Day 9 代码检索的结论一样，文档检索也要混合，只是主次反过来：向量检索是主力，因为文档问题多是语义问题；关键词检索是补充，专门抓精确名字、编号、错误码这些向量容易漏的。混合的做法是：两边各取一批，合并去重，再按分数排，Day 18 的重排就是干这件事的。

5. 索引更新：文档改了，向量库不能还留着旧的

文档一改，对应的块要重新切、重新向量化、重新入库，旧块要删掉或标记过期。更新不及时，检索回来的是旧答案，模型还一本正经地引用它，比没有答案更糟。更新机制和 Day 9 的索引过期是同一个坑，只是换到了文档这边。

6. 向量库怎么选：先看规模和持久化，再看产品

选型先问四件事：数据量多大、要不要持久化、要不要元数据过滤、要不要自己运维。问完再挑产品，别反过来。

产品定位适合注意
FAISS（Meta）内存向量库，快、免费几百万条以内、本地实验重启就丢，自己管持久化（存索引文件）
Chroma轻量、本地文件持久化，LangChain 集成最顺个人项目、小团队起步大规模性能一般
pgvector（Postgres 插件）向量存在 Postgres 里，和业务数据放一起已有 Postgres、要元数据过滤和事务超大规模不如专用库
Pinecone / Qdrant / Milvus托管或专用服务生产、大规模成本和数据出境要先算

口诀：起步用 Chroma（本地、零运维），数据量上来了或要和业务库放一起，再换 pgvector 或 Qdrant。换库只换存取层，切分和 Embedding 不用动——但换 Embedding 模型要全库重建索引（Day 15 已讲），换库和换模型是两回事，别混在一起。

7. pgvector 多说两句：建表、查、建索引

pgvector 值得多说两句，因为它是最容易上手的生产选择：不用多装一个服务，Postgres 里加个插件就行。表结构就是一块一行：正文、向量、元数据各一列。查的时候先 WHERE 过滤元数据、再按向量距离排序取 TopK——过滤和排序一条 SQL 全办了。向量维度要和 Embedding 模型一致（1024 维对应 Qwen3-Embedding 0.6B 和 BGE-M3），换模型要重建表和索引，这和换库是两回事。数据量小可以不建索引，全表扫也够快；量大了再建 HNSW 索引。LangChain 里用 PGVector，调用形状和 Chroma 一样，换库只换这一层。

容易踩的坑：TopK 取回来就直接拼进提示词，不做过滤。相似度分数很低的块，拼进去也是噪音。正确做法是：相似度设一个下限，低于下限的块不要，哪怕 TopK 没取满——宁缺毋滥，缺了模型还能说“资料里没有”，滥了模型就开始现编。

二、代码示例

示例 1：余弦相似度与 TopK（本地实测，小向量算给你看）

import math

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb)

docs = [("d1", [1, 0]), ("d2", [0, 1]), ("d3", [0.7, 0.7])]
query = [1, 0]
ranked = sorted([(cosine(query, v), name) for name, v in docs], reverse=True)
print(ranked[:2])  # [(1.0, 'd1'), (0.707..., 'd3')]：d1 方向完全一致，d3 次之

# 逻辑要点：方向越接近，分数越高；TopK 就是取分数最高的前 K 个
# 真实向量是几百上千维，公式一样，只是数字变长了

示例 2：混合检索的形状（概念代码，先看形状）

def hybrid_search(question, top_k=5):
    vector_hits = vector_search(question)   # 主力：语义相近
    keyword_hits = keyword_search(question) # 补充：精确名字、编号
    # 合并去重：向量在前、关键词补位，总数不超过 top_k
    # 相似度低于下限的块不要，宁缺毋滥
    seen, merged = set(), []
    for hit in vector_hits + keyword_hits:
        if hit["id"] not in seen and hit["score"] >= 0.5 and len(merged) < top_k:
            seen.add(hit["id"]); merged.append(hit)
    return merged

示例 4：pgvector 的 SQL 形状——建表、查、建索引（概念代码，先看形状）

-- 1. 开插件（装一次就行）
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. 建表：一块一行，正文、向量、元数据各一列
CREATE TABLE chunks (
  id SERIAL PRIMARY KEY,
  content TEXT,
  embedding VECTOR(1024),  -- 维度要和 Embedding 模型一致
  source TEXT,             -- 元数据：出处，过滤和引用靠它
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 3. 查：先 WHERE 过滤元数据，再按余弦距离排序取 Top 5
-- <=> 是余弦距离（越小越相似）；向量要先归一化（第 2 节）
SELECT content, embedding <=> $1 AS distance
FROM chunks
WHERE source = '产品手册'
ORDER BY distance
LIMIT 5;

-- 4. 索引：量大了再建，HNSW 是默认推荐
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

四、可能的面试题与答案

Q1：向量库存什么？为什么要存元数据？

向量、原文块、元数据三件套：向量算相似度，原文拼进提示词，元数据管引用和过滤。没有元数据，回答没法引用、没法按时间过滤。

Q2：TopK 怎么选？

起步 5，跑评测集看命中率和 Token 消耗一起调。太小漏关键块，太大噪音多、烧 Token；还要设相似度下限，低于下限不要，宁缺毋滥。

Q3：关键词和向量怎么混合？

向量是主力，关键词补充精确名字、编号、错误码。两边各取一批，合并去重，再按分数排，重排在 Day 18 讲。

Q4：余弦相似度和点积是什么关系？

向量归一化后，余弦相似度就等于点积。方向代表语义，长度受文本长短影响，所以看方向不看长度。

Q5：索引更新怎么做？

文档改了，对应块重新切、重新向量化、重新入库，旧块删掉或标记过期。更新不及时，检索回来的是旧答案，比没有答案更糟。

五、加分项

生产视角：向量库上线前，先问三个问题：元数据齐不齐？TopK 和相似度下限定了没有？文档更新机制有没有？三问有一个答不上来，检索就别上。

六、补充：混合检索：BM25 + 向量 + RRF 融合（结合岗位要求）

向量检索懂语义、但对精确名字不敏感，关键词检索（BM25）正好反过来：它看词频和稀有度，产品型号、人名、条款编号这种精确词，它找得更准。BM25 的核心就两句：词在文档里出现越多次分越高，但增长会饱和（出现 10 次不等于 10 倍分）；词越稀有分越高（全文档都有的词几乎不加分），再按文档长度归一化，长文档不会因为字多就占便宜。公式里 k1 约 1.2–2.0、b 约 0.75，调参前先记住这个意思，面试能讲清意思比背公式重要。

两路结果怎么合成一张名单？不要直接把分数相加——两路分数的量纲根本不一样。标准做法是 RRF（倒数排名融合）：只看排名，不看分数，每个文档的分数 = 1/(k + BM25 排名) + 1/(k + 向量排名)，k 通常取 60。算一笔就明白：A 在 BM25 排第 1、向量排第 4，得分 1/61 + 1/64 ≈ 0.0320；B 两路都排第 2，得分 1/62 + 1/62 ≈ 0.0323，B 反而胜出——RRF 奖励的是“两路都靠前”，而不是“某一路第一”。实操顺序：BM25 和向量各取 Top 50 左右，RRF 融合后再交给 Day 18 的重排，不要在融合这步就只留 5 个。
