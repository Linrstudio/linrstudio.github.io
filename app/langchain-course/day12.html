Day 12：上下文预算与多文件编辑

单文件改对了，多文件一改就乱，问题基本出在两个地方：上下文预算没分好、改文件的顺序没排好。今天把这两件事定下来。

一、核心解释

1. 预算要分账，不能一锅算

一次调用的总 Token 里，System、历史、检索结果、工具结果、输出都要算。正确做法是先分账、再装填：给每一类定一个上限，装填时按优先级来，超了就按优先级截断，而不是等爆了再整体砍。Day 6 的记忆预算是同一个道理，今天把它扩到整个代码任务上。

类别优先级超了怎么办
System（规则、角色）最高，永远保留不截断，System 本身就要写短
当前任务 + 最新 diff高不截断，这是本轮要做的事
检索到的文件中按相关度排序，超了就只留 TopN
历史对话、旧测试结果低先摘要、再截断，最后才丢
输出预留必须预留不预留，模型写到一半就断了

2. 多文件编辑的顺序：先共享、后依赖、再调用方

一个需求改三个文件，顺序不能乱：先改共享的类型、常量、接口，再改依赖这些共享部分的模块，最后改调用方。顺序反了，调用方改完发现接口变了，又要返工；更糟的是，测试在中间跑了一次，报的错是“接口对不上”，其实是顺序错了，不是代码错了。

3. 每改一个文件，要不要跑一次测试

看改动性质：共享接口改了，马上跑一次相关测试，接口对不上早发现；只是调用方内部逻辑改了，可以攒到最后一起跑。原则是：接口变了就早测，内部改动可以晚测。每次都全量跑，慢；最后才跑一次，错在哪一步都不知道。早测和晚测的取舍，问的是“这次改动会不会影响别人”，不是“测试跑得快不快”。

4. diff 怎么合：一个任务，一份 diff 清单

多文件改完，人确认时看的应该是一份按文件分组的 diff 清单：每个文件改了哪、怎么改，一目了然。不能每个文件各确认一次、确认完就忘——人要确认的是“整个任务的改动”，不是“某个文件的改动”。确认后落盘也要按同一份清单来，Day 10 的“预览和落盘共用同一份 diff”在这里同样适用。

容易踩的坑：检索结果塞太多文件，预算被文件吃光，留给输出的空间没了，模型写 diff 写到一半就断了。预算分账时，输出预留要先扣出来，不能等装完文件再看还剩多少。

二、代码示例

示例 1：预算分账，按优先级装填（本地实测）

budget = 4000
system_cost = 500
output_reserve = 500
# 先扣掉 System 和输出预留，剩下的才是给检索文件的
available = budget - system_cost - output_reserve  # 3000
files = [("types.py", 800), ("a.py", 1500), ("b.py", 2000)]  # 已按相关度排好序
used, picked = system_cost + output_reserve, []
for name, cost in files:
    if used + cost <= budget:
        picked.append(name); used += cost

# 本地实测：picked = ['types.py', 'a.py']，used = 3300
# b.py 没装下，不是丢了，是预算不够——要它，就得先把相关度低的换掉，或者摘要后再装

示例 2：多文件编辑顺序（概念代码，先看顺序）

# 需求：给计算器加一个取余运算，涉及 3 个文件
order = [
    "1. types.py：先加共享的类型 / 接口（别人依赖它）",
    "2. calc.py：再实现取余逻辑（依赖 types.py）",
    "3. main.py：最后改调用方（依赖 calc.py）",
]
# 每步的检查点：
# types.py 改完 → 跑一次相关测试，接口对不上早发现
# calc.py 改完 → 跑一次单元测试
# main.py 改完 → 跑一次端到端测试，整个任务才算完

动手任务（10 分钟）

1. 拿一个你熟悉的三文件需求，按“先共享、后依赖、再调用方”排一次顺序，再反过来排一次，对比测试报错会在哪一步出现。
2. 给你的任务定一份预算分账表：System、当前任务、检索文件、历史、输出预留各占多少？输出预留为什么要先扣？
3. 想一个检索文件太多、预算被吃光的场景：你会先摘要、还是先砍相关度低的？为什么？

四、可能的面试题与答案

Q1：上下文预算怎么分账？

先分账、再按优先级装填：System 最高永远保留，当前任务和最新 diff 高，检索文件按相关度取 TopN，历史先摘要再截断，输出预留先扣出来。超了按优先级截断，不是一锅算、爆了再整体砍。

Q2：多文件编辑，顺序为什么重要？

先共享、后依赖、再调用方：接口先定，依赖接口的模块再改，调用方最后改。顺序反了，调用方改完发现接口变了要返工，测试报错还会误导你以为是代码错了，其实是顺序错了。

Q3：每改一个文件都要跑测试吗？

看改动性质：接口变了就早测，内部改动可以晚测。每次都全量跑，慢；最后才跑一次，错在哪一步都不知道。取舍问的是“会不会影响别人”，不是“跑得快不快”。

Q4：diff 清单为什么要按文件分组？

人确认的是整个任务的改动，不是某个文件的改动。按文件分组的清单，一眼看出每个文件改了哪、怎么改；确认后落盘也按同一份清单，预览和落盘才不会对不上。

Q5：预算不够时，你会先砍哪类？

先砍优先级低的：历史先摘要再截断，检索文件按相关度换掉低的。System 和输出预留不砍——System 一砍规则就没了，输出预留一砍 diff 就写不完。

五、加分项

生产视角：多文件任务上线前，先问三个问题：预算分账表有没有输出预留？改动顺序是不是先共享后调用方？diff 清单是不是一份、按文件分组？三问有一个答不上来，任务就容易在中间乱掉。

简历讲法：别写“做过多文件编辑”，写“预算先分账、按优先级装填、输出预留先扣；多文件按先共享、后依赖、再调用方改，接口变了就早测，diff 按文件分组一次确认”。前者是名词，后者是可追问的流程。
