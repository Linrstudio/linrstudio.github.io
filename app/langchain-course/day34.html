Day 34：MCP 协议详解：Host、Client、Server

工具调用做到第 5 周，会遇到一个新问题：每个 Agent 都要接一堆工具，每个工具的接法都不一样，换个模型、换个平台就要重接一遍。MCP（Model Context Protocol）就是来解决这个问题的：它是一套开放协议，让模型和工具之间用同一种方式对话——工具不用为每个模型各写一套，模型也不用为每个工具各学一套接法。

一、核心解释

1. 三方分工：Host、Client、Server 各管什么

MCP 里有三方：Host 是用户直接用的应用（比如聊天客户端、IDE），它管界面、管模型调用、管把多个 Client 的结果汇总；Client 是 Host 里的一对一连接器，一个 Client 连一个 Server，负责按协议发请求、收结果；Server 是工具的提供方，它把自己的能力暴露出来，等 Client 来调。一个 Host 可以挂多个 Client，一个 Client 只连一个 Server——分工一清，出了问题就知道是界面、连接还是工具本身的问题。

一张图记住三方分工：餐厅点菜

客人（Host）只管点菜，服务员（Client）只负责把这桌的单传给厨房、把菜端回来，厨房（Server）只管做菜——菜上错了，先看是点错了、传错了，还是做错了，分工一清，问题就能定位。

2. Server 暴露三种能力：Tools、Resources、Prompts

能力是什么例子
Tools模型可以调用的函数，有输入 schema、有返回值查天气、查数据库、发消息
Resources只读的数据，模型可以读、不能改文件内容、数据库记录、网页
Prompts预置的提示词模板，Server 提供、Client 选用“按这份模板写周报”的模板

区分的关键是“能不能改东西”：Tools 能改（发消息、写文件），Resources 只读，Prompts 是模板。权限和审计都要按这个区分来定：只读的能力可以放宽，可写的工具必须过 Day 35 的纵深防御。

一张图记住三种能力：工具箱、书架、菜谱

工具箱里的东西是拿来动手改东西的，书架上的书只能翻、不能撕，菜谱是照着做的现成模板——分不清“能不能改”，权限就没法定。

3. 发现机制：list_tools，先问有什么、再决定调什么

Client 连上 Server 后，第一件事不是直接调工具，而是先发 list_tools 问一句：“你都提供什么工具？每个工具的输入长什么样？”Server 回一张工具清单，每个工具带名字、描述和输入 schema。模型看到清单，才决定调哪个、传什么参数。发现机制的好处是：Server 加了新工具，Client 不用改代码，下次 list 一下就看到了；Server 下掉工具，Client 也不会再去调一个不存在的工具。

4. 传输方式：stdio 与 Streamable HTTP，本地和远程各一套

两种传输：stdio 是本地进程间通信，Client 把 Server 当子进程启动、通过标准输入输出对话，适合本地工具，延迟低、不用走网络；Streamable HTTP 是走 HTTP 的远程方式，适合 Server 在另一台机器、或要给多人共用的场景，可以复用 HTTP 的鉴权、负载均衡。选哪个看部署：工具在本地就用 stdio，工具要远程共用就用 HTTP，协议本身不变，换传输不用重写工具逻辑。

容易踩的坑：把 MCP 当成“更快的本地函数调用”。MCP 的价值不在快，而在可移植：同一套工具，今天接 A 模型、明天接 B 平台，不用重写。只接一个模型、一个平台时，协议的收益不明显，成本（多一层协议、多一处故障点）反而先到。

一张图记住可移植：万能插头 vs 每台机器配专用插头

本地写死工具，就像给每台机器各配一个专用插头，插口一换就得重做；MCP 是一套统一的插口，同一套工具今天接 A 模型、明天接 B 平台，插上去就能用——这就是协议买单的价值。

二、代码示例

示例 1：发现 + 调用的形状（协议示意，先看流程）

# 流程：先发现，再调用，不要跳过发现直接硬编码工具名
# 1. Client 连上 Server，先问：你提供什么工具？
tools = client.list_tools()
# 返回示例：[{"name": "get_weather", "description": "查指定城市天气",
#            "input_schema": {"city": "string", "date": "string"}}]
# 2. 模型看到清单，决定调哪个、传什么参数
result = client.call_tool("get_weather", {"city": "深圳", "date": "今天"})
# 3. 结果带回 Host，汇总进回答；工具本身不知道调用方是哪个模型

示例 2：三种能力的区分（概念代码）

# Server 暴露的能力，按“能不能改东西”区分，权限和审计也按这个区分定
server_capabilities = {
    "tools": ["get_weather", "send_message"],  # 可写：必须过 Day 35 纵深防御
    "resources": ["docs/manual.md", "db/orders"],  # 只读：可以放宽，但也要鉴权
    "prompts": ["weekly_report_template"],     # 模板：Server 提供，Client 选用
}
# Host 汇总多个 Client 的结果时，要标清每个结果来自哪个 Server、哪个工具

四、可能的面试题与答案

Q1：MCP 是什么？三方怎么分工？

一套让模型和工具用同一种方式对话的开放协议。Host 是用户用的应用、管界面和汇总；Client 是 Host 里一对一连 Server 的连接器；Server 是工具提供方。一个 Host 挂多个 Client，一个 Client 只连一个 Server。

Q2：Tools、Resources、Prompts 各是什么？

Tools 是模型可调用的函数、可写；Resources 是只读数据、模型只能读；Prompts 是 Server 提供的提示词模板。区分关键是能不能改东西，权限和审计按这个区分定。

Q3：list_tools 是干嘛的？

发现机制：Client 连上 Server 先问有什么工具、输入 schema 长什么样，模型看到清单再决定调哪个。Server 加新工具、下掉工具，Client 不用改代码。

Q4：stdio 和 Streamable HTTP 怎么选？

本地工具用 stdio，延迟低、不走网络；远程共用用 Streamable HTTP，可复用 HTTP 鉴权和负载均衡。协议本身不变，换传输不用重写工具逻辑。

Q5：什么时候不值得上 MCP？

只接一个模型、一个平台时：协议收益不明显，还多一层协议、多一处故障点。工具要接多个模型或平台、可移植是刚需时，才值得上。

五、加分项

生产视角：接 MCP Server 前，先问三个问题：这个 Server 是谁提供的、可信吗？它暴露的 Tools 里有没有可写的高危操作？调用超时和失败怎么处理？三问有一个答不上来，Server 就别接。

简历讲法：别写“用过 MCP”，写“Host 挂多 Client、Server 暴露 Tools/Resources/Prompts、list_tools 发现后调用，本地 stdio、远程 Streamable HTTP”。前者是名词，后者是可追问的设计。
