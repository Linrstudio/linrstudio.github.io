Day 6：Memory：模型为什么“失忆”，记忆怎么做预算

模型每次调用都是失忆的，这句话 Day 1 就讲过，今天把它变成可落地的方案：记忆到底是什么、三种处理方式怎么选、预算怎么定、摘要会丢什么、怎么和提示词接起来。

一、核心解释

1. 先钉死一个事实：记忆不在模型里，在你手里

模型本身不保存会话，每次调用都要把历史消息重新发过去。所谓记忆，就是你帮它保管、挑选、压缩的那份历史清单。记忆做得好不好，不取决于模型多聪明，取决于你每次发过去的那份清单里，有没有保留该保留的、压缩了该压缩的、丢掉了可以丢的。

2. 三种处理方式，一张表分清

方式怎么做优点代价
全量保留（Buffer）历史原样全发什么都不丢，最准越聊越贵，迟早超上下文窗口
滑动窗口（Window）只保留最近 N 轮，旧的直接丢掉简单、成本可控会丢掉早期目标、关键决策
摘要（Summary）旧消息先摘要成一条，再带着摘要往下聊关键信息还在，成本可控摘要会失真，细节会被磨平

生产里最常用的是组合：System 保留 + 最近 N 轮全量 + 中间折叠成摘要。这就是咱们脚手架 memory.py 的思路，也是今天代码示例要跑通的方案。

3. 预算怎么定：三个数字要显式配置

  • 总预算：一次调用最多带多少字符 / Token，超过就触发折叠，不能等爆了再处理。
  • 保留窗口：至少保留最近几轮，保证当前话题不断。
  • 触发点：到预算才折叠，而不是每轮都摘要——摘要本身也要花 Token 和时间，没必要每轮都做。

粗算用字符数除以 4，精算用 tokenizer，真实账单看 usage_metadata，这三者的分工 Day 3 已经讲过，今天直接用起来。

4. 摘要会丢什么，要提前想好

摘要最容易丢的是三样东西：具体数字、否定信息（“不要 X”）、时间顺序。缓解办法是：摘要里强制保留“已确认的目标、已排除的选项、关键数字”，而不是让模型自由发挥写一段漂亮话。摘要模板本身也要写清楚，这和提示词设计是一个道理。

5. 记忆怎么和提示词接起来

Day 2 讲过 MessagesPlaceholder("history")：提示词里留一个插槽，调用时把记忆处理后的消息列表插进去。顺序永远是：System 在最前，摘要 / 折叠标记在中间，最近几轮在后，新问题在最后。顺序错了，模型先看到旧摘要、后看到新问题，理解就会乱。

容易踩的坑：只截断、不摘要，还截断了 System 和最近几轮。System 一丢，模型连角色和规则都没了；最近几轮一丢，当前话题就断了。截断的正确姿势是：System 永远保留，最近 N 轮永远保留，能动的只有中间那段。

二、代码示例

示例 1：脚手架的 SimpleMemory，组合策略（概念与 scaffold 一致）

from langchain_core.messages import SystemMessage, HumanMessage
from agent_core.memory import SimpleMemory

# max_chars：总预算；keep_recent：至少保留最近几条
memory = SimpleMemory(max_chars=4000, keep_recent=6)
memory.add(SystemMessage(content="你是一个助手"))
memory.add(HumanMessage(content="我的目标是做一个 Agent 项目"))
# ... 对话进行中，每轮都 add ...
messages = memory.get_messages()
# get_messages 的规则：
# 1. 总量没超预算：原样返回
# 2. 超了：System 保留 + 中间折叠成一条摘要占位 + 最近 6 条保留
# 3. 折叠标记会告诉模型“此处有省略”，而不是悄悄删掉

注意：脚手架里的折叠目前是占位标记，不是真的调模型做摘要。生产里把占位换成一次摘要调用，就是完整的 Summary 方案；先跑通占位版，再升级摘要版，步骤不要一次全上。

示例 2：和提示词接起来（Day 2 的插槽，今天用起来）

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个助手"),
    MessagesPlaceholder("history"),
    ("human", "{input}"),
])

messages = prompt.format_messages(
    history=memory.get_messages(),  # 记忆处理后的清单，直接插进插槽
    input="继续刚才的话题",
)
chain = prompt | llm | StrOutputParser()

四、可能的面试题与答案

Q1：Buffer、Window、Summary，你会怎么选？

短对话用 Buffer 全量保留；长对话用 Window + Summary 组合：System 保留、最近 N 轮全量、中间折叠成摘要。选型的依据是会话长度、成本预算、早期信息有多重要，三者缺一不可，只说“用摘要”是不够的。

Q2：摘要失真了，你怎么发现、怎么缓解？

发现靠评测：准备一批长对话，摘要前后分别跑同一批问题，对比答案有没有变。缓解靠摘要模板：强制保留目标、已排除选项、关键数字，否定信息和时间顺序单独列出来，别让模型自由发挥。

Q3：多用户并发时，记忆怎么隔离？

记忆必须按会话 / 用户隔离，不能共用一份历史清单。LangGraph 里用 thread_id 区分会话，checkpoint 按 thread 存状态；自己写循环时，也要按会话 ID 分开存，串会话是生产事故，不是小 bug。

Q4：Token 预算和记忆预算是什么关系？

记忆预算是 Token 预算的一部分：一次调用的总 Token 里，System、历史、工具描述、工具结果、输出都要算。记忆预算定得太大，留给工具结果和输出的空间就没了；定得太小，模型又记不住上下文。两者要一起算，不能各算各的。

Q5：记忆里要不要存工具结果？

要，但要挑着存。工具结果是模型下一步决策的依据，全删了模型就不知道上一步查到了什么；全留着又会把上下文撑爆。做法是：关键结果保留原文，次要结果只保留摘要或关键字段，和历史消息用同一套预算管。

五、加分项

生产视角：记忆要落库，不能只放内存；会话、用户、时间戳都要记，出了问题能按会话复盘。摘要调用本身也要记成本和耗时，别让“省 Token 的摘要”反而烧掉更多钱。

简历讲法：别写“会用 Memory”，写“做过 System 保留 + 最近 N 轮 + 中间摘要的组合记忆，预算显式配置，摘要模板强制保留目标、已排除选项和关键数字”。前者是名词，后者是可追问的方案。
