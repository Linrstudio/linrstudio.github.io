Day 13：Mini Cursor Web 界面（前端主场）

第 2 周的前端主场：Agent 再厉害，没有界面，人也看不见它在干什么。今天讲 Mini Cursor 的 Web 界面：四个界面元素怎么排、状态机怎么走、流式输出怎么接、确认按钮为什么不能只是好看。

一、核心解释

1. 四个界面元素，按任务顺序排

元素干什么对应 Agent 的哪一步
需求输入框人写需求，点开始任务开始，检索、plan
进度 / 步骤条显示现在走到哪一步了检索 → plan → diff → 测试
diff 预览区按文件分组展示 diff，改动行高亮改之前先给人看
确认 / 拒绝按钮 + 测试结果区人点头才落盘，落盘后跑测试、结果贴出来确认落盘、测试闭环

顺序就是任务顺序：输入在上、进度在中、diff 在下、确认和结果在最后。人一眼看出“现在到哪了、下一步要我干什么”，就是好界面；人要到处找“现在是不是该我点了”，就是坏界面。

2. 状态机：界面状态和 Agent 状态是同一份

idle（等输入） → running（检索、plan、生成 diff）
  → awaiting_confirm（diff 已出，等人确认）
  → confirmed（已落盘，跑测试）
  → done（测试通过） / failed（测试不过，报错贴回）
  → running（再改一轮）……步数到上限 → stopped（停下来给人看）

关键点：界面不能自己编状态。按钮能不能点、进度条到哪了，都由后端返回的状态决定；前端只是把状态画出来。前端自己维护一份“以为的状态”，和后端真实状态一脱节，按钮点下去没反应、或者重复落盘，都是这么来的。

3. 流式输出：先给步骤，再给全文

Agent 跑起来要几十秒，人不能对着空白等。流式输出的顺序是：先推步骤（“正在检索…”、“正在生成 diff…”），再推 diff 全文，最后推测试结果。步骤先到，人知道它在干活；全文后到，人再细看。顺序反了，人先看到一堆 diff、不知道现在到哪了，体验就乱了。

4. 确认按钮：不是好看，是护栏

确认按钮的职责是：点下去，才触发落盘；没点，diff 只能看、不能写。实现上要做到两点：① 确认要带任务 ID 和 diff 版本号，防止人确认的是旧 diff、落的是新 diff；② 确认后按钮要置灰、不可重复点，防止重复落盘。Day 10 的“预览和落盘共用同一份 diff”在这里就是：前端传回的版本号，必须和后端生成 diff 时的版本号一致。

容易踩的坑：把测试结果只写“通过 / 失败”两个字。失败时要贴全：哪个测试、哪一行、期望值和实际值——Day 11 讲过，报错是下一轮的输入，界面上只写“失败了”，人（和模型）都不知道下一步该改哪。

二、代码示例

示例 1：状态机，界面状态由后端决定（概念代码，先看形状）

# 后端返回的状态，前端只负责画，不自己编状态
STATES = ["idle", "running", "awaiting_confirm", "confirmed", "done", "failed", "stopped"]

# 前端按状态决定按钮能不能点：
# idle → 开始按钮可点；running → 开始按钮置灰，显示步骤条
# awaiting_confirm → 确认 / 拒绝按钮可点；confirmed → 按钮置灰，显示测试中
# done / failed / stopped → 显示结果，开始按钮恢复可点（新任务）

示例 2：确认请求要带任务 ID 和 diff 版本号（概念代码）

# 前端点确认时发给后端：
# POST /api/confirm { task_id: "t1", diff_version: 3 }
# 后端校验：diff_version 和生成 diff 时的版本号一致，才落盘；
# 不一致 → 返回“diff 已过期，请重新生成”，不落盘
# 确认后按钮置灰，不可重复点，防止重复落盘

示例 3：流式输出的顺序（概念代码）

# 后端按这个顺序推，前端按这个顺序画：
# 1. { type: "step", text: "正在检索相关文件…" }
# 2. { type: "step", text: "正在生成 diff 预览…" }
# 3. { type: "diff", files: [ { path: "calc.py", diff: "..." } ] }
# 4. { type: "test", passed: false, output: "哪个测试、哪一行、期望值、实际值" }
# 步骤先到、全文后到，人先知道在干活，再细看 diff

注意：示例都是“形状代码”，不是可直接跑的完整前后端——第 2 周动手时，先按这个形状搭页面和接口，再接真实 Agent；形状先对，细节后补，不跳步。

四、可能的面试题与答案

Q1：Agent 的界面，状态应该放在哪？

后端。界面状态和 Agent 状态是同一份，前端只负责画，不自己编状态。前端自己维护一份“以为的状态”，和后端真实状态一脱节，按钮没反应、重复落盘都是这么来的。

Q2：确认按钮怎么做，才不是摆设？

点下去才触发落盘，没点只能看不能写；请求带任务 ID 和 diff 版本号，版本号不一致就不落盘；确认后按钮置灰、不可重复点。三点缺一，确认就只是好看。

Q3：流式输出的顺序为什么重要？

先推步骤、再推全文、最后推结果：步骤先到，人知道它在干活；全文后到，人再细看。顺序反了，人先看到一堆 diff、不知道现在到哪了，体验就乱了。

Q4：前端主场，你的优势怎么讲？

按任务顺序排界面：输入、进度、diff、确认、结果；状态由后端决定、前端只画；流式先步骤后全文；确认带版本号防旧 diff 落盘。讲清这四点，比说“我会 React”可信得多。

Q5：测试结果区，最容易被忽略的是什么？

失败时的完整信息：哪个测试、哪一行、期望值和实际值。只写“通过 / 失败”两个字，失败时人（和模型）都不知道下一步该改哪，测试闭环就断在界面上了。

五、加分项

生产视角：界面上线前，先跑三个用例：后端状态变了，前端按钮能不能跟着变？确认旧 diff 会不会被版本号拦住？重复点确认会不会重复落盘？三个有一个没过，界面就别上。

简历讲法：别写“做过 Agent 前端”，写“界面按任务顺序排，状态由后端决定、前端只画，流式先步骤后全文，确认带任务 ID 和 diff 版本号、确认后置灰防重复落盘”。前者是名词，后者是可追问的界面架构。
