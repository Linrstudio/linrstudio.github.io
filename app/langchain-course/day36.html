Day 36：Verifier 与 Composer：校验与合成

Multi-Agent 的最后两步，经常被当成“顺手的事”：Verifier（校验者）查一遍，Composer（合成者）合起来。但这两步恰恰是质量的分水岭：没有独立的 Verifier，子 Agent 交什么、最终就是什么；没有规则的 Composer，多路结果一冲突，合成就会凭感觉取舍。这课讲清楚：Verifier 查什么、怎么打回，Composer 怎么合、冲突听谁的。

一、核心解释

1. Verifier 为什么必须独立于执行者

自己改、自己验，等于没验。执行者写答案时已经认定自己的做法是对的，校验时只会找支持自己的证据，找不出自己的错。所以 Verifier 必须是另一个节点、另一套提示词、最好是另一类标准：执行者负责“做出来”，Verifier 负责“按标准查”。独立还体现在数据上：Verifier 不能只看执行者的结论，要看原始材料——测试结果、引用块、schema 校验结果，结论和材料对不上，就打回。

2. Verifier 查哪三项：测试、引用、schema

标准查什么不过怎么办
测试代码类任务：测试是不是全过了打回执行者，附失败的测试名
引用结论里的数字、日期、人名，能不能在标的资料里找到打回改写或删除结论
schema输出格式对不对：字段全不全、类型对不对打回按格式重交

三项标准要事先写死，不能由执行者现场定，也不能由 Verifier 临场发挥。标准写死的好处是：打回有依据，执行者知道改哪里；复盘时也能看出来，是标准太松，还是执行者没达标。

场景：工厂质检 —— 每件产品过三道检查，数字 / 日期 / 出处对不上就打回

质检员不看工人说“做完了”，只看三样东西：测试跑没跑过、数字能不能在资料里找到、格式对不对。一项对不上，整件产品打回重做——但打回单上要写清错在哪。

3. 打回与重试上限：打回不是无限循环

打回要带意见：哪项标准不过、具体是哪条结论、原始材料是什么，不带意见的打回（“再改改”）只会让执行者瞎改。重试也要有上限，通常 2–3 次：超了就停下来，把“校验不过”本身写进结果，交给 Supervisor 决定——是换一路、降级，还是诚实告诉用户这部分没通过。没有上限的打回循环，成本和延迟都会炸，还掩盖了“这路根本做不出来”的事实。

场景：后厨返工 —— 只返工坏掉的那道菜，不重做整桌

校验不过只打回坏掉的那一路，别的路不用重跑；重试 2–3 次还不过，就把“这道菜做不出来”写进结果，交给 Supervisor 定夺，而不是无限返工。

4. Composer 怎么合成：分段、标出处、冲突听校验

Composer 的合成规则是三条：分段，每路结果各成一段，不要混写；标出处，每段标自己的来源（工具结果标工具名，文档结论标 [资料 N]）；冲突时听校验：两路结论冲突了，不看谁说得自信、看谁通过了校验——通过测试、有出处、格式对的那路为准；两路都没通过，就都写出来、标清冲突，让用户或 Supervisor 定夺，不要由 Composer 偷偷选一个。Composer 不生产新结论，只合成已校验的结论；合成时现编一句话，就是新的幻觉来源。

场景：拼图编辑 —— 只拼带出处的碎片，没出处的不进终稿

Composer 是拼图编辑，不是作者：每块碎片必须带出处标签才能拼进终稿，没出处的那块再顺眼也不拼；两块碎片拼不到一起（结论冲突），就按校验结果取舍，都没通过就把冲突写出来。

容易踩的坑：Composer 偷偷做取舍。两路冲突，Composer 凭“哪个读起来顺”选一个，还不告诉用户有冲突——用户看到的是一个干净但可能错的答案。冲突必须显式写出来，取舍要有依据。

二、代码示例

示例 1：Verifier 的三项标准（概念代码，先看标准）

def verifier(result):
    # 三项标准事先写死，不由执行者现场定、不由 Verifier 临场发挥
    checks = {
        "tests": run_tests(result.code),       # 代码类：测试全过才算过
        "citations": check_citations(result),  # 结论里的数字、日期、人名能在出处里找到
        "schema": validate_schema(result),     # 输出字段全、类型对
    }
    failed = [k for k, v in checks.items() if not v.passed]
    if not failed:
        return {"passed": True}
    # 打回要带意见：哪项不过、具体哪条、原始材料是什么
    return {"passed": False, "failed": failed,
            "details": {k: checks[k].detail for k in failed}}

示例 2：Composer 的合成规则（概念代码）

def composer(verified_results):
    # 分段：每路各成一段，不要混写；每段标自己的出处
    sections = []
    for name, res in verified_results.items():
        sections.append({"from": name, "content": res.content,
                         "source": res.source})  # 工具名或 [资料 N]
    # 冲突：不看谁说得自信，看谁通过了校验；都没通过就都写出来、标清冲突
    conflicts = find_conflicts(verified_results)
    if conflicts:
        sections.append({"from": "conflict_note",
                         "content": "以下两路结论冲突，均未通过全部校验，请定夺",
                         "conflicting": conflicts})
    return sections  # Composer 不生产新结论，只合成已校验的结论

四、可能的面试题与答案

Q1：Verifier 独立是什么意思？

节点独立、提示词独立、标准独立：执行者负责做出来，Verifier 按事先写死的标准查，还要看原始材料（测试结果、引用块、schema 结果），不是只看执行者的结论。

Q2：Verifier 的三项标准各查什么？

测试：代码类任务测试全过；引用：结论里的数字、日期、人名能在标的资料里找到；schema：输出字段全、类型对。三项事先写死，打回有依据。

Q3：打回和重试上限怎么定？

打回带意见：哪项不过、具体哪条、原始材料是什么；重试上限通常 2–3 次，超了就停，把校验不过写进结果，交给 Supervisor 换一路、降级或诚实告诉用户。

Q4：Composer 合成有哪三条规则？

分段：每路各成一段、不混写；标出处：每段标工具名或 [资料 N]；冲突听校验：通过校验的为准，都没通过就都写出来、标清冲突。

Q5：Composer 和 Verifier 的分工是什么？

Verifier 负责查：按标准验、打回带意见；Composer 负责合：分段、标出处、按校验结果处理冲突。Composer 不生产新结论，Verifier 不替执行者重做。

五、加分项

生产视角：Verifier 和 Composer 上线前，先问三个问题：三项标准写死了吗？打回意见带材料了吗？冲突显式写出来了吗？三问有一个答不上来，收口质量就没保证。

简历讲法：别写“做过结果校验”，写“Verifier 独立于执行者，测试、引用、schema 三项标准写死，打回带意见、重试上限 2 次，Composer 分段标出处、冲突以校验结果为准”。前者是名词，后者是可追问的设计。
