Day 35：工具安全纵深防御：Schema、ACL、幂等

工具一接上，安全问题就来了：模型可能传错参数、调错工具、重复调用、调了不该调的高危操作。纵深防御的意思是：不靠任何一层兜底，每一层都拦一部分，层层叠加。这课按调用链路的顺序讲：Schema 白名单、Pydantic 校验、ACL、幂等键、超时、沙箱、审计日志、高危操作人工确认——第 2 周的白名单是其中一层，这课补全整条链。

一、核心解释

1. Schema 白名单 + Pydantic 校验：参数进门先过两道关

Schema 白名单是第一道关：只允许清单里的工具、清单里的参数名，多一个参数、少一个必填参数、工具名不在清单里，直接拒绝，不走到执行。白名单在第 2 周 Day 11 已经讲过前缀匹配的漏洞：生产版要三条一起上——不用 shell（argv 执行）、拒绝元字符、参数元组精确匹配。Pydantic 校验是第二道关：参数名对了，值还要合法——类型对不对、范围对不对、枚举值在不在清单里，比如“城市”必须是白名单里的城市名、“金额”必须是正数。两道关分工不同：白名单拦“不该调的”，Pydantic 拦“调得不对的”。

2. ACL：谁能调哪个工具，先查权限再执行

ACL（访问控制列表）是一张表：行是调用方（用户、角色、子 Agent），列是工具，格子里写能不能调。普通用户能调“查天气”，不能调“发消息给全员”；Knowledge 子 Agent 能调“检索”，不能调“写文件”。ACL 要在执行前查，查完还要记下来：谁、在什么时候、调了哪个工具、结果如何，审计日志就是这张表的流水。没有 ACL，模型一旦被提示词注入带偏，就能调到它本不该调的工具。

3. 幂等键：同一个调用重复发了，只执行一次

网络重试、Supervisor 重试、用户手抖点了两次，都会让同一个调用发两次。发消息、写文件、扣款这种操作执行两次就是事故。幂等键的做法是：调用方给每次调用带一个唯一键（比如用户 ID + 任务 ID + 工具调用 ID 的组合），服务端先查这个键有没有执行过——执行过就直接返回上次的结果，不再执行；没执行过才执行、并把结果和键一起存下来。幂等键不是“去重显示”，是“去重执行”，只读查询不需要它，可写操作必须有它。

4. 超时、沙箱、审计日志、人工确认：剩下的四层

超时：每个工具设超时（比如 30 秒），超了就停、返回失败，不要让一个挂住的工具拖垮整张图。沙箱：工具在受限环境里跑，只能碰白名单里的文件和网络，跑测试、跑代码、跑命令都要进沙箱，不能直接跑在宿主机上。审计日志：每次调用记谁、什么时候、调了什么、传了什么参数、结果如何，出事后能复盘。人工确认：高危操作（删文件、发全员消息、扣款、改线上配置）执行前必须停下来、等人点了确认才继续，确认里要写清“要做什么、影响什么”，不能只写“是否继续”。

容易踩的坑：只做一层就以为安全了。只做白名单，参数值非法照样能捣乱；只做 Pydantic，越权调用照样能执行；只做幂等，超时挂住的工具照样拖垮全图。纵深防御的意思就是：每一层都拦一部分，缺一层就多一个口子。

二、代码示例

示例 1：调用链路的防御顺序（概念代码，先看顺序）

def safe_call(caller, tool_name, args, idempotency_key):
    # 1. Schema 白名单：工具名和参数名必须在清单里
    if tool_name not in ALLOWED_TOOLS or not args_match_schema(tool_name, args):
        return {"error": "工具或参数不在白名单"}
    # 2. Pydantic 校验：值要合法（类型、范围、枚举）
    validated = ToolArgs(**args)  # 不合法就抛错，不走到执行
    # 3. ACL：调用方有没有权限调这个工具
    if not acl_allows(caller, tool_name):
        return {"error": "无权限"}
    # 4. 幂等键：执行过就直接返回上次结果，不再执行
    if idempotency_key in executed:
        return executed[idempotency_key]
    # 5. 高危操作：先停下来，等人工确认
    if tool_name in HIGH_RISK_TOOLS and not human_confirmed():
        return {"error": "高危操作，需人工确认"}
    # 6. 超时 + 沙箱里执行，执行完写审计日志
    result = run_in_sandbox(tool_name, validated, timeout=30)
    executed[idempotency_key] = result
    audit_log(caller, tool_name, args, result)
    return result

四、可能的面试题与答案

Q1：工具安全纵深防御有哪几层？按顺序说。

Schema 白名单、Pydantic 校验、ACL、幂等键、超时、沙箱、审计日志、高危操作人工确认。按调用链路顺序拦，每一层拦一部分。

Q2：Schema 白名单生产版要哪三条一起上？

不用 shell（argv 执行）、拒绝元字符、参数元组精确匹配。只做前缀匹配有漏洞，比如以 pytest 开头的拼接命令会被放行。

Q3：ACL 和审计日志是什么关系？

ACL 是执行前查权限的表，审计日志是执行后记的流水：谁、什么时候、调了什么、传了什么参数、结果如何。没有 ACL，提示词注入带偏的模型能调到不该调的工具；没有日志，出事复盘不了。

Q4：幂等键怎么设计？

调用方带唯一键，比如用户 ID + 任务 ID + 工具调用 ID 的组合；服务端先查键有没有执行过，执行过直接返回上次结果，没执行过才执行并存下结果和键。不能只用时间戳，时间戳会撞、也区分不了不同调用。

Q5：沙箱和人工确认各防什么？

沙箱防工具跑出边界：只能碰白名单里的文件和网络，跑代码、跑命令都要进沙箱。人工确认防高危操作误执行：删文件、发全员消息、扣款、改线上配置，执行前必须停下来等人确认。

五、加分项

生产视角：工具安全上线前，先问三个问题：白名单、Pydantic、ACL 三层都上了吗？可写操作都有幂等键吗？高危操作的人工确认和审计日志都通了吗？三问有一个答不上来，工具就别上。

简历讲法：别写“做过工具安全”，写“Schema 白名单 + Pydantic 校验 + ACL 执行前查权 + 幂等键去重执行 + 超时沙箱 + 审计日志 + 高危操作人工确认”。前者是名词，后者是可追问的链路。
