Day 19：RAG 评测集：命中率、引用准确率、幻觉率

没有评测集的 RAG，调参就是碰运气。今天讲评测集怎么做、三个数怎么算、调参时看哪几个数一起变——这是第 3 周从“做出来”到“能证明变好了”的关键一课。

一、核心解释

1. 评测集怎么做：问题 + 标准答案块 + 标准答案，三件套

评测集里每条有三样东西：问题（用户真实会问的）、标准答案块（答案出自哪几块，事先标好）、标准答案（正确答案本身，用来比对生成结果）。起步 10 到 20 条就够了，关键是覆盖：常见问题、边界问题、资料里没有的问题，三类都要有——只有常见问题，评测集就是摆设。

2. 三个数，怎么算

指标怎么算低了说明什么
命中率检索回来的块里，有标准答案块的问题 / 总问题数切块、向量、TopK 有问题，检索这步就漏了
引用准确率回答里引用正确的结论 / 回答里的全部关键结论引用标错了，或者模型在引用块之外编了结论
幻觉率回答里资料里没有的结论 / 回答里的全部关键结论防幻觉的三道关有缺口，重点查 Day 18 的关卡

三个数要一起看：命中率高、引用准确率低，说明检索对了、生成标错了；命中率低，其他两个数再高也没用，因为答案根本没检索到；幻觉率高，先查检索为空分支和校验关，不要先换模型。

3. 调参看哪几个数一起变

调块大小、重叠、TopK、相似度下限时，每次只改一个数，跑一遍评测集，记下三个数和 Token 消耗的变化。一次改多个数，变好了也不知道是谁的功劳，变坏了也不知道是谁的锅。调参的记录表本身就是面试可讲的东西：改了什么、三个数怎么变、为什么停在这个值。

4. 评测集也要防作弊：别用同一批问题既调参又验收

调参用的问题和最终验收的问题要分开：同一批问题既调参又验收，调出来的数是虚高的——参数是照着这批问题调的，换一批问题就原形毕露。起步时可以先用一批，但心里要清楚：最终验收一定要换一批没见过的问题。

容易踩的坑：评测集里只有“资料里有答案”的问题，没有“资料里没有”的问题。没有后者，幻觉率永远测不出来——模型现编了，你也不知道，因为评测集里根本没有现编会被发现的题目。

二、代码示例

示例 1：三个数怎么算（本地实测，小数字算给你看）

# 评测集：2 条，标准答案块事先标好
gold = {"q1": "d1", "q2": "d2"}   # q1 答案在 d1，q2 答案在 d2
got = {"q1": "d1", "q2": "d3"}    # 检索回来：q1 对了，q2 错了
hit_rate = sum(1 for k in gold if got[k] == gold[k]) / len(gold)
print(hit_rate)  # 0.5：2 条里 1 条命中

# 引用准确率和幻觉率同理：
# 引用准确率 = 引用正确的关键结论 / 全部关键结论
# 幻觉率 = 资料里没有的关键结论 / 全部关键结论
# 三个数一起看，不要只看一个

示例 2：调参记录表（照着抄，不要只记“变好了”）

# 每次只改一个数，跑一遍评测集，记下四个数：
# 改动 | 命中率 | 引用准确率 | 幻觉率 | Token 消耗
# TopK 5 → 8 | 0.70 → 0.80 | 0.85 → 0.83 | 0.10 → 0.09 | +20%
# 结论：命中率上去了，引用准确率微降、Token 多了 20%，值不值要看场景
# 只记“变好了”三个字，下次再调，你连上次改了什么都想不起来

1. 给你的 RAG 写 10 条评测题：常见问题 5 条、边界问题 3 条、资料里没有的问题 2 条，再标好每条的标准答案块。
2. 用示例 1 的方法，手工算一次命中率，再写出如果命中率低，你先查切块、向量、TopK 里的哪一个。
3. 写一张调参记录表：只改 TopK 一个数，跑两遍，记下四个数的变化，再写出你停在这个值的理由。

四、可能的面试题与答案

Q1：RAG 评测集怎么做？三个数怎么算？

每条有问题、标准答案块、标准答案三件套，起步 10 到 20 条，覆盖常见、边界、资料里没有三类。命中率是检索命中标准块的比例，引用准确率是引用正确的关键结论比例，幻觉率是资料里没有的关键结论比例，三个数一起看。

Q2：命中率高、引用准确率低，说明什么？

检索对了、生成标错了：答案块检索到了，但模型引用标错了，或者在引用块之外编了结论。先查引用和生成，不要先动检索。

Q3：调参时，你怎么记录？

每次只改一个数，跑一遍评测集，记下命中率、引用准确率、幻觉率、Token 消耗四个数的变化。调参记录表本身就是面试可讲的东西：改了什么、三个数怎么变、为什么停在这个值。

Q4：幻觉率怎么测出来？

评测集里必须有“资料里没有”的问题，没有它，幻觉率永远测不出来。模型现编了，你也不知道，因为评测集里根本没有现编会被发现的题目。

Q5：评测集和第 1 周的最小评测集，是什么关系？

同一个思路，对象换了：第 1 周是 Agent 的最小评测集（工具选对没有、步数多少），这里是 RAG 的评测集（命中、引用、幻觉）。思路一样：先定评测集，再谈变好变坏，不要凭感觉。

五、加分项

生产视角：RAG 评测上线前，先问三个问题：评测集覆盖三类问题了吗？调参和验收的问题分开了吗？调参记录表写了吗？三问有一个答不上来，评测就是摆设。

简历讲法：别写“做过 RAG 评测”，写“10 到 20 条评测集，覆盖常见、边界、资料里没有三类，报命中率、引用准确率、幻觉率三个数，每次只改一个参数、记下四个数的变化”。前者是名词，后者是可追问的评测。

六、补充：EvalHarness：把评测做成脚手架（结合岗位要求）

单次评测是跑一遍，EvalHarness 是把评测变成可重复、可回归的脚手架，岗位上要的是后者。它的四件套是：数据集（问题 + 应该命中的块 + 标准答案，含“资料里没有”的否定问题）、运行器（同一批问题，分别跑不同版本的 RAG 或 Agent，参数写进配置不写进代码）、打分器（命中率、引用准确率、幻觉率、平均延迟、平均成本，五个指标一起报，只报命中率会掩盖幻觉和成本）、回归报告（新版本和基线版本同题对比，哪个指标掉了、掉了多少、掉在哪几题，一页纸说清）。

落到流程里就是三条规矩：一、改动先跑评测再上线，切块、Embedding、重排、提示词，任何一环改了都要跑同一套题；二、进 CI 设门禁，比如命中率掉超过 2 个百分点、或引用准确率掉超过 1 个百分点就拦住，不靠人眼看；三、坏题要进数据集，线上答错的真实问题，脱敏后补进评测集，下次改动如果还错，报告里会直接指出来。没有这套脚手架，评测就是一次性表演，有了它，评测才是治理。
