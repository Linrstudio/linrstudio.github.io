Day 9：仓库索引与代码检索

Day 8 说了“先检索、再读文件”，今天讲检索本身：索引到底存什么、关键词索引和向量索引怎么选、检索没找对时怎么发现、怎么和第 1 周的工具循环接起来。

一、核心解释

1. 索引是什么：一份“代码地图”，不是代码本身

索引不存全部代码原文，存的是能快速定位的线索：文件路径、函数名、类名、符号定义位置、调用关系、文件摘要。检索时先查地图、拿到短名单，再按名单读文件。没有索引，Agent 只能靠猜文件名、或把仓库全塞给模型——前者找不全，后者 Token 爆了还容易找偏。

2. 索引的粒度：文件、函数、块，三档怎么选

粒度存什么适合什么时候
文件级文件路径 + 摘要仓库小、文件少，先定位文件
函数 / 类级每个函数、类的名字和位置最常用：改代码基本都落到某个函数上
代码块级按逻辑块切分的小段大文件、长函数，需要精确定位到某一段

Mini Cursor 起步用函数级就够了：改代码的单位基本是函数，文件级太粗、块级太碎。粒度越细，索引越大、维护成本越高，不要一上来就追求最细。

3. 关键词索引 vs 向量索引，怎么选

方式擅长不擅长
关键词索引（倒排）精确名字：函数名、变量名、错误码，找得又快又准同义不同名：用户说“算钱”，代码里叫“结算”，关键词对不上
向量索引（语义）语义相近：用户说“算钱”，能找到“结算”相关的代码精确名字容易被语义相近但不对的代码挤掉，需要 Embedding 和向量库

生产里最常用的是混合：先用关键词把精确命中的排前面，再用向量补语义相关的，最后按相关度合并去重。只用一种，都会在另一类问题上翻车。面试时说出“混合检索”四个字，再讲清各自补什么短板，就比只说一种可信得多。

4. 检索结果怎么给模型：短名单 + 定位，不给全文

检索返回给模型的应该是：文件路径、函数名、行号、一两行摘要，最多再加一小段关键代码。模型按名单读文件时，用 read_file 只读指定范围，不要一次读整个大文件。名单长度也要设上限，比如 Top 5，超过就说明检索太宽、要收紧关键词或加过滤条件。

5. 检索没找对，怎么发现

三个信号，出现一个就要怀疑检索：模型读了名单里的文件还说“找不到相关代码”；模型改的文件和需求明显不沾边；测试报错指向的文件根本不在名单里。处理办法不是让模型继续猜，而是回到检索这一步：换关键词、放宽到文件级、补一个向量检索、或者直接问用户“你说的是哪个模块”。检索错了还往下走，diff 和测试全是白做功。

容易踩的坑：索引过期。代码改了、索引没更新，检索给的还是旧位置，模型按旧位置读文件、改代码，改完发现对不上。索引必须跟着代码走：文件一改就更新，或者至少在检索前校验一次位置还在不在。过期索引比没有索引更坑人，因为它给的是“看起来对”的错误答案。

二、代码示例

示例 1：函数级倒排索引，最小实现（本地实测）

import re

files = {
    "calc.py": "def add(a, b):\n    return a + b\n\ndef mul(a, b):\n    return a * b\n",
    "main.py": "from calc import add\nprint(add(1, 2))\n",
}

index = {}
for path, text in files.items():
    for name in re.findall(r"def (\w+)", text):
        index.setdefault(name, []).append(path)

print(index)            # {'add': ['calc.py'], 'mul': ['calc.py']}
print(index.get("add")) # ['calc.py']：搜 add，先定位到 calc.py，再读文件

这就是关键词索引的骨架：函数名 → 文件列表。真实项目里还要存行号、类名、调用关系，但骨架不变：先建“名字 → 位置”的映射，检索时按名字查映射，不用全文扫描。

示例 3：混合检索的思路（概念代码，先看形状）

def hybrid_search(query, top_k=5):
    keyword_hits = keyword_search(query)   # 精确名字，排前面
    vector_hits = vector_search(query)     # 语义相关，补同义不同名
    # 合并去重：精确命中优先，语义命中补位，总数不超过 top_k
    seen, merged = set(), []
    for hit in keyword_hits + vector_hits:
        if hit not in seen and len(merged) < top_k:
            seen.add(hit); merged.append(hit)
    return merged

注意：示例 3 的 vector_search 需要 Embedding 和向量库，第 3 周 RAG 会系统讲，今天先记住混合的形状——精确在前、语义补位、总数有上限。

四、可能的面试题与答案

Q1：关键词索引和向量索引，你会怎么选？

混合：关键词把精确命中排前面，向量补语义相关的，最后合并去重、总数设上限。只用关键词，同义不同名会漏；只用向量，精确名字容易被语义相近但不对的代码挤掉。选型的依据是问题类型，不是哪个更新就用哪个。

Q2：检索结果 TopK 怎么定？

看任务和上下文预算：TopK 太小会漏关键文件，太大又会把无关文件塞给模型、烧 Token 还带偏。起步 Top 5，跑评测集看命中率和 Token 消耗，再调。TopK 不是拍脑袋定的，是评测调出来的。

Q3：大仓库的索引怎么做增量更新？

全量重建只适合小仓库；大仓库要增量：文件一改只更新改动的文件和受影响的调用关系，或者按文件哈希判断有没有变，没变的跳过。增量更新的核心是“别每次都全量扫”，否则仓库一大，索引更新本身就成了负担。

Q4：检索和 RAG 的检索，是一回事吗？

思路一样，都是“先查、再答”，但对象不同：这里查的是代码结构（函数、调用关系），RAG 查的是文档内容（段落、知识）。代码检索更看重精确名字和结构，向量只是补充；文档检索更看重语义，关键词只是补充。主次是反的。

Q5：检索找对了，但模型还是改错了，问题可能在哪？

先分层定位：是检索名单里根本没有正确文件，还是名单对了但模型读错了范围，还是 diff 写错了，还是测试本身有问题。分层定位比笼统说“模型不行”有用得多，也是 Day 8 五工具分工干净的价值。

五、加分项

生产视角：索引是基础设施，不是临时工具：要有更新机制、过期校验、命中率监控。检索命中率掉了，先查索引是不是过期了、再查查询词是不是变了，别一上来就怪模型。

简历讲法：别写“做过代码检索”，写“给 Mini Cursor 做了函数级倒排索引，检索返回路径、函数名、行号的短名单，TopK 设上限，关键词与向量混合检索，索引过期时先校验位置再读文件”。前者是名词，后者是可追问的方案。
