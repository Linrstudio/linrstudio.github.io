Day 32：Planner 与任务分解：把任务拆成 DAG

Multi-Agent 的第一步不是动手，而是拆：Planner 把一个复杂任务拆成步骤、标出依赖、定出并行度。拆得好不好，决定了后面并行能不能跑、失败能不能隔离、结果能不能验收。拆问题这件事，第 3 周的混合问答已经练过一次，这课把它系统化：拆成 DAG（有向无环图），每个步骤都有输入、输出和验收标准。

一、核心解释

1. DAG 是什么：有向、无环、图，三个词拆开看

DAG 是 Directed Acyclic Graph 的缩写，有向无环图。三个词拆开看：图，就是节点加边，节点是步骤、边是依赖；有向，箭头有方向，A→B 表示 A 的输出是 B 的输入，A 必须先跑；无环，箭头不能绕回起点，A→B→A 这样的圈不允许出现。合起来一句话：DAG 就是一张能排成先后顺序的依赖图——只要没有圈，总能找到一个执行顺序，让每个步骤跑的时候它的依赖都已完成，这个顺序叫拓扑排序。

为什么必须无环？有圈的图排不出顺序：A 等 B、B 等 A，谁都动不了，就是死锁。所以 Planner 输出计划的第一件事就是判圈，判出圈就重拆，而不是等执行跑到一半卡住。判圈的办法就是拓扑排序：反复取“依赖都已完成”的步骤，取到最后还有剩下的步骤，说明剩下的互相依赖、成圈了（示例 3）。

形状长什么样和 DAG 的关系
链A→B→C，全串行DAG 的特例，每步只有一个前置
树一父多子，只有一个根DAG 的特例，一个步骤只有一个“父依赖”
DAG一个步骤可以有多个输入最一般的形状；本课的“对照差异”同时依赖两个检索结果，就是 DAG 不是树

注意别和 LangGraph 的图搞混：LangGraph 的图可以有环，循环边就是干这个的——ReAct 要一圈一圈跑，直到模型不再调工具。Planner 的任务 DAG 不能有环，因为任务计划是“做完就结束”的清单，有环就永远做不完。一个管循环执行、一个管一次性计划，环的允许与否是两者最大的区别。

一张图看懂链、树、DAG、有圈：前三个能排顺序，最后一个是死锁

链和树都是 DAG 的特例：链每步只有一个前置，树每步只有一个父依赖；DAG 最一般，一个步骤可以同时依赖两个检索结果。有圈排不出顺序，Planner 必须先判圈。

2. 为什么拆成 DAG：步骤之间只有两种关系

DAG 的意思是：步骤之间有箭头（依赖），但箭头不能绕成圈。两个步骤之间只有两种关系：有依赖（A 的输出是 B 的输入，必须先 A 后 B），没依赖（可以并行）。把关系画成图，Supervisor 就不用凭感觉派活：看图就知道哪步能跑、哪步要等、哪步卡住了。依赖成圈（A 等 B、B 等 A）是死锁，Planner 输出的第一件事就是检查有没有圈。

3. 拆的粒度：一步只做一件事，验收标准写在前面

每个步骤只做一件事：检索、执行、校验、合成，各是一步；“查资料并写答案”这种一步包两件事的拆法，失败时说不清是哪半步错了。每个步骤还要在动手前写清三样：输入（需要什么）、输出（交出什么格式）、验收标准（怎么算做完，比如“检索命中至少 2 块相关资料”或“测试全部通过”）。验收标准写在前面，Verifier 才有标准可查；动手后再定标准，等于自己给自己打分。

拆的粒度：一大步包两件事 vs 两小步各带验收标准

粒度停在“可独立验收”这一层就够了：再拆就碎到“打开一个文件”这种原子操作，通信成本反而上去。

4. 拆不干净怎么办：继续拆，直到每步只走一条路

判断拆没拆干净的标准，和第 3 周混合问答一样：一个步骤是不是只走一条路、只用一类工具、只产出一种结果？如果一个步骤里既要检索又要执行，就继续拆。拆到不能再拆、或者再拆就没有意义（步骤小到“打开一个文件”这种原子操作），就停下来。拆太碎也有代价：步骤越多，通信和汇总成本越高，所以粒度停在“可独立验收”这一层就够了。

5. 并行度从图里算出来，不是拍脑袋定的

图的“宽度”就是天然并行度：同一层没有依赖的步骤有几个，就能并行几个，但还要受 Day 31 的并行上限（3–5 个）和成本约束。图的“关键路径”是最长的一条依赖链，它决定了任务最少要花多久——优化要先优化关键路径上的步骤，并行再多，关键路径上的慢步骤不解决，总耗时也下不来。

宽度是并行度，红线是关键路径：优化先动红线上的步骤

并行度从图的宽度算，关键路径从图的最长链算：宽度告诉你能同时跑几个，关键路径告诉你最少要花多久。

容易踩的坑：计划只写步骤、不写验收标准。没有验收标准，Verifier 只能凭感觉说“好像做完了”，子 Agent 交上来的半成品也会被当成成品汇总，错误一路传到最终答案。

示例 2：按 DAG 执行：分层并行、关键路径优先（概念代码）

def run_plan(plan):
    done = {}  # 已完成步骤的结果
    while len(done) < len(plan):
        # 本层：依赖都已完成、还没跑的步骤，并行跑，但受并行上限约束
        ready = [s for s in plan if s["id"] not in done
                 and all(d in done for d in s["deps"])]
        if not ready:
            raise ValueError("依赖成圈或前置失败，计划卡住了")  # 死锁要显式报错
        for step in ready[:PARALLEL_LIMIT]:
            result = run_step(step, done)
            # 验收：不过就打回这一步，不重跑全图
            done[step["id"]] = verify_or_retry(step, result)
    return done

示例 3：判圈：拓扑排序排不出来就是有圈（可跑）

def has_cycle(plan):
    # Kahn 算法：反复取依赖已满足的步骤；取完还有剩下的，就是成圈
    deps = {s["id"]: set(s["deps"]) for s in plan}
    done, progress = set(), True
    while progress:
        progress = False
        for sid, ds in deps.items():
            if sid not in done and ds <= done:
                done.add(sid); progress = True
    return len(done) != len(plan)  # 还有没取出来的步骤，说明互相等、成圈了

ok = [{"id": "a", "deps": []}, {"id": "b", "deps": ["a"]}]
bad = [{"id": "a", "deps": ["b"]}, {"id": "b", "deps": ["a"]}]
print(has_cycle(ok))   # False：能排完，没圈
print(has_cycle(bad))  # True：A 等 B、B 等 A，死锁

四、可能的面试题与答案

Q1：Planner 是干嘛的？

把复杂任务拆成 DAG：步骤、依赖、并行度、每个步骤的输入、输出、验收标准。拆完先检查依赖有没有成圈，再交给 Supervisor 按图执行。

Q2：拆的粒度怎么把握？

停在“可独立验收”这一层：一步只做一件事，动手前写清输入、输出、验收标准；再拆就碎到原子操作、通信成本反而上去，就停下来。

Q3：并行度和关键路径是什么关系？

图的宽度是天然并行度，关键路径是最长依赖链、决定最少耗时。优化先优化关键路径，并行度还要受上限和成本约束。

Q4：依赖成圈了怎么办？

Planner 输出时就要检查出来，显式报错、让 Planner 重拆，而不是让执行跑到死锁才发现。执行里遇到 ready 为空，也要显式报错。

Q5：验收标准为什么必须写在前面？

因为 Verifier 要按标准查：检索命中几块、测试过没过、每条结论有没有出处。动手后再定标准，执行者会按对自己有利的标准交差。

Q6：DAG 是什么？和 LangGraph 的图有什么区别？

DAG 是有向无环图：节点是步骤、边是有方向的依赖、箭头不能绕成圈；没圈就能拓扑排序出合法执行顺序，有圈就是死锁。LangGraph 的图可以有环，循环边用来跑 ReAct 循环；Planner 的任务 DAG 不能有环，因为任务计划是做完就结束的清单。

五、加分项

生产视角：计划本身也要评测：同一任务，让 Planner 拆两次，步骤和依赖稳不稳定？不稳定的计划，执行再稳也稳不住。计划的稳定性，是 Multi-Agent 可靠性的第一道关。

简历讲法：别写“会任务分解”，写“把任务拆成 DAG，步骤带输入、输出、验收标准，依赖成圈显式报错，按层并行、关键路径优先”。前者是名词，后者是可追问的设计。
