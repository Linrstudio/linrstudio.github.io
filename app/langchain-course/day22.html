Day 22：Computer Use 总览：为什么让 Agent 操作电脑 | LangChain 30 天实战课

第 4 周开篇，先讲清一个大问题：Agent 不只会调 API，还能像人一样操作电脑。API 是软件留好的“后门”，有 API 当然好；但很多软件没有 API，或者 API 不全，这时 Agent 就直接看屏幕、点按钮、敲键盘，把活干完。这就是 Computer Use：让 Agent 操作电脑。

一、核心解释

1. 为什么让 Agent 操作电脑：没有 API 也能干活

先说清两条路的区别。调 API 是走“官方通道”：快、稳、结果结构化，但前提是对方给了 API，而且给了你要的那个接口。操作电脑是走“人走的路”：看界面、点按钮、填表单，软件长什么样，Agent 就怎么用。它的价值就一句话：能操作一切有界面的软件，不依赖 API。没有 API 的老系统、只做了网页版没做开放接口的工具、需要点几下鼠标才能完成的小流程，都能用这条路兜底。

但也要认清代价：操作电脑比调 API 慢，一步步点，还要等界面反应；而且界面一改版，坐标和按钮位置就可能变。所以原则是：有 API 优先用 API，没有 API 再用 Computer Use。Computer Use 是补位，不是首选。

2. 它能干什么、不能干什么：能力边界与安全红线

能做的事就三类：能看（截图、读屏幕文字，知道现在界面是什么状态）、能点（点按钮、点菜单、点链接）、能输（在输入框里打字、按快捷键）。这三类组合起来，大部分“人坐在电脑前能做的事”，Agent 都能做。

不能碰的，也要先划线。第一，没有授权的操作不能碰：没让你登录的账号、没让你打开的文件、没让你进的系统，一律不动。第二，删、发、支付类操作一律人工确认：删除文件、发送消息或邮件、提交订单和付款，这些动作一旦做了就很难撤回，Agent 必须先停下，把“要做什么、影响是什么”说清楚，等人点头再执行。第三，不确定的不猜：屏幕上看不清、按钮意思不明、弹了没见过的确认框，先截图问人，别凭感觉点下去。

安全红线要写进代码，不是写在提示词里：只在提示词里写“别乱删东西”是拦不住的，模型可能忘了、也可能理解错。删、发、支付这类动作，必须在代码层设一道关卡：没拿到人工确认，函数直接拒绝执行。这条后面示例 2 会写出来。

3. 工具集：截图、点击、输入、打开、读屏

Computer Use 不需要几十个工具，五个就够搭起骨架。每个工具要说清两件事：它是干什么的、它返回什么。

工具是干什么的返回什么
screenshot给当前屏幕拍一张照，是 Agent 的“眼睛”一张图片，Agent 靠它看界面状态
click(x, y)在坐标 (x, y) 处点一下鼠标是否点上了，一般要再截图确认效果
type(text)往当前焦点处输入一段文字是否输入完成，输入前要先点中输入框
open_app打开指定的应用或网址应用是否打开、窗口是否出现
read_screen_text把屏幕上的文字读出来，变成文本一段文本，Agent 靠它做判断、做校验

注意这个循环：截图 → 判断 → 点 / 输 → 再截图确认。Agent 不是闭着眼睛连点十下，而是每做一步就看一眼结果，确认这步生效了再走下一步。跳过“再截图确认”这步，是 Computer Use 最常见的翻车原因：点了没反应、输错了地方，后面全跟着错。

4. 先浏览器，后桌面：顺序不是随便定的

学 Computer Use 有个推荐顺序：先做浏览器，再做桌面。原因有三条。第一，浏览器可控：页面能刷新、能重开、环境相对干净，出了问题从头再来成本低。第二，浏览器可复现：同一个网址，别人打开也是一样的页面，方便调试、方便复盘，桌面软件在不同电脑上长得可能不一样。第三，浏览器能截图留痕：每步的页面状态都能存下来，出问题时有据可查。

桌面为什么放后面？桌面变量多、风险大：窗口位置会变、弹窗会抢焦点、不同系统和版本长得不一样，而且一不小心就可能动到真实文件和系统设置。先在浏览器里把“看—判断—点—确认”这个循环练熟，再去碰桌面，翻车的面会小很多。第 4 周就是按这个顺序排的：Day 23 先讲浏览器操作，桌面放到后面几天。

def screenshot():

    return take_screenshot()  # 返回图片数据

def click(x, y):

    return mouse_click(x, y)  # 返回是否点上了

def type_text(text):

def read_screen_text():

示例 2：危险操作的人工确认关卡（可运行，纯 Python）

# 安全红线写进代码：删 / 发 / 支付，先过确认关卡，没确认直接拒绝
DANGEROUS = {"delete", "send", "pay"}

def needs_confirm(action):
    """判断这个动作是否属于删 / 发 / 支付类，需要人工确认。"""
    return action in DANGEROUS

def run_action(action, confirmed=False):
    """执行动作前先过关卡：危险动作没确认就拒绝，不执行。"""
    if needs_confirm(action) and not confirmed:
        return "拒绝执行：%s 属于危险操作，需人工确认后再执行" % action
    return "已执行：%s" % action

if __name__ == "__main__":
    for action in ["click", "delete", "send", "pay", "type"]:
        print(action, "->", run_action(action))
    print("delete + 已确认 ->", run_action("delete", confirmed=True))

上面这段是纯 Python，本地可以直接跑，预期输出是：click 和 type 直接执行，delete / send / pay 没确认时被拒绝，delete 在 confirmed=True 时才执行。成本数字这里不涉及；如果后面要接真实模型调用，费用按示例写，替换成自己的账单数字。

四、可能的面试题与答案

Q1：什么是 Computer Use？

让 Agent 像人一样操作电脑：看截图、读屏幕文字、点按钮、输文字、打开应用，不依赖 API。核心循环是截图 → 判断 → 点 / 输 → 再截图确认，每步做完都要看一眼结果。

Q2：Computer Use 和 API 调用比，优势和风险各是什么？

优势：能操作一切有界面的软件，不依赖 API，没有 API 的老系统和网页流程也能兜底。风险：比 API 慢，要一步步等界面反应；界面一改版，坐标和定位就可能失效；还可能误点、误输，删、发、支付类操作一旦做错很难撤回。所以有 API 优先用 API，Computer Use 是补位，危险动作必须人工确认。

Q3：Computer Use 的工具集有哪些，各返回什么？

五个：screenshot 返回当前屏幕图片，是 Agent 的眼睛；click(x, y) 在坐标点一下，返回是否点上；type(text) 往焦点处输文字，返回是否输完；open_app 打开应用或网址，返回是否打开；read_screen_text 把屏幕文字读成文本，供判断和校验。

Q4：安全红线在工程上怎么落地？

写进代码，不只写在提示词里：删、发、支付类动作在代码层设确认关卡，没拿到人工确认直接拒绝执行；没有授权的账号、文件、系统一律不动；看不清、不确定的先停下问人，别猜着点。

Q5：为什么先浏览器，后桌面？

浏览器可控、可复现、能截图留痕，出问题重开成本低，适合先练“看—判断—点—确认”这个循环；桌面变量多、风险大，窗口位置会变、弹窗会抢焦点，还可能动到真实文件，等循环练熟了再碰。

五、加分项

生产视角：Computer Use 上线前先问三件事：危险动作的确认关卡写在代码里了吗？每步有没有截图留痕，出问题能复盘吗？界面改版后，定位失效时是停下报错，还是会猜着点下去？三问有一个答不上来，就别上生产。

简历讲法：别写“做过 Computer Use”，写“截图—判断—点输—再截图确认的循环，删 / 发 / 支付类动作代码层人工确认，先浏览器后桌面”。前者是名词，后者是可追问的设计。
