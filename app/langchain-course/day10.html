Day 10：文件工具与 diff 预览：改之前先给人看

Day 8 定了规矩，Day 9 定了检索，今天落到文件工具本身：read_file 怎么读指定范围、write_patch 的 diff 怎么生成、人确认后才落盘的流程怎么走、路径安全怎么守。

一、核心解释

1. 读文件：只读范围，不读全文

read_file 的参数应该是路径 + 起止行号，而不是只有路径。大文件一次读全文，既烧 Token 又把模型带偏；读指定范围，模型看到的是检索定位到的那一段。行号从 1 开始还是从 0 开始，要在工具描述里写死，模型按描述传参，工具按描述解析——描述和实现不一致，行号就永远对不上。

2. 改文件：先生成 diff，再谈落盘

write_patch 的正确流程是三步：① 生成 diff 预览 → ② 人确认 → ③ 按 diff 落盘。diff 只展示改动行，没改的行不出现，人一眼就能看出改了哪、怎么改。直接整文件重写的问题 Day 8 讲过：会悄悄丢掉边界条件和注释里的约定，diff 只改写明的地方，丢东西的面小得多。

3. 落盘前要校验：diff 和文件现状对得上吗

人确认 diff 到真正落盘之间，文件可能被别人改过。落盘前要校验 diff 里的“旧内容”还在不在文件里：对不上就停下来、重新生成 diff，不要硬套。硬套旧 diff 到新文件上，改错位置还不自知，是最难排障的一类 bug。

4. 路径安全：工具不能走出仓库

模型传来的路径可能是 ../etc/passwd，也可能是绝对路径。文件工具必须先把路径解析到仓库根目录下：解析后的路径不在仓库内，一律拒绝。路径校验要在读和写两个工具里都做，只做一个，另一个就是后门。

容易踩的坑：diff 预览和落盘用两套逻辑。预览时算的是一种 diff，落盘时又是另一种替换，结果人确认的和实际落盘的不一样。预览和落盘必须共用同一份 diff 计算，确认的是什么，落的就是什么。

二、代码示例

示例 1：读指定范围 + 路径守卫（本地实测）

from pathlib import Path

ROOT = Path("/repo").resolve()

def safe_path(path: str) -> Path:
    # 解析后必须还在仓库根目录下，否则拒绝：挡住 ../ 和绝对路径
    target = (ROOT / path).resolve()
    if not str(target).startswith(str(ROOT)):
        raise ValueError(f"拒绝访问仓库外路径：{path}")
    return target

def read_file(path: str, start: int, end: int) -> str:
    lines = safe_path(path).read_text().splitlines(True)
    return "".join(lines[start - 1:end])  # 行号从 1 开始，描述里要写死

# 本地实测：safe_path("src/a.py") 通过，safe_path("../etc/passwd") 被拒绝
# read_file 读 lines[1:3]，正好是第 2、3 行，不多不少

示例 2：diff 预览，确认后才落盘（本地实测）

import difflib

def preview_diff(old: str, new: str) -> str:
    return "".join(difflib.unified_diff(old.splitlines(True), new.splitlines(True)))

def apply_patch(path: str, old: str, new: str, confirmed: bool) -> str:
    if not confirmed:
        return preview_diff(old, new)  # 没确认，只返回 diff，不写盘
    current = safe_path(path).read_text()
    if old not in current:
        return "停下：文件现状已变，diff 里的旧内容对不上，请重新生成 diff"
    safe_path(path).write_text(current.replace(old, new, 1))
    return "已落盘"

# 本地实测：preview_diff 只输出改动行
# old="a=1\nb=2\n"，new="a=1\nb=3\n" → 只显示 -b=2 / +b=3，没改的 a=1 只做上下文

动手任务（10 分钟）

1. 给 agent-core 写一个 read_file：参数是路径、起止行号，行号从 1 开始，路径先过 safe_path 再读。

3. 想一个 diff 预览和落盘不一致的场景：预览算的 diff 和落盘用的替换逻辑不一样时，人确认的和实际落盘的会差在哪？

四、可能的面试题与答案

Q1：为什么改代码要用 diff，而不是整文件重写？

整文件重写会悄悄丢掉边界条件、注释里的约定这些没注意到的逻辑；diff 只改写明的地方，丢东西的面小、出了问题好定位、好回滚。预览和落盘共用同一份 diff，确认的是什么，落的就是什么。

Q2：diff 确认后、落盘前，文件被别人改了怎么办？

落盘前校验 diff 里的旧内容还在不在：对不上就停下来、重新生成 diff，不要硬套。硬套旧 diff 到新文件上，改错位置还不自知，是最难排障的一类 bug。

Q3：文件工具的路径安全怎么讲？

把路径解析到仓库根目录下，解析后不在仓库内的一律拒绝；读和写两个工具都要做，只做一个就是后门。../ 和绝对路径是测试时必问的两个用例。

Q4：read_file 为什么要限制范围？

上下文预算：大文件一次读全文烧 Token 还带偏模型。检索定位到某一段，read_file 就只读那一段；行号约定写在工具描述里，模型按描述传参。

Q5：diff 预览给人看时，应该展示什么、不展示什么？

展示改动行和少量上下文，没改的行不出现。人一眼看出改了哪、怎么改，才是“改之前先给人看”的意义；把全文贴出来，人根本看不出改动在哪。

五、加分项

生产视角：文件工具上线前，先跑三个用例：../ 能不能出去、确认前会不会写盘、文件现状变了能不能拦住。三个有一个没过，就别让它碰真实仓库。

简历讲法：别写“做过文件工具”，写“read_file 按行号读指定范围、路径解析后必须在仓库内，write_patch 先出 diff 预览、经人确认、落盘前校验旧内容对得上才写”。前者是名词，后者是可追问的流程。
