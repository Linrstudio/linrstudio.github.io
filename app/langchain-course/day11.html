Day 11：命令白名单与测试闭环

Day 8 给了白名单的形状，Day 10 给了 diff 的流程，今天把命令这道关讲透：白名单为什么不能只做前缀匹配、测试不过怎么贴回给模型再改、步数上限怎么防死循环。

一、核心解释

1. 前缀匹配的漏洞：先承认 Day 8 的简化版不够

Day 8 的示例用的是前缀匹配：命令以白名单某一项开头就放行。这个版本有个洞：pytest; rm -rf / 是以 pytest 开头的，前缀匹配会放行，shell 一执行，分号后面的命令也跟着跑了。所以前缀匹配只能当演示，生产版必须升级，承认简化版的边界，是这课最重要的一点。

2. 生产版白名单：三条规则一起上

  • 不用 shell：用参数列表（argv）执行，不走 shell，;、|、& 就没有“拼接命令”的语义了。
  • 拒绝元字符：命令字符串里出现 ;、|、&、$、反引号，一律拒绝，哪怕前面是白名单命令。
  • 精确匹配参数列表：解析后的参数元组必须在白名单集合里，pytest -q 在白名单里，pytest --cov 就不在——多一个参数也是另一个命令。

三条缺一不可：只不用 shell，模型还能传危险参数；只拒绝元字符，前缀匹配还是会放行多余参数；只精确匹配，不拒绝元字符，shell 注入还是能进来。

3. 超时：命令不能无限跑

测试挂住了、死循环了，Agent 不能跟着等一辈子。每个命令都要设超时，超时就杀掉、把“超时”当成一次失败结果贴回给模型。超时时间写在配置里，不写进提示词——提示词是给模型看的，超时是给执行器看的，两者别混。

4. 测试闭环：报错不是失败，是下一轮的输入

改代码 → 跑测试 → 测试不过
  → 把报错原文贴回给模型（不要只贴“失败了”三个字）
  → 模型再改 → 再跑测试
  → 测过为止，或者步数到上限停下来给人看

报错贴回时要给全：哪个测试、哪一行、期望值和实际值各是什么。只贴“测试失败”，模型只能瞎猜；贴全了，模型才知道改哪。贴回的报错也要算进上下文预算，太长的报错要截断关键部分，不能全文塞。

5. 步数上限：测试循环也会死循环

改 → 测 → 再改 → 再测，和第 1 周的工具循环一样需要上限。第 2 周验收写着“步骤 ≤5 步”：超了就停下来给人看——是测试本身有问题，还是检索一直找错地方，还是需求说不清。停下来定位，比一直烧 Token 瞎改强。

容易踩的坑：测试过了就以为代码对了。测试只覆盖了它写的那几条用例，没覆盖的边界还是可能错。测试是验收标准，不是正确性证明；面试时把这句讲清，比说“测试过了就是对了”可信得多。

二、代码示例

示例 1：生产版白名单（本地实测）

import shlex

ALLOWED = {("pytest",), ("pytest", "-q"), ("npm", "test"), ("tsc", "--noEmit")}

def allowed(cmd: str) -> bool:
    # 1. 拒绝 shell 元字符：; | & $ 反引号，一律不进执行器
    if any(c in cmd for c in ";|&$`"):
        return False
    try:
        parts = tuple(shlex.split(cmd))
    except ValueError:
        return False
    # 2. 参数列表必须精确在白名单里：多一个参数也是另一个命令
    return parts in ALLOWED

# 本地实测：pytest -q → 通过；pytest → 通过；npm test → 通过
# git push → 拒绝；pytest; rm -rf / → 拒绝；pytest --cov → 拒绝（不在白名单里）

注意：这个示例只做了“放行判断”，真实执行要接 subprocess 且 shell=False、设超时，今天先把判断做对，执行细节按这个判断接。

示例 2：测试闭环骨架（步数上限 + 报错贴回）

MAX_STEPS = 5

def run_task(patch_fn, run_tests):
    for step in range(1, MAX_STEPS + 1):
        patch_fn()                    # 模型改代码，出 diff、确认、落盘
        result = run_tests()          # 跑白名单里的测试命令，带超时
        if result.passed:
            return f"第 {step} 步：测试通过，任务完成"
        # 测试不过：把报错原文贴回给模型，下一轮再改
        # 报错太长时截断关键部分，不要全文塞进上下文
    return "步数到上限：停下来给人看，不要继续瞎改"

# 本地实测逻辑：第 2 步测试通过时，循环在第 2 步返回，不会跑满 5 步

2. 写一个 run_task 的变体：超时也算一次失败，超时结果贴回给模型时要写清“超时、命令、超时秒数”三项。
3. 找一个你写过的测试失败：把“只说失败了”和“贴全报错”两种贴回方式各写一遍，对比模型（或你自己）第二次改的时候，信息差在哪。

四、可能的面试题与答案

Q1：命令白名单只做前缀匹配，够吗？

不够。pytest; rm -rf / 以 pytest 开头，前缀匹配会放行。生产版要三条一起上：不用 shell、拒绝元字符、参数列表精确匹配。面试时先承认简化版的边界，再讲生产版，比一开始就说“我的白名单很安全”可信。

Q2：测试闭环里，报错贴回时要注意什么？

贴全关键信息：哪个测试、哪一行、期望值和实际值；太长时截断关键部分，不要全文塞进上下文。报错是下一轮的输入，不是失败的宣告。

Q3：超时怎么处理？

每个命令设超时，超时就杀掉、把“超时”当成一次失败结果贴回，写清超时、命令、超时秒数三项。超时时间是执行器配置，不写进提示词。

Q4：测试过了，能不能说代码就是对的？

不能。测试只覆盖了它写的那几条用例，没覆盖的边界还是可能错。测试是验收标准，不是正确性证明；讲清这句，比说“测试过了就是对了”可信得多。

Q5：步数上限 5 步，是怎么定的？

不是真理，是验收约定：一个任务最多走 5 步，超了就停下来给人看。定上限的依据是成本和定位：一直改下去烧 Token 不说，还掩盖了“检索错了、需求不清、测试本身有问题”这些真正的原因。

五、加分项

生产视角：命令工具上线前，先跑五个用例：白名单内、白名单外、前缀注入（;）、多余参数、超时。五个有一个没过，就别让它碰真实机器。

简历讲法：别写“做过命令白名单”，写“白名单不用 shell、拒绝元字符、参数列表精确匹配；测试闭环把报错原文贴回、步数上限 5 步，超时算一次失败”。前者是名词，后者是可追问的护栏。
