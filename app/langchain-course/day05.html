Day 5：手写 Tool Calling 循环（不依赖黑盒）

前面四天讲的都是“一次调用”：提示词进去、结果出来。今天开始讲 Agent 的核心——模型自己决定要不要调工具、调哪个、结果回来后怎么办。这一课不依赖 AgentExecutor，把循环的每一步都摊开写，就是你脚手架里 agent-core/agent_core/loop.py 的 run_agent。

一、核心解释

1. 循环就 4 步，面试要能口述

步骤做什么关键点
① 绑工具llm.bind_tools(tools)不绑，模型输出里就不会有 tool_calls，只能输出文本
② 模型决策把完整 history 发给模型模型回 AIMessage：要么带 tool_calls，要么是最终文本
③ 执行并回填按 tool_call 逐个执行工具结果必须包成 ToolMessage 追加回 history
④ 再决策或收尾回到第 ② 步没有 tool_calls 就收尾；跑满上限就返回 max_steps

记住这句口头禅：模型决策 → 调工具 → 结果回填 → 再决策。Agent 不是一个更聪明的模型，而是一个让模型能反复“看结果再决定”的循环。

2. 工具调用的三种消息，分工不能乱

  • HumanMessage：用户的原始问题，是循环的起点。
  • AIMessage（带 tool_calls）：模型本轮的决策。tool_calls 里的每一项是一个字典：{"name": 工具名, "args": 参数字典, "id": 本次调用的编号}。
  • ToolMessage：工具的执行结果。最关键的一点是 tool_call_id 必须和那次 tool_call 的 id 一模一样，模型才能把“结果”对应回“它刚才调的那一次工具”。id 对不上会报错——这是你 10 月 29 日小考第 3 题答对过的点：漏回填 ToolMessage，下一步调用会因 tool_call 未配对而报错。

还有一个容易忽略的细节：模型本轮的 AIMessage 本身也要追加进 history，下一轮模型才能看到它自己刚才调了什么工具。不追加，模型就等于失忆，会反复调同一个工具。

3. 一轮可以调多个工具

模型一轮的 tool_calls 是个列表，不是单个。所以执行那一步是 for 循环：逐个执行、逐个回填。你的 run_agent 里就是这么写的——result.tool_calls 累计的是执行次数，不是轮数。

4. 三条底线：工具报错不崩、未知工具不崩、死循环有上限

这是脚手架离线测试 3/3 PASS 验证过的三条线，也是面试时最能体现工程意识的地方：

  • 工具执行抛异常 → 转成 ToolMessage 发回给模型，让模型自己纠错或换工具，而不是让整个循环崩掉。工具的输入永远不可信，模型给的参数也要当成不可信输入处理。
  • 工具名不在列表里 → 同样回一条“未知工具”的 ToolMessage，继续循环，不崩。
  • 模型一直调工具 → 步数上限兜底。max_steps 跑满后返回 status="max_steps"，而不是报错，更不是死循环。调用方看到这个状态就知道是“被上限拦住了”，而不是“模型坏了”，可以据此决定是否继续追问、换策略，或者把已走过的轨迹拿去复盘。
容易踩的坑：把 history 直接传给循环、让循环在上面追加。你的 run_agent 里第一句就是 history = list(messages)——复制一份再追加，避免污染调用方的数据。另一个坑：把模型调用失败也当成普通异常往外抛；正确做法是返回 status="error" 并保留轨迹，复盘时才有东西可看。

5. 手写循环 vs AgentExecutor，选哪个

AgentExecutor 是 LangChain 封装好的黑盒：传 llm、tools、prompt 就能跑，省事，但中间每一步发生了什么、失败时卡在哪一步，你看不见。手写循环的价值恰恰是“每一步都看得见”：面试能口述流程，出问题能定位到某一步，步数、Token、工具调用次数都能自己记进日志（你的脚手架就有 runs/log.jsonl）。结论和 Day 3 的小考结论一致：单步简单调用不用框架，反复调工具才需要循环，流程分支与人工确认才上 LangGraph——Day 7 会讲后者。

二、代码示例

示例 1：循环骨架（就是 loop.py 的 run_agent，注释精简版）

from langchain_core.messages import AIMessage, HumanMessage, ToolMessage

def run_agent(llm, tools, messages, max_steps: int = 5):
    tools_by_name = {t.name: t for t in tools}
    llm_with_tools = llm.bind_tools(tools)  # ① 绑工具
    history = list(messages)  # 复制一份，不污染调用方

    for step in range(1, max_steps + 1):
        response = llm_with_tools.invoke(history)  # ② 模型决策
        history.append(response)  # 模型自己的回复也要追加

        calls = getattr(response, "tool_calls", None) or []
        if not calls:  # 没有 tool_calls = 模型给出最终答案
            return {"status": "done", "final_text": response.content}

        for call in calls:  # ③ 一轮可能调多个工具，逐个执行
            func = tools_by_name.get(call.get("name", ""))
            if func is None:
                history.append(ToolMessage(
                    content=f"未知工具: {call.get('name', '')}",
                    tool_call_id=call.get("id", "")))
                continue
            try:
                output = func.invoke(call.get("args", {}) or {})
            except Exception as exc:
                output = f"工具执行失败: {exc}"  # 工具报错不崩，转成消息回填
            # ④ 结果回填：tool_call_id 必须和这次调用的 id 一致
            history.append(ToolMessage(content=str(output),
                                       tool_call_id=call.get("id", "")))
    return {"status": "max_steps"}  # 跑满上限，不是报错

三、小测验（点选项判分，答完点解析）

得分：0 / 6

1. bind_tools 是干嘛的？

解析：选 B。不绑，模型只能输出文本，循环根本启动不了。

2. 模型怎么告诉循环“我要调工具”？

解析：选 A。模型只决策、不执行；执行是循环里按 tool_call 逐个做的。

3. ToolMessage 的 tool_call_id 写错了会怎样？

解析：选 C。id 配对是硬约束，不是可选项——这也是小考第 3 题的考点。

4. 工具执行抛了异常，循环应该？

解析：选 B。工具报错是模型的纠错输入，不是崩溃理由——离线测试第 2 条就是这条线。

5. 模型一直调工具停不下来，循环怎么兜底？

解析：选 A。max_steps 不是报错，是明确的状态：调用方知道是“被上限拦住了”，而不是“模型坏了”。

6. 手写循环相比 AgentExecutor 最大的好处是？

解析：选 C。省事选黑盒，要讲清楚、要排障、要记日志时，手写循环才拿得出手。

四、可能的面试题与答案

Q1：口述一遍 Tool Calling 循环的完整流程。

绑工具 → 把完整 history 发给模型 → 模型回 AIMessage：带 tool_calls 就逐个执行工具、把结果包成 ToolMessage（tool_call_id 必须配对）追加回 history，再调模型；没有 tool_calls 就是最终答案，收尾。跑满 max_steps 返回 max_steps 状态，保留轨迹。

Q2：为什么模型自己的 AIMessage 也要追加进 history？

不追加，下一轮模型就看不到自己刚才调了什么工具，等于失忆，会反复调同一个工具。history 必须是完整轨迹：用户问题、模型决策、工具结果，一步都不能少。

Q3：工具结果回填时，id 配对错了会发生什么？怎么排障？

模型无法把结果对应回那次调用，下一步会因 tool_call 未配对而报错。排障时先看轨迹：每条 ToolMessage 的 tool_call_id 是否和上一条 AIMessage 里对应 tool_call 的 id 一致，错一位都不行。

Q4：工具报错、未知工具、模型调用失败，三者的处理有什么区别？

前两者都转成 ToolMessage 回填，让模型自己纠错，循环不崩；模型调用失败是循环本身的问题，返回 status="error" 并保留轨迹，不伪装成工具结果。区分“工具层面的失败”和“循环层面的失败”，是这段代码最值得讲的设计。

Q5：什么时候用手写循环，什么时候用 AgentExecutor / LangGraph？

单步简单调用不用框架；反复调工具、要讲清流程、要记日志排障时用手写循环；流程出现分支、要人工确认、要状态管理时上 LangGraph。选型看的是“流程复杂度”，不是“工具新旧”。

五、加分项

生产视角：步数、工具调用次数、Token 用量、max_steps 触发率都要进日志和监控；max_steps 频繁触发往往意味着提示词没给模型“收尾”的信号，或者工具设计让模型走进了死胡同——先查提示词和工具描述，再调上限。

简历讲法：别写“会用 AgentExecutor”，写“手写 Tool Calling 循环：bind_tools 决策、ToolMessage 按 id 回填、工具异常与未知工具转消息不崩、max_steps 兜底并保留轨迹，离线 Fake 模型测试 3/3 通过”。前者是名词，后者是可验证的工程。
