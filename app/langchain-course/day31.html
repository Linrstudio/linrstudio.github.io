Day 31：Multi-Agent 协作总览：Supervisor 模式

第 5 周的第一课，先把 Multi-Agent 的总图讲清：一个任务不再由一个 Agent 从头做到尾，而是由一个 Supervisor（主管）分发给多个子 Agent，各自做完再汇总。单 Agent 是“一个人干全活”，Multi-Agent 是“一个团队分工干活”，团队的好处是能并行、能各用所长，代价是通信、汇总和失败处理都变复杂了。

一、核心解释

1. 为什么要多个 Agent：单 Agent 的三块天花板

第一，上下文天花板：一个 Agent 要同时记住规划、检索结果、工具输出、校验意见，上下文越长越容易顾此失彼；分工后，每个子 Agent 只看自己那部分，上下文反而变干净了。第二，能力天花板：检索、执行、校验是三种不同的活，一个提示词很难同时把三件事都做到最好，分开写提示词、分开配工具，各自才能调优。第三，并行天花板：单 Agent 只能一步一步来，多个子 Agent 可以同时动手，总耗时从“各步相加”变成“最慢的那步”。

2. Supervisor 模式：一张图，主管 + 子图

Supervisor 是图的中心节点：它收到任务，先判断该派给谁；子 Agent 做完，把结果写回共享状态；Supervisor 再判断是继续派、打回重做，还是收口汇总。子 Agent 本身也可以是一张小图（比如 Knowledge 子 Agent 内部就是检索循环），这就是“图里套图”。主管不直接干活，只做三件事：分发、判断、汇总——主管一旦开始自己动手查资料、自己写答案，分工就乱了。

3. 子 Agent 怎么通信：三种方式，各有适用场景

方式做法适合
共享状态所有子 Agent 读写同一份状态：任务、步骤、每步结果、校验意见大多数场景，复盘时能看到全过程
消息传递子 Agent 只把消息追加到消息列表，不直接改别人的字段对话式协作、需要留完整对话记录时
显式交接交接时写清“交给谁、为什么是它、带上哪些结果”关键节点交接，出问题时能定位责任

实操建议是三者混用：状态是底座，消息是过程记录，关键交接必须显式写清。只靠口头传话（让模型自己决定把什么传给下一个），出问题时根本查不清是哪一步丢了信息。

4. 并行与串行、失败隔离：团队协作的两条底线

没有依赖的步骤可以并行，有依赖的必须串行：先检索再生成、先执行再校验，并行跑会读到没出来的结果。并行的上限也要设——同时跑十个子 Agent，成本和限流都会炸，通常并行度设 3–5 个就够了。失败隔离是另一条底线：某一路子 Agent 挂了（工具超时、检索为空、校验不过），Supervisor 只重试那一路，不重跑整张图；重试超过上限（通常 2–3 次），就把失败写进结果、继续走别的路，而不是让整个任务崩掉。

容易踩的坑：为了“多 Agent”而多 Agent。任务本身一步就能做完，硬拆成五个子 Agent，只会多出通信成本和出错点。判断标准是：拆开后，每一路是不是真的有独立的输入、独立的工具、独立的验收标准？三项缺两项，就别拆。

二、代码示例

示例 1：Supervisor 图的骨架（概念代码，先看形状）

# 共享状态：任务、步骤、每步结果、校验意见，都写在这里，不靠口头传话
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages

class TeamState(TypedDict):
    task: str                    # 原始任务
    messages: Annotated[list, add_messages]  # 过程消息，各子 Agent 追加
    results: dict                # 每路子 Agent 的结果，键是子 Agent 名
    next_agent: str              # Supervisor 显式写清：下一步交给谁

def supervisor(state):
    # 主管只做分发、判断、汇总，不直接查资料、不直接写答案
    if all_done(state["results"]):
        return {"next_agent": "composer"}   # 收口
    return {"next_agent": pick_next(state)}  # 派给最缺的那一路

# 子 Agent 是节点，也可以是子图；Verifier 不过就打回对应节点，不重跑全图
graph = StateGraph(TeamState)
graph.add_node("supervisor", supervisor)
graph.add_node("planner", planner_node)
graph.add_node("knowledge", knowledge_node)
graph.add_node("tool", tool_node)
graph.add_node("verifier", verifier_node)
graph.add_node("composer", composer_node)
graph.set_entry_point("supervisor")
graph.add_edge("composer", END)

示例 2：并行与失败隔离的写法（概念代码）

# 没有依赖的两路并行跑，有依赖的两步必须串行
PARALLEL_LIMIT = 3   # 并行上限，防成本和限流炸掉
MAX_RETRY = 2        # 某一路重试上限，超了就写失败、不重跑全图

def run_team(task):
    results = run_parallel(["knowledge", "tool"], limit=PARALLEL_LIMIT)
    # 失败隔离：只重试失败的那一路，成功的不重跑
    for name, res in results.items():
        if res.failed and res.retries < MAX_RETRY:
            results[name] = retry_only(name)
        elif res.failed:
            results[name] = {"failed": True, "reason": res.reason}  # 写进结果，继续走
    return compose(results)

四、可能的面试题与答案

Q1：什么是 Supervisor 模式？

一张图里主管加子图：Supervisor 收到任务先判断派给谁，子 Agent 做完把结果写回共享状态，Supervisor 再判断是继续派、打回重做，还是收口汇总。主管只做分发、判断、汇总，不直接干活。

Q2：子 Agent 之间怎么通信？

三种方式混用：共享状态做底座，所有结果、校验意见都写进状态；消息传递留过程记录；关键交接必须显式写清交给谁、为什么是它、带上哪些结果。只靠口头传话，出问题查不清。

Q3：并行和串行怎么定？

看依赖：没有依赖的步骤并行，有依赖的必须串行，先检索再生成、先执行再校验。并行度设上限，通常 3–5 个，防成本和限流。

Q4：失败隔离怎么做？

某一路挂了，只重试那一路，不重跑全图；重试超过 2–3 次，就把失败和原因写进结果、继续走别的路，最终回答里写清哪段失败了，不要填空。

Q5：单 Agent 和 Multi-Agent 怎么选？

看三项：拆开后每路是不是有独立的输入、独立的工具、独立的验收标准？三项基本都满足就拆，缺两项就别拆；任务一步能做完，硬拆只多成本和出错点。

五、加分项

生产视角：Multi-Agent 上线前，先问三个问题：主管的判断逻辑写死了吗（不能全靠模型临场发挥）？失败隔离和重试上限设了吗？共享状态里能不能复盘全过程？三问有一个答不上来，多 Agent 就别上。

简历讲法：别写“做过 Multi-Agent”，写“Supervisor 分发、子 Agent 并行、共享状态复盘、失败隔离只重试失败路，重试上限 2 次”。前者是名词，后者是可追问的设计。
