Day 15：RAG 全链路：一张图讲清切分、向量、检索、生成

第 3 周的第一课，先把 RAG 的整条链路讲清，再拆开讲每一步：模型不知道答案时，不要让它现编，而是先去你的文档里找，再带着找到的东西回答。

一、核心解释

1. 一张图：RAG 的五步

离线（索引时做一次）：
文档 → 解析 → 切块 → Embedding 向量化 → 存进向量库

在线（每次提问都走）：
用户问题 → 向量化 → 在向量库里召回 Top 50 → 重排留 Top 5 → 把 Top 5 拼进提示词 → 模型生成回答
（回答要带引用：答案出自哪几块，写清楚）

RAG 的核心思想只有一句：生成之前先检索。模型本身的知识是训练时定型的、会过期、还会编造；你的文档是现成的、可更新的、可溯源的。检索把“模型不知道”变成“模型面前有资料”，幻觉就少了一大半。

2. RAG 和微调，什么时候选哪个

RAG微调
适合知识会变、要溯源、要引用出处要改风格、改格式、改行为习惯
成本低：建索引就行，不用训练高：要数据、要算力、要评测
更新文档一改，索引一更就生效知识一变就要重新训

面试时这句很关键：知识问题用 RAG，行为问题用微调。把知识问题拿去微调，又贵又难更新；把行为问题拿去 RAG，检索再准也改不了模型的说话方式。

3. 五步里，哪一步最容易背锅

新手一出问题就怪模型，其实 RAG 出问题时，第一嫌疑永远是检索：切块切碎了语义、Embedding 选错了模型、TopK 太小漏了关键块、拼进提示词时没带出处。Day 16 到 Day 19 就是按这个顺序，把每一步的坑逐个讲透：切块、向量、检索、评测。

4. 重排：召回和生成之间的第二道关

向量检索是召回，它只负责“别漏”，不负责“排准”：问题和文档各编一次向量、再算余弦相似度，快，但它看不到问题和文档之间的细交互，Top 50 里混进不少“看起来像、其实答不上”的块。重排（Rerank）就是在召回和生成之间再加一段：把问题和每个候选块拼在一起，交给一个 Cross-Encoder 模型直接打一个相关性分，按分重排，只留 Top 5–10 进提示词。所以全链路其实是五步：切块 → 向量化 → 召回 Top 50 → 重排留 Top 5 → 生成。

重排特别需要掌握的四点：一、两段式是铁律，召回取 20–100 个、重排后留 5–10 个，再加一个分数下限过滤噪声；重排模型慢，绝不能对全库重排，留太多进提示词也会稀释注意力。二、分清两种编码器：双编码器（Bi-Encoder）各编各的、算相似度，负责召回；交叉编码器（Cross-Encoder）问题加文档一起进模型、直接打分，负责重排，准但慢。三、选型有默认答案：自部署默认 bge-reranker-v2-m3（568M 参数、100+ 语言、Apache 2.0，CPU 也能跑）；有 GPU、要更高精度就用 Qwen3-Reranker-4B（0.6B/4B/8B 三档，32K 上下文）；不想运维就用 Cohere、Voyage 的托管重排 API。四、要会评测：重排有没有用，看 nDCG@10 和命中率有没有涨，不要只凭感觉——同一批问题，先跑“只召回”、再跑“召回加后重排”，两个数一对比就知道。nDCG@10 是什么？→ 文末知识点补充

5. Embedding 模型怎么选：中文主流是哪个

Embedding 模型就是把文本变成向量的模型，问题和文档必须用同一个模型编，否则向量不在同一个空间里、没法比。选它看四个数：维度（向量多长，换模型要全库重建索引）、上下文长度（一块最多多少 Token）、语言（中文强不强）、能不能本地部署（数据能不能出境）。

中文场景当前的主流就两个，都开源、可本地部署：Qwen3-Embedding（阿里通义，2025 年 6 月发布）是现在中文精度最高的默认选择，0.6B/4B/8B 三档，8B 在 MTEB 多语言榜上 70.58 分，32K 上下文，Apache 2.0 协议；起步用 0.6B（1024 维、又快又轻），要上限再上 4B/8B。BGE-M3（北京智源研究院 BAAI）是中文社区的老牌默认，568M 参数、1024 维、8192 Token、MIT 协议，一个模型同时支持稠密向量、稀疏向量、ColBERT 式多向量三种检索，100+ 语言，中英文混排、混合检索首选它。更早的 bge-large-zh-v1.5（中文经典，1024 维）现在更多是“稳定够用”的老选择，新项目一般在上面两个里挑。

选型口诀：纯中文 → Qwen3-Embedding（0.6B 起步）；中英文混排或要混合检索 → BGE-M3；数据不能出境 → 两个都开源可本地部署，别用纯 API 模型；最后一定在自己的数据上做 A/B——榜单分是参考，自己的问题、自己的文档上跑一遍命中率，才算数。Day 16 会再讲一次 Embedding 选型，Day 18 会把重排的代码和评测讲透。

6. 和第 2 周的关系：检索是同一套思路，对象换了

Day 9 讲代码检索，查的是函数、调用关系；这里查的是文档段落，查的是语义。思路一样，都是“先查、再答”，但代码检索更看重精确名字，向量只是补充；文档检索更看重语义，关键词只是补充。主次是反的，别把 Day 9 的结论原样搬过来。

7. 第 0 步：解析——格式不一样，解析方法也不一样

五步图从“切块”开始，但真实文档不是纯文本：docx、csv、html、pdf 都要先解析成带结构的纯文本，再切块。解析是第 0 步，不算在五步里，但跳过它，后面全是错的。

格式怎么解析注意点
docxpython-docx 读段落 + 表格（LangChain 有 Docx2txtLoader）表格要转成行文本；标题层级要留着，切分按标题切要用
csv按行读，每行是一条记录（CSVLoader）表头当字段名；长文本列单独成块；别把整张表当一块
html去标签留正文（BeautifulSoup / BSHTMLLoader）导航栏、页脚、广告是噪音要去掉；h1–h3 标题层级保留
pdfpypdf / PyPDFLoader 按页抽文本扫描版是图片要 OCR；双栏排版会串行

原则就一句：解析时保留结构和元数据。结构是标题、表格；元数据是文件名、页码、行号。Day 17 的引用和过滤全靠解析时留下的元数据——解析丢了结构，后面切分和引用都补不回来。

容易踩的坑：RAG 不是“把文档全塞给模型”。全塞进去，Token 爆了不说，模型还会在无关段落里找答案，越找越偏。正确姿势永远是：检索给短名单，模型只看名单里的块。

二、代码示例

示例 1：全链路骨架（概念代码，先看形状，不接真实模型）

# 离线：建索引（做一次）
chunks = split_documents(docs)          # Day 16：切块
vectors = embed(chunks)                 # Day 16：Embedding
store = VectorStore(vectors, chunks)    # Day 17：存进向量库

# 在线：问答（每次提问都走）
def answer(question):
    q_vec = embed([question])[0]
    topk = store.search(q_vec, top_k=5) # Day 17：检索
    topk = rerank(question, topk)       # Day 18：重排
    prompt = build_prompt(question, topk)  # 拼进提示词，带出处
    return llm.invoke(prompt)           # 生成，回答要带引用

示例 3：解析的形状——每种格式都变成（纯文本，元数据）（概念代码，先看形状）

# 解析只做两件事：抽正文、留元数据（来源、页码、行号）
def parse_docx(path):
    from docx import Document   # 需安装 python-docx
    doc = Document(path)
    text = "\n".join(p.text for p in doc.paragraphs)
    return text, {"source": path, "format": "docx"}

def parse_csv(path):
    import csv   # 标准库，不用装
    rows = []
    with open(path, encoding="utf-8") as f:
        for row in csv.DictReader(f):   # 表头当字段名
            rows.append(" | ".join(f"{k}:{v}" for k, v in row.items()))
    return "\n".join(rows), {"source": path, "format": "csv"}

四、可能的面试题与答案

Q1：RAG 是什么？一句话讲清。

生成之前先检索：把用户问题向量化，在向量库里找最相关的文档块，拼进提示词再让模型生成，回答带引用。离线建索引，在线检索加生成。

Q2：RAG 和微调怎么选？

知识问题用 RAG：知识会变、要溯源、要引用；行为问题用微调：改风格、改格式、改行为习惯。把知识问题拿去微调，又贵又难更新；把行为问题拿去 RAG，检索再准也改不了说话方式。

Q3：RAG 回答错了，你先查哪？

先查检索：切块是不是切碎了语义、Embedding 是不是选错了、TopK 是不是太小漏了关键块、拼提示词时有没有带出处。先查检索链路，再查模型和提示词，不要一上来就怪模型。

Q4：RAG 和第 2 周的代码检索，是一回事吗？

思路一样，都是先查再答，但对象和主次是反的：代码检索更看重精确名字，向量只是补充；文档检索更看重语义，关键词只是补充。

Q5：第 3 周结束时，你能拿出什么？

一个带评测的 RAG 加一个深圳天气 Agent：文档切块、向量检索、重排引用、防幻觉、评测集、工具路由、混合问答，全部能讲清、能演示、能报数字。

知识点补充：nDCG@10 是什么

nDCG@10 是给检索排序打分的指标，拆开念就明白了：DCG 是“打折后的累计收益”，n 是“归一化”，@10 是“只看前 10 个”。它要解决的问题是：命中率只能回答“相关文档在不在名单里”，回答不了“它排在第几”——而 RAG 里排第 1 和排第 10 差别很大，模型先看前面的，排后面的可能根本进不了提示词。

第一步，先给每个结果打相关度分。评测集里每块文档对这个问题都有个等级，比如 0 是不相关，1 是有点相关，2 是相关，3 是高度相关（就是能直接用来回答的那块）。这个分是人事先标好的，不是模型自己打的。

第二步，算 DCG，位置越靠后，分打折越多。第 i 位的收益是 (2^相关度 − 1)，折扣是 log₂(i+1)：相关度 3 的收益是 7，相关度 2 是 3，相关度 1 是 1，相关度 0 是 0；第 1 位除以 1，第 2 位除以约 1.58，第 3 位除以 2，第 10 位除以约 3.46。同样一块高度相关的文档，放第 1 位贡献 7 分，放第 10 位只贡献约 2 分。

举个具体数：假设返回的前 5 个相关度是 [3, 0, 2, 0, 1]，DCG = 7/1 + 0 + 3/2 + 0 + 1/2.58 ≈ 8.89。如果把这 5 块按相关度从高到低排成最理想的顺序 [3, 2, 1, 0, 0]，DCG 是 7 + 3/1.58 + 1/2 ≈ 9.39，这就是 IDCG（理想情况下的 DCG）。

第三步，归一化。nDCG = DCG / IDCG，上面这个例子就是 8.89 / 9.39 ≈ 0.95。归一化之后分永远在 0 到 1 之间，1 就是完美排序，这样不同问题之间才能比。@10 的意思就是只算前 10 个，第 11 个及以后不算分——召回和重排后一般只留 5–10 块给模型，排在 10 名开外的结果对回答基本没影响。

用的时候记住两个坑：nDCG 的好坏完全取决于相关度标得准不准，标错了，分再高也没用；别拿不同数据集上的 nDCG 直接比大小，它只适合在同一套评测集上比较“改动前和改动后”。
