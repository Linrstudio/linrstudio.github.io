Day 25：演示任务：多步闭环与按钮位置变化的兜底 | LangChain 30 天实战课

会点鼠标只是开始，能把一个多步任务从头做到尾、做对了才算数。这课拿一个最常见的演示任务练手：打开测试页，填表单，提交，截图确认结果。四步里任何一步都可能出岔子——页面没加载完、按钮挪了位置、提交后没反应。Agent 的本事不在“执行了”，而在“每步都验收、错了会兜底、兜不住会报错”。

一、核心解释

1. 演示任务：四步闭环，每步都要验收

任务是四步：打开页面 → 填表单 → 提交 → 截图确认结果。关键在箭头回来的那一步：每步做完都要验收，验收过了才走下一步。打开页面，验收是“表单真的出现了”；填表单，验收是“填进去的值和要填的一致”；提交，验收是“提交成功的结果出现了”；最后截图确认，是把结果留下来当证据。没有验收的执行，只是“看着像做完了”。

2. 验收怎么做：不要只看“执行了”，要看“结果对了”

新手最容易写的验收是“这步跑完了，没报错”。但“没报错”不等于“做对了”：点击了提交按钮，按钮可能根本没反应；填了表单，值可能填进了错误的框。好的验收看的是结果状态，不是执行动作。打开页面后，等表单元素出现再往下走；填完后，把框里的值读出来，和要填的值比对；提交后，等“提交成功”那行字出现，截图存证。验收要写成能返回“通过 / 不通过”的检查，而不是一句“跑完了”。验收失败时，也别急着重试——先看失败截图，分清是“页面还没加载完”（等一等就能好）还是“真的错了”（重试也没用）。

3. 按钮位置变化的 case：重试定位，还是直接失败？

最常见的翻车是：昨天按钮还在 (500, 300)，今天窗口一变、页面一改，按钮挪到 (500, 380) 了。按老坐标点下去，点的可能是空白，也可能是别的按钮。这时候 Agent 面临选择：重试定位，还是直接失败？答案是：先重试定位，但重试要有章法、有上限。无章法的重试是“同一个坐标连点三次”，点三次错的还是错的；有章法的重试是“换一种定位方式再找一次”。重试超过上限（通常 2–3 次），就直接失败、报错停下——不要静默继续，更不要猜着点。猜着点下去，点中删除按钮的代价，比任务失败大得多。

4. 兜底策略：多定位器降级、相对定位、失败截图 + 报错

定位不准时的兜底有三招，按顺序用：

兜底做法什么时候用
多定位器依次降级先用最稳的找：role（按钮角色）→ text（按钮文字）→ test-id（测试标识）→ 坐标，一个找不到就换下一个定位方式失效时，先换方式，不换坐标
相对定位找一个位置稳定的元素当锚点（比如表单标题），再按“锚点下方 80 像素”去找目标目标本身会动，但它和锚点的相对位置不变时
失败截图 + 报错兜底都失败了，截图保存当前屏幕，报错停下，不静默继续、不猜着点所有定位方式都失效时，最后的防线

顺序不能乱：先降级换方式，再相对定位找，最后截图报错。直接跳到“猜坐标点一下试试”，就是把一次定位失败变成一次误操作。记住一条红线：定位不准时，宁可任务失败，也不要猜着点——失败可以重跑，点错了可能要人来收拾。

容易踩的坑：验收只写“没报错就通过”，定位只用一套坐标。演示时页面固定、网络顺畅，两处都看不出问题；一到真实页面，加载慢半秒、按钮挪几个像素，任务就悄悄“做完了”——结果全是错的。验收看结果状态，定位留降级余地，这两条要在演示任务里就养成。

二、代码示例

示例 1：四步闭环的骨架，每步带验收（概念代码，先看形状）

# 每步 = 执行 + 验收；验收不过就停，不走到下一步
from playwright.sync_api import sync_playwright, expect

def run_demo():
    with sync_playwright() as p:
        page = p.chromium.launch().new_page()
        # 第 1 步：打开页面，验收是表单真的出现了
        page.goto("https://example.com/form")
        expect(page.locator("#name")).to_be_visible()
        # 第 2 步：填表单，验收是框里的值和要填的一致
        page.fill("#name", "Arale")
        assert page.input_value("#name") == "Arale", "填进去的值不对"
        # 第 3 步：提交，验收是成功提示出现了
        page.click("text=提交")
        expect(page.locator("text=提交成功")).to_be_visible()
        # 第 4 步：截图确认结果，留作证据
        page.screenshot(path="result.png")
        print("四步都通过，结果已截图")

示例 2：多定位器依次降级（概念代码，先看形状）

# 定位器按稳定程度排队：role → text → test-id → 坐标，依次降级
def find_submit(page):
    locators = [
        page.get_by_role("button", name="提交"),  # 最稳：按角色和名字找
        page.get_by_text("提交"),                  # 其次：按文字找
        page.get_by_test_id("submit-btn"),        # 再其次：按测试标识找
    ]
    for loc in locators:
        if loc.count() > 0:        # 找到了就用它，不再往下试
            return loc
    # 都找不到才退到坐标，且坐标是最后手段、要打日志
    print("警告：定位器全部失效，退到坐标定位")
    return None

submit = find_submit(page)
if submit is None:
    page.screenshot(path="locate_failed.png")
    raise SystemExit("提交按钮定位失败，截图已存 locate_failed.png")

示例 3：相对定位 + 失败截图（概念代码，先看形状）

# 相对定位：以稳定的表单标题为锚点，目标在锚点下方找
anchor = page.get_by_text("报名表单")   # 锚点：位置稳定、不常改
box = anchor.bounding_box()            # 锚点的坐标和大小
if box is None:
    page.screenshot(path="anchor_failed.png")
    raise SystemExit("锚点没找到，截图已存 anchor_failed.png")

# 目标在锚点下方约 80 像素处找，不用死记绝对坐标
target = page.locator("button").nth(0)
target_box = target.bounding_box()
if target_box is None or abs(target_box["y"] - (box["y"] + 80)) > 120:
    # 目标离锚点太远：要么找错了，要么页面变了，停下不猜
    page.screenshot(path="relative_failed.png")
    raise SystemExit("相对位置对不上，截图已存 relative_failed.png")
target.click()

动手任务（10 分钟）

1. 拿任意一个有表单的测试页，照示例 1 写四步闭环：把每步的验收条件写出来（比如“提交后哪行字必须出现”），再故意把其中一步的验收写错，看它能不能拦住你。
2. 把示例 2 的定位器顺序换成“坐标优先”，想一想：页面一改版，第一个挂掉的是哪一步？
3. 模拟按钮挪位：把提交按钮的定位器全删掉，只留坐标，跑一次，看失败截图 + 报错那条路是不是真的走了。

四、可能的面试题与答案

Q1：屏幕元素定位不准时，你有哪些兜底策略？

三招按顺序用：多定位器依次降级，先 role 再 text 再 test-id，最后才退到坐标；相对定位，找位置稳定的元素当锚点，按锚点的相对位置去找目标；兜底都失败就截图保存、报错停下，不静默继续、不猜着点。重试要有上限，通常 2–3 次，超了就直接失败。

Q2：多步任务里，验收应该怎么写？

验收看结果状态，不看执行动作：打开页面看表单出现了没有，填完把框里的值读出来比对，提交后等成功提示出现，最后截图存证。每步验收不过就停，不走到下一步；验收要能返回通过 / 不通过，而不是一句“跑完了”。

Q3：按钮位置变化时，重试定位还是直接失败？

先有章法地重试，再失败：换一种定位方式再找，而不是同一个坐标连点三次；重试超过 2–3 次就直接失败、报错停下。不要静默继续，更不要猜着点——猜中删除按钮的代价比任务失败大得多。

Q4：相对定位和绝对坐标定位，各适合什么情况？

绝对坐标只适合页面完全不动的演示；目标会动、但和锚点的相对位置不变时，用相对定位——先找稳定的锚点（比如表单标题），再按“锚点下方多少像素”去找目标。坐标是最后手段，不是第一选择。

Q5：一个演示任务跑通了，怎么证明它是真的跑通了？

四样东西：每步的验收记录（结果状态通过了哪几项）、最后的截图（提交成功的结果在图里）、失败时的截图和报错（兜底那条路走没走）、步数和重试次数（没超过上限）。只有“执行了”的日志，没有验收和截图，不算跑通。

五、加分项

生产视角：演示任务上线前，先问三个问题：每步的验收是不是看结果状态、而不是“没报错”？定位器是不是按 role → text → test-id → 坐标排了降级顺序？兜底失败时，截图 + 报错那条路真的跑通过吗？三问有一个答不上来，多步任务就别上。

简历讲法：别写“做过自动化演示”，写“四步闭环每步结果验收、多定位器 role/text/test-id/坐标依次降级、相对定位锚点、失败截图报错、重试上限 2–3 次”。前者是名词，后者是可追问的设计。
