镜像、容器与应用运行

Docker 核心与实战

12 题 · 从概念到排障

01Docker 镜像与容器到底有什么区别？

口述版可以把镜像理解成应用运行所需的只读模板：它由分层的文件系统和运行所需的元数据组成。容器则是这个模板启动后得到的一个运行实例。容器会在镜像层上再加一层自己的可写层，同时拥有运行中的进程、网络配置和资源限制等状态。容器删除后，可写层里的数据通常也会一起消失，所以需要长期保留的数据，不要只放在容器里，而应使用 volume（Docker 管理的持久化存储）或 bind mount（把宿主机目录挂载进容器）。同一个镜像可以启动多个彼此隔离的容器。面试时还要强调：镜像是可复用的构建产物，容器有自己的运行生命周期；镜像本身不等于正在运行的服务。

记忆要点

  • 镜像是可复用的只读模板，容器是镜像启动后的运行实例；镜像不等于正在运行的服务。
  • 容器有自己的生命周期和可写层；需要保留的状态不要只写进容器可写层，应使用 volume 或 bind mount。
02Dockerfile 里的 RUN、CMD、ENTRYPOINT 到底有什么区别？

口述版可以把它们按时间分开看：RUN 是构建镜像时执行命令的指令，比如安装依赖；每条 RUN 通常会生成一个新的镜像层。CMD 和 ENTRYPOINT 是容器启动时才生效的配置。CMD 提供默认命令或默认参数，启动容器时可以被覆盖；ENTRYPOINT 用来指定容器的主程序，通常不希望被普通启动参数替换，而是让 CMD 作为它的默认参数。实际使用时，应用一般优先写成 JSON exec 形式，让应用直接作为容器进程运行，这样更容易正确接收停止信号。这里的“镜像层”可以理解成镜像构建过程中的一层变更记录，而不是容器启动时才执行的一次命令。

示例与边界

  • ENTRYPOINT ["python","app.py"] 加 CMD ["--port","8000"]：默认相当于运行 python app.py --port 8000；启动容器时提供新的参数，可以替换 CMD 的默认参数。
  • JSON exec 写法会直接启动目标程序；shell 写法会先经过 shell，信号转发和参数处理更容易出问题。确实需要 shell 逻辑时，要注意最后用 exec 替换 shell 进程，让真正的应用接收停止信号。
  • CMD 的默认命令或参数可以在启动容器时覆盖；ENTRYPOINT 通常作为固定入口，但也可以通过 Docker 的 --entrypoint 显式改掉。
03只写 EXPOSE，宿主机能访问容器端口吗？EXPOSE 和端口映射有什么区别？

口述版EXPOSE 可以理解为镜像里写的一条“端口说明”：它记录应用预计使用哪个容器端口，但只是元数据，不会自动把这个端口发布到宿主机。所以只写 EXPOSE 80，宿主机通常不能直接通过宿主机端口访问。运行容器时还要配置端口映射，例如 -p 8080:80，意思是把宿主机的 8080 端口转到容器的 80 端口。另外，如果多个容器接入同一个 Docker 网络，它们通常可以直接用服务名访问对方的容器端口，不需要为了容器间通信再发布宿主机端口。

记忆要点

  • EXPOSE 80 不等于 -p 8080:80：前者是端口说明，后者才是运行时的宿主机到容器端口映射。
  • 检查映射关系可以看 docker ps 或执行 docker port；同时要确认应用确实监听映射的容器端口，否则即使映射存在也访问不到。
04Docker 容器里的服务为什么通常要监听 0.0.0.0，而不能只监听 localhost？

口述版localhost（通常就是 127.0.0.1）表示“只接受当前网络环境自己的连接”；在 Docker 里，它指的是当前容器自己的回环接口，也就是容器内部的自通信地址。如果服务只绑定在这里，来自容器网络接口的请求通常无法到达它，所以即使宿主机做了端口映射也没有用。需要接收容器外部连接时，一般绑定 0.0.0.0，它的意思是监听容器的所有网络接口。不过，这只决定服务在哪些接口上接收连接，不等于把服务公开到公网；还要通过端口映射、防火墙或网络策略限制谁能访问。

记忆要点

  • 绑定地址和端口映射是两个不同环节，不能互相替代：前者决定服务监听哪些网络接口，后者决定外部端口是否转发到容器。
  • 不要把“监听所有接口”误解成“应该向公网开放”；服务的实际暴露范围还要单独限制。
05容器里的服务访问不到，应该按什么顺序排查？

口述版我会沿着请求链路一层层排查，不会一上来就重建容器。先确认容器这个隔离运行环境是否还在运行，应用进程是否正常；再检查应用监听的地址和端口，尤其要确认它是不是只监听了容器内的 127.0.0.1，而不是能接受外部连接的地址。接着在容器内部用 curl http://127.0.0.1:端口 访问本机服务，并查看日志和健康状态。容器内部能访问后，再核对端口映射，例如 -p 宿主机端口:容器端口，以及宿主机防火墙和云安全组。若是容器之间调用，还要确认双方是否接入同一个 Docker 网络、服务名能否解析，以及调用的目标端口是否正确。这样可以把应用没启动、监听地址不对、端口映射错误和网络隔离区分开。

排查顺序

  • docker ps -a 看容器是否退出，docker logs 看应用输出，docker inspect 查看容器配置和 health 状态；health 状态是容器配置的健康检查结果，不等于端口一定能从外部访问。
  • 按“进程与监听地址 → 容器内访问 → 端口映射 → 防火墙 / 云安全组 → Docker 网络与 DNS”的顺序排查。
  • Dockerfile 里的 EXPOSE 只是声明容器可能使用的端口，不会自动把端口发布到宿主机；是否能从外部访问，还要看实际的端口映射和网络策略。
06Docker Compose 里，应用为什么要用 Redis 的服务名连接，而不是 localhost？

口述版在 Docker Compose 里，多个服务通常会加入同一个共享网络，也就是容器之间用来互相通信的内部网络。应用容器连接 Redis 时，通常写 redis:6379：这里的 redis 是 Compose 配置中的服务名，Compose 会把它当作容器网络内的 DNS 名称；可以把它类比成内部通讯录里的名字，但它不是宿主机地址。localhost 在应用容器里指向应用容器自己，不是 Redis 容器，所以通常不对。只有应用进程和 Redis 确实运行在同一个容器里时，localhost 才可能指向 Redis。Redis 是否要发布端口到宿主机，要看是否需要从宿主机直接访问；应用容器之间通过服务名通信时，不一定要发布这个端口。

补充

  • 确认应用和 Redis 使用相同的 Compose project 或 network，并核对端口、密码、TLS 等连接配置。
  • 服务名解决的是容器网络内部寻址；宿主机端口映射解决的是宿主机访问容器，二者不能互相替代。
07Docker 的可写层、named volume 和 bind mount，应该怎么选？

口述版先看数据要不要跟着容器一直保留：容器可写层，就是容器运行时在镜像之上临时产生的修改层；容器删掉后它也会消失，所以不适合存必须保留的数据。Named volume（命名卷）由 Docker 管理实际存储位置，适合数据库文件等需要持久化的数据，环境之间也比直接依赖主机路径更容易迁移。Bind mount（绑定挂载）是把宿主机，也就是运行 Docker 的那台机器上的一个明确路径，映射到容器里；它常用于本地开发热更新，或确实需要让容器直接读写主机文件的场景，但会依赖宿主机目录结构和权限。选择时要一起考虑数据生命周期、备份与迁移、权限隔离和环境可移植性。还要注意，挂载到容器里的目录会遮住镜像中该目录原本的内容；这不是删除镜像文件，但容器运行时看不到它们。

记忆要点

  • 生产环境的数据库数据通常使用 named volume 或外部存储，并且必须配套备份和恢复方案；持久化不等于自动备份。
  • bind mount 依赖宿主机路径，适合明确需要共享主机文件的场景；匿名卷没有固定名称，生命周期和是否能被复用要提前确认。
  • docker compose down -v 会删除 Compose 管理的卷，执行前要确认数据后果；不要把它当成无风险的清理命令。
08Compose 的 depends_on 能确保依赖服务已经可用吗？healthcheck 和重试怎么配合？

口述版depends_on 默认主要只负责安排服务的启动顺序，不能证明依赖服务已经初始化完成、可以正常处理请求。healthcheck 可以理解为定期做一次真实可用性检查：不要只看进程有没有活着，还要检查服务是否真的能接受请求。在实际使用的 Compose 语法支持的前提下，可以让依赖关系等待服务进入 healthy 状态。不过，应用自己仍要设置连接超时、有限次数的重试和退避，也就是每次失败后隔一段时间再试，而且等待时间逐步增加，因为服务运行期间仍可能重启或暂时不可达。健康检查解决“服务现在是否可用”，启动顺序解决“先启动谁”，应用重试解决“运行中暂时失败怎么办”；三者是互补关系，不能互相替代。

面试细节

  • healthcheck 要检查真实可用性，例如能否完成一次必要的健康请求，而不只是确认进程还活着。
  • 重试必须设置上限、退避时间和清晰的错误处理；不要无间隔、无限重试，否则可能在依赖故障时形成雪崩。
  • 面试或落地时要确认实际使用的 Compose 版本，以及当前语法是否支持等待 healthy 状态的配置。
09Docker 构建缓存如何复用？为什么必须写好 .dockerignore？

口述版Docker 会把 Dockerfile 的步骤按层保存并尝试复用；只要某一层的输入变了，这一层以及后面的层就可能重新构建。面试里我会这样设计：先复制变化较少的依赖清单，比如 Node 项目的 lockfile 和 package manifest，再安装依赖，最后才复制经常修改的源代码。这样改业务代码时，通常不必每次都重新安装依赖。.dockerignore 可以理解成构建上下文的排除清单：它决定哪些本地文件不发送给 Docker 参与构建。写好它能减少无用文件传输，也能降低把本地文件意外带进去、甚至泄露的风险。

示例与边界

  • Node 项目可以先复制 lockfile 和 package manifest，再执行安装依赖的命令，之后再复制源代码；具体命令要按 npm、pnpm 或 yarn 等包管理器调整。
  • .dockerignore 通常排除 .git、本地依赖目录、构建产物、临时文件和敏感文件，避免它们进入构建上下文。
  • 不要把密钥通过 Dockerfile 的 ARG 或 ENV 烘焙进镜像；如果构建过程确实需要秘密，应使用合适的 secret mount 机制。
10Docker 多阶段构建是什么，解决了什么问题？

口述版Docker 多阶段构建，就是在同一个 Dockerfile 里写多个 FROM 阶段：前面的构建阶段负责安装编译工具、执行测试和生成产物，最后的运行阶段只复制真正需要运行的文件。可以把它类比成前端打包：开发依赖和源码用于构建，但不会全部进入发布包；不过这只是类比，Docker 最终交付的是可运行的镜像。这样能避免把编译器、开发依赖和临时文件带进生产镜像，通常可以缩小镜像，也能减少攻击面。要注意，构建阶段通过不代表最终镜像一定能运行，所以还要用最终镜像启动并做运行测试，确认运行时依赖都在。

记忆要点

  • 要清楚区分 build stage（负责构建和测试的阶段）与 runtime stage（只负责运行程序的阶段）。
  • 从构建阶段拷贝运行产物时，不能漏掉运行时库、配置或证书；镜像即使做得很小，也要保持可维护、可调试。
11docker compose down 和 docker compose down -v 到底会删掉什么？

口述版可以把 Docker Compose 理解成按项目管理一组容器的工具。docker compose down 通常会停止并移除这个项目的容器和网络，但默认不会删除 Compose 文件里声明的 named volume，也就是由 Docker 管理、用来长期保存数据的存储卷；匿名卷默认也不会被自动删除。不过，之后重新创建容器时，匿名卷不一定会自动重新挂回原来的那个卷。加上 -v 后，会删除 Compose 文件声明的 named volume，以及关联的匿名卷；标记为 external 的 volume 不会被这个命令删除。因为卷里可能放着数据库数据，执行 docker compose down -v 前，一定要确认目标项目和其中的数据确实可以丢弃。

记忆要点

  • 只有在需要重置本地数据库等数据时，才考虑 docker compose down -v；不要把它当成没有风险的日常清理命令。
  • 不同 Docker Compose 版本和具体参数可能影响细节；涉及重要数据时，先备份，再核对项目和 volume 名称。
12Docker 停止容器时，PID 1、SIGTERM 和优雅关闭分别做什么？

口述版可以把容器里的 PID 1 理解成这个容器的主进程，也就是容器启动后最先运行、通常负责带着应用工作的进程。执行 docker stop 时，Docker 会先向 PID 1 发送 SIGTERM，它是一种“请尽快结束”的终止信号；如果应用在停止宽限时间内还没退出，Docker 才会发送 SIGKILL，强制结束进程。要做到优雅关闭，应用本身必须处理 SIGTERM：先停止接收新任务，再完成或取消正在处理的工作，刷新必要数据，最后关闭连接并退出。启动命令最好使用 exec 形式，让应用直接成为容器主进程；如果用 shell 包装，信号可能先发给 shell，应用子进程就不一定能按预期收到。容器里如果有多个进程，还要考虑 PID 1 是否负责回收已经结束的子进程，必要时可以使用 init 进程。这里的关键是，Docker 只负责发信号和等待，业务任务能不能安全收尾，仍然取决于应用自己的关闭逻辑。

实践细节

  • Compose 可以配置停止宽限时间，但超时后仍可能进入强制终止，不是无限等待。
  • 注意 shell-form 的 ENTRYPOINT / CMD：它可能让信号先到 shell，导致真正的应用进程处理信号不符合预期；exec 形式通常更容易正确收信号。
  • 优雅关闭需要应用配合。单靠 Docker 的停止配置，不能保证业务任务一定安全完成。

13RAG 从文档入库到回答生成，完整流程是什么？

口述版我会把 RAG（检索增强生成，先从资料库找相关内容，再让模型据此回答）分成离线建库和在线问答两条链路。离线先解析、清洗文档，按语义和长度切块，并给每块保留来源、版本、租户、权限等元数据，也就是描述这段内容从哪里来、属于谁、谁能看。然后把文本转成 embedding（把文字表示成可比较相似度的数字向量），写入向量索引；需要时也同步建立关键词索引。在线收到问题后，先在服务端校验用户身份和数据权限，再做查询理解或改写，召回相关片段；必要时融合关键词检索结果，并用重排进一步调整相关性顺序。接着选择合适的上下文交给模型生成答案，最后返回答案和可追溯的引用。上线后还要结合检索指标、答案质量和线上 trace（记录一次请求经过哪些步骤及结果的链路记录）持续评估。权限必须在服务端检索链路中执行，不能先把用户无权查看的内容取回来，再只靠前端隐藏。

讲清楚的几层

  • 数据摄取与索引：解析、清洗、切块，保存必要元数据，建立向量索引，必要时建立关键词索引。
  • 查询与权限过滤：先理解或改写问题，并在服务端按用户身份、租户和权限过滤数据。
  • 召回、融合和重排：先找出候选片段，可融合向量和关键词结果，再重排相关性。
  • 上下文构造与生成：挑选合适片段组成上下文，交给模型生成回答。
  • 引用、评估和监控：返回可追溯引用，并持续看检索指标、答案质量和线上 trace。
  • 安全边界：权限控制属于服务端检索链路的一部分；前端隐藏无权内容不能替代真正的权限校验。
14RAG 文档分块怎么设计？chunk size 和 overlap 如何取舍？

口述版RAG，也就是先从文档库检索相关内容，再交给模型生成答案。文档分块（chunk）就是把长文切成可检索的小段；我不会机械地按固定字符数切，而会围绕实际检索问题设计。通常优先沿着标题、段落、列表、代码块等自然边界切，并把文档路径、标题、版本等元数据（描述这段内容来源和属性的信息）一起保存到 chunk 上。chunk 太小，可能缺少回答问题所需的上下文；太大，则可能混入多个主题，降低召回的精确度，还会占用更多上下文窗口。overlap 是相邻块之间重复的一小段内容，用来减少边界处的信息被切断；但 overlap 太大，会产生很多重复片段，导致索引变大、检索结果重复。实际项目里，我会用真实问题集比较不同的 chunk 长度、overlap 和召回数量：看 Recall（相关内容被检索回来的比例）、重复率、token 成本（模型处理的文本单位数量）以及最终答案质量，再按文档类型和任务选择方案，而不是把某个固定 token 数当成通用标准。

可以尝试

  • 按文档结构切分，尽量保留标题、段落、列表和代码块等完整语义；必要时使用父子块，或先召回较小的块，再补取它所在的父块或邻近上下文。
  • 用真实问题集评估 chunk 长度、overlap 和召回数量对 Recall、重复率、token 成本与生成质量的影响，不要只凭直觉调参数。
  • 不同文档和检索任务的合适参数可能不同，不要把某个固定 token 数说成所有文档都适用的标准值。
15向量检索和 BM25 到底差在哪，分别适合什么场景？

口述版简单说，向量检索是把文本转换成一串表示语义的数字，再找语义相近的内容，所以即使措辞不同，只要意思接近，也可能被检索出来。BM25 是按词项是否出现、出现频率等因素打分的字面检索，更擅长命中特定词、产品名、错误码、代码符号和罕见术语。两者解决的漏检类型不同，没有谁在所有场景都更好。企业知识库通常会把两种结果合并，必要时再做“重排”，也就是用第二个模型或规则对候选结果重新评分排序。最后要用自己业务的评测集验证效果，因为模型、语料、语言和查询类型都会影响结果。

记忆要点

  • 向量检索：偏语义相似，适合不同说法但意思接近的查询；BM25：偏字面命中，适合专有词、精确标识符和罕见术语。
  • 模型、语料、语言和查询类型都会影响结果，不能只凭经验判断；要用应用自己的评测集验证。
  • 常见做法是混合检索，再根据评测结果决定是否需要重排。
16什么是混合检索？如何把向量检索和 BM25 的结果合并？

口述版混合检索就是同时使用两种找资料的方法：dense vector（稠密向量检索，把问题和文档转成数字向量，按语义相似度查找）和 BM25（传统关键词检索，按关键词匹配和词频等因素计算相关性）。通常让两路检索并行召回候选结果，再合并、去重；如果需要，还可以交给 reranker（重排模型，对候选结果再做一次更细的相关性排序）。要注意，两种检索器的原始分数，量纲和分布可能不一样，所以不能未经验证就直接相加。更稳妥的做法是用 Reciprocal Rank Fusion，也就是按名次给结果分配融合分数；如果有标注数据，还可以学习或校准两路结果的权重。最后要用同一批问题，比较单独使用每一路、混合召回以及重排后的效果，同时看准确性、延迟和成本。

评估方向

  • 比较 dense-only（只用向量检索）、BM25-only（只用 BM25）、混合召回和重排后的 Recall@K、MRR / nDCG。Recall@K 看前 K 个结果覆盖了多少相关内容；MRR 和 nDCG 则分别更关注相关结果首次出现的位置，以及相关结果整体排序质量。
  • 关注候选结果的重复程度、两种检索器是否能互相补充、融合权重是否稳定，以及混合方案带来的额外延迟。
17RAG 检索不准时，如何分层定位问题？

口述版我会先用一组固定的、标注了相关文档的黄金问题集来测试。RAG 可以简单理解为“先检索资料，再让模型根据资料回答”。排查时按层往下走：先确认目标文档有没有进入索引，以及解析、分块时有没有丢掉关键信息；再检查用户权限和元数据过滤（按权限等字段筛选）有没有把正确内容误排除。接着看查询改写是否改变了用户原意，embedding（把文本转成便于相似度检索的数字表示）、向量字段和索引版本是否一致；然后确认候选召回数量和内容是否足够。之后再看混合检索和 reranker（对初步候选重新排序的模型）有没有改变排名。只有确认检索结果本身没问题后，才排查上下文拼装，以及生成阶段有没有误用或忽略证据。每个请求都要记录查询、过滤条件、候选片段、分数和各阶段耗时，形成逐层 trace（记录一次请求经过各阶段的过程），这样才能复现和定位。

排查原则

  • 先区分“检索没找到”，还是“已经找到，但答案没有用好”。
  • 结合逐层 trace 和固定的黄金问题集，不要只靠主观试问判断。
  • 权限过滤出错本身就是检索错误；不能为了提高召回率而绕过权限。
18如何区分 Recall@K、MRR 和 nDCG？评估 RAG 不能只看检索指标，还要看什么？

口述版我会先把它们看成检索阶段的三个指标。Recall@K（前 K 条结果里，找回了多少应该相关的文档）关注相关证据有没有被召回；MRR（第一个相关结果的倒数排名）关注第一条相关结果出现得是否靠前，越靠前分数越高；nDCG（按相关程度给结果打分的排名指标）可以区分“非常相关”和“部分相关”，同时会让排在后面的结果贡献更小。它们主要评价检索和排序，不能直接说明 RAG 最终生成的答案是对的。完整评估还要看答案正确性、是否忠于检索到的证据、引用是否真的支持结论、该拒答时能否恰当拒答，以及延迟、成本和权限隔离。实际可以结合离线黄金集（预先准备并标注好的测试问题和标准结果）、人工评审和线上用户反馈一起判断。

补充

  • 先统一标注口径、相关性等级、K 值和问题覆盖范围，否则不同实验的分数不能直接比较。
  • 生成质量指标不能替代检索指标；检索指标也不能单独代表用户价值。
  • 做线上实验时要注意用户隐私和采样偏差，也要防止失败样本被漏记。
19RAG 中如何落实文档 ACL、租户隔离和检索权限？

口述版我会先在服务端确认当前用户身份、所属租户（同一系统里彼此隔离的客户或组织）以及可访问范围。检索时通过可信的元数据过滤，或使用彼此隔离的索引，确保无权文档不会进入模型上下文。这里的 ACL（访问控制列表）就是记录“谁能访问哪份文档”的权限清单。拿到候选文档后，还要再做一次最终权限校验。权限发生变化时，要及时同步到索引；缓存键也要包含用户标识或权限版本等隔离信息，避免一个用户命中的内容被另一个用户复用。不能先把敏感数据返回给浏览器，再靠前端隐藏来保证安全。

必须验证

  • 覆盖跨租户访问、权限撤销、共享文档、过滤失败和缓存命中等边界场景。
  • 确认索引元数据与源系统 ACL 的同步时效，并明确同步失败时是默认拒绝访问，还是采用有边界的降级策略。
  • 对高风险数据保留审计能力，也就是能追踪谁在什么时间访问了什么内容，并遵循最小权限原则：只授予完成当前任务所需的最少权限。
20文档更新、删除或换版本时，怎样避免 RAG 检索到过期内容？

口述版我会给每份文档设置稳定的 canonical ID，也就是不随内容变化的唯一身份，再给每个版本记录版本号。文档更新时，按文档 ID 写入新版本，也就是 upsert（有则更新、无则新增），同时清理旧版本留下的 chunks，也就是切分后的文本片段。文档删除时，不能只删源系统里的文件，还要向索引传播 tombstone（表示这份内容已删除的标记），避免它继续被检索到。发布时可以先构建完整的新索引或新版本，确认无误后再用 alias（指向当前索引的别名）一次性切换，避免新旧版本混在一起。缓存也要按文档版本或变更事件失效，不能只依赖 TTL（到期自动删除缓存）。另外要明确同步延迟、失败重试和回滚方案，并监控更新是否成功、延迟多久，这样索引才可观测、可恢复。

记忆要点

  • chunk ID 与文档 ID、版本号的关系要稳定，避免更新后重复写入或残留旧片段。
  • 切换期间要防止旧、新版本混杂；权限撤销和删除尤其要重点验证，不能只验证普通更新。
  • 缓存 TTL 不是保证一致性的唯一方案，还要结合失效事件和版本校验。
21RAG 和微调到底有什么区别，面试中怎么选？

口述版我会先判断，问题到底是“模型缺知识”，还是“模型不会按要求做”。RAG，也就是检索增强生成，可以理解成模型回答前先去外部知识库查资料，再根据查到的内容作答；它适合知识经常变化、需要引用来源，或者必须按用户权限读取数据的场景。它的代价是要维护一整条链路：文档解析、切分和索引、检索、权限校验，以及把证据交给模型。这里的权限不能只靠提示词约束，而要在取数链路中真正检查。微调则是用训练数据改变模型参数，让模型更稳定地学会某种任务行为、输出风格或固定模式；它不适合把频繁变化的事实当成唯一知识库。两者也可以组合：RAG负责提供最新事实，微调负责让模型更稳定地遵循任务格式。最后不要把微调当成检索问题的通用修复，而要根据失败样本和评估数据，对比任务效果、合规性、延迟和总成本后再选。

取舍

  • 先判断是“缺知识”还是“不会按要求做”，再确认是否需要最新事实、来源追踪和权限控制。
  • RAG要承担召回质量、知识时效和检索基础设施的成本；微调要承担数据准备、训练和后续维护的成本。
  • 用真实任务效果、合规要求、响应延迟和总成本做评估，不要只凭技术偏好选型。
22复杂问题为什么要在 RAG 中拆成子问题？怎样避免拆偏？

口述版RAG（检索增强生成）就是先从资料库里查证据，再据此组织答案。复杂问题可能同时涉及多个对象、条件或证据需求，所以可以拆成几个可单独检索的子问题，分别找证据，也更容易发现哪一部分没有依据。但拆分可能误解原意、越拆越偏。我会保留原始问题和每次拆分的理由，限制子问题的数量和拆分深度；每个子问题单独检索并记录引用，最后始终回到原问题，把有证据的结果合并起来。简单问题不需要强行拆分；如果子问题已经超出原意，或者找不到足够证据，就应该收敛问题、请求澄清，或明确说明限制。

设计要点

  • 限制规划轮数、子问题数量、总 token（模型处理的文本计量单位）和总耗时，避免拆分无限进行。
  • 保留“原问题—子问题—检索证据—最终结论”的可追溯关系，方便复核答案依据。
  • 模型自行生成的子问题只是待验证的检索计划，不能直接当成已经确认的事实。
23RAG 的多跳检索是什么？它和普通的 top-K 检索有什么区别？

口述版RAG（检索增强生成）可以理解为：先从资料库找证据，再让模型根据证据回答。普通的 top-K 检索是用用户问题一次性找出最相关的 K 个片段；多跳检索则要连续查几次，把上一跳找到的实体或关系作为下一跳的查询。例如，先查出某个实体关联的项目，再用项目名称去查它的时间或负责人。每一跳都要保留可追溯的来源证据，不能让模型凭空补出中间事实；必要时还要从证据中抽取实体或关系，生成下一跳问题。最后要对整条证据链去重、排序和验证。多跳检索适合处理分散在不同文档、需要串起跨文档关系的问题，但会增加延迟，也会让前一跳的错误传到后面，所以要限制跳数；如果任一跳证据不足，就应停止，或者明确说明不确定。

面试补充

  • 重点区分“有证据支撑的多跳证据链”和“模型凭空补出的中间事实”。
  • 调试和评估时，记录每一跳的问题、候选结果、来源以及停止原因；可以用多跳黄金问题集（预先准备、答案和证据都已确定的问题）评估端到端成功率。
24RAG 如何防住检索文档里的 Prompt Injection？

口述版RAG（先检索资料，再让模型生成答案）里，检索到的文档只能当作不可信的参考数据，不能当成系统指令。Prompt Injection（提示词注入）就是把“忽略原规则、泄露秘密、调用工具”之类的文字藏进文档，试图改变模型行为。系统提示要明确区分“要执行的指令”和“只供参考的文档内容”，不能因为文档这样要求就授权模型执行。也不能只依赖模型自己识别注入：高风险工具要采用最小权限，只允许明确的操作，服务端还要重新做授权和参数校验，必要时要求人工确认；密码、密钥等秘密也不应放进模型能看到的上下文。最后，还要校验模型输出和工具参数，并用恶意文档测试从检索到工具调用的整条链路。

纵深防御

  • 隔离文档来源，并在上下文中清楚标记哪些是指令、哪些是引用内容；对高风险工具设置 allowlist（只允许列出的操作），同时做参数校验和权限检查。
  • 检索文本无论提出什么要求，都不能直接导致凭据泄露或有副作用的操作。
  • 过滤器只能辅助发现注入，不能保证识别所有新型攻击；真正的权限边界必须由程序在工具和服务端执行。
25RAG 的 trace 要记录什么？如何用 p50 和 p95 找出慢请求？

口述版我会先给每次请求分配一个 trace ID，也就是能把这次请求各个处理步骤串起来的编号；再把鉴权与过滤、查询改写、各路召回、结果融合、reranker（对召回结果再次排序的模型或步骤）、上下文构建、模型首 token 和完整生成耗时分别记成 span，也就是可单独计时和排查的一段处理过程。每个阶段还要记录候选数量、模型版本、索引版本、token 数，以及错误和重试等必要信息。p50 是中位延迟，表示一半请求不超过这个时间；p95 是 95 分位延迟，表示最慢的约 5% 请求通常落在这个时间之后。如果 p50 正常但 p95 很高，说明主要是长尾慢请求，不应只看平均值或总耗时，而要按查询类型、索引分片、文档长度、是否重试，以及各阶段耗时分组，定位到底是哪一类请求或哪一步拖慢了。日志还要脱敏，并限制访问权限，不能无策略地记录完整用户问题或敏感文档原文。

常见延迟分解

  • 按阶段看请求排队、检索、重排、上下文拼装、模型首 token，以及生成总时长。
  • 同时看各阶段和整体的 p50、p95 等分位数及分布，也要关注超时率、错误率、token 用量和成本。
  • 不要无策略地记录完整用户问题或敏感文档原文；需要排查时，应优先记录脱敏后的内容、摘要或标识，并配合访问控制。
26RAG 检索的 top-K 怎么选？K 越大越好吗？

口述版不一定。top-K 里的 K，指检索阶段先取多少个候选片段。K 变大，通常更容易把相关证据召回，但也会带来更多噪声和重复内容，增加排序开销与上下文 token，甚至让模型注意力被无关内容分散。实际要把两个数量分开选：先用较大的候选 K 保证召回，再通过结果融合或 reranker（重新给候选片段排序的模型或方法）挑出少量真正适合放进上下文的片段。应该用黄金问题集，也就是一组带有标准答案或标准证据的问题，测试 Recall@K（前 K 个候选里是否包含相关证据）、MRR / nDCG（衡量相关结果排得是否靠前）、最终回答质量、延迟和成本，再按查询类型调整 K，而不是直接套用一个未经验证的通用值。

注意

  • 区分初始候选 K 和最终放入上下文的片段数：前者重点保证召回，后者要受上下文 token 预算限制。
  • 评估时同时看 token 预算、片段重复率、文档长度和问题复杂度；不能只看某一个检索指标。
  • 如果候选里根本没有相关证据，应先修复召回问题，例如检查切分、索引或检索策略，不要只靠盲目增大上下文片段数量。
27Reranker 是什么，什么时候值得加入？

口述版Reranker（重排器）可以理解为检索系统的第二轮筛选：第一阶段先用速度较快的向量检索或关键词检索，尽量找出一批候选文档；这里的“候选”就是暂时认为可能相关、还没最终定顺序的结果。第二阶段再让重排模型逐一比较“用户问题—文档片段”是否真正匹配，并把更相关的内容排到前面。它不能找回第一阶段完全没有召回的文档，但通常能减少噪声、提高前几条结果的质量。适合加入的情况是：初步检索结果杂、不同文档的语义差别很关键，而且质量提升能抵消新增的延迟和费用。是否启用，不能只凭感觉，要同时看排序指标、最终答案质量，以及端到端延迟和成本。

一句话记忆

  • 召回器负责“尽量找全”：先找出可能相关的候选；reranker 负责“更准确地排好”：只重新排序已经找到的候选。
  • 重排通常要对多个“问题—文档”组合逐一判断，会增加模型调用成本和响应时间，所以要限制候选数量，并用实测确认收益。
  • 常见观察指标包括 MRR 和 nDCG（衡量相关结果排得是否靠前）、答案忠实度（答案是否有检索内容依据）、p95 延迟（最慢的 5% 请求大致要等多久）以及单位请求成本。
28知识库里的文档互相冲突时，你如何判断答案该信哪个？

口述版我不会因为模型生成的答案听起来顺，就直接把它当成冲突处理结果。先在索引元数据里记录文档来源、权威级别、适用范围、生效时间和版本。这里的“索引元数据”，就是跟着文档保存、用于判断这份内容来自哪里以及何时适用的信息。检索时按业务规则优先选择当前有效、权威级别更高、并且适用于当前产品、地区或角色的来源，同时检查不同来源之间有没有冲突。如果无法判断哪个来源优先，或者适用范围不清楚，就同时给出各自的依据和差异，明确说明不确定性；必要时追问用户，而不是把互相矛盾的内容拼成一个确定结论。

预防与处理

  • 在源系统做好版本治理，也就是明确哪些版本有效、哪些已经失效；同时标注失效状态，并维护文档责任人。
  • 检索时过滤已过期文档，并明确时间范围以及适用的产品、地区和角色。
  • 引用要能指向具体文档版本，方便面试官或用户核验，也便于发现问题后纠错。
29更换 embedding 模型后，如何安全迁移现有向量索引？

口述版先说明一点：embedding 是把文本转换成能表示语义的数字向量。新旧模型生成的向量通常不在同一个向量空间里，所以不能直接用新模型的查询向量去匹配旧模型的文档向量。我的做法是给索引和每条向量记录标记模型版本，创建新的 collection 或向量索引，然后为全部文档重新生成 embedding。接着用评测集比较召回质量，同时检查过滤结果和查询延迟。上线时可以双写新旧索引，或者先把迁移期间的增量变更补齐；验证稳定后，通过 alias 或配置做原子切换，并保留旧索引用于回滚。运行一段时间、确认没有问题后，再清理旧数据。

迁移检查

  • 确认新旧索引的向量维度、归一化方式、距离函数、分块版本和元数据字段是否符合预期；这些设置不一致，可能导致检索结果失真或查询无法正常运行。
  • 明确迁移期间新增、更新、删除的数据怎样同步或补齐，并确认切换后不会把不同模型生成的向量混在同一次检索中。
  • 提前设计索引回滚方案，并估算全量重建和双写带来的资源成本；同时记录模型版本、索引状态、召回质量和延迟，便于观测迁移是否稳定。

30Python 的动态类型是什么意思？类型提示会在运行时强制检查吗？

口述版Python 是动态类型语言，意思是：变量名只是绑定到对象上，真正的类型属于对象，不属于变量。所以同一个变量在不同时间可以指向不同类型的对象。比如先让 x 指向整数，之后再让它指向字符串，这本身是允许的。类型提示只是把开发者预期的类型写出来，方便 IDE、静态检查器和文档理解；Python 默认不会在运行时因为类型提示不匹配，就自动拒绝这个值。

记忆要点

  • 动态类型不等于没有类型：每个对象始终都有自己的类型，只是变量名本身不固定绑定某一种类型。
  • 类型提示主要改善可读性，并帮助工具提前发现问题；要做静态校验，需要配合 mypy、pyright 等工具。
  • 面试时要区分：动态类型说的是 Python 运行时如何绑定和使用对象；类型提示说的是开发者给工具和读者看的类型约定，默认不是运行时强制检查。
31Python 里的 list、tuple、set、dict 分别适合什么场景？

口述版可以这样区分：list 是有顺序、可以修改、允许重复的序列，适合需要按位置访问，并且会增删或更新元素的场景。tuple 也是有顺序的序列，但创建后不能修改，适合表示不希望被改写的固定组合。set 只保存不重复的元素，元素需要是可哈希的，也就是 Python 能稳定计算它的标识，用来判断元素是否存在或做去重、并集、交集等集合运算。dict 保存键和值的映射，适合通过 key 快速查找对应的数据。Python 的 dict 会保留键的插入顺序，但不要把 set 的遍历顺序当成稳定契约。

快速对照

  • 需要有顺序，并且会增删或修改：list；表示不希望被改写的固定组合：tuple。
  • 去重、判断成员是否存在、做集合关系运算：set；根据 key 查找对应值：dict。
32Python 中可变对象、不可变对象，以及赋值和复制分别是什么？有哪些常见坑？

口述版可以这样理解：不可变对象是创建后不能在原对象上直接改内容的对象，比如 int、str、tuple；可变对象则可以在原对象上更新，比如 list、dict、set。b = a 只是让 a 和 b 两个名字指向同一个对象，不会产生副本，所以通过一个名字修改可变对象时，另一个名字也会看到变化。浅拷贝只复制最外层容器，里面嵌套的列表或字典仍然共享；需要连嵌套对象一起复制时，可以考虑 copy.deepcopy，但要先确认对象结构，并权衡性能。这里的“共享”可以类比成前端里两个变量拿到同一个引用，但这只是帮助理解，Python 的具体对象和复制规则仍要按 Python 语义判断。

常见追问

  • 浅拷贝可以用 a.copy() 或 copy.copy(a)。如果是嵌套列表，要特别小心内部对象仍可能是同一个引用。
  • 函数默认参数不要写成 items=[]，因为这个列表会在多次调用之间被复用。通常写成 items=None，再在函数内部新建列表。
33Python 中，`==` 和 `is` 有什么区别？为什么判断 `None` 要用 `is`？

口述版== 比较的是两个对象的值是否相等，也就是内容是否相同；具体怎么比较，可以由类的 __eq__ 方法定义。is 比较的是对象身份，也就是两个变量是否指向同一个对象。可以把它类比成：== 像比较两个输入框里的文字，is 像检查两个变量是不是拿着同一个输入框，但这只是帮助理解，实际判断仍然遵循 Python 的值比较和对象身份规则。None 是 Python 中表示“没有值”的单例对象，程序里使用的是同一个对象，所以判断它应写成 value is None 或 value is not None。不要用 is 判断字符串或数字是否相等，因为驻留、缓存等实现细节可能让结果看起来偶尔正确，却不能作为程序正确性的依据。

面试提醒

  • 值相等用 ==；对象身份用 is。
  • 判断空值用 is None。空列表、空字符串等也可以直接按真值判断，例如放在 if 条件里，但要根据业务语义区分“没有值”和“值为空”。
34为什么 Python 的 dict 键和 set 元素必须可哈希？

口述版可以把“哈希”理解成根据对象内容算出的一个快速定位编号。dict 会用这个编号快速找到 key 对应的值，set 也用它快速判断某个元素是否存在；如果不同对象算出了同一个编号，再通过相等性比较来处理冲突。因此，key 或 set 元素在放进去之后，必须在整个存活期间保持哈希值和相等关系稳定，否则对象可能还在容器里，却再也找不到。不可变的 int、str，以及满足条件的 tuple 通常可以哈希；list、dict 和 set 可以被修改，所以不能哈希。平均情况下，dict 查找和 set 成员判断接近 O(1)，但这是平均复杂度，并不表示所有输入都一定是常数时间。

补充

  • 相等的对象必须有相同的哈希值；如果自己定义对象，要谨慎设计 __hash__ 和 __eq__，让这两个规则保持一致。
  • tuple 只有在其中每个元素都可哈希时，才能作为 dict 的 key 或 set 的元素。
35Python 集合的并集、交集、差集分别是什么？差集为什么有方向？

口述版Python 的 set（集合）可以理解为一组不重复元素，适合做成员关系和集合运算。设 A、B 是两个集合：并集包含 A 或 B 中出现过的所有元素；交集只保留同时属于 A 和 B 的元素；差集 A - B 保留在 A 里、但不在 B 里的元素，所以差集有方向，A - B 和 B - A 可能不同。比如 a={1,2,3}、b={3,4} 时，并集是 {1,2,3,4}，交集是 {3}，a-b 是 {1,2}，b-a 是 {4}。实际使用时，集合运算符适合简洁表达，union() 等方法更直观；这些运算都会返回新集合，不会直接改掉原集合。

高频记忆卡

  • 运算符：并集用 a | b，交集用 a & b，差集用 a - b，对称差集用 a ^ b。对称差集表示“只出现在其中一个集合、但不同时出现在两个集合”的元素。
  • 方法：a.union(b)、a.intersection(b)、a.difference(b)、a.symmetric_difference(b)，它们都会返回新集合。
  • 例子：权限校验中可用 required - granted 找出“要求有但实际没有”的权限；比较两版数据时，可以用交集找共同项，用对称差集找只在一版中出现的项。涉及权限时仍要结合真实的授权校验，不能只把集合差集当成安全判断。
36Python 列表推导式怎么写？for 后面的 if 是过滤条件吗？

口述版列表推导式可以把“遍历、处理并生成一个新列表”写在一行，基本形式是 [表达式 for 项目 in 可迭代对象 if 条件]。这里的“可迭代对象”就是能被逐个取出元素来遍历的对象，比如列表。比如 [n * n for n in nums if n % 2 == 0]：先遍历 nums，只保留偶数，再把它们平方。因此，for 后面的 if 是过滤条件，不符合条件的项不会进入结果。要是目标不是过滤，而是让每个项按条件变成不同的值，就把条件表达式写在最前面，例如 [n if n >= 0 else 0 for n in nums]，负数会变成 0，其他数保持不变。

高频记忆卡

  • 记法：先写结果表达式，再写 for；末尾的 if 表示“只保留符合条件的项”。
  • 过滤写法：[x for x in xs if 条件]；条件转换写法：[A if 条件 else B for x in xs]。前者会减少结果项，后者通常会为每个输入项生成一个结果。
  • 多层循环或条件太复杂时，普通 for 循环通常更容易读，也更容易调试。
37Python 函数的参数绑定、默认值和 *args/**kwargs 怎么理解，怎么避免默认值踩坑？

口述版可以把函数参数理解成调用函数时传进去的值与形参的对应规则。位置参数按传入顺序匹配；关键字参数按参数名匹配，所以更能表达调用意图。带默认值的参数可以省略，函数定义时会使用这个默认值。*args 会把多出来的位置参数收集成一个 tuple（元组，就是有顺序的一组值），**kwargs 会把多出来的关键字参数收集成一个 dict（字典，就是参数名到值的映射）。要特别注意：默认参数表达式只在函数定义时求值一次，因此如果默认值是 list、dict 这类可变对象，多次调用可能会共享同一个对象。常见的安全写法是默认设为 None，进入函数后再创建新的对象。参数设计上，还可以用 / 标记仅限位置参数、用单独的 * 标记仅限关键字参数，让 API 的调用方式更稳定，但不必为了形式而过度使用。

面试补充

  • 当调用方需要明确表达每个值的含义时，优先考虑关键字参数；位置参数更简短，但参数顺序必须正确。
  • *args 收集的是额外的位置参数，类型是 tuple；**kwargs 收集的是额外的关键字参数，类型是 dict。它们也常用于把可变数量的参数继续传给另一个函数。
  • 例如不要写 def add_item(item, items=[]): ... 来保存每次调用的数据；应写成 def add_item(item, items=None):，并在函数内部用 if items is None: items = [] 创建新列表。
  • 参数顺序、仅限位置参数 /、仅限关键字参数 * 都可以用来设计更稳定的 API；是否使用要看可读性和兼容性，不必过度使用。
38Python 异常处理怎么设计？try、except、else、finally 分别什么时候用？

口述版我会先把可能失败的代码放进 try，把异常理解成“程序运行时发现无法正常继续的情况”。except 用来捕获并处理预期的、具体的异常；不要写一个空的 except 把所有错误静默吞掉。else 只在 try 完全没有异常时执行，适合放成功后的逻辑；finally 通常无论是否出错都会执行，适合关闭文件、释放连接等清理工作。异常处理的边界要合适：当前层能恢复，就在这里处理；不能恢复，就补充必要上下文后继续向上抛出。对调用方有意义的业务失败，可以定义清晰的自定义异常；如果是在处理底层异常时转换成业务异常，使用 raise ... from exc 保留异常链，这样既方便调用方识别，也方便排查原始原因。

实用原则

  • 尽量捕获具体异常，不要用过宽的捕获范围；处理时保留上下文，避免错误被悄悄隐藏。
  • 文件、网络请求等外部操作要区分超时、连接失败、状态错误和数据格式错误，因为它们的恢复方式可能不同。
  • finally 适合做清理，不要把必须完成的业务结果只依赖在清理代码里；它通常会执行，但异常终止等特殊情况不能简单等同于普通流程。
39Python 里的可迭代对象、迭代器和生成器有什么区别？

口述版可以这样区分：可迭代对象是“能被逐项遍历的数据”，比如列表、字符串或文件；对它调用 iter(obj)，可以得到一个迭代器。迭代器像一个记住当前位置的取数器，实现了 __next__，每次取一项，取完后会抛出 StopIteration。生成器是创建迭代器的一种方便方式：在函数里使用 yield，调用这个函数时不会立刻算完全部结果，而是得到生成器对象；每次迭代运行到一个 yield 就暂停，下次继续执行。它们适合流式处理大文件或数据管道，因为可以一项一项处理，避免一次把所有结果放进内存；但生成器通常只能从头消费一次，不能像列表那样随意重复遍历。

记忆要点

  • return 是结束函数并返回结果；yield 是产出一项结果，同时保留函数的执行状态，之后还能从暂停处继续。
  • 需要重复遍历时，先确认对象是否可重用；如果必须保存结果，可以物化为 list，但要权衡由此增加的内存占用。
40Python 的 `with` 语句和上下文管理器如何保证资源正确清理？

口述版with 语句和上下文管理器，解决的是资源生命周期管理问题：上下文管理器可以把资源的获取、使用和清理配成一套规则；离开代码块时，即使中间抛出异常，也会执行退出逻辑。比如 with open(path) as f: 用完后会自动关闭文件。自定义上下文管理器通常实现 __enter__ 和 __exit__，也可以用 contextlib.contextmanager 来定义。数据库事务、锁和临时资源等，也适合用这种方式明确生命周期。

面试要点

  • 重点不只是少写几行代码，而是让资源释放在正常结束和异常路径上都可靠。
  • 异步资源可以使用 async with，它对应异步上下文管理器协议。
41Python 的 async/await 是什么？调用 async def 函数会马上执行吗？

口述版async def 用来定义协程函数。协程可以先理解成一段能暂停、之后再继续的异步代码。调用这个函数时，通常只是创建一个 coroutine（协程）对象，并不会立刻把函数体从头执行到尾。要让它真正运行，需要在事件循环中用 await 等待，或用 asyncio.create_task 把它安排成任务。运行到网络、文件或数据库等可等待操作时，协程可以暂时让出控制权，让其他协程先运行。它适合同时处理很多 I/O 等待任务，但不会自动让 CPU 密集型计算变快；如果在事件循环里直接调用同步的阻塞函数，整个事件循环都会被卡住，其他任务也无法及时运行。

关键边界

  • 创建了协程对象不等于它已经执行。要记得用 await 等待，或把它交给事件循环创建任务；否则可能出现“协程从未等待”的警告。
  • 异步代码应配合异步 HTTP 客户端、异步数据库客户端等真正支持异步的工具，并设置超时、取消和异常处理。不要在事件循环里直接做长时间的同步阻塞工作。
42I/O 密集和 CPU 密集任务，线程、进程、asyncio 怎么选？

口述版I/O 密集任务主要是在等网络、磁盘等外部操作完成：如果要同时处理很多连接，而且使用的库支持异步，可以用 asyncio，也就是用一个事件循环统一安排等待中的任务；如果库本身是同步的，或者并发量没那么大，线程通常更直接。CPU 密集任务主要是在做大量计算；在常见的 CPython 构建中，GIL（全局解释器锁，可以先理解为同一进程内同一时刻通常只有一个线程执行 Python 字节码）会限制多个线程同时跑 Python 计算，所以通常要评估多进程或进程池，利用多个 CPU 核心并行。最终不能只看任务标签，还要确认依赖库是否会释放 GIL、任务规模是否值得并行、进程间序列化和通信成本、共享状态怎么处理，以及部署环境是否适合。并发也不是越多越好，应通过超时、限流和队列控制资源，并用实测的吞吐量和延迟验证选择。

简化判断

  • 大量并发 I/O：优先在异步库可用时评估 asyncio；同步库或适中并发可考虑线程。
  • CPU 密集计算：在常见 CPython 场景下优先评估多进程或进程池；如果依赖库会释放 GIL，也要结合实测再判断线程是否合适。
  • 并发不是越多越好：用超时、限流和队列控制资源，并以实测吞吐量与延迟为准。
43Python 调 REST API 时，怎样正确解析 JSON 并处理请求错误？

口述版调用 REST API 时，我会把“请求有没有成功”和“响应内容能不能解析”分开处理。标准库里的 json.loads(text) 是把 JSON 文本解析成 Python 对象，json.dumps(obj) 是把 Python 对象序列化成 JSON 文本；requests 或 httpx 的 response.json() 则是解析这次 HTTP 响应的响应体。需要注意，JSON 能解析，不代表 HTTP 请求成功，所以不能只调用 response.json() 就当作成功。比较稳妥的流程是先设置连接超时和读取超时，再检查状态码，例如调用 raise_for_status()；同时捕获网络错误和 JSON 解码错误。解析成功后，还要在边界处验证关键字段的类型和必填约束。这里的 schema 可以理解为“数据结构和字段规则”，因为 JSON 语法正确，不代表数据符合业务要求。

实用检查

  • 语法正确不等于业务数据正确：JSON 只要格式合法就能解析，但字段可能缺失，或者类型不对，所以要在 API 边界验证结构、类型和必填字段。
  • 重试要谨慎：重试应设置次数上限和退避，也就是每次重试前逐步等待更长时间。对非幂等写请求（重复执行可能重复创建或产生多次副作用的请求），如果没有专门设计，就不要盲目重试。
44Python 中的模块、包和 `if __name__ == "__main__"` 分别有什么作用？

口述版模块通常就是一个 Python 文件，用来承载可复用的函数、类或变量；包则是把多个相关模块按目录组织起来，方便管理和导入。执行 import 时，Python 会执行被导入模块的顶层代码，所以顶层最好只放定义和必要的配置，不要直接启动服务、跑昂贵任务或做其他副作用操作（也就是导入时意外改变外部状态）。if __name__ == "__main__": 可以理解为“只有直接运行这个文件时才执行这里”：文件作为主程序启动时，条件成立；被其他代码导入时，条件不成立。因此它常用于命令行入口、参数解析和本地演示。前端可以类比为：一个文件既能被别的模块复用，也能单独启动调试，但这只是帮助理解的类比，不等同于 JavaScript 模块的运行规则。

设计提示

  • 把可复用逻辑放进函数或类里，入口层只负责参数解析和启动；这样被导入时不会顺便执行整套流程。
  • 绝对导入和相对导入要与包结构保持一致。遇到导入错误时，应检查包结构和启动方式，不要靠随意修改工作目录来掩盖问题。
45Python 项目怎样隔离环境并管理可复现依赖？

口述版虚拟环境可以理解成每个 Python 项目的独立依赖目录：项目各自安装需要的包，避免不同项目使用不同版本时互相冲突。通常先用 python -m venv .venv 创建环境，再激活它，用 pip 安装依赖。例如，开发和 CI 不应依赖某台机器上“刚好能用”的全局环境，而要明确 Python 版本和依赖版本。项目还应提交依赖声明，并按团队选定的工具生成锁定版本，这样部署时能尽量复现同一套依赖。升级依赖前要运行测试，确认版本变化没有破坏项目。

注意

  • 常用工具包括 venv（Python 自带的虚拟环境工具）、pip（安装 Python 包的工具）、pyproject.toml（项目和依赖配置文件），以及团队选定的锁文件方案。依赖声明说明“需要什么”，锁文件则进一步固定“具体用哪个版本”。
  • 部署和 CI 要明确使用的 Python 版本与依赖版本；升级依赖时先运行测试，不要把某台机器上的全局环境当成可靠依据。
  • 密钥不应写进依赖文件或提交到仓库；配置应从安全的环境或密钥管理机制注入。
46类型提示和 Pydantic 运行时校验有什么区别？

口述版类型提示，就是在函数参数、返回值和数据结构旁边写清楚“应该是什么类型”的说明，主要帮助静态分析器和 IDE 在运行前发现部分问题、提供补全；但 Python 默认不会因为写了类型提示，就在运行时自动做完整的类型检查。Pydantic 这类数据校验工具则是在程序运行时，按定义好的模型解析和验证数据。比如收到 HTTP 的 JSON 请求体时，可以先检查字段是否存在、类型是否正确，再把外部输入转换成受约束的数据模型。两者是互补关系：类型提示偏向代码可读性、维护和开发期检查，Pydantic 偏向系统边界的运行时输入校验。进入业务逻辑前仍要检查业务规则、权限和安全限制，不能只依靠类型声明，也不能把 Pydantic 校验当成完整的安全授权机制。

常见说法

  • 静态类型检查和运行时数据验证解决的是不同阶段的问题，互相补充，不能互相替代。
  • 来自 HTTP 请求、文件或其他外部系统的数据，先用运行时校验验证，再进入业务逻辑；内部代码则用类型提示帮助维护、重构和 IDE 补全。
47怎样用 pytest 测试 Python API 和业务逻辑，覆盖边界又避免 mock 失真？

口述版我会先把单元测试放在可独立验证的函数或模块上。pytest 能自动发现测试，并提供断言、fixture 和参数化测试：fixture 可以理解为测试前准备、测试后清理的可复用工具；参数化就是用多组输入重复运行同一个测试。对网络、时间、随机数这类外部依赖，我会优先用依赖注入，或者用 mock，也就是可控的替身，来固定测试条件。API 层除了正常请求，还要覆盖输入校验失败、鉴权失败、依赖超时和异常响应。断言应关注调用者能观察到的结果和行为，而不是把内部实现细节原样复刻；必要时，再补充连接真实依赖的集成测试。异步代码要使用和项目兼容的异步测试支持，同时不能只靠 mock，否则可能掩盖真实协议或异步交互的问题。

面试要点

  • 用 fixture 管理重复的准备和清理逻辑，用参数化测试覆盖边界输入。
  • 异步代码使用与项目兼容的异步测试支持；mock 要适量，避免测试通过了，却没有发现真实协议问题。
48在 RAG 系统中，Python 主要负责哪些离线和在线环节？

口述版可以把 RAG 理解成“先把资料找出来，再让模型根据资料回答”。Python 通常负责两条链路。离线链路是先摄取文档，也就是把文件读进系统；再解析内容、切块，并调用 embedding 模型把文字转换成便于相似度检索的向量，最后写入向量库。在线链路则负责鉴权、查询预处理、检索和重排、拼接上下文、调用模型、整理引用，最后通过 API 返回结果。工程上通常会把这些环节分层，并明确每层的输入输出、数据模型、超时、重试、日志和评估接口。LangChain 这类框架可以加快集成，但不能替代你对检索质量、权限过滤和数据流的理解。面试时要把离线索引和在线查询分开讲，并说明 ACL（访问控制列表，简单说就是“谁能看哪些资料”）必须在服务端执行；同时要保证索引版本和模型版本可追踪，日志注意脱敏。没有实际做过的项目不要说成自己做过。

回答框架

  • 先区分离线索引与在线查询：离线侧说明文档摄取、解析、切块、embedding 和写入向量库；在线侧说明鉴权、查询预处理、检索、重排、上下文构造、模型调用、引用整理和 API 返回。
  • 说明每一层的输入输出，并提到数据模型、超时、重试、日志和评估接口。
  • 强调 ACL 要在服务端执行，索引与模型版本要可追踪，日志要注意脱敏；不要声称做过自己没做过的项目。
49用 Python 做 Agent／工具调用服务时，怎样兼顾可靠性和安全性？

口述版我会把 Agent 拆成四层：模型负责做决策，工具 schema 规定参数的格式和取值规则，服务端执行器真正调用工具，结果整理层再把结果交给模型或用户。这里要特别注意，schema 只是校验输入的规则，不等于权限。服务端还要做身份认证和授权、工具 allowlist（只允许明确批准的工具）、速率限制、超时限制，以及结果大小限制。模型输出、检索到的文本和工具返回结果都要当作不可信输入，不能因为提示词里写了什么就直接放行。对会产生副作用或风险较高的工具，要按业务要求设置人工确认门槛。可靠性方面，要限制最多迭代多少步，明确失败时停止、超时时取消；重试时要考虑幂等性，也就是同一个请求重复执行不会造成重复副作用，并处理重复调用。最后记录可脱敏的 trace（一次调用链的过程记录），方便排查问题，但不要把敏感信息原样写进日志。

面试要点

  • Prompt 不是权限边界；检索文本或模型输出不能自行授权工具操作，真正的权限判断必须在服务端完成。
  • 要明确失败停止、超时取消、重复调用处理和人工确认策略，并配合最大迭代步数、重试与幂等控制。

  • 复用的是可运行、可配置、可验证的能力包，不是只保存一条通用提示词。
  • 应按实际任务和数据量选择实现方式，不预设每日规模，也不为展示技术而先上复杂的多 Agent 编排。
51一份可复用的 AI 分析资产，必须包含哪些内容？

口述版我会把它做成一套可交付、可复用的分析包，而不是一段孤立的提示词。至少要有适用场景和边界、输入 Schema（也就是规定输入字段、格式和必填关系的协议）、样例数据、预处理规则、提示词、输出 Schema、分析代码、报告模板、评测样本和版本说明。输入和输出都要约定成功、缺字段、空数据、异常等情况，并说明哪些字段必填、哪些可选、哪些可以标记为未知。业务方只要按协议提供数据和配置，就能得到格式稳定的结果。项目变化时，优先调整题目映射、标签体系和报告模板，不要复制整套代码；提示词、标签、模型和统计口径都要记录版本，方便比较效果，也方便回滚。

资产交付清单

  • 输入与输出样例：成功、缺字段、空数据和异常情况都要有示例，并明确必填项、可选项和未知值怎么表示。
  • 配置与代码分离：业务名称、分析窗口、标签体系和报告模板应该做成可配置项。权限控制不能交给提示词，必须由系统本身负责。
  • 可复用的版本包：可以按 schemas、prompts、rules、templates、evals 和 runner 组织，并附一个最小调用示例。
52问卷分析数据资产：如何从输入设计到稳定输出？

口述版输入要包括问卷题目、选项、量表方向、跳题规则、问卷版本，以及已经脱敏的答卷。先用程序做格式、范围和逻辑校验，再用 SQL 或代码计算单选、多选、量表和分群统计；不要让模型自由计算这些数字。模型更适合处理开放题：比如把回答分类、归纳主题，并生成能回到原始回答的摘要。最后输出统计口径清楚的表格、开放题主题、代表性原话、样本局限和还需要验证的建议。换一份问卷时，用题目映射和配置复用这套能力，而不是重新手工分析。

  • 处理链路：先做题目映射，再做有效性校验；然后进行确定性统计，再做开放题语义分析，最后校验报告并人工复核。这里的“确定性统计”是指同样的输入和规则应得到同样的结果。
  • 可复用内容：题目 Schema（也就是描述题目、选项和数据结构的统一格式）、统计函数、开放题提示词、分群配置、报告模板，以及用于检查结果的问卷评测集。

53问卷分析怎样避免分母、样本偏差和跨期比较出错？

口述版我会先把每个指标的统计口径说清楚：分母就是这个比例实际除以的人数，同时列出符合条件的人数、有效答题人数和缺失情况。未答、跳题、不适用，以及确实选了低分，要分开处理；多选题还要注明分母，并说明一个人可以选多个答案。做分群比较时展示每组样本量，样本太小就不下强结论。比较不同时间的数据前，先确认题目、量表和样本人群一致。模型只能帮助解释已经观察到的差异，不能替人补全缺失答案，也不能把便利样本——比如容易接触到的一批人——的结果直接说成全部用户的看法。

把统计口径写进分析资产和规则

  • 用一小份答案已知的数据集做校验，检查人数、占比、量表方向和跳题逻辑；模型生成的摘要还要另外核对证据。
  • 开放题可以给同一条回答打多个标签，所以各标签占比相加可能超过 100%；报告中必须明确说明这一点。
  • 只有在有合理的抽样依据和校正依据时，才做相应加权；加权就是让不同样本对总体结果的影响按规则调整。没有依据时，就明确写出样本局限。
54网站和功能使用反馈分析：要收集哪些输入，最后产出什么？

口述版核心是把用户反馈整理成可核实的问题线索，而不是直接下结论。输入包括用户原话、涉及的页面或功能、提交时间、版本、设备，以及在获得授权后可用的使用上下文。先做脱敏（去掉姓名、联系方式等不必要的个人信息）和去重，再提取问题、诉求、严重度和证据，归并相似主题，生成可审核的问题卡片。问题卡片要写清现象、影响范围、用户原话、已知上下文、未知项和排查建议；必要时，再通过受控工具（只允许查询规定数据、权限和范围的工具）补查行为指标。网站反馈和功能使用反馈可以共用这套分析资产，但要保留各自的入口和触发条件。

反馈分析能力包

  • 可复用的内容包括：反馈输入协议、问题标签、主题归并规则、证据抽取提示词、问题卡片模板和评测集。
  • 网站反馈要记录反馈页面和入口；功能反馈还要记录用户处于哪个使用阶段、是否完成操作、邀请评价的时机以及版本。
  • 最终产物是待核实的问题和建议：它们不是已经确认的根因，也不会自动修改功能或自动触达用户。
55怎样用行为证据分析反馈，并避免把相关性误说成因果？

口述版以“导出失败”为例，我会先保留用户的原话，再在明确的时间窗口和权限范围内，查询对应版本的导出错误、耗时和是否完成等行为证据，也就是用户或系统实际做了什么的记录。然后把已确认的事实、推测和还要验证的事项分开写。匿名数据或跨端数据无法可靠关联时，就保留“未知”，不强行补全。反馈率必须说明分母：是所有使用用户、收到邀请的用户，还是其他范围；如果只邀请成功用户，失败体验就可能被漏掉。行为变化和反馈同时出现，只能说明相关性，也就是两件事一起发生，不能据此证明一件事导致另一件事；要判断因果，还需要实验或进一步排查。

原话 → 可查证事实 → 假设 → 验证

  • 查询工具只开放参数化、只读的白名单接口：参数化是把查询条件作为受控参数传入，不能让模型拼接任意查询；不允许模型执行任意 SQL。
  • 评测重点包括：证据是否真的支持结论、不同问题的主题是否被错误合并、严重问题是否漏掉，以及是否编造了原始反馈中没有的上下文。
  • 问题排序要综合影响人数、严重度和证据可信度，不能只看反馈条数。
56客服会话分析：怎样把多轮对话整理成可复用的结构化结果？

口述版我会先准备一份脱敏的对话数据，里面保留会话 ID、角色、轮次和时间，也可以带上工单状态。这里的“结构化”可以理解为：不只写一段摘要，而是把对话中的关键信息放进固定字段，方便后续搜索、统计和复用。处理时先按会话把上下文组织起来，再抽取用户诉求、产品问题、客服做了什么、承诺了什么、当前是否解决，以及这些结论对应的证据轮次。长会话可以先分段抽取，最后再在会话级合并，这样能保留问题和状态前后变化。最终可以输出会话摘要、问题标签、待跟进事项和可追溯的证据，也可以按主题做汇总。这是一项独立的会话分析能力，不要求一定接入问卷或网站反馈。

客服会话能力包

  • 可复用内容：角色与轮次 Schema（也就是约定字段和数据格式的结构）、会话切分规则、用于抽取诉求和承诺的提示词、状态定义、摘要模板，以及评测集。
  • 结构化字段示例：intent（用户诉求）、product_issue（产品问题）、service_action（客服动作）、resolution_status（解决状态）、follow_up（待跟进事项）、evidence_turns（对应的证据轮次）。
  • 标签边界：客服服务问题和产品问题要分开打标；一段会话可能同时包含多个问题，不要强行压缩成一个标签。
57客服会话里，怎样判断问题是否真的解决，并验证分析质量？

口述版我不会只听客服说“已解决”，而会把状态分成几类：客服声称处理过、用户明确确认解决、系统记录能提供证据，以及目前无法判断。这里的“证据轮次”，就是能支持这个判断的具体对话轮次或系统记录。每个解决状态都要标出证据；如果承诺没有兑现，或者前后信息矛盾，就转人工复核。验证分析质量时，我会准备覆盖多种情况的评测集，包括转人工、重复咨询、多问题、模板化话术和长会话，分别检查它有没有识别真实诉求、找到证据位置、提取客服承诺并正确判断状态。用户没有再次咨询，也不能直接说明问题已经解决。

状态必须有证据

  • “首次解决率”是一次联系后解决的问题比例；“重复咨询率”是同一问题再次来咨询的比例；“解决时长”是从受理到确认解决所用的时间。三项指标都要先按业务约定好统计窗口和口径，再由程序计算，不能凭感觉估算。
  • 摘要必须保留未完成的事项和不确定之处；不能为了让报告看起来完整，就补写原文没有的处理结果。
  • 会话原文要按权限和留存规则保护。默认只把完成分析所必需、且已经脱敏的内容交给模型。
58三类资产哪些能力可以共用，哪些业务语义必须分开？

口述版可以共用的是技术底座，也就是支撑功能的通用部分：文件读取、脱敏（把姓名、手机号等敏感信息隐藏或替换）、模型接口封装、JSON 校验、失败重试、版本记录、日志，以及人工审核组件。不能直接混在一起的是业务协议，也就是每类资产对数据含义和处理流程的约定：问卷要保留题目和分母，反馈要保留触发它的上下文，会话要保留角色和问题是否解决。三类资产都应该有自己的调用入口、输入输出格式、评测集和报告模板。以后如果确实要比较不同来源的数据，应先做明确的映射，再单独出比较报告，不能默认把所有数据拼成一份“满意度”。

共享底座，不合并业务语义

  • 可以放在同一个代码仓库中，按三个模块组织；不必为了独立复用就拆成三个微服务。微服务是通过网络独立部署和调用的服务，这里并不是必须的架构选择。
  • 共用同一个模型或 SDK，不代表它们就是同一个 Agent。Agent 可以理解为围绕特定任务运行的一套工作单元；真正决定模块边界的是任务、协议和评测方式。
  • 每类资产只能读取已经获授权的数据。若要跨模块关联用户或记录，必须有明确的业务依据和相应权限，不能因为技术上能关联就直接合并。
59用 Node.js 和 MySQL，怎样从一个简单可用的资产原型开始？

口述版我会先选定一类资产和一份脱敏样本，也就是去掉姓名、账号等敏感信息、但保留分析所需结构的样本，先跑通一个最小闭环：导入数据、预处理、做确定性统计（同样输入按同样规则得到同样结果）、调用模型分析、校验输出结构、保存结果，再让人复核。Node.js 主要负责流程编排和接口，MySQL 负责保存任务、输入引用、配置版本、结果和审核记录。小任务先用同步处理或简单批处理；等实测发现耗时、并发或数据量成为问题，再考虑队列、并发和增量处理。每次任务都保留任务 ID 和输入摘要，这样重跑时能追溯到底用了什么输入和配置。不要一开始就上大规模平台，也不要把复杂架构本身当成资产价值。

按真实需求渐进建设

  • 任务元数据可以包括 asset_type、asset_version、input_ref、config_version、model、status、result_ref。元数据就是描述任务及其版本、状态和结果位置的信息；原始证据要放在独立权限控制下，不能因为普通任务记录可见就一并暴露。
  • 模型输出先做 Schema 校验。Schema 可以理解为规定字段、类型和必填项的“数据格式合同”；通过后还要回头核验证据，确认结论有对应依据。超时或失败只做有限重试；重跑要保留版本，避免同一业务工单被重复提交。
  • 先用真实样本测量耗时、成本和错误类型，再决定是否需要队列、缓存或向量检索。向量检索是按内容语义相似度查找资料，不是普通的精确关键词查询；没有实际需求和测量结果时，不必预先引入。
60怎样验证这些资产能复用、质量可评测，而且不会越权执行？

口述版我会把“复用”理解为：换一份问卷、一个产品或一个会话来源，主要靠配置就能继续使用，而不是每次重写代码；把“评测”理解为：用一组提前标注、标准明确的样本，检查结果是否达标。具体做法是先为每类资产准备独立的人工标注样本和验收标准，再测试这些替换场景。分别检查统计是否正确、分类是否准确、结论有没有证据支持、遇到未知情况会不会明确处理，以及报告是否易读；同时记录运行成功率、耗时和成本。外部文本只当作不可信数据，不能让它直接决定权限。工具授权、参数校验和审批都放在服务端控制。默认只允许分析和生成草稿；创建工单、修改业务或触达用户，必须经过明确授权。

复用、质量与安全分开验收

  • 同一资产要覆盖正常数据、空数据、缺字段、噪声、证据冲突和包含恶意指令的样本，不能只展示一次成功结果。
  • 模型、提示词或规则升级前，先跑原来的评测集；保留新旧结果差异和可回滚版本，便于发现退化并恢复。
  • 报告生成、审核通过、业务执行和问题改善是四种不同状态。能生成分析报告，不等于已经审核、自动解决了业务问题，更不等于可以直接执行操作。
61面试时，怎样在 90 秒内讲清三类可复用的 AI 资产？

口述版可以这样说：我会把用户洞察拆成三个能单独复用的能力包。第一类是问卷分析：做确定性统计，也就是输入和规则相同，结果应当可复核；再归纳开放题。第二类是网站和功能反馈分析：把反馈整理成带上下文和证据的问题卡片，方便追查原始信息。第三类是客服会话分析：提取用户诉求、已经采取的处理动作、还没解决的事项，以及最终解决状态。每一类资产都明确输入输出协议、规则和提示词、运行代码、报告模板与评测集；公共部分则包括脱敏、模型调用和人工审核底座。先用小范围真实任务验证价值，再根据实测结果扩展。只有确实需要动态补查时，才加入有边界的 Agent——也就是能按步骤调用工具、补充信息的程序，并限制它能查什么、做什么。

业务场景 → 资产交付 → 复用验证 → 安全边界

  • 结合前端／UI、Node.js 和 MySQL 经验，可以展示导入配置、结果校验、证据查看和人工审核界面。
  • 要明确区分方案设计和真实项目经历；没有实测，就不要编造准确率、节省人力或上线规模。
  • 不要把调用模型接口说成算法训练，也不要把三个场景包装成一个包办所有数据的大 Agent。
62每年约 9000 条开放式问卷回答，怎样清洗、区分情绪和真实诉求，并给原话可靠打标？什么时候需要 RAG？

口述版如果每年大约有 9000 条开放式回答，我会先做可追溯的批处理，不会一开始就上 RAG。RAG，也就是先从资料库检索相关内容，再让模型生成或判断；它适合查资料，不等于能替代全量统计。处理时保留脱敏后的原话和记录 ID，用规则标记空白、乱码和明显无关内容，但“无意见”和纯情绪不能直接当垃圾删掉。重复也要谨慎：只有确认是重复导入或重复提交，才按业务规则合并并留下记录；不同用户说了相同诉求，仍要保留人数和频次。模型按统一标注规范，把一条回答拆成必要的诉求片段，分别提取情绪、问题主题、具体诉求和对应证据原文；无法判断时允许标记“未知”，还要标出需要人工复核的情况，不能从抱怨中臆测用户需求。先用覆盖典型情况的人工样本校准标签，再分批处理全量数据。最后由程序统一汇总人数、回答条数和分母，并重点复核低置信度、边界案例和新出现的主题。这个规模的重点是规则、结构化抽取和质量验证；只有需要按问题回查历年原话，或要结合产品文档解释反馈时，才按需加入检索增强。RAG 不能替代全量分类和频次统计。

清洗 → 分层打标 → 全量统计 → 人工复核；需要回查时再加检索

  • 清洗不能把用户声音抹掉：保留脱敏原文、清洗版本、处理状态和排除原因。短回答、负面评价或“没有意见”，不能只因为长度短或情绪负面就判为无效；一条回答无效，也不代表整份问卷自动无效。
  • 重复要分两层处理：同一答卷被重复导入，或确认是重复提交，可以按业务规则合并并保留处理痕迹；不同受访者说了同一句话，只归到同一主题，不能删除人数。近似文本只能作为候选提示，不能仅凭语义相似度判定重复。
  • 例如原话是：“太难用了，每次上传大文件都失败，希望支持断点续传。”可以标为：情绪=负面；主题=文件上传／可靠性；问题=大文件上传失败；诉求=支持断点续传；证据分别指向对应原文。“太难用了”如果单独出现，只能标为负面情绪、体验笼统、缺少具体诉求，不能擅自推断成性能问题。
  • 先定义标签，再允许扩展：写清每个标签的含义、包含和排除条件、正例、反例以及“未知”项。一条回答可以有多个主题。结构可以包含 response_id、segment_id、emotion、topic、issue、request、evidence_span、needs_review、label_version。新主题先放入候选池，经过人工确认后再纳入并版本化。
  • 质量检查和分母核算要分开验证：人工样本要覆盖正常回答、无诉求、纯情绪、多诉求、否定和反讽等情况；检查是否误删无效回答、主题和诉求是否识别正确、证据是否真的支持标签。模型自己给出的置信度只能用来安排复核，不能直接当准确率。统计时按题目的有效回答数或有效受访者数去重，并明确分母；因为允许多标签，各标签占比相加可能超过 100%。
  • 实现可以从简单方案开始：用 Node.js 分批调用模型并校验 JSON，用 MySQL 保存原话引用、标签、证据和版本，再用 SQL 汇总全量结果。不要把 9000 条一次性塞进提示词，也不要用向量检索返回的 top-K 片段来估算总体频次。只有需要语义回查时，才补充向量索引；查询仍必须受权限和年份过滤约束。

复习建议：先遮住答案用 1–2 分钟说出结论，再用“原理 → 取舍 → 排查 / 验证”补充。术语要说准，数据和项目经历只讲自己真实做过的内容。
