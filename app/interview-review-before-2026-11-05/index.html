Containers · Images · Runtime

Docker 核心与实战

12 题 · 从概念到排障

01Docker 镜像和容器有什么区别？

口述版镜像是构建出来的只读模板，由分层文件系统和运行所需的元数据组成；容器则是镜像启动后的运行实例。容器在镜像层之上有自己的可写层，进程、网络和资源限制也属于运行时状态；容器删除后，可写层里的数据通常会一起消失，持久化数据应放到 volume 或 bind mount。一个镜像可以启动多个相互隔离的容器。

记忆要点

  • 镜像可复用，容器有生命周期；镜像不等于正在运行的服务。
  • 需要保留的状态不要只写进容器可写层。
02Dockerfile 的 RUN、CMD 和 ENTRYPOINT 分别做什么？

口述版RUN 在构建镜像时执行命令，通常会形成新的镜像层；CMD 和 ENTRYPOINT 则定义容器启动时运行什么。CMD 提供默认命令或默认参数，运行容器时可以被覆盖；ENTRYPOINT 定义容器的主程序，CMD 常用来给它提供默认参数。通常优先使用 JSON exec 写法，让应用直接作为进程运行并正确收到停止信号。

示例与边界

  • ENTRYPOINT ["python","app.py"] 加 CMD ["--port","8000"]：默认运行 app，也可替换参数。
  • shell 写法会经过 shell，信号转发和参数处理更容易踩坑；需要 shell 逻辑时注意最后用 exec 替换 shell 进程。
03EXPOSE 和端口映射有什么区别？只写 EXPOSE，宿主机能访问吗？

口述版EXPOSE 是镜像里的端口说明和元数据，不会自动把容器端口发布到宿主机。宿主机访问通常要在运行时配置端口映射，例如 -p 8080:80，把宿主机 8080 映射到容器 80。容器之间如果接入同一个 Docker 网络，一般可以直接通过服务名访问容器端口，不需要为了容器间通信发布宿主机端口。

记忆要点

  • EXPOSE 80 不等于 -p 8080:80。
  • 检查映射时看 docker ps 或 docker port；还要确认应用确实监听映射的容器端口。
04容器里的服务为什么经常需要监听 0.0.0.0，而不能只监听 localhost？

口述版127.0.0.1 或 localhost 只代表当前容器自己的回环接口。若服务只绑定这里，来自容器网络接口的连接通常到不了它，即使宿主机配置了端口映射也一样。服务需要接受容器外部连接时，一般绑定 0.0.0.0，表示监听容器的所有网络接口；同时仍需通过端口映射、防火墙或网络策略控制谁可以访问。

记忆要点

  • 绑定地址和端口映射是两个不同环节，不能互相替代。
  • 不要把“监听所有接口”误解成“应该向公网开放”；外部暴露范围还要单独限制。
05容器服务访问不到，通常按什么顺序排查？

口述版我会沿着请求链路逐层排查，而不是先重建容器：先看容器是否在运行、应用进程是否正常，再确认应用监听的地址和端口；接着从容器内部 curl 本机服务，检查容器日志和健康状态；之后核对端口映射、宿主机防火墙及云安全组；如果是容器间调用，再确认双方网络、服务名解析和目标端口。这样能把应用没启动、绑定地址错误、映射错误和网络隔离区分开。

排查顺序

  • docker ps -a、docker logs、docker inspect / health 状态。
  • 进程与监听地址 → 容器内访问 → 端口映射 → 防火墙 / 安全组 → Docker 网络与 DNS。
  • Dockerfile 的 EXPOSE 不是发布端口的证据。
06Docker Compose 中，应用服务应该怎么连接 Redis？为什么 localhost 往往不对？

口述版在 Compose 创建的共享网络里，服务通常可以用 Compose 配置中的服务名做 DNS 名称。所以应用容器应连接 redis:6379 这样的服务地址，而不是 localhost。localhost 在应用容器里指向应用容器自己，不是 Redis 容器；只有应用进程和 Redis 真正在同一容器内时，localhost 才可能指向目标服务。Redis 是否需要发布端口到宿主机，取决于是否需要从宿主机直接访问。

补充

  • 用相同 Compose project/network；核对端口、密码、TLS 等连接配置。
  • 服务名是容器网络内部的寻址方式，宿主机端口映射不能替代它。
07Docker volume、bind mount 和容器可写层怎么选？

口述版容器可写层跟随容器生命周期，不适合放必须保留的数据。Named volume 由 Docker 管理，适合数据库文件等持久数据；bind mount 把宿主机某个明确路径挂进容器，常用于本地开发热更新或需要直接共享主机文件的场景。选择时要考虑数据生命周期、迁移备份、权限和环境可移植性；还要注意挂载会遮住镜像里目标目录原本的内容。

记忆要点

  • 数据库生产数据常用 named volume 或外部存储，并配置备份与恢复。
  • bind mount 路径依赖宿主机环境；匿名卷生命周期和复用行为也要明确。
  • down -v 会删除受管理的卷，执行前要确认数据后果。
08Compose 的 depends_on 能保证依赖服务已经可用吗？healthcheck 和重试策略怎么配合？

口述版depends_on 默认主要解决服务启动顺序，不代表依赖已经完成初始化并能处理请求。可以给依赖服务配置 healthcheck，并在支持的 Compose 语法中让依赖关系等待 healthy 状态；但应用本身仍应该有连接超时、有限次数的重试和退避策略，因为运行中依赖也可能重启或暂时不可达。健康检查、启动顺序和应用重试是互补的，不是替代关系。

面试细节

  • healthcheck 要检测真实可用性，而不只是“进程还活着”。
  • 重试要有上限、退避和清晰错误；避免无间隔无限重试造成雪崩。
  • 确认实际使用的 Compose 版本与语法支持情况。
09Docker 构建缓存怎么利用？.dockerignore 为什么重要？

口述版Docker 通常按层复用构建缓存，前面某层的输入变化后，它和后续层可能需要重建。因此我会先复制变化频率低的依赖清单并安装依赖，再复制经常变化的源码，让源码修改不必每次重装依赖。.dockerignore 则用于排除不需要进入构建上下文的文件，减少传输和意外泄露风险。

示例与边界

  • Node 项目可先复制 lockfile 与 package manifest、安装，再复制源代码；具体命令按包管理器调整。
  • 排除 .git、本地依赖目录、构建产物、临时文件和敏感文件。
  • 密钥不要通过 Dockerfile 的 ARG / ENV 烘焙进镜像；构建时需要的秘密应采用合适的 secret mount 机制。
10什么是 Docker 多阶段构建？它解决什么问题？

口述版多阶段构建是在同一个 Dockerfile 里使用多个 FROM 阶段：前面的阶段安装编译工具、执行测试或构建产物，最后的运行阶段只把真正需要的文件复制进去。这样能避免把编译器、开发依赖和临时文件带进生产镜像，通常可以缩小镜像并减少攻击面。最后仍要从最终镜像做启动和运行测试，因为构建阶段通过不等于运行阶段具备全部运行时依赖。

记忆要点

  • 清楚区分 build stage 与 runtime stage。
  • 拷贝运行产物时别漏掉运行时库、配置或证书；最小镜像也要保持可维护与可调试。
11docker compose down 和 docker compose down -v 有什么区别？

口述版docker compose down 通常会停止并移除该项目的容器和网络，默认不删除声明的 named volumes；匿名卷也默认不会被 down 自动删除，但之后重新创建容器时不一定会自动重新挂回原来的匿名卷。加 -v 会删除 Compose 文件声明的 named volumes 以及关联的匿名卷；external volumes 不会因为这个命令被移除。由于卷里可能有数据库数据，执行前要确认目标项目和数据是否可丢弃。

记忆要点

  • 要重置本地数据库时才考虑 down -v，不要把它当成无害的日常清理。
  • 不同版本和命令参数可能影响细节；重要数据先备份并核对卷名。
12容器的 PID 1、SIGTERM 和优雅关闭有什么关系？

口述版容器内的主进程通常承担 PID 1。执行 docker stop 时，Docker 会先向容器主进程发 SIGTERM，等待宽限时间后仍未退出才发送 SIGKILL。应用需要能处理终止信号，停止接新任务、完成或取消正在处理的工作、刷新必要数据并关闭连接。使用 exec 形式让应用成为直接进程，通常比 shell 包装更容易正确收信号；多进程容器还要考虑 PID 1 的子进程回收，可按需使用 init 进程。

实践细节

  • Compose 可配置停止宽限时间；超时不是无限等待。
  • 注意 shell-form ENTRYPOINT / CMD 可能让信号先到 shell，导致子进程处理不符合预期。
  • 优雅关闭需要应用配合，单靠 Docker 配置不能保证业务任务安全完成。

Retrieval · Grounding · Evaluation

RAG 检索与系统设计

17 题 · 从检索到上线治理

13请从头到尾讲一下 RAG 的基本流程。

口述版RAG 通常分为离线建库和在线问答两条链路。离线侧先解析、清洗文档，按语义和长度切块并保留来源、版本、租户和权限等元数据，再生成 embedding、写入向量索引，也可以同步建立关键词索引。在线侧先校验用户身份和数据权限，再做查询理解或改写，召回相关片段，必要时融合关键词结果并重排，选择合适上下文交给模型生成，最后返回答案和可追溯引用。要通过检索指标、答案质量和线上 trace 持续评估。

讲清楚的几层

  • 数据摄取与索引；查询与权限过滤；召回、融合和重排；上下文构造与生成；引用、评估和监控。
  • 权限应在服务端的检索链路里执行，而不是把无权内容取回后只在前端隐藏。
14RAG 的文档分块怎么做？chunk size 和 overlap 怎么取舍？

口述版分块要以检索任务为目标，不是机械地按固定字符数切。通常优先保留标题、段落、列表或代码块等自然边界，并把文档路径、标题、版本等元数据带到 chunk 上。块太小可能丢失上下文，太大则主题混杂、召回不精确并占用更多上下文窗口；overlap 可以补上边界信息，但太多会造成重复片段和索引膨胀。我会用真实问题集比较不同策略的召回与答案效果。

可以尝试

  • 按文档结构切分，必要时用父子块或先小块召回、再取邻近上下文。
  • 评估 chunk 长度、overlap 和召回数量对 Recall、重复率、token 成本与生成质量的影响。
  • 不要把某个固定 token 数说成所有文档都适用的标准值。
15向量检索和 BM25 有什么差别？分别适合什么场景？

口述版向量检索把文本映射到语义向量空间，适合找表达不同但含义相近的内容；BM25 是基于词项匹配与词频等因素的稀疏检索，对精确词、产品名、错误码、代码符号或罕见术语往往更有优势。它们针对的错误类型不同，没有一个在所有场景里必然更好。企业知识库常会把两者结合，再根据效果决定是否需要重排。

记忆要点

  • 向量：语义相似、同义表达；BM25：字面命中、专有词和精确标识符。
  • 模型、语料、语言和查询类型都会影响结果，应用自己的评测集验证。
16什么是混合检索？如何合并向量召回和 BM25 结果？

口述版混合检索通常并行做 dense vector 和 BM25 检索，再把候选结果融合、去重，必要时交给 reranker 排序。由于两路检索分数的量纲和分布可能不同，不能不加验证就把原始分数直接相加；可以采用 Reciprocal Rank Fusion 这类基于名次的融合，或在有标注数据时学习或校准融合权重。最后要在同一组问题上比较各路单独效果和融合后的收益、延迟与成本。

评估方向

  • 比较 dense-only、BM25-only、混合召回及重排后的 Recall@K、MRR / nDCG。
  • 关注候选重复、不同检索器的互补性、权重稳定性和额外延迟。
17RAG 检索不准时，你会怎样分层定位问题？

口述版先用带相关文档标注的测试问题判断问题发生在哪一层：目标文档是否进入索引、文档解析和分块是否丢了关键信息；用户权限和元数据过滤是否误排除；查询改写是否偏离原意；embedding、向量字段或索引版本是否一致；候选召回是否不足；再看混合检索和 reranker 是否改变了排名；最后才看上下文拼装与生成是否误用或忽略证据。每个请求要能看到查询、过滤条件、候选片段、分数和阶段耗时，便于复现。

排查原则

  • 先区分“检索没找到”与“找到了但答案没用好”。
  • 结合逐层 trace 和固定的黄金问题集，不只靠主观试问。
  • 权限过滤错误也是检索错误，不能为了提升召回而绕过权限。
18Recall@K、MRR 和 nDCG 分别衡量什么？RAG 还要评估什么？

口述版Recall@K 看前 K 条里找回了多少相关文档，重点是相关证据有没有被召回；MRR 看第一个相关结果出现的位置，越靠前分数越高；nDCG 可以处理分级相关性，并对排名靠后的结果做折扣。它们主要评价检索排序，不代表最终回答正确。我还会评估答案正确性、是否忠于检索证据、引用是否支持结论、拒答是否恰当，以及延迟、成本和权限隔离。离线黄金集、人工评审和线上反馈要结合起来看。

补充

  • 统一标注口径、相关性等级、K 值和问题覆盖范围。
  • 生成质量指标不能替代检索指标，检索指标也不能单独代表用户价值。
  • 线上实验注意用户隐私、采样偏差和失败样本被漏记的问题。
19RAG 如何落实文档 ACL、租户隔离和检索权限？

口述版先在服务端识别当前用户、租户和权限范围，再在检索阶段用可靠的元数据过滤或隔离索引，确保无权文档不会进入模型上下文；拿到候选文档后仍可以做最终权限校验。权限变更要能同步到索引，缓存键也要包含用户或权限版本等隔离信息，防止一个用户命中的内容被另一个用户复用。不能先把敏感数据返回给浏览器，再靠前端隐藏来保证安全。

必须验证

  • 跨租户、权限撤销、共享文档、过滤失败和缓存命中等边界场景。
  • 索引元数据与源系统 ACL 的同步时效，失败时默认拒绝还是降级的策略。
  • 对高风险数据保留审计能力，并遵循最小权限原则。
20文档更新、删除和版本变更，怎样保证 RAG 索引不返回过期内容？

口述版为文档建立稳定的 canonical ID 和版本号，更新时根据文档 ID upsert 新版本，并删除旧版本遗留的 chunks；删除时也要传播 tombstone，避免只从源系统删掉而检索索引还留着。可以先构建新索引或新版本，再通过 alias / 版本切换原子发布；缓存需要按文档版本或变更事件失效。系统要定义同步延迟、失败重试和回滚方案，让索引更新可观测、可恢复。

记忆要点

  • chunk ID 与文档 ID / 版本的关系要稳定，避免更新后重复或残留。
  • 切换期间要防止旧新版本混杂；权限撤销和删除应重点验证。
  • 缓存 TTL 不是唯一一致性方案，需结合失效事件和版本校验。
21RAG 和微调有什么区别？什么时候选哪一种？

口述版RAG 在推理时从外部知识源检索证据，适合知识经常变化、需要引用来源或需要按用户权限取数的场景；它需要维护解析、索引、检索和权限链路。微调通过训练改变模型参数，更适合学习稳定的任务行为、输出风格或特定模式，不适合把频繁变化的事实当作唯一知识库。两者也可以结合：RAG 提供最新事实，微调帮助模型更稳定地遵循任务格式。最终要针对失败样本和评估数据选择，而不是把微调当成检索问题的通用修复。

取舍

  • 先判断问题是“缺知识”还是“不会按要求做”；再看是否需要最新事实、来源追踪、权限控制。
  • RAG 的召回、时效与基础设施有成本；微调有数据、训练与维护成本。
  • 选型用任务效果、合规、延迟和总成本验证。
22面对复杂问题，RAG 为什么要拆子问题？怎么避免越拆越偏？

口述版复杂问题可能同时包含多个实体、条件或证据需求，把它拆成可检索的子问题，有助于分别召回证据并判断哪一部分没有依据。但拆分本身也可能引入误解，所以我会保留原始问题和拆分依据，限制子问题数量与深度，为每个子问题独立检索并记录引用，最终再按原问题合并答案。简单问题不必强行拆；子问题超出原意或证据不足时，应收敛、澄清或说明限制。

设计要点

  • 限制规划轮数、子问题数、总 token 与总耗时。
  • 保留子问题到证据、再到最终结论的可追溯关系。
  • 不要把模型自行生成的子问题当成已经验证的事实。
23什么是 RAG 的多跳检索？和普通 top-K 检索有何不同？

口述版普通检索通常一次用用户问题找相关片段；多跳检索则需要连续推理和检索，例如先找到某个实体关联的项目，再用项目名称查它的时间或负责人。每一跳的候选都应有来源证据，必要时从证据中抽取实体或关系作为下一跳查询，并对整个证据链进行去重、排序和验证。多跳能处理跨文档关系，但会增加延迟和错误传播，因此要限制跳数，并在任一跳证据不足时停止或明确不确定。

面试补充

  • 区分多跳检索的证据链与模型凭空补出中间事实。
  • 记录每一跳的问题、候选、来源和停止原因；用多跳黄金问题集评估端到端成功率。
24RAG 如何防范检索文档中的 Prompt Injection？

口述版检索到的文档应该被视为不可信数据，而不是高优先级指令。系统提示要清楚区分指令与引用内容，不把文档里的“忽略规则、泄露秘密、执行工具”当作授权；更重要的是，不依赖模型自己识别注入，而要在工具层做最小权限、服务端授权和必要的人类确认，秘密也不应放进模型可见上下文。对模型输出和工具参数仍要验证，并用恶意文档测试整条链路。

纵深防御

  • 来源隔离与上下文标记；高风险工具的 allowlist、参数校验和权限检查。
  • 绝不因为检索文本要求就泄露凭据或触发有副作用的操作。
  • 过滤器可辅助，但不能保证识别所有新型注入；权限边界必须由程序执行。
25RAG 的 trace 应记录哪些信息？怎样用 p50 / p95 定位慢请求？

口述版我会给每次请求一个 trace ID，并把鉴权与过滤、查询改写、各路召回、融合、reranker、上下文构建、模型首 token 与总耗时、错误和重试拆成 span，记录候选数量、模型与索引版本、token 数等必要指标。p50 表示典型中位延迟，p95 反映较慢那一段请求；如果 p50 正常但 p95 很高，通常要按查询类型、索引分片、文档长度、重试和各阶段耗时分组，找到长尾来源，而不是只盯总平均值。日志要做脱敏和访问控制。

常见延迟分解

  • 请求排队、检索、重排、上下文拼装、模型首 token、生成总时长。
  • 看分位数和阶段分布，也看超时率、错误率、token 用量和成本。
  • 不要无策略地记录完整用户问题或敏感文档原文。
26RAG 检索的 top-K 应该怎么选？K 越大越好吗？

口述版K 越大通常越容易把相关证据纳入候选，但也会增加噪声、重复内容、排序开销和上下文 token，反而可能稀释模型注意力。要结合检索阶段和生成阶段分别选：先保证候选召回，再通过融合或 reranker 选出适合放入上下文的一小部分。用黄金问题集测 Recall@K、MRR / nDCG、回答质量、延迟和成本，按查询类型调整，而不是使用一个没有验证的通用 K。

注意

  • 区分初始候选 K 与最终上下文片段数。
  • 按 token 预算、片段重复率、文档长度与问题复杂度做评估。
  • 候选不足先修召回，不要仅靠盲目增大上下文数量。
27Reranker 是什么？在什么情况下值得加？

口述版Reranker 是第二阶段排序器：先用较快的向量或关键词检索取一批候选，再让重排模型针对“查询—文档片段”对进行更细的相关性判断并重新排序。它不能找回第一阶段完全没召回的文档，但常能改善候选集的精度和前排质量。适合检索结果噪声较大、语义区分重要且质量收益能覆盖延迟与成本的场景；是否启用要通过排名指标、最终答案质量和端到端延迟共同验证。

一句话记忆

  • 召回器负责尽量找全候选，reranker 负责更精细地排好已有候选。
  • 对候选对逐一重排会增加成本，需限制候选数并测量收益。
  • 常观察 MRR / nDCG、答案忠实度、p95 延迟和单位请求成本。
28知识库里有多个互相冲突的文档，答案该相信哪个？

口述版不要把“模型选了一个听起来顺的答案”当成冲突解决。我会尽量在索引元数据里标注文档来源、权威级别、适用范围、生效时间和版本；检索时据业务规则优先使用当前有效的权威来源，并检测冲突。如果来源的优先级或适用范围无法判定，就同时呈现依据与差异，说明不确定性，必要时追问用户，而不是拼接成一个确定结论。

预防与处理

  • 源系统做好版本治理、失效标记和文档责任人管理。
  • 过滤已过期文档，明确时间范围与适用产品 / 地区 / 角色。
  • 引用应能指向具体版本，方便核验与纠错。
29更换 embedding 模型时，怎样迁移现有向量索引？

口述版新旧模型的向量空间通常不兼容，不能把新模型生成的查询向量直接拿去和旧模型文档向量比较。我会给索引和向量记录标记模型版本，建立新 collection 或索引并对全量文档重新生成 embedding，再用评测集验证召回质量、过滤和延迟。部署上可双写或补齐增量变更，准备好后通过 alias 或配置原子切换，并保留旧索引用于回滚；验证稳定后再清理旧数据。

迁移检查

  • 维度、归一化方式、距离函数、分块版本和元数据字段是否一致。
  • 迁移期间新增、更新、删除如何补齐，切换后是否会混用不同模型的向量。
  • 索引回滚、资源成本和版本观测都要提前设计。

Python 基础与 Agent 应用

20 题 · 从语法、数据结构到 RAG / Agent 工程

30Python 是动态类型语言是什么意思？类型提示会在运行时强制检查吗？

口述版Python 变量名绑定到对象，类型属于对象而不是变量；同一个变量可以在不同时间指向不同类型的对象，因此称为动态类型。类型提示表达开发者预期，供 IDE、静态检查器和文档使用，Python 默认不会因为类型提示自动拒绝不匹配的值。

记忆要点

  • 动态类型不等于没有类型；对象始终有类型。
  • 类型提示改善可读性与工具检查，但需要 mypy、pyright 等工具做静态校验。
31list、tuple、set、dict 分别适合什么场景？

口述版list 是有序、可变序列，允许重复；tuple 是有序、不可变序列，适合表示不希望被改写的固定组合；set 保存不重复的可哈希元素，适合成员测试和集合运算；dict 保存键值映射，适合按键快速查找。Python 的 dict 保留插入顺序，但不要把 set 的遍历顺序当作稳定契约。

快速对照

  • 需要顺序且会增删：list；固定组合：tuple。
  • 去重 / 成员判断 / 集合关系：set；按 key 查值：dict。
32Python 的可变与不可变对象有什么区别？赋值和复制有什么坑？

口述版不可变对象（如 int、str、tuple）创建后不能原地修改；可变对象（如 list、dict、set）可以原地更新。b = a 只是让两个名字引用同一个对象，不会复制。浅拷贝只复制外层容器，内部嵌套对象仍共享；需要递归复制时可考虑 copy.deepcopy，但要先确认对象结构和性能需求。

常见追问

  • 用 a.copy() 或 copy.copy(a) 做浅拷贝；嵌套列表要特别注意内部别名。
  • 函数默认参数不要写成 items=[]；用 None 作默认值，再在函数内新建列表。
33`==` 和 `is` 有什么区别？为什么判断 None 要用 `is`？

口述版== 比较两个对象的值是否相等，具体行为可由类的 __eq__ 定义；is 比较是否为同一个对象。None 是单例，因此惯用 value is None 或 value is not None。不要用 is 比较字符串或数字的值，驻留 / 缓存等实现细节不应成为程序正确性的前提。

面试提醒

  • 值相等：==；对象身份：is。
  • 判断空值用 is None，空列表、空字符串等也可直接按真值判断，但需区分业务语义。
34dict 的 key 和 set 的元素为什么必须可哈希？

口述版dict 和 set 通过哈希值快速定位对象，并用相等性处理哈希冲突；所以 key / 元素必须在其存活期间保持稳定的哈希与相等关系。不可变的 int、str 和满足条件的 tuple 常可哈希；list、dict、set 因为可变而不可哈希。平均情况下 dict 查找和 set 成员判断接近 O(1)，但这是平均复杂度，不代表所有输入下都保证常数时间。

补充

  • 相等的对象必须有相同哈希值；自定义对象要谨慎设计 __hash__ 与 __eq__。
  • 元组只有在其中所有元素都可哈希时，才可用作 dict key 或 set 元素。
35Python set 的并集、交集、差集分别是什么？

口述版设 A、B 是两个集合：并集包含 A 或 B 中出现的所有元素；交集只保留同时属于 A 和 B 的元素；差集 A - B 保留在 A 里、但不在 B 里的元素，因此差集有方向。对 a={1,2,3}、b={3,4}，并集是 {1,2,3,4}，交集是 {3}，a-b 是 {1,2}，b-a 是 {4}。

高频记忆卡

  • 运算符：并集 a | b，交集 a & b，差集 a - b，对称差集 a ^ b。
  • 方法：a.union(b)、a.intersection(b)、a.difference(b)、a.symmetric_difference(b)；这些返回新集合。
  • 例如权限差异可用 required - granted 找缺少项；比较两版数据可用交集或对称差集。
36列表推导式怎么写？其中的 if 是过滤条件吗？

口述版列表推导式的基本形式是 [表达式 for 项目 in 可迭代对象 if 条件]。例如 [n * n for n in nums if n % 2 == 0] 会只挑出偶数并平方：这里 if 写在 for 后面，作用是过滤，不符合条件的项目不会进入结果。若要对每个项目做条件转换而不是过滤，应把三元表达式放在最前面，例如 [n if n >= 0 else 0 for n in nums]。

高频记忆卡

  • 记法：先写结果表达式，再写 for，末尾 if 表示“只保留符合条件的项”。
  • 过滤：[x for x in xs if 条件]；转换：[A if 条件 else B for x in xs]。
  • 多层循环和条件过于复杂时，普通 for 循环通常更容易读、也更容易调试。
37Python 函数的位置参数、关键字参数、默认值和 `*args/**kwargs` 怎么理解？

口述版位置参数按传入顺序绑定，关键字参数按参数名绑定；有默认值的参数可省略。*args 收集额外的位置参数为 tuple，**kwargs 收集额外的关键字参数为 dict。默认参数表达式在函数定义时求值一次，因此可变对象默认值会在多次调用间共享；常见写法是默认 None，在函数内部创建新对象。

面试补充

  • 让调用方更清楚地表达意图时可使用关键字参数。
  • 参数顺序、仅限位置参数 /、仅限关键字参数 * 可用于设计稳定 API；不必过度使用。
38Python 中怎样设计异常处理？`try/except/else/finally` 各做什么？

口述版try 放可能失败的代码；except 捕获并处理预期异常；else 只在 try 没有异常时执行；finally 无论是否发生异常通常都会执行，适合清理资源。应尽量捕获具体异常并保留上下文，不要用空的 except 吞掉错误。对调用方有意义的业务失败可定义清晰的自定义异常，并用 raise ... from exc 保留异常链。

实用原则

  • 异常处理边界要合适：能恢复就处理，不能恢复就补充上下文后向上抛出。
  • 文件、网络请求等操作应区分超时、连接失败、状态错误和数据格式错误。
39什么是可迭代对象、迭代器和生成器？

口述版可迭代对象可以通过 iter(obj) 得到迭代器；迭代器实现 __next__，逐项产生数据，结束时抛出 StopIteration。生成器函数在函数体内使用 yield，调用后得到生成器对象，执行会在每次 yield 暂停并在下次迭代继续。它们适合流式处理大文件或数据管道，避免一次把所有结果放进内存；但生成器通常只能消费一次。

记忆要点

  • return 结束函数；yield 产出一项并保留执行状态。
  • 需要重复遍历时先确认对象是否可重用；必要时物化为 list，但要权衡内存。
40`with` 语句和上下文管理器解决什么问题？

口述版with 会把资源获取和清理配对起来，即使代码块中发生异常，也会调用上下文管理器的退出逻辑。文件对象是常见例子：with open(path) as f: 结束后会关闭文件。自定义上下文管理器可实现 __enter__ / __exit__，也可使用 contextlib.contextmanager；数据库事务、锁和临时资源也适合用此模式明确生命周期。

面试要点

  • 重点不是少写几行代码，而是让资源释放在异常路径上也可靠。
  • 异步资源可使用 async with，对应异步上下文管理器协议。
41`async` / `await` 是什么？调用 `async def` 会立刻执行吗？

口述版async def 定义协程函数；调用它通常只会创建 coroutine 对象，不会从头到尾立即执行。协程需要在事件循环中通过 await、asyncio.create_task 等方式运行；遇到可等待操作时可让出控制权，使其他协程继续。它适合大量 I/O 等待任务的并发处理，并不会自动让 CPU 密集计算变快；事件循环中的同步阻塞调用会卡住其他任务。

关键边界

  • 记得等待协程或把任务交给事件循环，否则可能出现未等待协程警告。
  • 使用异步 HTTP / 数据库客户端，设置超时、取消和异常处理；不要在事件循环里直接做长时间阻塞工作。
42I/O 密集和 CPU 密集任务，线程、进程、asyncio 怎么选？

口述版I/O 密集任务主要在等网络或磁盘：可以用 asyncio 管理大量协程，也可以在合适场景用线程；CPU 密集任务需要大量计算，在常见 CPython 构建中线程受 GIL 限制，通常可考虑多进程或进程池获得多核并行。选择前还要考虑依赖库是否释放 GIL、任务规模、序列化成本、共享状态与部署环境。

简化判断

  • 大量并发 I/O：asyncio 或线程；CPU 密集计算：优先评估多进程。
  • 并发不是越多越好；用超时、限流、队列和实测吞吐 / 延迟控制资源。
43Python 调 REST API 时，JSON 解析和错误处理要注意什么？

口述版标准库 json.loads(text) 把 JSON 字符串解析为 Python 对象，json.dumps(obj) 把对象序列化为 JSON 文本；requests 或 httpx 的 response.json() 则解析响应体，但不应把它当作 HTTP 成功检查。稳妥流程包括设置连接 / 读取超时、检查状态码（如 raise_for_status()）、处理网络错误和 JSON 解码错误，并验证关键字段的类型与必填约束。

实用检查

  • JSON 语法正确不代表数据符合业务 schema；在边界处验证结构。
  • 重试要有上限和退避；对非幂等写请求，不要未经设计就盲目重试。
44Python 模块、包和 `if __name__ == "__main__"` 有什么作用？

口述版模块通常是一个 Python 文件；包用于组织相关模块。import 会执行模块顶层代码，因此模块顶层宜放定义而不是启动服务、运行昂贵任务或产生副作用。if __name__ == "__main__": 中的代码只在文件作为主程序执行时运行，作为模块导入时不会运行，常用于命令行入口和本地演示。

设计提示

  • 把可复用逻辑放函数 / 类中，入口层负责参数解析和启动。
  • 绝对导入和相对导入要与包结构保持一致，避免通过随意改工作目录掩盖导入问题。
45Python 项目为什么要用虚拟环境？依赖如何管理？

口述版虚拟环境为项目隔离 Python 包，减少不同项目之间的版本冲突。常见流程是创建并激活 venv，再用 pip 安装依赖；项目应记录依赖声明，并根据团队工具生成可复现的锁定版本。部署和 CI 应使用明确的 Python / 依赖版本，升级依赖时运行测试，而不是依赖某台机器上“刚好能用”的全局环境。

注意

  • 常用工具包括 venv、pip、pyproject.toml 及团队选定的锁文件方案。
  • 密钥不应写进依赖文件或提交到仓库；配置从安全的环境或密钥管理机制注入。
46类型提示和 Pydantic 这类数据校验工具有什么区别？

口述版类型提示让参数、返回值和数据结构的预期更清楚，静态分析器可在运行前发现部分问题；Python 默认不会自动执行完整的运行时类型校验。Pydantic 等验证库可在运行时解析并验证外部输入，例如 HTTP JSON 请求体，适合在系统边界把不可信数据转成受约束的数据模型。校验仍应覆盖业务规则、权限和安全限制，不能只依靠类型声明。

常见说法

  • 静态类型检查与运行时数据验证互补，不是互相替代。
  • 外部数据先验证再进入业务逻辑；内部类型提示帮助代码维护与 IDE 补全。
47怎样用 pytest 测试 Python API 或业务逻辑？

口述版单元测试应聚焦可独立验证的函数或模块；pytest 会发现测试并提供断言、fixture 和参数化测试。网络、时间、随机数等外部依赖可通过依赖注入或 mock 控制；API 层还要覆盖正常输入、校验失败、鉴权失败、依赖超时和异常响应。测试要验证可观察行为，而不只是复刻内部实现；必要时再增加真实依赖的集成测试。

面试要点

  • 用 fixture 管理重复的准备 / 清理逻辑，用参数化覆盖边界输入。
  • 异步代码要使用与项目兼容的异步测试支持；避免测试通过 mock 掩盖真实协议问题。
48在 RAG 系统里，Python 通常承担哪些环节？

口述版Python 常用于离线文档摄取、解析与切块，调用 embedding 模型并写入向量库；在线链路则负责鉴权、查询预处理、检索与重排、上下文构造、模型调用、引用整理和 API 返回。工程上会把这些环节分层，明确数据模型、超时、重试、日志和评估接口；LangChain 等框架可加速集成，但不替代对检索质量、权限过滤和数据流的理解。

回答框架

  • 把离线索引与在线查询分开说清楚，并解释每层输入输出。
  • 强调 ACL 在服务端执行、索引与模型版本可追踪、日志注意脱敏；不要声称做过自己没做过的项目。
49用 Python 构建 Agent / 工具调用服务时，如何保证可靠与安全？

口述版可把 Agent 拆为模型决策、工具 schema、服务端执行器和结果整理层。工具参数要按 schema 校验，服务端还要做身份授权、allowlist、速率 / 超时限制和结果大小限制；模型输出与工具结果都应视为不可信输入。对有副作用或高风险的工具，应按业务要求设置确认门槛；还要限制最大迭代步数、提供重试与幂等策略，并记录可脱敏的 trace。

面试要点

  • Prompt 不是权限边界；检索文本或模型输出不能自行授权工具操作。
  • 明确失败停止、超时取消、重复调用处理和人工确认策略。

用户洞察：三类可复用 AI 资产

13 题 · 独立场景、输入输出、复用与评测

三个独立能力包，不是一个包办所有数据的 Agent。每类可单独输入数据、运行分析并交付结果；按实际需求配置，不预设每日数据量。

01 · 调查问卷数据分析
输入：题目、选项、规则与脱敏答卷。输出：统计表、开放题主题、证据与调研摘要。可复用：题目映射、统计代码、分析提示词、报告模板与评测集。

02 · 网站在线反馈／功能使用反馈分析
输入：用户原话、页面／功能与授权上下文。输出：问题卡片、主题、证据和排查建议。可复用：反馈协议、标签规则、证据抽取提示词、卡片模板与评测集。

03 · 客服会话分析
输入：带角色、轮次与时间的脱敏会话。输出：诉求、处理动作、解决状态与待跟进事项。可复用：会话 Schema、切分规则、抽取提示词、摘要模板与评测集。

  1. 场景边界
  2. 输入输出协议
  3. 规则与提示词
  4. 运行代码
  5. 报告模板
  6. 样例与评测集

共享底座，独立业务口径。脱敏、模型调用、结构校验、版本记录和人工审核可共用；问卷分母、反馈触发条件与会话解决状态分别定义。流程确定时用程序与模型调用，需要动态补查证据时才引入有边界的 Agent；业务执行另走授权与审批。

50为什么把用户洞察拆成三类可复用 AI 资产，而不是做一个包办所有数据的 Agent？

口述版我会分别做调查问卷数据分析、网站在线反馈／功能使用反馈分析、客服会话分析三类资产。每类都有自己的输入协议、分析流程、提示词、输出模板和评测集，可以独立调用与迭代。共用脱敏、模型调用、结构校验和审核等底座，但不混用业务口径。流程确定时用普通程序和模型调用即可，只有需要根据中间结果补查证据时才引入有边界的 Agent。

三类资产，独立使用

  • 问卷资产输出统计表、开放题主题和调研摘要；反馈资产输出问题卡片与证据；客服资产输出会话结构化结果与待跟进事项。
  • 复用的是可运行、可配置、可验证的能力包，不是只保存一条通用提示词。
  • 按实际任务与数据量选实现，不预设每日规模，也不为展示技术而先上复杂多 Agent 编排。
51一份可复用 AI 分析资产，具体应该包含哪些东西？

口述版至少包含适用场景与边界、输入 Schema、样例数据、预处理规则、提示词与输出 Schema、分析代码、报告模板、评测样本和版本说明。业务方提供符合协议的数据与配置，就能得到稳定格式的结果。项目变化时优先调整题目映射、标签和模板，而不是复制整套代码；提示词、标签、模型与统计口径都记录版本，便于比较和回滚。

资产交付清单

  • 输入与输出都提供成功、缺字段、空数据和异常样例；明确必填项、可选项与未知值。
  • 配置和代码分离：业务名称、分析窗口、标签体系与报告模板可配置；权限不交给提示词控制。
  • 版本包可组织为 schemas、prompts、rules、templates、evals 和 runner，并附最小调用示例。
52调查问卷数据分析资产：从输入到输出怎么设计？

口述版输入是问卷题目、选项、量表方向、跳题规则、问卷版本和脱敏答卷。先用程序校验和清洗，再用 SQL 或代码计算单选、多选、量表和分群统计；模型负责开放题分类、主题归纳和带证据的摘要。最终输出口径明确的统计表、开放题主题、代表原话、样本局限和待验证建议。换一份问卷时通过题目映射与配置复用，不把统计计算交给模型自由发挥。

问卷分析能力包

  • 处理链路：题目映射 → 有效性校验 → 确定性统计 → 开放题语义分析 → 报告校验与人工复核。
  • 复用内容：题目 Schema、统计函数、开放题提示词、分群配置、报告模板与问卷评测集。
  • 年终调研或日常问卷可复用同一能力，但各自保留招募方式、问卷版本与分析目的。
53问卷分析怎样保证分母、样本偏差和跨期比较不出错？

口述版每个指标先说明符合条件人数、有效答题人数和缺失情况。未答、跳题、不适用和真实低分分别处理，多选题注明分母与可多选。分群比较要展示样本量，样本过小不下强结论；跨期先核对题目、量表和样本人群是否一致。模型可以解释观察到的差异，但不能自行补全缺失答案，也不能把便利样本的结果直接外推为全部用户的看法。

统计口径写进资产规则

  • 用小型已知答案的数据集校验人数、占比、量表方向和跳题逻辑；模型摘要另做证据核验。
  • 开放题允许多标签，标签占比相加可能超过 100%，报告必须说明。
  • 只有存在合理抽样与校正依据时才做相应加权；没有依据就明确样本局限。
54网站在线反馈／功能使用反馈分析资产：核心输入和产物是什么？

口述版输入是用户原话、页面或功能、提交时间、版本、设备，以及获得授权的使用上下文。先脱敏和去重，再提取问题、诉求、严重度与证据，归并同类主题，形成可审核的问题卡片。卡片包含现象、影响范围、原话、已知上下文、未知项和排查建议；需要时再由受控工具补查行为指标。网站反馈和功能后反馈可以共用这类资产，但保留各自入口和触发条件。

反馈分析能力包

  • 复用内容：反馈输入协议、问题标签、主题归并规则、证据抽取提示词、问题卡片模板与评测集。
  • 网站反馈记录页面和入口；功能反馈记录使用阶段、是否完成、邀请评价时机及版本。
  • 产物是待核实的问题与建议，不直接认定根因，也不自动改功能或触达用户。
55反馈分析怎样结合行为证据，而不把相关性说成因果？

口述版以导出失败为例，先保留用户描述，再在明确的时间窗口与权限范围内查询对应版本的导出错误、耗时和完成情况，最后将事实、推测与待验证项分开写。匿名或跨端数据无法可靠关联时保留未知。反馈率需说明分母是使用用户、收到邀请的用户还是其他范围；只邀请成功用户会漏掉失败体验。行为变化与反馈同时出现只能支持相关性，因果还需实验或进一步排查。

原话 → 可查证事实 → 假设 → 验证

  • 查询工具只开放参数化、只读的白名单接口；不允许模型执行任意 SQL。
  • 评测重点：证据是否支持结论、主题是否误合并、严重问题是否漏掉、是否编造缺失上下文。
  • 问题排序结合影响人数、严重度和证据可信度，不只看反馈条数。
56客服会话分析资产：怎样把多轮对话变成可复用的结构化结果？

口述版输入是带会话 ID、角色、轮次和时间的脱敏对话，以及可选的工单状态。先按会话组织上下文，再抽取用户诉求、产品问题、客服动作、承诺事项、解决状态和证据轮次。长会话可分段抽取，再在会话级合并，避免丢失前后变化。输出会话摘要、问题标签、待跟进事项与可追溯证据，也可以按主题汇总；它是独立的会话分析能力，不需要接入问卷或网站反馈才能运行。

客服会话能力包

  • 复用内容：角色与轮次 Schema、会话切分规则、诉求／承诺抽取提示词、状态定义、摘要模板和评测集。
  • 结构化字段示例：intent、product_issue、service_action、resolution_status、follow_up、evidence_turns。
  • 客服服务问题与产品问题分别打标；一段会话可以包含多个问题，不强行压成一个标签。
57客服会话中，怎样判断问题是否解决并验证分析质量？

口述版我会区分客服宣称已处理、用户明确确认、系统记录支持和状态未知，不能把客服一句已解决当成事实。解决状态需要附证据轮次，未兑现承诺与矛盾信息进入人工复核。评测集覆盖转人工、重复咨询、多问题、模板话术和长会话，分别检查诉求识别、证据位置、承诺抽取与状态判断。没有再次咨询也不能直接认定已解决。

状态必须有证据

  • 首次解决率、重复咨询率与解决时长采用业务确认的窗口和定义，由程序计算。
  • 摘要保留未决事项和不确定性；不要为了让报告完整而补写不存在的处理结果。
  • 会话原文按权限和留存规则保护，默认只把完成分析所必需的脱敏内容交给模型。
58三类资产可以共享哪些能力？哪些内容不能混在一起？

口述版可以共享文件读取、脱敏、模型接口封装、JSON 校验、重试、版本记录、日志与人工审核组件；这些是技术底座。问卷的题目与分母、反馈的触发上下文、会话的角色与解决状态则属于各自业务协议，应该独立。每类资产有自己的调用入口、输入输出、评测集和报告模板。以后确有跨来源比较需求，再做显式映射和单独报告，不默认把所有数据拼成一份满意度。

共享底座，不合并业务语义

  • 可以是同一个代码仓库里的三个模块，不必为了独立复用拆成三个微服务。
  • 同一个模型或 SDK 不代表同一个 Agent；模块边界由任务、协议与评测决定。
  • 各资产只读取被授权的数据，跨模块关联用户或记录需要明确的业务依据与权限。
59用 Node.js 和 MySQL，怎样从一个简单可用的资产原型开始？

口述版先选一类资产和一份脱敏样本，做导入、预处理、确定性统计、模型分析、结构校验、结果保存与人工复核的最小闭环。Node.js 负责流程与接口，MySQL 保存任务、输入引用、配置版本、结果和审核记录。小任务先同步或简单批处理，按实测再增加并发、队列和增量处理。通过任务 ID 与输入摘要保证重跑可追踪，不默认引入大规模平台，也不把复杂架构当成资产价值。

按真实需求渐进建设

  • 任务元数据可含 asset_type、asset_version、input_ref、config_version、model、status、result_ref；原始证据受独立权限保护。
  • 模型输出先校验 Schema，再核验证据；超时与失败有限重试，重跑保留版本，不重复提交业务工单。
  • 用实际样本测耗时、成本和错误类型，再决定是否需要队列、缓存或向量检索。
60怎样证明这些资产可复用、可评测，而且不会越权执行？

口述版先为每类资产准备独立的人工标注样本和验收标准，再测试更换问卷、产品或会话来源后能否通过配置复用。分别检查统计正确性、分类质量、证据支持、未知处理和报告可读性；同时记录运行成功率、耗时和成本。外部文本当作不可信数据，工具授权、参数校验与审批由服务端控制。默认只分析和生成草稿，创建工单、改业务或触达用户必须走明确授权流程。

复用、质量与安全分开验收

  • 同一资产测试正常、空数据、缺字段、噪声、冲突证据与恶意指令样本；不能只展示一次成功结果。
  • 模型、提示词或规则升级先跑原评测集，并保留差异与回滚版本。
  • 报告生成、审核通过、业务执行和问题改善是不同状态；分析资产不承诺自动解决业务问题。
61面试时怎样用 90 秒讲清这三类 AI 资产？

口述版可以这样说：我会将用户洞察拆成三个可独立复用的能力包。问卷分析做确定性统计与开放题归纳；网站和功能反馈分析生成带上下文和证据的问题卡片；客服会话分析抽取诉求、处理动作、未决事项和解决状态。每类都交付输入输出协议、规则与提示词、运行代码、报告模板和评测集，共享脱敏、模型调用与审核底座。先用小范围真实任务验证价值，再按实测扩展；确需动态补查时才加入有边界的 Agent。

业务场景 → 资产交付 → 复用验证 → 安全边界

  • 结合前端／UI、Node.js 与 MySQL 经验，可展示导入配置、结果校验、证据查看和人工审核界面。
  • 方案设计与真实项目经历要明确区分；没有实测就不编造准确率、节省人力或上线规模。
  • 不把调用模型接口等同于算法训练，也不把三个场景描述成一个包办所有数据的大 Agent。
62每年约 9000 条开放式问卷回答，如何清洗、区分情绪与诉求、给原话打标？需要 RAG 吗？

口述版如果每年约 9000 条开放式回答，我会先做可追溯的批处理，而不是直接上 RAG。保留脱敏原话和记录 ID，用规则标记空白、乱码与明显无关内容；“无意见”和纯情绪单列，不等于垃圾。去重只剔除确认重复提交的记录，不同用户表达同一诉求仍保留频次。模型按统一的标注规范，把每条回答拆成必要的诉求片段，分别输出情绪、问题主题、具体诉求、证据原文与待复核标记，允许多标签和未知，不能从抱怨里编造需求。先用人工标注样本校准标签，再分批处理全量，由程序汇总人数、条数和分母，复核低置信度、边界案例及新主题。这个规模的核心是规则、结构化抽取和质量验证；只有需要按问题回查历年原话，或结合产品文档解释反馈时，才考虑检索增强。RAG 不替代全量分类统计。

清洗 → 分层打标 → 全量统计 → 复核；检索按需加

  • 清洗不抹掉声音：保留原始脱敏文本、清洗版本、处理状态和排除原因；短回答、负面评价或“没有意见”都不能仅凭长度或情绪判无效，回答级无效也不自动使整份问卷无效。
  • 重复分两层：同一答卷被重复导入或确认重复提交，按业务规则合并并留痕；不同受访者说同一句话，只归并主题，不删除人数。近似文本可做候选提示，不能只凭语义相似度判重复。
  • 原话示例：“太难用了，每次上传大文件都失败，希望支持断点续传。”可标为：情绪=负面；主题=文件上传／可靠性；问题=大文件上传失败；诉求=断点续传；证据分别指向对应原文。“太难用了”单独出现时，只能标负面情绪、体验笼统、缺少具体诉求，不能脑补为性能问题。
  • 标签先定义再扩展：写清标签含义、包含／排除条件、正反例与未知项，一条回答可有多个主题。结构可含 response_id、segment_id、emotion、topic、issue、request、evidence_span、needs_review、label_version；新主题先进入候选池，经人工确认后版本化。
  • 质量和分母单独验证：人工样本覆盖正常、无诉求、纯情绪、多诉求、否定与反讽；检查无效误删、主题／诉求识别和证据一致性。模型自报置信度只作复核线索，不当作准确率；按题目有效回答或有效受访者去重计数，说明分母，多标签占比之和可能超过 100%。
  • 实现从简单开始：Node.js 分批调用模型并校验 JSON，MySQL 保存原话引用、标签、证据和版本，SQL 汇总全量结果；不把 9000 条一次塞进提示词，也不拿向量检索 top-K 的片段估算总体频次。需要语义回查时才补向量索引，查询仍受权限与年份过滤约束。

复习建议：先遮住答案用 1–2 分钟说出结论，再用“原理 → 取舍 → 排查 / 验证”补充。术语要说准，数据和项目经历只讲自己真实做过的内容。
