Containers · Images · Runtime

Docker 核心与实战

12 题 · 从概念到排障

01Docker 镜像和容器有什么区别？

口述版镜像是构建出来的只读模板，由分层文件系统和运行所需的元数据组成；容器则是镜像启动后的运行实例。容器在镜像层之上有自己的可写层，进程、网络和资源限制也属于运行时状态；容器删除后，可写层里的数据通常会一起消失，持久化数据应放到 volume 或 bind mount。一个镜像可以启动多个相互隔离的容器。

记忆要点

  • 镜像可复用，容器有生命周期；镜像不等于正在运行的服务。
  • 需要保留的状态不要只写进容器可写层。
02Dockerfile 的 RUN、CMD 和 ENTRYPOINT 分别做什么？

口述版RUN 在构建镜像时执行命令，通常会形成新的镜像层；CMD 和 ENTRYPOINT 则定义容器启动时运行什么。CMD 提供默认命令或默认参数，运行容器时可以被覆盖；ENTRYPOINT 定义容器的主程序，CMD 常用来给它提供默认参数。通常优先使用 JSON exec 写法，让应用直接作为进程运行并正确收到停止信号。

示例与边界

  • ENTRYPOINT ["python","app.py"] 加 CMD ["--port","8000"]：默认运行 app，也可替换参数。
  • shell 写法会经过 shell，信号转发和参数处理更容易踩坑；需要 shell 逻辑时注意最后用 exec 替换 shell 进程。
03EXPOSE 和端口映射有什么区别？只写 EXPOSE，宿主机能访问吗？

口述版EXPOSE 是镜像里的端口说明和元数据，不会自动把容器端口发布到宿主机。宿主机访问通常要在运行时配置端口映射，例如 -p 8080:80，把宿主机 8080 映射到容器 80。容器之间如果接入同一个 Docker 网络，一般可以直接通过服务名访问容器端口，不需要为了容器间通信发布宿主机端口。

记忆要点

  • EXPOSE 80 不等于 -p 8080:80。
  • 检查映射时看 docker ps 或 docker port；还要确认应用确实监听映射的容器端口。
04容器里的服务为什么经常需要监听 0.0.0.0，而不能只监听 localhost？

口述版127.0.0.1 或 localhost 只代表当前容器自己的回环接口。若服务只绑定这里，来自容器网络接口的连接通常到不了它，即使宿主机配置了端口映射也一样。服务需要接受容器外部连接时，一般绑定 0.0.0.0，表示监听容器的所有网络接口；同时仍需通过端口映射、防火墙或网络策略控制谁可以访问。

记忆要点

  • 绑定地址和端口映射是两个不同环节，不能互相替代。
  • 不要把“监听所有接口”误解成“应该向公网开放”；外部暴露范围还要单独限制。
05容器服务访问不到，通常按什么顺序排查？

口述版我会沿着请求链路逐层排查，而不是先重建容器：先看容器是否在运行、应用进程是否正常，再确认应用监听的地址和端口；接着从容器内部 curl 本机服务，检查容器日志和健康状态；之后核对端口映射、宿主机防火墙及云安全组；如果是容器间调用，再确认双方网络、服务名解析和目标端口。这样能把应用没启动、绑定地址错误、映射错误和网络隔离区分开。

排查顺序

  • docker ps -a、docker logs、docker inspect / health 状态。
  • 进程与监听地址 → 容器内访问 → 端口映射 → 防火墙 / 安全组 → Docker 网络与 DNS。
  • Dockerfile 的 EXPOSE 不是发布端口的证据。
06Docker Compose 中，应用服务应该怎么连接 Redis？为什么 localhost 往往不对？

口述版在 Compose 创建的共享网络里，服务通常可以用 Compose 配置中的服务名做 DNS 名称。所以应用容器应连接 redis:6379 这样的服务地址，而不是 localhost。localhost 在应用容器里指向应用容器自己，不是 Redis 容器；只有应用进程和 Redis 真正在同一容器内时，localhost 才可能指向目标服务。Redis 是否需要发布端口到宿主机，取决于是否需要从宿主机直接访问。

补充

  • 用相同 Compose project/network；核对端口、密码、TLS 等连接配置。
  • 服务名是容器网络内部的寻址方式，宿主机端口映射不能替代它。
07Docker volume、bind mount 和容器可写层怎么选？

口述版容器可写层跟随容器生命周期，不适合放必须保留的数据。Named volume 由 Docker 管理，适合数据库文件等持久数据；bind mount 把宿主机某个明确路径挂进容器，常用于本地开发热更新或需要直接共享主机文件的场景。选择时要考虑数据生命周期、迁移备份、权限和环境可移植性；还要注意挂载会遮住镜像里目标目录原本的内容。

记忆要点

  • 数据库生产数据常用 named volume 或外部存储，并配置备份与恢复。
  • bind mount 路径依赖宿主机环境；匿名卷生命周期和复用行为也要明确。
  • down -v 会删除受管理的卷，执行前要确认数据后果。
08Compose 的 depends_on 能保证依赖服务已经可用吗？healthcheck 和重试策略怎么配合？

口述版depends_on 默认主要解决服务启动顺序，不代表依赖已经完成初始化并能处理请求。可以给依赖服务配置 healthcheck，并在支持的 Compose 语法中让依赖关系等待 healthy 状态；但应用本身仍应该有连接超时、有限次数的重试和退避策略，因为运行中依赖也可能重启或暂时不可达。健康检查、启动顺序和应用重试是互补的，不是替代关系。

面试细节

  • healthcheck 要检测真实可用性，而不只是“进程还活着”。
  • 重试要有上限、退避和清晰错误；避免无间隔无限重试造成雪崩。
  • 确认实际使用的 Compose 版本与语法支持情况。
09Docker 构建缓存怎么利用？.dockerignore 为什么重要？

口述版Docker 通常按层复用构建缓存，前面某层的输入变化后，它和后续层可能需要重建。因此我会先复制变化频率低的依赖清单并安装依赖，再复制经常变化的源码，让源码修改不必每次重装依赖。.dockerignore 则用于排除不需要进入构建上下文的文件，减少传输和意外泄露风险。

示例与边界

  • Node 项目可先复制 lockfile 与 package manifest、安装，再复制源代码；具体命令按包管理器调整。
  • 排除 .git、本地依赖目录、构建产物、临时文件和敏感文件。
  • 密钥不要通过 Dockerfile 的 ARG / ENV 烘焙进镜像；构建时需要的秘密应采用合适的 secret mount 机制。
10什么是 Docker 多阶段构建？它解决什么问题？

口述版多阶段构建是在同一个 Dockerfile 里使用多个 FROM 阶段：前面的阶段安装编译工具、执行测试或构建产物，最后的运行阶段只把真正需要的文件复制进去。这样能避免把编译器、开发依赖和临时文件带进生产镜像，通常可以缩小镜像并减少攻击面。最后仍要从最终镜像做启动和运行测试，因为构建阶段通过不等于运行阶段具备全部运行时依赖。

记忆要点

  • 清楚区分 build stage 与 runtime stage。
  • 拷贝运行产物时别漏掉运行时库、配置或证书；最小镜像也要保持可维护与可调试。
11docker compose down 和 docker compose down -v 有什么区别？

口述版docker compose down 通常会停止并移除该项目的容器和网络，默认不删除声明的 named volumes；匿名卷也默认不会被 down 自动删除，但之后重新创建容器时不一定会自动重新挂回原来的匿名卷。加 -v 会删除 Compose 文件声明的 named volumes 以及关联的匿名卷；external volumes 不会因为这个命令被移除。由于卷里可能有数据库数据，执行前要确认目标项目和数据是否可丢弃。

记忆要点

  • 要重置本地数据库时才考虑 down -v，不要把它当成无害的日常清理。
  • 不同版本和命令参数可能影响细节；重要数据先备份并核对卷名。
12容器的 PID 1、SIGTERM 和优雅关闭有什么关系？

口述版容器内的主进程通常承担 PID 1。执行 docker stop 时，Docker 会先向容器主进程发 SIGTERM，等待宽限时间后仍未退出才发送 SIGKILL。应用需要能处理终止信号，停止接新任务、完成或取消正在处理的工作、刷新必要数据并关闭连接。使用 exec 形式让应用成为直接进程，通常比 shell 包装更容易正确收信号；多进程容器还要考虑 PID 1 的子进程回收，可按需使用 init 进程。

实践细节

  • Compose 可配置停止宽限时间；超时不是无限等待。
  • 注意 shell-form ENTRYPOINT / CMD 可能让信号先到 shell，导致子进程处理不符合预期。
  • 优雅关闭需要应用配合，单靠 Docker 配置不能保证业务任务安全完成。

Retrieval · Grounding · Evaluation

RAG 检索与系统设计

17 题 · 从检索到上线治理

13请从头到尾讲一下 RAG 的基本流程。

口述版RAG 通常分为离线建库和在线问答两条链路。离线侧先解析、清洗文档，按语义和长度切块并保留来源、版本、租户和权限等元数据，再生成 embedding、写入向量索引，也可以同步建立关键词索引。在线侧先校验用户身份和数据权限，再做查询理解或改写，召回相关片段，必要时融合关键词结果并重排，选择合适上下文交给模型生成，最后返回答案和可追溯引用。要通过检索指标、答案质量和线上 trace 持续评估。

讲清楚的几层

  • 数据摄取与索引；查询与权限过滤；召回、融合和重排；上下文构造与生成；引用、评估和监控。
  • 权限应在服务端的检索链路里执行，而不是把无权内容取回后只在前端隐藏。
14RAG 的文档分块怎么做？chunk size 和 overlap 怎么取舍？

口述版分块要以检索任务为目标，不是机械地按固定字符数切。通常优先保留标题、段落、列表或代码块等自然边界，并把文档路径、标题、版本等元数据带到 chunk 上。块太小可能丢失上下文，太大则主题混杂、召回不精确并占用更多上下文窗口；overlap 可以补上边界信息，但太多会造成重复片段和索引膨胀。我会用真实问题集比较不同策略的召回与答案效果。

可以尝试

  • 按文档结构切分，必要时用父子块或先小块召回、再取邻近上下文。
  • 评估 chunk 长度、overlap 和召回数量对 Recall、重复率、token 成本与生成质量的影响。
  • 不要把某个固定 token 数说成所有文档都适用的标准值。
15向量检索和 BM25 有什么差别？分别适合什么场景？

口述版向量检索把文本映射到语义向量空间，适合找表达不同但含义相近的内容；BM25 是基于词项匹配与词频等因素的稀疏检索，对精确词、产品名、错误码、代码符号或罕见术语往往更有优势。它们针对的错误类型不同，没有一个在所有场景里必然更好。企业知识库常会把两者结合，再根据效果决定是否需要重排。

记忆要点

  • 向量：语义相似、同义表达；BM25：字面命中、专有词和精确标识符。
  • 模型、语料、语言和查询类型都会影响结果，应用自己的评测集验证。
16什么是混合检索？如何合并向量召回和 BM25 结果？

口述版混合检索通常并行做 dense vector 和 BM25 检索，再把候选结果融合、去重，必要时交给 reranker 排序。由于两路检索分数的量纲和分布可能不同，不能不加验证就把原始分数直接相加；可以采用 Reciprocal Rank Fusion 这类基于名次的融合，或在有标注数据时学习或校准融合权重。最后要在同一组问题上比较各路单独效果和融合后的收益、延迟与成本。

评估方向

  • 比较 dense-only、BM25-only、混合召回及重排后的 Recall@K、MRR / nDCG。
  • 关注候选重复、不同检索器的互补性、权重稳定性和额外延迟。
17RAG 检索不准时，你会怎样分层定位问题？

口述版先用带相关文档标注的测试问题判断问题发生在哪一层：目标文档是否进入索引、文档解析和分块是否丢了关键信息；用户权限和元数据过滤是否误排除；查询改写是否偏离原意；embedding、向量字段或索引版本是否一致；候选召回是否不足；再看混合检索和 reranker 是否改变了排名；最后才看上下文拼装与生成是否误用或忽略证据。每个请求要能看到查询、过滤条件、候选片段、分数和阶段耗时，便于复现。

排查原则

  • 先区分“检索没找到”与“找到了但答案没用好”。
  • 结合逐层 trace 和固定的黄金问题集，不只靠主观试问。
  • 权限过滤错误也是检索错误，不能为了提升召回而绕过权限。
18Recall@K、MRR 和 nDCG 分别衡量什么？RAG 还要评估什么？

口述版Recall@K 看前 K 条里找回了多少相关文档，重点是相关证据有没有被召回；MRR 看第一个相关结果出现的位置，越靠前分数越高；nDCG 可以处理分级相关性，并对排名靠后的结果做折扣。它们主要评价检索排序，不代表最终回答正确。我还会评估答案正确性、是否忠于检索证据、引用是否支持结论、拒答是否恰当，以及延迟、成本和权限隔离。离线黄金集、人工评审和线上反馈要结合起来看。

补充

  • 统一标注口径、相关性等级、K 值和问题覆盖范围。
  • 生成质量指标不能替代检索指标，检索指标也不能单独代表用户价值。
  • 线上实验注意用户隐私、采样偏差和失败样本被漏记的问题。
19RAG 如何落实文档 ACL、租户隔离和检索权限？

口述版先在服务端识别当前用户、租户和权限范围，再在检索阶段用可靠的元数据过滤或隔离索引，确保无权文档不会进入模型上下文；拿到候选文档后仍可以做最终权限校验。权限变更要能同步到索引，缓存键也要包含用户或权限版本等隔离信息，防止一个用户命中的内容被另一个用户复用。不能先把敏感数据返回给浏览器，再靠前端隐藏来保证安全。

必须验证

  • 跨租户、权限撤销、共享文档、过滤失败和缓存命中等边界场景。
  • 索引元数据与源系统 ACL 的同步时效，失败时默认拒绝还是降级的策略。
  • 对高风险数据保留审计能力，并遵循最小权限原则。
20文档更新、删除和版本变更，怎样保证 RAG 索引不返回过期内容？

口述版为文档建立稳定的 canonical ID 和版本号，更新时根据文档 ID upsert 新版本，并删除旧版本遗留的 chunks；删除时也要传播 tombstone，避免只从源系统删掉而检索索引还留着。可以先构建新索引或新版本，再通过 alias / 版本切换原子发布；缓存需要按文档版本或变更事件失效。系统要定义同步延迟、失败重试和回滚方案，让索引更新可观测、可恢复。

记忆要点

  • chunk ID 与文档 ID / 版本的关系要稳定，避免更新后重复或残留。
  • 切换期间要防止旧新版本混杂；权限撤销和删除应重点验证。
  • 缓存 TTL 不是唯一一致性方案，需结合失效事件和版本校验。
21RAG 和微调有什么区别？什么时候选哪一种？

口述版RAG 在推理时从外部知识源检索证据，适合知识经常变化、需要引用来源或需要按用户权限取数的场景；它需要维护解析、索引、检索和权限链路。微调通过训练改变模型参数，更适合学习稳定的任务行为、输出风格或特定模式，不适合把频繁变化的事实当作唯一知识库。两者也可以结合：RAG 提供最新事实，微调帮助模型更稳定地遵循任务格式。最终要针对失败样本和评估数据选择，而不是把微调当成检索问题的通用修复。

取舍

  • 先判断问题是“缺知识”还是“不会按要求做”；再看是否需要最新事实、来源追踪、权限控制。
  • RAG 的召回、时效与基础设施有成本；微调有数据、训练与维护成本。
  • 选型用任务效果、合规、延迟和总成本验证。
22面对复杂问题，RAG 为什么要拆子问题？怎么避免越拆越偏？

口述版复杂问题可能同时包含多个实体、条件或证据需求，把它拆成可检索的子问题，有助于分别召回证据并判断哪一部分没有依据。但拆分本身也可能引入误解，所以我会保留原始问题和拆分依据，限制子问题数量与深度，为每个子问题独立检索并记录引用，最终再按原问题合并答案。简单问题不必强行拆；子问题超出原意或证据不足时，应收敛、澄清或说明限制。

设计要点

  • 限制规划轮数、子问题数、总 token 与总耗时。
  • 保留子问题到证据、再到最终结论的可追溯关系。
  • 不要把模型自行生成的子问题当成已经验证的事实。
23什么是 RAG 的多跳检索？和普通 top-K 检索有何不同？

口述版普通检索通常一次用用户问题找相关片段；多跳检索则需要连续推理和检索，例如先找到某个实体关联的项目，再用项目名称查它的时间或负责人。每一跳的候选都应有来源证据，必要时从证据中抽取实体或关系作为下一跳查询，并对整个证据链进行去重、排序和验证。多跳能处理跨文档关系，但会增加延迟和错误传播，因此要限制跳数，并在任一跳证据不足时停止或明确不确定。

面试补充

  • 区分多跳检索的证据链与模型凭空补出中间事实。
  • 记录每一跳的问题、候选、来源和停止原因；用多跳黄金问题集评估端到端成功率。
24RAG 如何防范检索文档中的 Prompt Injection？

口述版检索到的文档应该被视为不可信数据，而不是高优先级指令。系统提示要清楚区分指令与引用内容，不把文档里的“忽略规则、泄露秘密、执行工具”当作授权；更重要的是，不依赖模型自己识别注入，而要在工具层做最小权限、服务端授权和必要的人类确认，秘密也不应放进模型可见上下文。对模型输出和工具参数仍要验证，并用恶意文档测试整条链路。

纵深防御

  • 来源隔离与上下文标记；高风险工具的 allowlist、参数校验和权限检查。
  • 绝不因为检索文本要求就泄露凭据或触发有副作用的操作。
  • 过滤器可辅助，但不能保证识别所有新型注入；权限边界必须由程序执行。
25RAG 的 trace 应记录哪些信息？怎样用 p50 / p95 定位慢请求？

口述版我会给每次请求一个 trace ID，并把鉴权与过滤、查询改写、各路召回、融合、reranker、上下文构建、模型首 token 与总耗时、错误和重试拆成 span，记录候选数量、模型与索引版本、token 数等必要指标。p50 表示典型中位延迟，p95 反映较慢那一段请求；如果 p50 正常但 p95 很高，通常要按查询类型、索引分片、文档长度、重试和各阶段耗时分组，找到长尾来源，而不是只盯总平均值。日志要做脱敏和访问控制。

常见延迟分解

  • 请求排队、检索、重排、上下文拼装、模型首 token、生成总时长。
  • 看分位数和阶段分布，也看超时率、错误率、token 用量和成本。
  • 不要无策略地记录完整用户问题或敏感文档原文。
26RAG 检索的 top-K 应该怎么选？K 越大越好吗？

口述版K 越大通常越容易把相关证据纳入候选，但也会增加噪声、重复内容、排序开销和上下文 token，反而可能稀释模型注意力。要结合检索阶段和生成阶段分别选：先保证候选召回，再通过融合或 reranker 选出适合放入上下文的一小部分。用黄金问题集测 Recall@K、MRR / nDCG、回答质量、延迟和成本，按查询类型调整，而不是使用一个没有验证的通用 K。

注意

  • 区分初始候选 K 与最终上下文片段数。
  • 按 token 预算、片段重复率、文档长度与问题复杂度做评估。
  • 候选不足先修召回，不要仅靠盲目增大上下文数量。
27Reranker 是什么？在什么情况下值得加？

口述版Reranker 是第二阶段排序器：先用较快的向量或关键词检索取一批候选，再让重排模型针对“查询—文档片段”对进行更细的相关性判断并重新排序。它不能找回第一阶段完全没召回的文档，但常能改善候选集的精度和前排质量。适合检索结果噪声较大、语义区分重要且质量收益能覆盖延迟与成本的场景；是否启用要通过排名指标、最终答案质量和端到端延迟共同验证。

一句话记忆

  • 召回器负责尽量找全候选，reranker 负责更精细地排好已有候选。
  • 对候选对逐一重排会增加成本，需限制候选数并测量收益。
  • 常观察 MRR / nDCG、答案忠实度、p95 延迟和单位请求成本。
28知识库里有多个互相冲突的文档，答案该相信哪个？

口述版不要把“模型选了一个听起来顺的答案”当成冲突解决。我会尽量在索引元数据里标注文档来源、权威级别、适用范围、生效时间和版本；检索时据业务规则优先使用当前有效的权威来源，并检测冲突。如果来源的优先级或适用范围无法判定，就同时呈现依据与差异，说明不确定性，必要时追问用户，而不是拼接成一个确定结论。

预防与处理

  • 源系统做好版本治理、失效标记和文档责任人管理。
  • 过滤已过期文档，明确时间范围与适用产品 / 地区 / 角色。
  • 引用应能指向具体版本，方便核验与纠错。
29更换 embedding 模型时，怎样迁移现有向量索引？

口述版新旧模型的向量空间通常不兼容，不能把新模型生成的查询向量直接拿去和旧模型文档向量比较。我会给索引和向量记录标记模型版本，建立新 collection 或索引并对全量文档重新生成 embedding，再用评测集验证召回质量、过滤和延迟。部署上可双写或补齐增量变更，准备好后通过 alias 或配置原子切换，并保留旧索引用于回滚；验证稳定后再清理旧数据。

迁移检查

  • 维度、归一化方式、距离函数、分块版本和元数据字段是否一致。
  • 迁移期间新增、更新、删除如何补齐，切换后是否会混用不同模型的向量。
  • 索引回滚、资源成本和版本观测都要提前设计。

复习建议：先遮住答案用 1–2 分钟说出结论，再用“原理 → 取舍 → 排查 / 验证”补充。术语要说准，数据和项目经历只讲自己真实做过的内容。
