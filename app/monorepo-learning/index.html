01 / THE MODEL

Monorepo 解决的是协作摩擦

01

它不等于微前端，也不会自动让架构变好。价值在于：把相关项目放在一起后，能用统一工具共享代码、检查边界、协调测试与发布；代价则是仓库体积、权限隔离和 CI 编排要认真设计。

⇢Multirepo一个项目一个仓库
web-app repodesign-system repoapi-client repo

跨项目改动常要同步 PR、版本与发布节奏；边界隔离更直观。

⌘Monorepo多个项目一个仓库
acme-platform repo
apps/webpackages/uipackages/sdk

原子化跨包变更更容易；需要工具帮助控制边界、任务和权限。

要点

选择仓库策略时，比较的是团队协作、权限与发布需求，不是“哪种架构更高级”。

02 / WORKSPACES

Workspace 让本地包像依赖一样被管理

02

Workspace 是包管理器提供的工作区能力：在一个仓库中发现多个 package，并用包名连接它们。它解决“怎么安装和链接”，不等于完整的任务编排或发布方案。

pnpm-workspace.yaml示意
packages:
  - "apps/*"
  - "packages/*"

# packages/ui/package.json
{
  "name": "@acme/ui",
  "dependencies": {
    "@acme/tokens": "workspace:*"
  }
}
↳ workspace:* 表示解析到本仓库中的工作区包；发布时的转换行为依包管理器而定。
↗依赖要显式声明

不要依赖“刚好被 hoist 到顶层”的包；每个 package 应声明自己直接 import 的依赖。

⌁共享也要有边界

用 lint、CODEOWNERS 或 Nx 边界规则约束允许的依赖方向，避免 packages 变成杂物间。

工具分工

pnpm / Yarn 管 workspace 与安装；Nx / Turborepo 等提供任务图、缓存等编排能力。实际功能随版本与配置而异。

04 / TASKS & CACHE

从“全都重跑”到“只跑有变化的任务”

04

任务图描述 build / test / lint 之间的先后依赖；缓存用任务输入和配置生成 key。输入不变时可复用输出——但如果缓存 key 漏掉重要输入，就可能错误命中。

这是确定性教学模拟；不会执行 shell 命令。

DELIVERY / RELEASE

发布策略没有唯一答案

↗
01定版本策略

固定版本（fixed）便于协同升级；独立版本（independent）适合包的节奏差异，但需要更多发布管理。

02记录变更意图

Changesets 一类工具可把包变更与 semver 意图关联；团队要明确 breaking change 和发布门槛。

03只发该发的包

按变更集合计算待发包，生成 changelog，再通过 CI 校验、审批与发布。

常见误区：“用了 Monorepo 就必须所有包同版本”并不成立；选择要看消费者、兼容承诺和发布流程。
