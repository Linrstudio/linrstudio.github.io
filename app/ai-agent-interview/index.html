01

讲一个你做过的 AI 产品或 Agent 项目

真实经历

回答主线我会讲 Agent 洞察分析工具：基于用户调研和微信小店客服会话，从 2 万多条会话中筛出 1,216 条有效反馈，归纳出 70 多项需求。我参与了洞察工具的开发，也建设腾讯广告 AI Agent 项目的设计系统并推动五层约束体系落地。我的经历更偏 Agent 周边工具和设计系统，不会把它描述成我独立完成了核心对话产品端到端。

展开顺序

  • 用户与问题：谁在什么流程中遇到什么困难。
  • 个人职责：讲清你亲自负责的前端、工具或设计系统范围。

02

如果设计 AI 对话前端架构与状态，你会怎么拆？

设计思路

回答主线我会拆成 UI、前端会话状态、传输层和服务端 Agent。前端负责输入、消息展示、取消、滚动与局部交互；服务端负责权威会话、权限、上下文、模型和工具执行。消息用稳定 ID 关联会话，并显式记录生成状态、工具步骤、引用和错误，避免切换会话时串数据。

状态边界

  • UI 状态：输入框、焦点、滚动位置、展开态。
  • 会话数据：消息列表、流式状态、工具步骤、错误。
  • 服务端状态：权限、上下文、Agent 运行与最终结果；前端不把本地缓存当权威。

关键标识

为会话、消息、请求和工具步骤分配稳定 ID；所有异步响应校验 conversationId / requestId。用户可见状态可建模为 idle、streaming、waiting-confirmation、success、error、cancelled。

经验边界

以上是架构设计思路，不是已确认亲自上线过完整对话系统。可以联系你真实做过的设计系统治理经验：强调跨业务一致性、组件契约和约束落地，但不要把系统治理等同于对话后端实现。

可加一句

我会先根据产品的多轮上下文、工具执行和权限风险确定状态模型，再决定状态放在哪里，而不是先选某个状态管理库。

03

SSE 和 WebSocket 怎么选？

设计思路

回答主线SSE 是服务端向浏览器的单向事件流，适合用户发起一次请求后，服务端持续推送回答；WebSocket 是双向长连接，适合高频双向消息，例如实时语音或协作。选择时还要看鉴权、代理与基础设施支持、重连语义、并发和运维成本，不只比较协议本身。

SSE 更合适

请求由 HTTP 发起，浏览器主要接收增量文本、状态事件或工具进度；需设计心跳、断线重连、取消与错误处理。

WebSocket 更合适

客户端和服务端都要持续、频繁地推送消息，比如实时语音、协同编辑或双向控制；需要管理连接生命周期和消息协议。

说明权衡

如果只是回答生成，不必为了“实时”默认上 WebSocket；同时检查网关超时、连接数限制、鉴权方式，以及浏览器端是否需要自定义重连。

经验边界

这里按系统设计题回答。不要说自己已经在生产中负责过 SSE / WebSocket 链路，除非能给出亲自实现的模块和故障处理细节。

04

SSE 流解析时最容易踩什么坑？

设计思路

回答主线网络返回的 chunk 不等于完整的 SSE 事件，也不一定正好落在 UTF-8 字符边界。我会用流式解码器处理字节，保留未完成的文本片段，按 SSE 的空行边界拼出事件，再解析 data 字段；同时覆盖结束标记、错误、断线和主动取消。

处理步骤

  • 用支持流式模式的 UTF-8 解码器，避免多字节字符被拆开后乱码。
  • 累积文本残片，按事件分隔符切分；完整事件处理后，留下尾部残片。
  • 按 SSE 规范处理多行 data、注释行、空行边界和结束条件。

错误与生命周期

读流期间检查 HTTP 状态、服务端事件类型、EOF、AbortSignal 和解析异常；清理 reader 与监听器，区分主动取消和意外断线。

测试边界

人为把中文字符拆开、把一个事件拆成多块、把多个事件合并一块；再测空 data、多行 data、异常 JSON、无结束标记和中途 EOF。

经验边界

这是实现 checklist。若没有亲自实现过生产解析器，可以直接说“这是我会采用的解析方式”，不要把设计稿说成已上线经验。

05

停止生成、重试和切换会话，如何避免串请求？

设计思路

回答主线为每次生成绑定 requestId、conversationId 和 AbortController。停止时中止当前请求并把对应消息标记为 cancelled；切换会话时取消旧请求，或在每次更新前检查会话 ID，不匹配就丢弃响应。重试用新请求标识和服务端幂等键，避免重复执行有副作用的操作。

防竞态

更新状态前验证 requestId 仍是当前请求；异步响应带 conversationId，不把旧会话内容写进新会话。请求状态和消息状态分开维护。

取消语义

取消前端 fetch 不代表服务端一定停止推理或工具。若产品要求真正停止，协议需支持取消信号 / cancel API，且服务端要校验权限和任务归属。

重试规则

明确重试是继续、重新生成还是从头重发；纯读取可按策略重试，可能造成外部影响的工具调用必须依靠服务端幂等与确认。

容易漏掉

组件卸载清理 AbortController 和订阅；取消错误单独识别，避免显示成“系统异常”；切换回来时加载该会话真实状态而非旧闭包数据。

06

Agent 连续多次调用工具，前端怎么展示？

设计思路

回答主线把 Agent 的工具调用展示成可理解的步骤，而不只是一个转圈。每步显示工具名称、简短意图、当前状态和必要的结果摘要；状态覆盖执行中、等待确认、成功、失败和取消。涉及外部影响的动作要展示将要执行的具体内容并让用户确认，权限和参数仍由服务端校验。

信息层级

  • 默认展示用户关心的摘要，原始参数与长结果按需展开。
  • 连续步骤按时间顺序呈现，可定位某一步失败或等待确认。
  • 最后把工具结果与 Agent 最终回答关联起来。

状态反馈

清楚区分正在执行与模型生成；可重试的失败提供原因和恢复入口；取消后不显示成成功完成。

安全边界

发送邮件、改数据等有外部影响的操作，确认卡应明确动作对象和影响。前端确认只改善交互，不能替代服务端权限校验。

设计经验连接

可结合 AI Agent 设计系统建设与五层约束体系的经历，讲如何沉淀一致组件、状态规范和治理方式；不要推断五层的具体命名或实现细节，除非自己能准确说明。

07

长对话的性能和滚动体验怎么处理？

设计思路

回答主线我会先用 React Profiler 和浏览器性能工具找到瓶颈，再决定是否需要虚拟列表、局部状态或批量刷新。滚动上区分“用户本来就在底部”和“正在回看历史”：前者可跟随新内容，后者保留位置并提示有新消息，不强行把用户拉回底部。

渲染策略

  • 长历史按需虚拟化，稳定 key，避免整个消息树随 token 更新重建。
  • 高频流式更新做节流或批量提交，不牺牲关键信息反馈。
  • Markdown / 代码高亮可分块、增量或在生成完成后处理，避免每个 token 都全量解析。

滚动策略

以接近底部阈值判断是否自动跟随；用户向上浏览时不抢滚动，显示“有新内容”按钮，点击后再回到底部。

验证方式

在长历史、长代码块和持续流式输出下观察主线程耗时、React commit、内存、滚动位置稳定性和低端设备体验。

不要先下结论

虚拟列表与 memo 会增加复杂度。先测量消息数量、更新频率和实际卡顿，再针对瓶颈优化。

08

React 高频重渲染怎么排查和优化？

设计思路

回答主线先用 Profiler 找到是哪些组件、因为什么 props 或 state 更新而重渲染，再把高频状态局部化，避免一个 token 更新带动整页刷新。确有必要时批量更新、稳定传入值，再用 memo、useMemo 或 useCallback；我不会在没有测量的情况下到处加 memo。

排查顺序

  • 定位高频 commit 与耗时组件。
  • 检查状态放置位置、Context value 是否每次重建、列表 key 是否稳定。
  • 区分“发生了重渲染”与“渲染真的很慢”。

优先手段

状态下沉、拆分订阅范围、避免无意义对象/函数变化；对 token 流按合理频率合并更新。保证用户感知及时，不为微观次数而牺牲交互。

缓存取舍

useMemo / useCallback 有依赖维护、比较和认知成本。只有稳定引用能阻止昂贵子树重渲染、避免重复计算或满足依赖契约时再用。

真实经验落点

可以用 React 项目经历讲你真实做过的性能或组件治理工作；如果手上没有具体性能指标案例，就描述排查方法，不要伪造优化百分比。

09

如何设计一套可复用的 AI 对话组件库？

真实经验可连接

回答主线我会把基础展示组件、组合模式和业务编排层分开：基础层提供消息气泡、输入、引用、错误态等稳定原语；组合层支持消息列表、工具步骤卡等模式；业务层处理会话策略和具体产品规则。契约要覆盖状态、主题、可访问性和扩展点，并且从实际复用场景出发，避免抽象过度。

分层建议

  • 基础组件：按钮、输入、气泡、引用、加载与错误状态。
  • 对话模式：消息列表、工具调用卡、确认卡、空状态。
  • 产品编排：会话、权限策略、工具注册和数据来源。

组件契约

明确 props / events、受控与非受控边界、状态语义、键盘操作、主题 token、国际化和扩展插槽；对错误与无障碍状态一并设计。

真实经历连接

腾讯广告设计系统多年建设，覆盖 60+ 平台和 5+ 部门；可重点谈组件复用、治理、落地约束，以及在 AI Agent 设计系统中的建设经验。

避免空泛

不要只说“做成通用组件”。说明哪些变化点稳定、哪些留给业务层，并说明如何用真实业务验证抽象是否成立。

10

生成中断、网络断开或服务报错，前端如何恢复？

设计思路

回答主线先把用户主动取消、网络断开、超时、服务端错误和业务错误区分开，再决定恢复方式。是否能续传取决于服务端是否提供稳定事件 ID 或序号；支持时按游标续接并去重，不支持时明确提示重新生成或从头重试，不假装无缝恢复。

恢复策略

  • 可续传：带最后处理的事件 ID / 序号重连，服务端校验会话与权限。
  • 不可续传：保留已有部分结果，说明状态，提供明确的重新生成操作。
  • 对可能有副作用的工具调用，优先查任务状态和幂等结果，不盲目重放。

一致性

用消息 ID、请求 ID 和幂等键防止重复追加；服务端是最终事实源，重连后对齐消息状态与工具执行状态。

错误体验

保留已生成文本并标注“未完成”，给出重试、复制已有内容或继续其他操作的路径；错误信息说清用户可以做什么。

关键前提

前端无法单独保证服务端续传。面试中把需要后端提供的事件序号、持久化任务状态和幂等语义明确说出来。

11

RAG 回答里的引用与权限如何设计？

设计思路

回答主线把引用和回答内容建立可追溯关联，呈现来源标题、相关片段、时间或可访问链接；前端负责清晰展示和交互。真正的数据权限必须由服务端在检索前或检索过程中校验，不能靠前端把无权数据隐藏起来。

引用呈现

支持回答内引用标记与来源列表互相定位；长片段折叠，来源不可用时给出状态；链接打开前按产品策略处理外链。

服务端责任

用户身份、租户、文档 ACL 和权限变更都需服务端验证；检索索引过滤与最终文档读取均要遵守权限策略。

前端边界

前端鉴权状态只用于交互，不是安全边界；不能将敏感原文预先发到浏览器再用 CSS 或条件渲染隐藏。

可用性

避免把来源标记做成难以辨认的脚注；让用户能看出答案的依据、来源是否可打开以及内容的时效性。

12

怎么评估 AI 对话前端做得好不好？

评估框架

回答主线我会先定义用户任务和埋点口径，再看首字延迟、完整回答耗时、成功 / 中断 / 取消率、长对话滚动体验和任务完成率。只看页面渲染速度不够；还要把前端体验指标与回答质量、工具成功率等服务端指标关联，避免把模型问题误归因给 UI。

体验指标

  • 从提交到首个可见反馈的时间、完整回答时间。
  • 生成中断率、主动取消率、错误率、重试率。
  • 长对话滚动稳定性、工具状态可理解度、无障碍操作。

任务指标

结合用户是否完成目标、是否接受或修正答案、是否重复追问等业务口径；指标需先统一分母、采样范围和失败定义。

避免误判

指标上涨不自动等于体验变好。分场景、设备和网络分析，并与后端 Agent / 工具结果质量联看；涉及会话数据时遵守隐私与最小化采集。

真实结果

如果没有做过生产对话产品的线上指标分析，不报虚构数字。可用洞察工具的已知数据举例说明你如何把大量反馈转成 70+ 项需求。

13

你怎么看 Cursor / Claude Code 这类 AI 编码工具？

工程方法

回答主线我会把 AI 编码工具用于探索代码、生成样板、补测试和解释陌生模块，但把任务拆小并明确约束；产出的代码仍需经过类型检查、单测、E2E、代码审查和安全检查。对流式交互，重点验证取消、断线、重复请求、长文本和特殊字符这些边界。

可控流程

  • 先给上下文、范围、不能改动的接口和完成标准。
  • 一次聚焦一个可验证变更，要求补测试和说明风险。
  • 由开发者审查差异、运行项目现有验证，不盲目接受自动修改。

高风险点

依赖 API 幻觉、隐含安全漏洞、大范围重构、未经运行的测试，以及对代码库旧约定理解错误。

个人经验边界

若没有实际使用过某个具体工具，不要说“我日常用它”。可以讲你认可的工程化使用方法，或举确实用过的工具与任务。

成熟度信号

说明如何设定验收标准、验证生成结果、识别不确定性；AI 提效不能替代对代码与业务后果的责任。

React 状态更新为什么会触发重渲染？useMemo / useCallback 什么时候值得用？

当组件 state 更新、父组件重渲染，或订阅的 Context / 外部 store 发生变化时，React 会重新计算相关组件输出；重渲染不一定等于 DOM 一定变化。先用 Profiler 找到真正耗时点，再判断是状态范围太大、Context 广播、props 引用每次变化，还是子树计算昂贵。useMemo 缓存计算结果，useCallback 稳定函数引用；如果没有减少昂贵计算、避免 memo 子组件重复渲染或满足依赖契约，缓存本身会增加依赖管理和认知复杂度。

15

多请求乱序返回、组件卸载后请求还在跑，怎么防竞态和资源泄漏？

用 AbortController 在切换、卸载或主动取消时中止 fetch；每次请求带递增 requestId / 会话 ID，响应写状态前校验它仍是当前请求。对无法真正取消的异步任务，忽略过期结果并解除事件监听、订阅和定时器。取消应被识别为正常生命周期，不显示成服务错误。若后端任务也需终止，还要有服务端取消协议，不能只 abort 浏览器请求。

16

如何用 TypeScript 联合类型描述消息、流事件和工具状态？

用判别字段区分事件种类，让每种状态只带该状态合法的数据；解析外部 JSON 时仍要做运行时校验，因为类型擦除不能验证网络输入。

type Message =
  | { id: string; role: "user"; text: string }
  | { id: string; role: "assistant"; status: "streaming"; text: string }
  | { id: string; role: "assistant"; status: "done"; text: string }
  | { id: string; role: "assistant"; status: "error"; text: string; error: string };

type ToolStep =
  | { id: string; state: "running"; name: string }
  | { id: string; state: "waiting-confirmation"; name: string; summary: string }
  | { id: string; state: "success"; name: string; result: unknown }
  | { id: string; state: "failed"; name: string; error: string };

更新状态时按 state 做穷尽分支，避免让“成功却没有结果”之类非法状态通过编译。示例是类型设计思路，不代表已确认项目实际采用此模型。

17

会话列表、当前会话和流式消息放组件状态、Context 还是全局 store？

按共享范围、更新频率和一致性需求决定，不先押某个库。输入框草稿、焦点和局部展开状态放组件内；多个页面共享且需要缓存的会话列表 / 当前会话数据，可以放合适的 store 或数据层；Context 适合低频、稳定的依赖，不适合把每个 token 都广播给整棵组件树。流式消息可按会话和消息订阅，限制每次更新影响的组件范围。还要明确服务端状态和本地临时 UI 状态的边界。

18

从零搭 AI 对话前端，目录、API、路由、状态和权限怎么拆？

一个可讨论的边界是：routes/ 负责页面入口与路由守卫；features/chat/ 负责会话 UI、状态编排和交互；api/ 封装 HTTP / SSE 协议与错误映射；components/ 放稳定可复用展示组件；auth/ 处理身份和前端能力门控；shared/ 放通用工具。权限检查必须在服务端执行，前端路由拦截只是体验层；按团队规模与现有仓库习惯调整，不为目录整齐而拆碎代码。

19

Markdown 渲染怎么防 XSS？模型返回 HTML、链接和代码块怎么办？

默认把模型输出当不可信输入：尽量禁用原始 HTML，或经成熟的 sanitizer 按白名单净化后再渲染；不要直接把回答塞进未经净化的 dangerouslySetInnerHTML。限制允许的 URL 协议，安全处理新窗口链接；代码块走文本节点 / 安全高亮器，不执行模型生成内容。使用 CSP 等纵深防御，并对恶意标签、事件属性、javascript: URL、SVG / data URL 做安全测试。具体库和策略需结合产品依赖审查。

20

SSE parser、停止生成、会话切换、重连和工具确认分别如何测试？
  • Parser：切碎 UTF-8 多字节字符，拆分或合并事件，覆盖多行 data、空事件、异常 payload 和 EOF。
  • 停止 / 切会话：模拟慢请求，快速切换会话并检查旧响应不会污染当前状态；确认取消后资源被清理。
  • 重连：覆盖网络中断、重复事件、缺少事件序号和服务端不支持续传等路径。
  • 工具确认：验证确认前不执行、拒绝后不会执行、越权由服务端拒绝；对有副作用的重试验证幂等性。
  • 组合测试：长回答、连续工具步骤、并发请求与键盘 / 屏幕阅读器交互。

AI 回答很慢、拒答、工具失败或结果不可靠，界面怎么帮助用户继续？

按原因提供不同反馈，不要用一个通用“出错了”覆盖全部情况。慢时先确认请求已提交，显示阶段性状态并提供取消；拒答时说明边界并给可调整的问题方向；工具失败时显示哪一步失败及可恢复入口；低置信或来源不足时明确标注限制、展示引用并鼓励核验。保留已完成内容，支持重新尝试、修改问题或换路径。措辞不应暗示 AI 结果绝对正确。
